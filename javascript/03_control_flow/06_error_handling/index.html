    Error Handling

    1. Overview

    Definition

    Error handling is the practice of anticipating, detecting, and responding to failures in a program so that it can continue operating, degrade gracefully, or terminate cleanly. In JavaScript, error handling spans several mechanisms — the try/catch/finally construct, promise rejection handling, global handlers, custom error types, and the newer using declaration for deterministic resource cleanup (ES2026).

    // Synchronous error handling
try {
    const data = JSON.parse(input);
} catch (error) {
    logger.error("Parse failed", { error, input });
    throw new AppError("INVALID_JSON", 400);
}

// Asynchronous error handling
try {
    const res = await fetch("/api/users");
    if (!res.ok) throw new AppError("HTTP_ERROR", res.status);
} catch (error) {
    if (error instanceof AppError && error.statusCode === 404) {
        return [];
    }
    throw error;
}

// Deterministic resource cleanup (ES2026)
{
    using connection = await db.connect();
    await connection.query("SELECT 1");
} // connection[Symbol.asyncDispose]() called automatically

    Error handling is not a single feature — it is a strategy that combines language constructs, error taxonomy, logging, and recovery patterns. It is the final concept in Control Flow because it is the mechanism that deals with everything control flow cannot predict.

    Purpose

    Error handling exists to solve the failure problem: programs fail. Networks drop, files disappear, inputs are malformed, servers return errors. A program that cannot handle failure is a program that crashes. Error handling provides:

    • Detection — identify when something has gone wrong.
    • Isolation — prevent one failure from cascading into others.
    • Recovery — allow the program to continue or degrade gracefully.
    • Diagnosis — capture enough information to debug the failure later.
    • Cleanup — release resources regardless of outcome.

    Error handling is what separates toy programs from production systems. A program that only works when everything succeeds is not a program — it is a demo.

    2. Why It Exists

    The Problem

    Every non-trivial program encounters failures. But handling failure poorly is worse than not handling it at all. A program that swallows errors silently hides bugs. A program that crashes on every error is unusable. A program that leaks internal details in error messages is a security risk.

    The problem is not "how do I catch an error?" — JavaScript provides try/catch for that. The problem is "what do I do with the error once I catch it?" That is the question error handling answers.

    Previous Limitations

    Era Limitation
    No structured errors Errors were strings — no type, no stack, no metadata
    No async error handling Callbacks had no standard error propagation
    No custom errors All errors were generic Error objects
    No cause Chained errors required manual property copying
    No Error.isError() instanceof Error failed across realms
    No resource cleanup try/finally was the only option — verbose and error-prone

    Why Error Handling Evolved

    Error handling in JavaScript has evolved from basic exception catching to a layered strategy:

    • ES3 (1999) — try/catch/finally brought structured exceptions.
    • ES6 (2015) — class extends Error enabled custom error types.
    • ES2019 — optional catch binding removed noise.
    • ES2021 — AggregateError wrapped multiple errors.
    • ES2022 — Error.cause chained errors.
    • ES2026 — Error.isError() and using declarations for reliable detection and deterministic cleanup.

    Each addition solved a specific weakness in the previous generation's approach. The result is a layered defense — not a single mechanism, but a set of tools that work together.

    The Modern Consensus (2026)

    By 2026, the industry has converged on several principles:

    1. Structured errors — use custom error classes with codes and metadata, not raw Error objects.
    2. Structured logging — log errors as queryable JSON, not console.error(err).
    3. Centralized handling — use middleware, error boundaries, and global handlers.
    4. Boundary catching — catch at trust boundaries, not everywhere.
    5. Graceful degradation — fail one component, not the whole system.
    6. Resource safety — use using for deterministic cleanup (ES2026).
    7. Reliable detection — use Error.isError() instead of instanceof (ES2026).

    3. Syntax / Basic Usage

    The try/catch/finally Construct

    try {
    // code that may throw
} catch (error) {
    // handle the error
} finally {
    // always runs — cleanup
}

    Throwing Errors

    throw new Error("Something went wrong");
throw new TypeError("Expected a string");
throw new RangeError("Value out of range");
throw new AppError("USER_NOT_FOUND", 404, { userId });

    Always throw Error objects — they have message, stack, and standard properties. Throwing strings or plain objects loses this information.

    Custom Error Classes

    class AppError extends Error {
    constructor(message, code, statusCode = 500, context = {}) {
        super(message);
        this.name = "AppError";
        this.code = code;
        this.statusCode = statusCode;
        this.context = context;
        Error.captureStackTrace?.(this, this.constructor);
    }
}

    Custom errors add domain-specific metadata — error codes, HTTP status codes, field names — enabling precise handling.

    Error Chaining with cause (ES2022)

    try {
    const config = JSON.parse(rawConfig);
} catch (err) {
    throw new AppError("Failed to load configuration", "CONFIG_ERROR", 500, {
        cause: err,
    });
}

    The cause option preserves the original error, creating a chain of causation that aids debugging.

    Error.isError() (ES2026)

    try {
    riskyOperation();
} catch (err) {
    if (Error.isError(err)) {
        logger.error("Real error", { message: err.message, stack: err.stack });
    } else {
        logger.warn("Non-error thrown", { value: String(err) });
    }
}

    Error.isError() is a static method that reliably identifies Error objects. It replaces instanceof Error, which fails across realms (iframes, workers) and returns false positives for objects with Error.prototype in their chain.

    Optional Catch Binding (ES2019)

    try {
    JSON.parse(input);
} catch {
    showError("Invalid JSON");
}

    When the error object is not needed, omit the binding.

    Promise Error Handling

    // .catch()
fetch("/api")
    .then(res => res.json())
    .catch(err => logger.error("Fetch failed", { err }));

// async/await with try/catch
async function loadData() {
    try {
        const res = await fetch("/api");
        if (!res.ok) throw new AppError("HTTP_ERROR", res.status);
        return await res.json();
    } catch (err) {
        logger.error("Load failed", { err });
        throw err;
    }
}

    Global Handlers

    // Browser
window.addEventListener("error", (event) => {
    reportToTelemetry({ type: "sync", error: event.error });
});

window.addEventListener("unhandledrejection", (event) => {
    reportToTelemetry({ type: "async", reason: String(event.reason) });
});

// Node.js
process.on("uncaughtException", (err) => {
    logger.fatal("Uncaught exception", { err });
    process.exit(1);
});

process.on("unhandledRejection", (reason) => {
    logger.fatal("Unhandled rejection", { reason });
    process.exit(1);
});

    Deterministic Cleanup with using (ES2026)

    {
    using file = openFile("data.txt");
    const data = file.read();
} // file[Symbol.dispose]() called automatically — even if read() throws

{
    await using conn = await db.connect();
    await conn.query("SELECT 1");
} // await conn[Symbol.asyncDispose]() called automatically

    using and await using guarantee resource cleanup when the block exits — normally or via exception. This replaces verbose try/finally patterns.

    AggregateError (ES2021)

    const errors = results
    .filter(r => r.status === "rejected")
    .map(r => r.reason);

if (errors.length > 0) {
    throw new AggregateError(errors, "Multiple operations failed");
}

    AggregateError wraps multiple errors into one — useful for batch operations and Promise.any().

    4. Mental Model

    The "Boundary Layer" Mental Model

    Error handling is most effective when organized as boundaries:

    ┌─────────────────────────────────────────────────────┐
│                   Application                       │
│                                                     │
│  ┌─────────────────┐  ┌─────────────────┐          │
│  │   HTTP Layer    │  │   Data Layer    │          │
│  │   (Express)     │  │   (Database)    │          │
│  │                 │  │                 │          │
│  │  try/catch      │  │  try/catch      │          │
│  │  → AppError     │  │  → AppError     │          │
│  └─────────────────┘  └─────────────────┘          │
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │           Global Handler                     │   │
│  │  uncaughtException / unhandledRejection     │   │
│  └─────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘

    Each boundary catches, translates, and rethrows errors in the vocabulary of that layer. The HTTP layer translates database errors into HTTP responses. The global handler catches anything that escapes.

    The "Error Taxonomy" Mental Model

    Not all errors are the same. Classify them:

    ┌─────────────────────────────────────────────────────┐
│                   Error Types                        │
│                                                     │
│  ┌─────────────────────┐  ┌─────────────────────┐  │
│  │  Operational        │  │  Programmer          │  │
│  │  (expected)          │  │  (bug)              │  │
│  │                      │  │                      │  │
│  │  • Network timeout  │  │  • TypeError         │  │
│  │  • Validation fail  │  │  • ReferenceError    │  │
│  │  • 404 Not found    │  │  • Logic bugs        │  │
│  │                      │  │                      │  │
│  │  → Handle gracefully│  │  → Fix the code      │  │
│  │  → Retry             │  │  → Log and crash     │  │
│  │  → Degrade           │  │  → Alert developer   │  │
│  └─────────────────────┘  └─────────────────────┘  │
└─────────────────────────────────────────────────────┘

    Operational errors are expected — handle them. Programmer errors are bugs — fix the code, don't swallow the error.

    The "Layered Defense" Mental Model

    Layer 1: Local try/catch       → handle what you can
Layer 2: Boundary translation  → translate to layer vocabulary
Layer 3: Centralized middleware→ consistent API responses
Layer 4: Global handlers       → last resort — log and exit

    Each layer has a specific job. No single layer handles everything.

    The "Resource Lifetime" Mental Model

    using ties a resource's lifetime to a block:

    {
    using file = openFile("data.txt");
    // use file
} // file disposed automatically — even on exception

    This is the JavaScript equivalent of C#'s using and Python's with. It replaces the try/finally pattern with deterministic, automatic disposal.

    5. Core Concepts

    Concept 1: Operational vs. Programmer Errors

    Type Example Handling
    Operational Network timeout, 404, validation failure Handle, retry, degrade gracefully
    Programmer TypeError, ReferenceError, logic bugs Fix the code; don't swallow

    Operational errors are expected — they are part of normal operation. Programmer errors are bugs — they should be fixed, not handled.

    Concept 2: Error Boundaries

    An error boundary is a layer that catches errors from below and translates them into a form suitable for above:

    • HTTP boundary — catches database errors, returns HTTP status codes.
    • UI boundary — React Error Boundary catches rendering errors.
    • Module boundary — catches errors from a subsystem and translates them.

    Concept 3: Structured Errors

    Structured errors carry metadata:

    class AppError extends Error {
    constructor(message, code, statusCode, context) {
        super(message);
        this.code = code;
        this.statusCode = statusCode;
        this.context = context;
    }
}

    This enables machine-readable handling — the caller can switch on error.code instead of string-matching the message.

    Concept 4: Structured Logging

    Replace console.error(err) with structured logging:

    logger.error("Failed to fetch users", {
    error: err.message,
    stack: err.stack,
    endpoint: "/api/users",
    component: "UsersList",
});

    Structured logs are queryable JSON — the difference between debugging in seconds vs hours.

    Concept 5: Error Chaining with cause (ES2022)

    try {
    parseConfig(data);
} catch (err) {
    throw new AppError("Config load failed", "CONFIG_ERROR", 500, { cause: err });
}

    The cause preserves the original error, creating a chain of causation that aids debugging.

    Concept 6: Error.isError() (ES2026)

    Error.isError(new Error());        // true
Error.isError({ message: "fake" }); // false
Error.isError("error");            // false

    Error.isError() performs a branded check for the internal [[ErrorData]] slot. It is:

    • Reliable across realms — works for errors from iframes and workers.
    • Resistant to prototype pollution — objects with Error.prototype in their chain return false.
    • A replacement for instanceof Error — which fails in both cases.

    Concept 7: Optional Catch Binding (ES2019)

    try {
    JSON.parse(input);
} catch {
    console.error("Invalid JSON");
}

    When the error object is unused, omit the binding.

    Concept 8: AggregateError (ES2021)

    throw new AggregateError([err1, err2], "Multiple failures");

    Wraps multiple errors into one — useful for batch operations and Promise.any().

    Concept 9: Unhandled Rejections

    In Node.js 15+, unhandled promise rejections crash the process by default. In browsers, they fire the unhandledrejection event.

    Best practice: Always attach .catch() to promise chains, or use try/catch with await.

    Concept 10: Global Handlers

    // Node.js — last resort: log and exit
process.on("uncaughtException", (err) => {
    logger.fatal("Uncaught exception", { err });
    process.exit(1);
});

    Global handlers are not a recovery mechanism — they are for logging and graceful shutdown. After an uncaught exception, the process is in an unknown state.

    Concept 11: Retry with Exponential Backoff

    async function withRetry(fn, maxAttempts = 3) {
    for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
            return await fn();
        } catch (err) {
            if (attempt === maxAttempts) throw err;
            await sleep(2 ** attempt * 100);
        }
    }
}

    Retry transient failures — network timeouts, rate limits, temporary unavailability. Do not retry permanent failures — 400 Bad Request, validation errors.

    Concept 12: using for Deterministic Cleanup (ES2026)

    {
    using file = openFile("data.txt");
    // use file
} // file[Symbol.dispose]() called automatically

    using guarantees disposal even if an exception occurs. It replaces try/finally for resource cleanup.

    Concept 13: Error Suppression and Masking

    Never swallow errors silently:

    try { risky(); } catch (e) { } // ❌ hides bugs

    If you cannot handle an error, rethrow it or log it. Silent failure is a security risk — it masks attacks and leaves the system in an unknown state.

    Concept 14: finally and Cleanup

    finally runs regardless of outcome — but it is verbose:

    let file;
try {
    file = openFile("data.txt");
    process(file);
} finally {
    file?.close();
}

    ES2026's using replaces this pattern with automatic disposal.

    Concept 15: Error Handling in React

    React has Error Boundaries — components that catch errors in their child tree:

    class ErrorBoundary extends React.Component {
    state = { hasError: false };
    static getDerivedStateFromError() { return { hasError: true }; }
    render() {
        if (this.state.hasError) return <div>Section failed to load</div>;
        return this.props.children;
    }
}

    Place boundaries at multiple levels — one crash should not kill the entire UI.

    Concept 16: Error Handling in Express

    Express 5 automatically forwards async handler rejections to error middleware:

    app.get("/users/:id", async (req, res, next) => {
    try {
        const user = await getUser(req.params.id);
        res.json(user);
    } catch (err) {
        next(err); // forward to error middleware
    }
});

app.use((err, req, res, next) => {
    if (err instanceof AppError) {
        return res.status(err.statusCode).json({ code: err.code, message: err.message });
    }
    res.status(500).json({ code: "INTERNAL_ERROR", message: "Unexpected error" });
});

    In Express 4, async rejections bypass error middleware unless wrapped.

    Concept 17: Error Handling in Server Actions

    Server Actions should return structured error state — never throw uncaught:

    return { ok: false, fieldErrors: { email: "Invalid" }, formError: null };

    Validation errors render inline with role="alert" and aria-invalid.

    Concept 18: ES2026 Error Handling Features

    • Error.isError() — reliable error detection across realms.
    • using / await using — deterministic resource cleanup.
    • AggregateError — already in ES2021, but now widely adopted.
    • Error.cause — already in ES2022, but now standard practice.

    6. How It Works

    Step-by-Step: Error Propagation

    1.  Error is thrown at some point in the call stack.
    │
    ▼
2.  Engine unwinds the stack, running finally blocks.
    │
    ▼
3.  First try...catch in the stack catches the error.
    │
    ▼
4.  If no catch exists → global handler fires.
    │
    ▼
5.  If no global handler → program terminates.

    Step-by-Step: Promise Rejection Handling

    1.  Async function throws or promise rejects.
    │
    ▼
2.  The rejection propagates through the promise chain.
    │
    ▼
3.  First .catch() or try/catch around await handles it.
    │
    ▼
4.  If no handler → unhandledRejection fires.
    │
    ▼
5.  In Node.js 15+ → process crashes by default.

    Step-by-Step: Error Boundary Translation

    1.  Database query fails with a low-level error.
    │
    ▼
2.  Data layer catches and translates to AppError.
    │
    ▼
3.  HTTP layer catches AppError and maps to status code.
    │
    ▼
4.  Client receives structured JSON error response.
    │
    ▼
5.  Client-side error handler displays user-friendly message.

    Step-by-Step: using Disposal (ES2026)

    1.  using resource = acquire() executes.
    │
    ▼
2.  Resource is registered with the block's disposal stack.
    │
    ▼
3.  Block body executes.
    │
    ▼
4.  Block exits — normally or via exception.
    │
    ▼
5.  Resources are disposed in reverse order.
    │
    ▼
6.  Symbol.dispose() or Symbol.asyncDispose() is called.

    Step-by-Step: Retry with Exponential Backoff

    1.  Attempt 1 → fail
    │
    ▼
2.  Wait 100ms
    │
    ▼
3.  Attempt 2 → fail
    │
    ▼
4.  Wait 200ms
    │
    ▼
5.  Attempt 3 → succeed
    │
    ▼
6.  Return result

    7. Internal Architecture / Under the Hood

    Completion Records

    In the ECMAScript spec, every statement returns a Completion Record:

    { [[Type]]: normal | break | continue | return | throw,
  [[Value]]: any,
  [[Target]]: label }

    throw produces a ThrowCompletion. try/catch checks the completion type.

    The [[ErrorData]] Internal Slot

    Error objects have an internal slot called [[ErrorData]]. Error.isError() performs a branded check for this slot — the same mechanism used by Array.isArray().

    Stack Trace Capture

    When an Error object is created, V8 captures the current call stack. This is the most expensive part of throwing. V8 captures the stack lazily — only when error.stack is accessed.

    Error Boundaries in Frameworks

    • React — componentDidCatch and getDerivedStateFromError.
    • Express — error middleware (app.use((err, req, res, next) => {})).
    • Next.js — error.tsx per route segment.

    using Implementation

    using is implemented via DisposableStack and AsyncDisposableStack — internal data structures that track resources and dispose them in reverse order. Babel transforms using into try/catch/finally with _usingCtx helpers.

    Global Handler Implementation

    • Browser — window.onerror / window.addEventListener("error").
    • Node.js — process.on("uncaughtException") and process.on("unhandledRejection").
    • Web Workers — self.onerror / self.addEventListener("error").

    Performance in the JIT

    • try blocks do not deoptimize in modern V8.
    • throw is expensive — stack capture, object allocation, unwinding.
    • finally adds overhead — every exit path runs finally.
    • Error.isError() is fast — branded check, no prototype walk.

    8. Lifecycle / Workflow

    Error Handling Lifecycle

    Detect → Throw/Reject → Propagate → Catch at boundary → Translate → Log → Respond → Recover

    Production Error Handling Workflow

    1.  Anticipate failure points (I/O, network, parsing, validation)
    │
    ▼
2.  Throw structured errors (AppError with code, status, context)
    │
    ▼
3.  Catch at trust boundaries (HTTP, DB, UI)
    │
    ▼
4.  Log structured data (error, code, stack, context)
    │
    ▼
5.  Translate to layer-specific response
    │
    ▼
6.  Global handler as last resort (log and exit)

    Development Workflow

    Write code → Identify failure points → Add try/catch → Add finally/using
    │
    ▼
Lint (ESLint no-unused-vars, no-unsafe-finally)
    │
    ▼
Type-check (TypeScript strict, useUnknownInCatchVariables)
    │
    ▼
Run tests → Verify error paths
    │
    ▼
Monitor production → Alert on error rates

    Error Recovery Workflow

    Error thrown
    │
    ▼
Catch at appropriate boundary
    │
    ├── Recoverable? → Retry, fallback, degrade
    │
    ├── Not recoverable? → Log, translate, respond
    │
    └── Unknown? → Log, rethrow, global handler

    Example 5: Retry with Exponential Backoff

    async function withRetry(fn, maxAttempts = 3) {
    for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
            return await fn();
        } catch (err) {
            if (attempt === maxAttempts) throw err;
            const delay = 2 ** attempt * 100;
            await new Promise(resolve => setTimeout(resolve, delay));
        }
    }
}

const result = await withRetry(() => paymentProvider.charge(amount));

    Breakdown:

    • Retries on failure.
    • Exponential backoff — 200ms, 400ms, 800ms.
    • Throws on final attempt.

    Breakdown:

    • Fire-and-forget async calls need explicit .catch().
    • Otherwise, an unhandled rejection crashes the process.

    11. Best Practices

    1. Use structured errors with codes and metadata. Why: enables machine-readable handling.
    2. Use Error.isError() instead of instanceof Error. Why: reliable across realms (ES2026).
    3. Use Error.cause to chain errors. Why: preserves the original cause (ES2022).
    4. Log structured data, not console.error(err). Why: queryable JSON is debuggable.
    5. Catch at boundaries, not everywhere. Why: avoids swallowing errors.
    6. Always rethrow if you cannot handle. Why: lets the caller decide.
    7. Never swallow errors silently. Why: hides bugs and security issues.
    8. Use using for resource cleanup. Why: deterministic, exception-safe (ES2026).
    9. Use exponential backoff for retries. Why: avoids overwhelming failing services.
    10. Attach .catch() to fire-and-forget promises. Why: prevents process crashes.
    11. Use global handlers for logging and graceful shutdown. Why: last resort — not recovery.
    12. Place Error Boundaries at multiple levels in React. Why: one crash doesn't kill the page.
    13. Centralize Express error handling in middleware. Why: consistent responses.
    14. Keep try blocks focused. Why: precise error handling.
    15. Enable TypeScript useUnknownInCatchVariables. Why: forces type-safe error handling.

    12. Common Mistakes

    ❌ Mistake: Swallowing Errors

    try { risky(); } catch (e) { } // ❌ silent failure

    ✅ Correct:

    try { risky(); } catch (e) { logger.error(e); throw e; }

    ❌ Mistake: Using instanceof Error Across Realms

    if (err instanceof Error) { /* fails for errors from iframes */ }

    ✅ Correct:

    if (Error.isError(err)) { /* works across realms */ }

    ❌ Mistake: console.error(err) for Production

    catch (err) { console.error(err); } // ❌ unstructured

    ✅ Correct:

    catch (err) {
    logger.error("Operation failed", { error: err.message, stack: err.stack, context });
}

    ❌ Mistake: No .catch() on Fire-and-Forget Promises

    sendNotification(userId); // ❌ unhandled rejection

    ✅ Correct:

    sendNotification(userId).catch(err => logger.error("Notification failed", { err }));

    ❌ Mistake: return in finally

    try { return "try"; } finally { return "finally"; } // overrides

    ✅ Correct: Never use return in finally.

    ❌ Mistake: Throwing Strings

    throw "Something went wrong"; // ❌ no stack trace

    ✅ Correct:

    throw new AppError("Something went wrong", "GENERIC_ERROR");

    ❌ Mistake: Catching Too Much

    try {
    validateInput();
    saveToDatabase();
    sendEmail();
} catch (e) {
    console.error("Something failed"); // which one?
}

    ✅ Correct: Keep try blocks focused.

    ❌ Mistake: Missing Global Handlers

    // No uncaughtException handler

    ✅ Correct:

    process.on("uncaughtException", (err) => { logger.fatal(err); process.exit(1); });

    ❌ Mistake: Using uncaughtException to Continue

    process.on("uncaughtException", () => { /* ignore and continue */ });

    ✅ Correct: Log and exit — the process is in an unknown state.

    ❌ Mistake: Assuming Express 4 Forwards Async Errors

    app.get("/", async (req, res) => { throw new Error(); }); // Express 4: not caught

    ✅ Correct: Use try/catch + next(err) in Express 4; Express 5 forwards automatically.

    13. Performance Considerations

    • throw is expensive — stack capture, object allocation, unwinding.
    • try blocks do not deoptimize — modern V8 optimizes them.
    • finally adds overhead — every exit path runs finally.
    • using adds disposal registry overhead — proportional to resource count.
    • Error.isError() is fast — branded check, no prototype walk.
    • Structured logging has overhead — batch or sample in high-throughput systems.
    • Retries increase latency — use only for transient failures.
    • Global handlers add minimal overhead — they fire only on uncaught errors.

    Performance Tips

    1. Use exceptions for exceptional conditions, not control flow.
    2. Keep try blocks focused — the overhead is proportional to block size.
    3. Use Error.isError() — faster than instanceof across realms.
    4. Batch structured logging in high-throughput paths.
    5. Profile with --trace-opt / --trace-deopt if exceptions appear in hot paths.

    14. Security Considerations

    Information Disclosure via Stack Traces

    Stack traces leak file paths, framework versions, and internal function names.

    Defense: Log full detail internally; return generic messages externally. Keep source maps off public paths.

    Broken Flows Leave Unsafe State

    An uncaught exception mid-sequence can leave the system half-committed — a deduction with no audit record.

    Defense: Wrap security-sensitive flows so failures roll back rather than stopping mid-sequence.

    Uncaught Errors Mask Attacks

    A malicious payload that triggers an exception you swallow silently loses the signal.

    Defense: Log all errors — even handled ones. Never suppress error signals.

    Unhandled Rejections Crash the Process

    In Node.js 15+, unhandled rejections crash the process by default.

    Defense: Always attach .catch() or use try/catch with await.

    Prototype Pollution and Error Detection

    instanceof Error can be fooled by objects with Error.prototype in their chain.

    Defense: Use Error.isError() — branded check, immune to prototype pollution.

    Sensitive Data in Error Messages

    Error messages may contain user data, SQL fragments, or connection strings.

    Defense: Sanitize error messages before returning them to users.

    Denial of Service via Uncaught Exceptions

    An uncaught exception can crash the process — a DoS vector.

    Defense: Per-request error boundaries; global handlers for graceful shutdown.

    15. Debugging Tips

    • Structured logging — log errors as JSON with context.
    • Error.captureStackTrace() — Node.js — cleaner stack traces.
    • Error.isError() — reliably identify error objects (ES2026).
    • debugger; — pause inside catch blocks.
    • console.trace() — print a stack trace at the current point.
    • Chrome DevTools Sources panel — set breakpoints on throw and catch.
    • Node.js --inspect-brk — step through error handling.
    • ESLint no-unused-vars — flags unused catch bindings.
    • ESLint no-unsafe-finally — flags return/break/continue in finally.
    • TypeScript useUnknownInCatchVariables — forces type-safe error handling.

    17. When Not to Use

    • For normal control flow — use conditionals.
    • For expected validation failures — return error objects.
    • In hot loops — exceptions are expensive.
    • To swallow errors — always handle or rethrow.
    • return in finally — overrides try/catch.
    • instanceof Error across realms — use Error.isError().
    • uncaughtException to continue — log and exit.
    • console.error(err) in production — use structured logging.
