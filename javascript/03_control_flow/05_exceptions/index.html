    Exceptions

    1. Overview

    Definition

    An exception is a signal that an unexpected or exceptional condition has occurred during program execution, interrupting the normal flow of control. JavaScript provides a built-in mechanism for throwing, propagating, and catching exceptions through the throw statement and the try...catch...finally construct.

    try {
    riskyOperation();
} catch (error) {
    console.error("Something went wrong:", error.message);
} finally {
    cleanup();
}

    Exceptions in JavaScript are values — you can throw any expression, not just Error objects. In practice, however, you should always throw Error objects (or instances of Error subclasses), because code that catches the error may expect standard properties like message, name, and stack to be present.

    Purpose

    Exceptions exist to solve the error propagation problem: when something goes wrong deep in a call stack, the code that can handle the error is often many frames away. Without exceptions, every function would need to return a status code, and every caller would need to check it — verbose, error-prone, and easy to forget.

    Exceptions serve as the error signaling layer of the language:

    • throw — signal that an exceptional condition has occurred.
    • try — mark a block of code that may throw.
    • catch — handle the exception if one occurs.
    • finally — guarantee cleanup regardless of outcome.

    Where It Fits

    Control Flow
├── Conditionals          ✅ done
├── Loops                 ✅ done
├── break & continue      ✅ done
├── Labels                ✅ done
├── Exceptions            ← you are here
└── Error Handling

    Exceptions sit after Labels because they are the final control flow mechanism — the one that handles the unpredictable. The next concept, Error Handling, describes the strategies and patterns for using exceptions effectively.

    2. Why It Exists

    The Problem

    A program that cannot signal failure must encode failure in return values. Every function that can fail must return either a value or an error code, and every caller must check which one it got. In a deep call stack, this means every frame must handle every possible error from below — even if it cannot do anything useful with it.

    // Without exceptions — error codes everywhere
function readConfig(path) {
    const result = readFile(path);
    if (result.error) return { error: result.error };
    const parsed = parseJSON(result.data);
    if (parsed.error) return { error: parsed.error };
    return { value: parsed.value };
}

    Exceptions solve this by separating the detection of an error from its handling. A function deep in the stack can throw; a function high in the stack can catch. Everything in between is bypassed automatically.

    Previous Limitations

    Era Limitation
    Pre-ES3 No try/catch — errors were handled via return codes
    No finally Cleanup required duplication in every code path
    No Error subclassing All errors were generic
    catch without binding Required a named binding even when unused (ES2019 fixed this)
    No cause Chained errors required custom properties (ES2022 fixed this)

    Why New Error Features Were Introduced

    • try/catch (ES3, 1999) — brought structured exception handling to JavaScript.
    • finally (ES3) — guaranteed cleanup regardless of whether an exception was thrown.
    • Error subclassing (ES6, 2015) — enabled custom error types with class extends Error.
    • Optional catch binding (ES2019) — catch {} without a parameter when the error is unused.
    • Error.cause (ES2022) — chain errors to preserve the original cause.
    • Error.isError() (ES2026) — reliably identify error objects across realms, replacing unreliable instanceof Error checks.

    Each feature solved a specific gap in error handling expressiveness.

    3. Syntax / Basic Usage

    The throw Statement

    throw expression;

    The throw statement stops execution of the current function and passes control to the first catch block in the call stack. If no catch exists, the program terminates.

    throw new Error("Something went wrong");
throw new TypeError("Expected a string");
throw new RangeError("Value out of range");
throw new ValidationError("Invalid input", { field: "email" });

    You can throw any expression, but you should throw Error objects:

    throw "a string";       // ❌ works, but no stack trace
throw 42;               // ❌ works, but no message
throw new Error("ok");  // ✅ always throw Error objects

    The try...catch Statement

    try {
    // code that may throw
} catch (error) {
    // handle the error
}

    The try block executes first. If it throws, the catch block executes with the thrown value bound to error. If no exception is thrown, catch is skipped.

    The try...catch...finally Statement

    try {
    // code that may throw
} catch (error) {
    // handle the error
} finally {
    // always runs, regardless of outcome
}

    The finally block always executes before control leaves the construct — whether an exception was thrown, caught, or not thrown at all. It runs even if the try or catch block contains a return, break, or continue.

    try...finally (Without catch)

    try {
    // code that may throw
} finally {
    // cleanup — the exception propagates after finally runs
}

    A try block can have finally without catch. The exception propagates up the stack after finally completes.

    Optional Catch Binding (ES2019)

    try {
    risky();
} catch {
    console.error("Something went wrong");
    // error object is not available
}

    When you don't need the error object, you can omit the binding entirely.

    The Error Constructor

    new Error("message");
new Error("message", { cause: originalError }); // ES2022

    The cause option chains errors — preserving the original error that led to the current one.

    Error.isError() (ES2026)

    Error.isError(new Error());        // true
Error.isError({ message: "fake" }); // false
Error.isError("error");            // false

    Error.isError() is a static method that determines whether a value is a genuine Error object. It performs a branded check for a private field initialized by the Error() constructor — the same mechanism used by Array.isArray().

    It is more reliable than instanceof Error because it:

    • Rejects values that are not real Error instances, even if they have Error.prototype in their prototype chain (instanceof would accept them).
    • Accepts Error objects created in another realm (e.g., an iframe) — instanceof Error returns false for these because the Error constructor identity differs between realms.

    Error.isError() also returns true for DOMException instances, because DOMException behaves like Error for the purposes of this check.

    4. Mental Model

    The "Bubble" Mental Model

    Think of an exception as a bubble rising through water:

    Call Stack:
┌─────────────────────┐
│  functionC()        │  ← throws
│    ↑                │
│  functionB()        │  ← no catch — bubble passes through
│    ↑                │
│  functionA()        │  ← no catch — bubble passes through
│    ↑                │
│  main()             │  ← catch — bubble stops here
└─────────────────────┘

    When a function throws, the exception bubbles up the call stack, bypassing every frame that does not have a try/catch. The first catch it encounters handles it. If it reaches the top without being caught, the program crashes.

    The "Fire Alarm" Mental Model

    Exceptions are like fire alarms:

    • throw — pull the alarm. You don't handle the fire yourself; you signal that something is wrong.
    • try — the building where the alarm might go off.
    • catch — the fire department. They respond to the alarm.
    • finally — the evacuation procedure. It happens regardless of whether there was a fire.

    The "Separation of Concerns" Mental Model

    Exceptions separate detection from handling:

    ┌─────────────────────────────────────────┐
│            Deep in the stack            │
│                                         │
│  "Something is wrong here."             │
│         ↓                               │
│      throw new Error(...)               │
│                                         │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│           High in the stack             │
│                                         │
│  "I know how to handle this."           │
│         ↓                               │
│      try { ... } catch (e) { ... }      │
│                                         │
└─────────────────────────────────────────┘

    The code that detects an error is often not the code that handles it. Exceptions let each function do what it is best at.

    The "Stack Unwinding" Mental Model

    When an exception is thrown, JavaScript unwinds the call stack — it discards frames from the throw point back to the catch point. This means:

    • Local variables in discarded frames are destroyed.
    • finally blocks in discarded frames run before the frame is destroyed.
    • The stack property of the Error object records where the exception was thrown.

    5. Core Concepts

    Concept 1: throw Stops Execution

    When throw executes, the current function stops immediately. Statements after throw do not run. Control passes to the nearest catch in the call stack.

    function f() {
    console.log("before");
    throw new Error("stop");
    console.log("never runs"); // unreachable
}

    Concept 2: catch Binds the Thrown Value

    try {
    throw new TypeError("bad type");
} catch (error) {
    console.log(error.name);    // "TypeError"
    console.log(error.message); // "bad type"
}

    The catch parameter receives whatever was thrown — not necessarily an Error object.

    Concept 3: finally Always Runs

    The finally block executes before control leaves the try construct, regardless of:

    • Whether an exception was thrown.
    • Whether an exception was caught.
    • Whether return, break, or continue was used.
    function f() {
    try {
        return "from try";
    } finally {
        console.log("finally runs");
    }
}
f(); // logs "finally runs", returns "from try"

    Concept 4: try Can Have catch, finally, or Both

    Construct Valid?
    try { } catch { } ✅
    try { } finally { } ✅
    try { } catch { } finally { } ✅
    try { } alone ❌ SyntaxError

    Concept 5: Exceptions Propagate Up the Call Stack

    function a() { b(); }
function b() { c(); }
function c() { throw new Error("deep"); }

try {
    a();
} catch (e) {
    console.log(e.message); // "deep"
}

    The exception thrown in c() propagates through b() and a() — neither of which has a catch — and is caught in the outer try.

    Concept 6: Built-in Error Types

    JavaScript provides several built-in error constructors:

    Error Type When It Occurs
    Error Generic base error
    TypeError Value is not of expected type
    RangeError Value is outside valid range
    ReferenceError Undeclared variable used
    SyntaxError Invalid syntax (usually at parse time)
    URIError Invalid URI handling
    EvalError Rare — eval() misuse
    AggregateError Multiple errors wrapped together (ES2021)

    Concept 7: Custom Error Classes

    class ValidationError extends Error {
    constructor(message, field) {
        super(message);
        this.name = "ValidationError";
        this.field = field;
    }
}

    Custom error classes extend Error and add domain-specific properties. They should set this.name explicitly for better stack traces.

    Concept 8: Error.cause (ES2022)

    try {
    parseConfig(data);
} catch (err) {
    throw new Error("Failed to load config", { cause: err });
}

    The cause option preserves the original error, creating a chain of causation.

    Concept 9: AggregateError (ES2021)

    throw new AggregateError([err1, err2], "Multiple operations failed");

    AggregateError wraps multiple errors into one — useful for Promise.any() and batch operations.

    Concept 10: Error.isError() (ES2026)

    Error.isError(new Error());        // true
Error.isError(new TypeError());    // true
Error.isError({ message: "x" });   // false
Error.isError("error");            // false

    Error.isError() is the reliable way to check if a value is an error object. It replaces instanceof Error, which fails across realms and produces false positives for objects with Error.prototype in their chain.

    Concept 11: Optional Catch Binding (ES2019)

    try {
    JSON.parse(input);
} catch {
    console.error("Invalid JSON");
}

    When the error object is not needed, the binding can be omitted.

    Concept 12: finally Overrides try and catch Returns

    If finally contains a return statement, it overrides any return from try or catch:

    function f() {
    try {
        return "try";
    } finally {
        return "finally"; // overrides "try"
    }
}
f(); // "finally"

    This is almost always a mistake. Never use return in a finally block.

    Concept 13: Exceptions and Async Code

    Exceptions in async functions become rejected promises:

    async function f() {
    throw new Error("async error");
}
f().catch(e => console.log(e.message)); // "async error"

    try...catch works inside async functions:

    async function f() {
    try {
        await risky();
    } catch (e) {
        console.error(e);
    }
}

    Concept 14: Uncaught Exceptions

    If an exception is not caught by any catch, it propagates to the top of the call stack and the program terminates. In browsers, the window.onerror / unhandledrejection events fire. In Node.js, the uncaughtException / unhandledRejection events fire.

    Concept 15: The stack Property

    Error objects have a stack property that records the call stack at the point of the error:

    const err = new Error("test");
console.log(err.stack);
// Error: test
//     at <anonymous>:1:13

    Concept 16: finally and Resource Cleanup

    finally is the pre-ES2026 way to guarantee cleanup:

    let file;
try {
    file = openFile("data.txt");
    process(file);
} finally {
    file?.close();
}

    ES2026's using declaration replaces this pattern:

    {
    using file = openFile("data.txt");
    process(file);
} // file closed automatically

    Concept 17: Throwing in Callbacks

    Exceptions thrown in asynchronous callbacks are not catchable by the outer try:

    try {
    setTimeout(() => {
        throw new Error("async"); // NOT caught here
    }, 0);
} catch (e) {
    console.log("never runs");
}

    The exception propagates to the global handler instead.

    Concept 18: Exceptions Are Expensive

    Throwing and catching exceptions has performance cost — the engine must capture the stack trace, unwind the stack, and create the error object. Do not use exceptions for normal control flow.

    6. How It Works

    Step-by-Step: throw Execution

    1.  `throw expression` is encountered.
    │
    ▼
2.  Expression is evaluated to produce the thrown value.
    │
    ▼
3.  Execution of the current function stops immediately.
    │
    ▼
4.  Control passes to the nearest enclosing try...catch.
    │
    ▼
5.  If none exists in the call stack → program terminates.

    Step-by-Step: try...catch Execution

    1.  `try` block begins execution.
    │
    ▼
2.  If no exception is thrown:
    │   - `try` completes normally.
    │   - `catch` is skipped.
    │   - `finally` runs (if present).
    │
    ▼
3.  If an exception is thrown:
    │   - `try` block execution stops.
    │   - `catch` block executes with the thrown value bound to its parameter.
    │   - `finally` runs (if present).

    Step-by-Step: finally Execution

    1.  try block completes (normally or via exception).
    │
    ▼
2.  catch block completes (if it ran).
    │
    ▼
3.  finally block ALWAYS executes.
    │
    ▼
4.  If finally has a return/throw, it overrides the pending completion.
    │
    ▼
5.  Control resumes after the try statement.

    Step-by-Step: Error.isError() (ES2026)

    1.  Error.isError(value) is called.
    │
    ▼
2.  Engine performs a branded check for a private field.
    │
    ▼
3.  If the private field is present → true.
    │
    ▼
4.  If not → false.

    Step-by-Step: Exception Propagation in Async Code

    1.  Async function throws.
    │
    ▼
2.  The exception is captured.
    │
    ▼
3.  The returned promise is rejected with the error.
    │
    ▼
4.  Caller's .catch() or try/catch around await handles it.

    7. Internal Architecture / Under the Hood

    The Spec's Treatment of Exceptions

    The ECMAScript specification covers exceptions in Section 14.15 (try Statement) and Section 14.14 (throw Statement). Key concepts:

    • Completion Records — every statement returns a completion record with a [[Type]] of normal, break, continue, return, or throw.
    • ThrowCompletion — the completion record produced by throw.
    • UpdateEmpty — ensures thrown values are propagated correctly.

    The [[ErrorData]] Internal Slot

    Error objects have an internal slot called [[ErrorData]]. The Error.isError() method checks for this slot via a branded check — the same mechanism used by Array.isArray().

    Stack Trace Capture

    When an Error object is created, V8 captures the current call stack and stores it in the stack property. This is the most expensive part of throwing an exception — capturing the stack involves walking every frame.

    Stack Unwinding

    When an exception propagates, V8 unwinds the call stack — discarding frames from the throw point back to the catch point. For each frame, it:

    1. Runs any finally blocks.
    2. Destroys local variables.
    3. Moves to the previous frame.

    finally and Completion Records

    finally blocks are implemented via Completion records. The try block produces a completion record. The finally block runs. If finally produces a completion record of type normal, the original completion is preserved. If finally produces return, throw, break, or continue, it overrides the original.

    Performance in the JIT

    • try blocks do not deoptimize by themselves in modern V8.
    • throw and catch are expensive — stack capture, object allocation, and unwinding.
    • finally blocks add overhead to every exit path from the try.
    • Engines optimize by not capturing stack traces unless the error is actually used.

    Error.isError() Implementation

    Error.isError() is implemented as a branded check — it inspects the internal [[ErrorData]] slot directly, bypassing the prototype chain entirely. This makes it fast, reliable, and immune to prototype pollution.

    8. Lifecycle / Workflow

    Exception Lifecycle

    Thrown → Propagates up stack → Caught → Handled → Execution resumes after catch
                                      │
                                      └── Not caught → Program terminates

    try...catch...finally Lifecycle

    try block → (exception?) → catch block → finally block → after try
     │                                        │
     └── (no exception) ──────────────────────┘

    Development Workflow

    Write code → Identify failure points → Add try/catch → Add finally for cleanup
    │
    ▼
Lint (ESLint no-unused-vars, no-unsafe-finally)
    │
    ▼
Type-check (TypeScript strict)
    │
    ▼
Run tests → Catch unhandled exceptions

    Error Recovery Workflow

    Exception thrown
    │
    ▼
Catch at appropriate level
    │
    ├── Recoverable? → Handle and continue
    │
    ├── Not recoverable? → Log and rethrow
    │
    └── Unknown? → Let propagate

    9. Practical Examples

    Example 1: Basic try...catch

    try {
    const data = JSON.parse('{"invalid": }');
} catch (error) {
    console.error("Parse failed:", error.message);
}

    Breakdown:

    • JSON.parse throws a SyntaxError for invalid JSON.
    • catch handles the error gracefully.

    Example 2: try...finally for Cleanup

    function readFile(path) {
    let file;
    try {
        file = openFile(path);
        return file.read();
    } finally {
        file?.close();
    }
}

    Breakdown:

    • finally guarantees the file is closed even if read() throws.
    • file?.close() handles the case where openFile itself failed.

    Example 3: Custom Error Class

    class ValidationError extends Error {
    constructor(message, field) {
        super(message);
        this.name = "ValidationError";
        this.field = field;
    }
}

function validateEmail(email) {
    if (!email.includes("@")) {
        throw new ValidationError("Invalid email", "email");
    }
}

    Breakdown:

    • ValidationError extends Error.
    • this.name is set explicitly for better stack traces.
    • field stores domain-specific data.

    Example 4: Error.cause (ES2022)

    try {
    const config = JSON.parse(rawConfig);
} catch (err) {
    throw new Error("Failed to load configuration", { cause: err });
}

    Breakdown:

    • The original SyntaxError is preserved as error.cause.
    • The new error adds context without losing the original.

    Example 5: Error.isError() (ES2026)

    try {
    riskyOperation();
} catch (err) {
    if (Error.isError(err)) {
        console.error("Real error:", err.message);
    } else {
        console.warn("Non-error thrown:", err);
    }
}

    Breakdown:

    • Error.isError() reliably identifies real error objects.
    • Handles the fact that JavaScript allows throwing anything.

    Example 6: AggregateError

    const results = await Promise.allSettled([
    fetch("/a"),
    fetch("/b"),
    fetch("/c"),
]);

const errors = results
    .filter(r => r.status === "rejected")
    .map(r => r.reason);

if (errors.length > 0) {
    throw new AggregateError(errors, "Some requests failed");
}

    Breakdown:

    • AggregateError wraps multiple errors into one.
    • Useful for batch operations.

    Example 7: Async Error Handling

    async function loadUser(id) {
    try {
        const res = await fetch(`/api/users/${id}`);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return await res.json();
    } catch (err) {
        console.error("Failed to load user:", err);
        throw err; // rethrow — caller decides what to do
    }
}

    Breakdown:

    • try/catch works inside async functions.
    • throw err rethrows — preserving the error for the caller.

    Example 8: Optional Catch Binding (ES2019)

    try {
    JSON.parse(input);
} catch {
    console.error("Invalid JSON");
}

    Breakdown:

    • No binding needed when the error object is not used.

    Example 9: using for Resource Cleanup (ES2026)

    {
    using file = openFile("data.txt");
    const data = file.read();
} // file closed automatically — even if read() throws

    Breakdown:

    • using replaces try/finally for resource cleanup.
    • Disposal happens in reverse order.

    Example 10: Uncaught Exception Handler (Node.js)

    process.on("uncaughtException", (err) => {
    console.error("Uncaught exception:", err);
    process.exit(1);
});

process.on("unhandledRejection", (reason) => {
    console.error("Unhandled rejection:", reason);
    process.exit(1);
});

    Breakdown:

    • Global handlers for exceptions that escape all catch blocks.
    • Should log and exit — not swallow.

    11. Best Practices

    1. Always throw Error objects. Why: standard properties (message, stack) are expected by catch blocks.
    2. Use Error.isError() instead of instanceof Error. Why: reliable across realms (ES2026).
    3. Use Error.cause to chain errors. Why: preserves the original cause (ES2022).
    4. Use custom error classes for domain errors. Why: enables specific handling.
    5. Always set this.name in custom errors. Why: better stack traces.
    6. Use finally for cleanup. Why: guarantees execution.
    7. Never use return in finally. Why: overrides try/catch returns.
    8. Use using instead of try/finally for resource cleanup. Why: cleaner, less error-prone (ES2026).
    9. Never swallow errors silently. Why: hides bugs and security issues.
    10. Rethrow if you cannot handle. Why: lets the caller decide.
    11. Keep try blocks focused. Why: avoid catching unrelated errors.
    12. Do not use exceptions for normal control flow. Why: expensive — stack capture and unwinding.
    13. Handle async errors with try/catch or .catch(). Why: async functions reject promises.
    14. Use optional catch binding when the error is unused. Why: cleaner code (ES2019).
    15. Log errors with context. Why: bare console.error(e) loses information.

    12. Common Mistakes

    ❌ Mistake: Throwing Strings Instead of Errors

    throw "Something went wrong"; // ❌ no stack trace

    ✅ Correct:

    throw new Error("Something went wrong");

    ❌ Mistake: Using instanceof Error Across Realms

    if (err instanceof Error) { /* fails for errors from iframes */ }

    ✅ Correct:

    if (Error.isError(err)) { /* works across realms */ }

    ❌ Mistake: Swallowing Errors

    try { risky(); } catch (e) { } // ❌ silent failure

    ✅ Correct:

    try { risky(); } catch (e) { console.error(e); throw e; }

    ❌ Mistake: return in finally

    try { return "try"; } finally { return "finally"; } // overrides

    ✅ Correct: Never use return in finally.

    ❌ Mistake: Catching Too Much

    try {
    validateInput();
    saveToDatabase();
    sendEmail();
} catch (e) {
    console.error("Something failed"); // which one?
}

    ✅ Correct: Keep try blocks focused on one operation.

    ❌ Mistake: Assuming catch Catches Async Errors

    try {
    setTimeout(() => { throw new Error("async"); }, 0);
} catch (e) { /* never runs */ }

    ✅ Correct: Handle async errors in the callback or use promises.

    ❌ Mistake: Missing name in Custom Errors

    class MyError extends Error {} // name is "Error"

    ✅ Correct:

    class MyError extends Error {
    constructor(msg) { super(msg); this.name = "MyError"; }
}

    ❌ Mistake: Using finally Without catch for Recovery

    try { risky(); } finally { cleanup(); } // exception still propagates

    ✅ Correct: Use catch if you want to handle the error.

    ❌ Mistake: Throwing Non-Errors in Libraries

    throw { code: 404 }; // ❌ no message, no stack

    ✅ Correct:

    const err = new Error("Not found");
err.code = 404;
throw err;

    ❌ Mistake: Not Handling Unhandled Rejections

    fetch("/api").then(r => r.json()); // no catch

    ✅ Correct:

    fetch("/api").then(r => r.json()).catch(console.error);

    13. Performance Considerations

    • throw is expensive — capturing the stack trace is the most costly part.
    • catch is cheap — binding the error is a simple assignment.
    • try blocks do not deoptimize — modern V8 optimizes them.
    • finally adds overhead — every exit path from try runs finally.
    • Stack capture can be deferred — V8 captures the stack only when error.stack is accessed.
    • Do not use exceptions for flow control — a throw/catch pair is orders of magnitude slower than an if check.
    • Error.isError() is fast — it performs a branded check, not a prototype walk.
    • AggregateError has overhead — wrapping many errors creates many objects.

    Performance Tips

    1. Use exceptions for exceptional conditions, not normal control flow.
    2. Prefer return values or Result-style objects for expected failures.
    3. Avoid throwing in hot loops.
    4. Keep try blocks small — the overhead is proportional to the block size.
    5. Use Error.isError() — it's faster than instanceof across realms.
    6. Profile with --trace-opt / --trace-deopt if exceptions appear in hot paths.

    14. Security Considerations

    Information Leakage via Stack Traces

    Stack traces can leak internal file paths, function names, and library versions.

    Defense: Sanitize error messages before returning them to users; log full traces server-side only.

    Uncaught Exceptions as DoS

    An uncaught exception can crash the process — a denial-of-service vector.

    Defense: Handle exceptions at trust boundaries; use per-request error boundaries.

    Error Objects as Attack Surface

    Error objects may contain user-controlled data in their messages.

    Defense: Sanitize error messages; never render them as HTML.

    Prototype Pollution and Error Detection

    instanceof Error can be fooled by objects with Error.prototype in their chain.

    Defense: Use Error.isError() — it performs a branded check, immune to prototype pollution.

    Rethrowing Sensitive Errors

    Rethrowing an error with cause can leak the original error's details.

    Defense: Create new errors for user-facing messages; log the cause internally.

    uncaughtException Handler Abuse

    A global uncaughtException handler that swallows errors leaves the process in an unknown state.

    Defense: Log, clean up, and exit the process.

    AggregateError and Sensitive Data

    AggregateError may wrap errors containing sensitive data.

    Defense: Sanitize before aggregating; never expose raw aggregates to users.

    17. When Not to Use

    • For normal control flow — use conditionals.
    • For expected validation failures — return error objects instead.
    • In hot loops — exceptions are expensive.
    • To swallow errors — always handle or rethrow.
    • return in finally — overrides try/catch.
    • instanceof Error across realms — use Error.isError().
    • Throwing non-Error values — always throw Error objects.
    • Catching exceptions you cannot handle — let them propagate.

    • Exceptions signal unexpected conditions and interrupt normal control flow.
    • throw stops execution and passes control to the nearest catch.
    • try...catch handles exceptions; finally guarantees cleanup.
    • Always throw Error objects — they have message, stack, and standard properties.
    • Error.isError() (ES2026) is the reliable way to identify error objects.
    • Error.cause (ES2022) chains errors to preserve the original cause.

    • Exceptions propagate up the call stack until caught or the program terminates.
    • Async exceptions become rejected promises; use try/catch with await.
    • Uncaught exceptions crash the program — handle at trust boundaries.
    • Exceptions are expensive — use them for exceptional conditions, not control flow.
