    Labels

    1. Overview

    Definition

    A labeled statement is any JavaScript statement prefixed with an identifier followed by a colon. The label gives a name to the statement, which can then be referenced by break or continue statements nested within it.

    label: statement;

    outer: for (let i = 0; i < 3; i++) {
    inner: for (let j = 0; j < 3; j++) {
        if (i === 1 && j === 1) break outer;
        console.log(i, j);
    }
}
// Output:
// 0 0
// 0 1
// 0 2
// 1 0

    A label is an identifier — any valid JavaScript identifier that is not a reserved word — and the statement it prefixes can be any statement, not just a loop. However, continue can only reference labels attached to looping statements, while break can reference any labeled statement.

    Purpose

    Labels exist to solve the nested loop exit problem. Without labels, a break inside an inner loop only exits the inner loop. Exiting an outer loop requires either:

    • A flag variable checked on every iteration.
    • Refactoring the loops into separate functions.
    • return from the enclosing function (only works if the loop is the last thing the function does).

    Labels provide a direct, built-in mechanism for this problem:

    // Without labels — flag variable
let found = false;
for (let i = 0; i < 3 && !found; i++) {
    for (let j = 0; j < 3 && !found; j++) {
        if (grid[i][j] === target) {
            found = true;
            result = { i, j };
        }
    }
}

// With labels — direct
outer: for (let i = 0; i < 3; i++) {
    for (let j = 0; j < 3; j++) {
        if (grid[i][j] === target) {
            result = { i, j };
            break outer;
        }
    }
}

    Labels serve as the loop targeting layer of the language — the bridge that lets an inner statement control an outer loop.

    Where It Fits

    Control Flow
├── Conditionals          ✅ done
├── Loops                 ✅ done
├── break & continue      ✅ done
├── Labels                ← you are here
├── Exceptions
└── Error Handling

    Labels sit directly after break & continue because labels extend what break and continue can target. They are inseparable from those statements — a label without break or continue is dead code.

    2. Why It Exists

    The Problem

    Nested loops are common in programming — searching a 2D grid, validating a matrix, walking a tree, matching patterns. But break and continue only affect the innermost loop. To control an outer loop from an inner one, developers needed a way to name the outer loop so an inner statement could reference it.

    Previous Limitations

    Era Limitation
    No labels Nested loop exits required flag variables
    Flag variables Checked on every iteration; verbose and error-prone
    forEach limitation forEach cannot break at all, let alone target outer loops
    No goto JavaScript never had goto — labels are the closest alternative

    Why Labels Were Introduced

    Labels were part of the original JavaScript (1995). They solved the nested loop problem by allowing a statement to be named and referenced from within. The design was deliberately limited:

    • Labels can only be used with break and continue.
    • There is no goto — you cannot jump to an arbitrary label from anywhere.
    • A label is only in scope within the statement it prefixes.
    • continue can only target looping statements; break can target any labeled statement.

    This limited design was intentional. By the mid-1990s, goto had become widely discouraged — Dijkstra's famous 1968 letter "Go To Statement Considered Harmful" had shaped programming language design for a generation. JavaScript's labels are a watered-down version of goto — enough to solve the nested loop problem, but not enough to create spaghetti code.

    Why Labels Are Discouraged in Modern JavaScript

    Despite solving a real problem, labels carry a readability cost. They make control flow harder to trace — a reader must jump between the label and the break/continue that references it. Modern JavaScript offers better alternatives:

    • return from a function — usually the cleanest solution.
    • .some() / .find() — declarative search with early exit.
    • .flatMap() / .filter() — restructure the problem.
    • Extracting inner loops into functions — encapsulate the logic.

    ESLint's no-labels rule disallows labels entirely, and the JavaScript coding standards at James Madison University explicitly advise: "Avoid the continue statement, but if necessary, use a labeled continue statement." The general consensus in 2026 is: use labels only when nothing else works.

    3. Syntax / Basic Usage

    Basic Label Syntax

    label: statement;
    • label — any valid JavaScript identifier that is not a reserved word.
    • statement — any JavaScript statement.

    Labeled Loop with break

    outer: for (let i = 0; i < 3; i++) {
    for (let j = 0; j < 3; j++) {
        if (i === 1 && j === 1) break outer;
        console.log(`i = ${i}, j = ${j}`);
    }
}
// Output:
// "i = 0, j = 0"
// "i = 0, j = 1"
// "i = 0, j = 2"
// "i = 1, j = 0"

    When break outer is encountered, the outer loop terminates entirely, and execution continues after the labeled statement.

    Labeled Loop with continue

    outer: for (let i = 0; i < 3; i++) {
    for (let j = 0; j < 3; j++) {
        if (j === 1) continue outer;
        console.log(`i = ${i}, j = ${j}`);
    }
}
// Output:
// "i = 0, j = 0"
// "i = 1, j = 0"
// "i = 2, j = 0"

    When continue outer is encountered, the outer loop proceeds to its next iteration — the inner loop is abandoned for the current outer iteration.

    Labeled Block with break

    Labels can be attached to any statement, not just loops. A labeled block with break acts as an early exit from the block:

    outerBlock: {
    console.log("1");
    innerBlock: {
        console.log("2");
        break outerBlock; // exits both blocks
        console.log("never runs");
    }
    console.log("never runs");
}
// Output:
// "1"
// "2"

    break outerBlock terminates the labeled block entirely, and execution continues after it. This pattern is occasionally used to simulate a multi-level early return within a function without using a function.

    continue Requires a Loop

    continue can only target looping statements — for, while, do...while, for...in, for...of, for await...of:

    // ✅ Valid — label is on a loop
loop: for (let i = 0; i < 3; i++) {
    continue loop;
}

// ❌ SyntaxError — label is on a block, not a loop
block: {
    continue block;
}

    Multiple Labels on One Statement

    A statement can have multiple labels:

    outer: inner: for (let i = 0; i < 3; i++) {
    break outer; // both labels are equivalent
}

    All labels on the same statement are functionally equivalent — break outer and break inner behave identically.

    Labeled Function Declaration (Deprecated)

    // ❌ DEPRECATED — do not use
label: function f() {}

    The labeled function declaration syntax is deprecated and should not be used, even in non-strict code. In strict mode, it is a syntax error.

    ASI Pitfall with Labels

    // ❌ This is NOT a labeled statement
let x = 1;
foo: bar(); // `foo` is a label for `bar()`

    Labels are parsed at statement boundaries. A line like foo: bar(); creates a label foo on the expression statement bar(). This is rarely intentional.

    4. Mental Model

    The "Named Door" Mental Model

    Think of a label as a named door on a room:

    ┌─────────────────────────────────────────┐
│                 Building                 │
│                                         │
│  ┌─────────────┐   ┌─────────────┐     │
│  │  Room A      │   │  Room B      │     │
│  │  (outer loop)│   │  (inner loop)│     │
│  │              │   │              │     │
│  │  ┌────────┐  │   │  ┌────────┐  │     │
│  │  │ Door:  │  │   │  │ Door:  │  │     │
│  │  │ outer  │◄─┼───┼──│ inner  │  │     │
│  │  └────────┘  │   │  └────────┘  │     │
│  └─────────────┘   └─────────────┘     │
└─────────────────────────────────────────┘
    • break outer — open the outer door and leave the building (exit outer loop).
    • continue outer — open the outer door and go to the next iteration of the outer loop.
    • Without labels — you can only use the inner door (exit the inner loop).

    The "Flag Variable Replacement" Mental Model

    Labels replace flag variables for nested loops:

    Without labels:                        With labels:
┌─────────────────────────────┐       ┌─────────────────────────────┐
│ let found = false;          │       │ outer: for (i) {            │
│ for (i; i < n && !found; i++)│       │   for (j; j < n; j++) {    │
│   for (j; j < n && !found; j++)│     │     if (match) {           │
│     if (match) {            │       │       result = x;          │
│       found = true;         │       │       break outer;         │
│       result = x;           │       │     }                      │
│     }                       │       │   }                        │
│ }                           │       │ }                          │
│                             │       │                            │
│ Flag checked every iteration│       │ Direct exit. Clean.        │
└─────────────────────────────┘       └─────────────────────────────┘

    The "No goto" Mental Model

    Labels are not goto. The limitations are deliberate:

    What labels CAN do:                What labels CANNOT do:
─────────────────────              ─────────────────────
✅ Exit a labeled statement         ❌ Jump to an arbitrary label
✅ Continue a labeled loop         ❌ Jump backward to earlier code
✅ Target from nested code          ❌ Jump into a labeled statement
✅ Work with break/continue         ❌ Work with any other statement

    Labels only allow forward jumps out of a statement — never backward, never into a statement. This prevents the most dangerous uses of goto while still solving the nested loop problem.

    The "Scope of a Label" Mental Model

    A label is in scope only within the statement it prefixes:

    outer: for (i) {
    // `outer` is in scope here
    // `outer` can be referenced by break/continue
}
// `outer` is OUT of scope here — cannot be referenced

    Think of a label as a local variable available only inside its own statement.

    5. Core Concepts

    Concept 1: Labels Name Statements

    label: statement;

    A label is an identifier followed by a colon, prefixed to any statement. The label gives the statement a name.

    Concept 2: Labels Are Only Used with break and continue

    JavaScript has no goto. Labels can only be referenced by break or continue statements nested within the labeled statement.

    outer: for (...) {
    break outer;    // ✅ valid
    continue outer; // ✅ valid
    // goto outer; // ❌ no goto in JavaScript
}

    Concept 3: break label Exits Any Labeled Statement

    break can target any labeled statement — loop, block, switch, if, or even a plain expression statement.

    block: {
    console.log("1");
    break block;
    console.log("never runs");
}

    Concept 4: continue label Requires a Looping Statement

    continue can only target labels attached to looping statements:

    • for
    • while
    • do...while
    • for...in
    • for...of
    • for await...of
    // ❌ SyntaxError
block: {
    continue block;
}

    Concept 5: Label Scope Is Limited to the Labeled Statement

    A label is available only within the statement it prefixes. It cannot be referenced from outside.

    outer: for (...) {
    // `outer` is available here
}
// `outer` is NOT available here

    Concept 6: Multiple Labels on One Statement

    A statement can have multiple labels, all functionally equivalent:

    outer: inner: for (let i = 0; i < 3; i++) {
    break outer; // same as break inner
}

    Concept 7: Labels and Nested Loops

    Labels solve the nested loop exit problem:

    outer: for (let i = 0; i < 3; i++) {
    for (let j = 0; j < 3; j++) {
        if (i === 1 && j === 1) break outer;
        console.log(i, j);
    }
}

    Without break outer, only the inner loop would exit.

    Concept 8: Labels and continue Semantics

    • continue outer — skips the rest of the inner loop and the rest of the current outer iteration, then proceeds to the next outer iteration.
    • continue inner — skips the rest of the current inner iteration only.

    Concept 9: Labels and break Semantics

    • break outer — exits the outer loop entirely.
    • break inner — exits the inner loop only.

    Concept 10: Labeled Function Declaration Is Deprecated

    // ❌ DEPRECATED
label: function f() {}

    The labeled function declaration syntax is deprecated and should not be used, even in non-strict code. In strict mode, it is a syntax error.

    Concept 11: Labels Are Rarely Used in Modern JavaScript

    JavaScript coding standards and ESLint rules discourage labels:

    • ESLint no-labels — disallows labels entirely.
    • JMU coding standards — "Avoid the continue statement, but if necessary, use a labeled continue statement."
    • MDN — "Labels are not very commonly used in JavaScript since they make programs harder to read and understand."

    Concept 12: Alternatives to Labels

    Alternative When to Use
    return Exit from a function
    .some() Search with early exit
    .find() Find first match
    .findIndex() Find index of first match
    Extracted function Encapsulate nested loop
    throw Exceptional early exit

    Concept 13: Array.prototype.forEach Cannot Use Labels

    forEach takes a callback function — break and continue cannot be used inside it, with or without labels:

    [1, 2, 3].forEach(x => {
    // break outer; // ❌ SyntaxError
});

    Use for...of when early termination is needed.

    Concept 14: Labels and switch

    Labels can be attached to switch statements:

    mySwitch: switch (value) {
    case 1:
        break mySwitch; // exits the switch
}

    break mySwitch exits the switch — same as unlabeled break inside a switch.

    Concept 15: Labels and try/finally

    break label and continue label inside a try block still execute the finally block:

    outer: for (let i = 0; i < 3; i++) {
    try {
        if (i === 1) break outer;
        console.log(i);
    } finally {
        console.log("finally", i);
    }
}
// Output:
// 0
// finally 0
// finally 1

    Concept 16: ESLint no-labels Rule

    ESLint's no-labels rule disallows labeled statements. It warns whenever:

    • A labeled statement is encountered.
    • break or continue is used with a label.

    The rule has options:

    Option Default Meaning
    allowLoop false If true, ignores labels on loop statements
    allowSwitch false If true, ignores labels on switch statements

    Concept 17: ES2026 and Labels

    ES2026 does not introduce new label syntax or features. Labels remain as they have been since 1995 — a limited, rarely-used mechanism for nested loop control. The ES2026 spec (Section 14.13) covers labeled statements, including early errors for invalid labeled continue targets and labeled identifier forms accepted in non-strict code.

    Concept 18: Labels and continue in for...of

    outer: for (const row of grid) {
    for (const cell of row) {
        if (cell === null) continue outer;
        process(cell);
    }
}

    continue outer skips to the next row when a null cell is found.

    6. How It Works

    Step-by-Step: Label Resolution

    1.  Parser encounters `identifier: statement`.
    │
    ▼
2.  Parser adds `identifier` to the label set.
    │
    ▼
3.  Parser parses the labeled statement.
    │
    ▼
4.  Within the statement, `break identifier` and `continue identifier`
    │   are resolved against the label set.
    │
    ▼
5.  After the statement, `identifier` is removed from the label set.

    Step-by-Step: break label Execution

    1.  `break label` is encountered inside a labeled statement.
    │
    ▼
2.  Engine searches for the matching label.
    │
    ▼
3.  If found and `break` is nested within it:
    │   - Terminate the labeled statement.
    │
    ▼
4.  If the labeled statement is a loop with an iterator:
    │   - Call iterator.return() for cleanup (IteratorClose).
    │
    ▼
5.  Resume execution after the labeled statement.

    Step-by-Step: continue label Execution

    1.  `continue label` is encountered inside a labeled loop.
    │
    ▼
2.  Engine searches for the matching loop label.
    │
    ▼
3.  If found and the label is on a loop:
    │   - Skip to the next iteration of that loop.
    │
    ▼
4.  If the label is not on a loop:
    │   - SyntaxError.

    Step-by-Step: Label Scope

    1.  Parser enters a labeled statement.
    │
    ▼
2.  Label is added to the active label set.
    │
    ▼
3.  Parser processes the statement body.
    │   - `break label` and `continue label` are valid here.
    │
    ▼
4.  Parser exits the labeled statement.
    │
    ▼
5.  Label is removed from the active label set.
    │   - `break label` outside is a SyntaxError.

    Step-by-Step: Nested Labels

    outer: inner: for (i) {
    // Both `outer` and `inner` are in scope here.
    // break outer and break inner are equivalent.
}

    7. Internal Architecture / Under the Hood

    The Spec's Treatment of Labels

    The ECMAScript specification covers labeled statements in Section 14.13 (Labelled Statements). Key points:

    • A LabelledStatement is an identifier followed by : and a statement.
    • IsLabelledFunction — static semantics determine whether a labeled statement contains a function declaration.
    • Early errors — the spec defines when labeled continue targets are invalid.
    • Labeled identifier forms — the spec accepts certain labeled identifier forms in non-strict code.

    Completion Records and Labels

    break and continue with labels produce Completion Records:

    break outer → { [[Type]]: break, [[Target]]: "outer" }
continue outer → { [[Type]]: continue, [[Target]]: "outer" }

    The [[Target]] field stores the label identifier. Loop evaluation checks this target to decide whether to handle the completion.

    Label Resolution in the Parser

    Labels are resolved during parsing, not at runtime. The parser maintains a label set — a stack of active labels. When a break or continue with a label is encountered:

    1. The parser checks that the label exists in the current label set.
    2. For continue, the parser checks that the label is attached to a looping statement.
    3. The parser checks that the break/continue is nested within the labeled statement.

    If any check fails, a SyntaxError is thrown before the code ever runs.

    Runtime Semantics

    At runtime, labels have no representation in the bytecode. A break label compiles to an unconditional jump to the end of the labeled statement. A continue label compiles to a jump to the loop's update/condition. There is zero runtime overhead for using labels.

    Optimization in the JIT

    The JIT compilers (Sparkplug, Maglev, TurboFan) treat labeled break/continue as control flow edges in the loop's control flow graph. They are optimized like any other branch.

    Labeled Function Declarations

    Labeled function declarations are deprecated in the spec. In strict mode, they are a syntax error. Engines may still support them in sloppy mode for backward compatibility, but they should never be used in new code.

    IteratorClose with Labeled Break

    When break label exits a for...of loop with a label, IteratorClose is invoked — the iterator's return() method is called to clean up resources. This works identically to unlabeled break.

    9. Practical Examples

    Example 1: Basic Labeled break

    outer: for (let i = 0; i < 3; i++) {
    for (let j = 0; j < 3; j++) {
        if (i === 1 && j === 1) break outer;
        console.log(`i = ${i}, j = ${j}`);
    }
}
// Output:
// "i = 0, j = 0"
// "i = 0, j = 1"
// "i = 0, j = 2"
// "i = 1, j = 0"

    Breakdown:

    • break outer exits both loops.
    • Execution resumes after the labeled statement.

    Example 2: Basic Labeled continue

    outer: for (let i = 0; i < 3; i++) {
    for (let j = 0; j < 3; j++) {
        if (j === 1) continue outer;
        console.log(`i = ${i}, j = ${j}`);
    }
}
// Output:
// "i = 0, j = 0"
// "i = 1, j = 0"
// "i = 2, j = 0"

    Breakdown:

    • continue outer skips to the next outer iteration.
    • The inner loop is abandoned for the current outer iteration.

    Example 3: Labeled Block with break

    function process(data) {
    validation: {
        if (!data) {
            console.log("No data");
            break validation;
        }
        if (!data.id) {
            console.log("No ID");
            break validation;
        }
        if (!data.name) {
            console.log("No name");
            break validation;
        }
        console.log("All valid");
    }
    console.log("Done");
}

    Breakdown:

    • Labeled block acts as a multi-level early return.
    • break validation exits the block and continues after it.

    Example 4: Search in a 2D Grid

    function findInGrid(grid, target) {
    let result = null;

    search: for (let row = 0; row < grid.length; row++) {
        for (let col = 0; col < grid[row].length; col++) {
            if (grid[row][col] === target) {
                result = { row, col };
                break search;
            }
        }
    }

    return result;
}

    Breakdown:

    • break search exits both loops when the target is found.
    • Cleaner than a flag variable.

    Example 5: Labeled continue in a for...of Loop

    const grid = [
    [1, 2, 3],
    [4, null, 6],
    [7, 8, 9],
];

outer: for (const row of grid) {
    for (const cell of row) {
        if (cell === null) continue outer;
        console.log(cell);
    }
}
// Output:
// 1, 2, 3
// (row 2 skipped)
// 7, 8, 9

    Breakdown:

    • continue outer skips to the next row when a null cell is found.

    Example 6: Multiple Labels

    outer: inner: for (let i = 0; i < 3; i++) {
    break outer; // both labels are equivalent
}

    Example 7: Labels vs. return

    // With labels
function findWithLabel(grid, target) {
    search: for (let i = 0; i < grid.length; i++) {
        for (let j = 0; j < grid[i].length; j++) {
            if (grid[i][j] === target) {
                return { i, j };
            }
        }
    }
    return null;
}

// Same function — no labels needed
function findWithoutLabel(grid, target) {
    for (let i = 0; i < grid.length; i++) {
        for (let j = 0; j < grid[i].length; j++) {
            if (grid[i][j] === target) {
                return { i, j };
            }
        }
    }
    return null;
}

    Breakdown:

    • When the loop is the last thing the function does, return is cleaner than a label.
    • Labels are only needed when more code follows the loops.

    Example 8: Labels vs. .find()

    // With labels
function findWithLabel(rows, predicate) {
    outer: for (const row of rows) {
        for (const cell of row) {
            if (predicate(cell)) break outer;
        }
    }
}

// Without labels — using .some()
function findWithSome(rows, predicate) {
    rows.some(row => row.some(predicate));
}

    Breakdown:

    • .some() provides early exit without labels.
    • More declarative, but returns a boolean, not the value.

    Example 9: Labeled break in a while Loop

    outer: while (true) {
    const input = prompt("Enter a number (or 'quit'):");
    if (input === "quit") break outer;

    let n = Number(input);
    while (isNaN(n)) {
        const retry = prompt("Invalid — enter a number:");
        if (retry === "quit") break outer;
        n = Number(retry);
    }
    console.log("You entered:", n);
}

    Breakdown:

    • break outer exits the outer while loop from within the inner loop.

    Example 10: ESLint no-labels Rule

    {
    "rules": {
        "no-labels": ["error", { "allowLoop": true }]
    }
}

    Breakdown:

    • no-labels disallows all labels.
    • allowLoop: true permits labels on loop statements only.
    • allowSwitch: true permits labels on switch statements only.

    Scenario Label Pattern
    Search 2D grid break search after finding target
    Validate multi-field object Labeled block with break
    Skip invalid rows continue outer
    Exit nested loops on error break outer
    Simulate multi-level return Labeled block with break
    Target outer loop from inner break outer / continue outer

    11. Best Practices

    1. Avoid labels when return works. Why: return is clearer and achieves the same result.
    2. Prefer .some() / .find() for searches. Why: declarative, no labels needed.
    3. Extract inner loops into functions. Why: encapsulates logic, eliminates labels.
    4. Use labels only when no cleaner alternative exists. Why: labels reduce readability.
    5. Keep labels close to their usage. Why: distant labels are hard to trace.
    6. Use meaningful label names. Why: outer beats lbl1.
    7. Never use labeled function declarations. Why: deprecated; syntax error in strict mode.
    8. Remember continue requires a loop label. Why: blocks cannot be continued.
    9. Enable ESLint no-labels for new projects. Why: enforces label-free code.
    10. If using labels, document why. Why: future readers need context.
    11. Don't nest more than two loops. Why: deep nesting is a design smell.
    12. Consider restructuring data. Why: a flat array may eliminate nested loops entirely.
    13. Use break label for early exit, not continue label. Why: break is more predictable.
    14. Test label behavior at boundary conditions. Why: labels can hide bugs at loop edges.
    15. Know the alternatives before reaching for labels. Why: labels are a last resort.

    12. Common Mistakes

    ❌ Mistake: continue Targeting a Block

    block: {
    continue block; // ❌ SyntaxError
}

    ✅ Correct: continue requires a loop label.

    ❌ Mistake: Labeled Function Declaration

    label: function f() {} // ❌ Deprecated; SyntaxError in strict mode

    ✅ Correct: Never use labeled function declarations.

    ❌ Mistake: Unnecessary Labels

    outer: for (let i = 0; i < 3; i++) {
    break outer; // unnecessary — the loop breaks anyway
}

    ✅ Correct: Remove unnecessary labels.

    ❌ Mistake: Label Out of Scope

    outer: for (...) { }
break outer; // ❌ SyntaxError — label out of scope

    ✅ Correct: Labels must be used within the labeled statement.

    ❌ Mistake: Forgetting continue Requires a Loop

    myLabel: if (condition) {
    continue myLabel; // ❌ SyntaxError — `if` is not a loop
}

    ✅ Correct: continue only works with loop labels.

    ❌ Mistake: Using Labels Instead of return

    function find(grid) {
    search: for (let i = 0; i < grid.length; i++) {
        for (let j = 0; j < grid[i].length; j++) {
            if (grid[i][j]) break search;
        }
    }
    return result; // more code after
}

    ✅ Correct: If nothing follows the loops, use return.

    ❌ Mistake: Nested Labels on Same Statement Thinking They Differ

    outer: inner: for (...) {
    break inner; // same as break outer — both exit the loop
}

    ✅ Correct: Multiple labels on the same statement are equivalent.

    ❌ Mistake: Labels in forEach

    [1, 2, 3].forEach(x => {
    outer: for (...) { } // ❌ cannot break/continue the forEach
});

    ✅ Correct: Use for...of when labels and early exit are needed.

    ❌ Mistake: break in switch Inside a Loop Without a Label

    for (const x of items) {
    switch (x) {
        case 1: break; // exits switch, not loop
    }
}

    ✅ Correct: Use break loop with a label to exit the loop.

    ❌ Mistake: ASI with Labels

    let x = 1;
foo: bar(); // `foo` is a label — rarely intended

    ✅ Correct: Understand that foo: is a label, not part of the expression.

    13. Performance Considerations

    • Labels have zero runtime cost — they are resolved at parse time and compile to jumps.
    • break label is as fast as unlabeled break — no additional overhead.
    • Labels can be faster than flag variables — no per-iteration flag check.
    • return is ~25% faster than labels for breaking nested loops in some benchmarks.
    • Labels are ~1% faster in HPC/science workloads — negligible difference.
    • Labels do not affect JIT optimization — they are control flow edges like any other branch.

    Performance Tips

    1. Labels are free — do not avoid them for performance reasons.
    2. Use return when it works — slightly faster and cleaner.
    3. Avoid flag variables — labels are faster and cleaner.
    4. Profile only if labels are in a hot path.

    14. Security Considerations

    Labels Are Not goto

    Labels cannot jump arbitrarily — they can only exit labeled statements via break or continue. This prevents the most dangerous goto-style control flow.

    Iterator Cleanup with Labeled Break

    break label from a for...of loop triggers IteratorClose — resources are cleaned up. This prevents resource leaks in generators and async iterators.

    finally Interaction

    break label and continue label inside try blocks still execute finally. This is safe but can be surprising — ESLint's no-unsafe-finally rule flags break/continue in finally blocks.

    Labeled Statements and Security

    Labels themselves have no security implications. They are a parse-time construct with no runtime representation.

    Loop Bound Enforcement

    Labels can enforce maximum iteration limits in nested loops, preventing denial-of-service (DoS) via unbounded iteration.

    15. Debugging Tips

    • console.log at the label and break — verify label targeting.
    • debugger; — pause inside labeled loops.
    • ESLint no-labels — flags label usage.
    • ESLint no-extra-label — flags unnecessary labels.
    • ESLint no-unreachable — flags code after break label.
    • Chrome DevTools Sources panel — set breakpoints at label and break.
    • Check label scope — labels only work within the labeled statement.
    • Verify continue target — only loop labels can be continued.

    16. When to Use

    Scenario Use Label?
    Exit nested loops when more code follows ✅ Yes
    Skip to next outer iteration ✅ Yes
    Search in 2D data with early exit ⚠️ Prefer .some() / .find()
    Exit from a function ❌ Use return
    Simulate multi-level return ⚠️ Prefer labeled block or restructure
    Simple single loop ❌ No label needed
    forEach iteration ❌ Cannot use labels

    17. When Not to Use

    • When return works — cleaner.
    • When .some() / .find() works — declarative.
    • When the inner loop can be extracted into a function — encapsulated.
    • When a flag variable is clear enough — labels are not always better.
    • In new projects with ESLint no-labels — follow the rule.
    • When labels make code harder to understand — readability wins.
    • In forEach callbacks — impossible.
    • With labeled function declarations — deprecated.
