    ECMAScript

    1. Overview

    Definition

    ECMAScript is the standardized specification that defines the JavaScript language. It is published by Ecma International as the ECMA-262 standard and describes the syntax, types, semantics, built-in objects, and execution model of the language — but not the browser APIs, Node.js APIs, or any host environment.

    // This is ECMAScript:
const x = 10;
const double = (n) => n * 2;
const arr = [1, 2, 3].map(double);

// This is NOT ECMAScript (it's a host API):
document.getElementById("app");
process.argv;
fetch("/api");

    The relationship is precise: ECMAScript is the language spec; JavaScript is the language as implemented in engines, plus whatever host APIs the environment provides.

    Purpose

    ECMAScript exists to solve a fundamental coordination problem: how do you evolve a programming language used by billions of devices without breaking the web? The spec provides:

    • A single source of truth for what the language is.
    • A compatibility contract so engines agree on behavior.
    • A predictable evolution process (TC39 proposals, annual releases).
    • A test suite (Test262) to verify conformance.
    • A legal and technical separation between the language and its implementations.

    Without ECMAScript, each browser vendor would invent its own dialect — and the web would fragment.

    Where It Fits

    ┌────────────────────────────────────────────────────────┐

    • ECMAScript — the language core.
    • Host environments — provide the platform-specific APIs.
    • Engines — implement ECMAScript (V8, SpiderMonkey, JavaScriptCore).
    • Runtimes — combine an engine with host APIs (browsers, Node.js, Deno, Bun).

    Other ECMAScript standards exist alongside ECMA-262:

    Standard Scope
    ECMA-262 The language itself
    ECMA-402 Internationalization API (Intl)
    ECMA-419 Embedded systems API
    ECMA TR/114 Runtime keys

    2. Why It Exists

    The Problem

    In 1995, Netscape shipped JavaScript and Microsoft shipped JScript. They were almost compatible — but not quite. Each added features the other lacked. Developers had to write branching code or pick a side. The web was heading toward dialect fragmentation — the same problem that had plagued BASIC, SQL, and other standards-optional languages.

    A language used by every browser, on every OS, by every device must have a single definition. Without it:

    • Code written for one browser breaks in another.
    • Features can't be added safely.
    • Engines can't be held accountable.
    • Documentation and education become incoherent.

    Previous Limitations

    Limitation Consequence
    No standard Browser-specific dialects (document.all, ActiveX, etc.)
    No evolution process Features added ad hoc, inconsistently
    No conformance suite Engines shipped partial or buggy implementations
    No versioning "JavaScript 1.5" meant different things to different vendors
    No legal clarity "JavaScript" trademarked by Sun/Oracle; spec needed a neutral name

    Why It Was Introduced

    Netscape submitted the language to ECMA International in November 1996. The first edition of ECMA-262 was published in June 1997. The name "ECMAScript" was a compromise — "JavaScript" was trademarked by Sun Microsystems (later Oracle), so a neutral name was needed for the standard.

    Since then, ECMAScript has gone through 17 editions (as of 2026), evolving from a small scripting language into a full-featured, multi-paradigm programming language used across browsers, servers, mobile, desktop, and embedded systems.

    3. Syntax / Basic Usage

    What ECMAScript Defines

    // Values and types
const n = 42;               // Number
const s = "hello";          // String
const b = true;             // Boolean
const u = undefined;        // Undefined
const nul = null;           // Null
const sym = Symbol("id");   // Symbol
const big = 9007199254740993n; // BigInt

// Objects and arrays
const obj = { a: 1, b: 2 };
const arr = [1, 2, 3];

// Functions
function add(a, b) { return a + b; }
const mul = (a, b) => a * b;

// Classes
class Point {
    constructor(x, y) { this.x = x; this.y = y; }
    distance() { return Math.hypot(this.x, this.y); }
}

// Control flow
if (n > 10) { /* ... */ }
for (const item of arr) { /* ... */ }
try { /* ... */ } catch (e) { /* ... */ }

// Async
async function fetchData() {
    const res = await fetch("/api"); // fetch is a host API, not ECMAScript
    return res.json();
}

// Modules
export const VERSION = "1.0";
import { VERSION } from "./config.js";

    What ECMAScript Does Not Define

    // ❌ Not in ECMAScript:
document.querySelector("div");   // DOM (WHATWG)
window.localStorage;             // Storage (WHATWG)
setTimeout(() => {}, 1000);      // Timers (WHATWG / Node)
fetch("/api");                   // Fetch (WHATWG)
process.env;                     // Node.js
Deno.readFileSync("file");       // Deno
Bun.file("file");                // Bun
console.log("hi");               // Console (WHATWG / Node) — technically a host API

    The line is often blurry in practice, but it matters: ECMAScript describes the language; everything else is the host.

    A Conforming ECMAScript Program

    // Runs in any conforming ECMAScript host with no host APIs:
function fibonacci(n) {
    let [a, b] = [0, 1];
    for (let i = 0; i < n; i++) [a, b] = [b, a + b];
    return a;
}

const result = fibonacci(10); // 55

    This program uses only language features — no DOM, no Node, no browser APIs.

               │  implemented by
               ▼

    The spec is normative — it defines what must happen. Engines are conformant to varying degrees. Test262 verifies conformance.

    The "Constitution" Mental Model

    ECMAScript is like a constitution:

    • It defines the rules (grammar, semantics).
    • It is amended over time (annual editions).
    • Amendments go through a formal process (TC39 stages).
    • Courts (engines) interpret and apply it.
    • Citizens (developers) live under it — often without reading it.

    The "Layered Standards" Mental Model

    ┌─────────────────────────────────────────┐
│  ECMA-262  → the language               │
├─────────────────────────────────────────┤
│  ECMA-402  → Intl (internationalization)│
├─────────────────────────────────────────┤
│  WHATWG    → DOM, Fetch, Streams, URL   │
├─────────────────────────────────────────┤

├─────────────────────────────────────────┤
│  IETF      → HTTP, TLS, URLs            │
└─────────────────────────────────────────┘

    ECMAScript is one layer in a stack of standards. "JavaScript" the colloquial term spans all of them.

    The "Annual Train" Mental Model

    Since 2015, ECMAScript releases on a predictable annual cadence:

    Proposal → Stage 0 → Stage 1 → Stage 2 → Stage 3 → Stage 4 → Next Edition

    Features that reach Stage 4 by the cutoff are included in that year's edition. This replaced the old "big bang" releases (ES6 took six years) with a steady train of smaller, safer changes.

    5. Core Concepts

    Concept 1: ECMA-262 Is the Language Spec

    ECMA-262 defines:

    • Grammar — what valid programs look like.
    • Types — Undefined, Null, Boolean, String, Symbol, Number, BigInt, Object.
    • Semantics — what each construct does.
    • Built-in objects — Object, Array, Map, Set, Promise, Math, JSON, Reflect, Proxy, etc.
    • Execution model — realms, agents, jobs, the event loop contract.

    It does not define:

    • The DOM.
    • console.
    • Timers.
    • Networking.
    • File systems.
    • Rendering.

    Concept 2: Editions and Versions

    Edition Year Common Name Highlights
    1 1997 ES1 Initial standard
    2 1998 ES2 Editorial
    3 1999 ES3 Regex, try/catch, switch
    5 2009 ES5 Strict mode, JSON, getters/setters
    6 2015 ES2015 / ES6 let/const, classes, modules, promises, arrows
    7 2016 ES2016 **, Array.prototype.includes
    8 2017 ES2017 async/await, Object.entries
    9 2018 ES2018 Rest/spread for objects, async iteration
    10 2019 ES2019 flat, flatMap, Object.fromEntries
    11 2020 ES2020 Optional chaining, nullish coalescing, BigInt
    12 2021 ES2021 replaceAll, Promise.any, logical assignment
    13 2022 ES2022 Top-level await, .at(), class fields
    14 2023 ES2023 toSorted, toReversed, findLast
    15 2024 ES2024 Object.groupBy, Map.groupBy, Promise.withResolvers
    16 2025 ES2025 Iterator helpers, Set methods, JSON modules, regex modifiers
    17 2026 ES2026 Temporal, Map.getOrInsert, Array.fromAsync, Error.isError

    Note: Edition 4 was abandoned (too ambitious); edition 5 came after a long gap.

    Concept 3: TC39 — The Standards Committee

    TC39 (Technical Committee 39) is the ECMA committee that evolves ECMAScript. Members include representatives from browser vendors (Google, Mozilla, Apple, Microsoft), tooling companies, and invited experts.

    TC39 operates by consensus — no single vendor can force a feature through.

    Concept 4: The TC39 Proposal Process

    Stage 0 → Stage 1 → Stage 2 → Stage 3 → Stage 4 → Included in next edition
    Stage Name Meaning
    0 Strawperson An idea submitted to TC39
    1 Proposal A champion is identified; problem is well-defined
    2 Draft Spec text is written; syntax and semantics are precise
    2.7 — Spec text is complete; implementations underway
    3 Candidate Spec is complete; implementations and feedback begin
    4 Finished Two+ implementations ship; Test262 tests pass; included in spec

    Features at Stage 4 are guaranteed to be in the next annual edition.

    Concept 5: Test262

    Test262 is the official ECMAScript conformance test suite. Engines must pass it to claim conformance. It contains tens of thousands of tests covering every part of the spec.

    Concept 6: The Annual Release Cadence

    Since ES2015:

    • February 1 — TC39 meeting; features that reached Stage 4 by this date are candidates.
    • March — Final Stage 4 approval.
    • June — Ecma General Assembly approves the new edition.
    • Publication — ECMA-262 year edition is published.

    This cadence makes the language predictable — developers know when to expect new features and can plan upgrades.

    Concept 7: Backward Compatibility

    ECMAScript is strictly backward-compatible. No feature has ever been removed. This is why:

    • var still exists despite let/const.
    • == still coerces despite ===.
    • typeof null === "object" is still a bug.
    • with is deprecated but not deleted.

    The web cannot break — old pages must keep working forever.

    Concept 8: Strict Mode

    "use strict";

    Introduced in ES5, strict mode:

    • Turns silent errors into exceptions.
    • Forbids with, implicit globals, and octal literals.
    • Makes this undefined in plain function calls.
    • Is default in modules and classes.

    Concept 9: ECMA-402 (Internationalization)

    ECMA-402 standardizes the Intl object:

    new Intl.DateTimeFormat("de-DE").format(new Date());
new Intl.NumberFormat("ja-JP", { style: "currency", currency: "JPY" }).format(1000);

    It is a separate standard from ECMA-262 but part of the ECMAScript family.

    Concept 10: The Relationship with TypeScript

    TypeScript is a superset of ECMAScript. It adds:

    • Static types.
    • Interfaces, generics, enums.
    • Decorators, namespaces.

    Then it compiles to ECMAScript. The TypeScript team tracks ECMAScript editions closely and adds support for new features as they reach Stage 3/4.

    Concept 11: Feature Detection over Version Detection

    You cannot reliably detect "ES2020 support" in a browser. Instead:

    if (typeof BigInt !== "undefined") { /* ... */ }
if (typeof Array.prototype.at === "function") { /* ... */ }

    Feature detection is the correct approach.

    Concept 12: Polyfills and Transpilation

    • Polyfills — implement missing APIs at runtime.
    • Transpilers (Babel, SWC) — rewrite newer syntax into older syntax.

    Both are bridges between the spec and the engines that lag behind it.

    Concept 13: The ecma262 Repository

    The ECMAScript spec lives at tc39.es/ecma262 and is maintained in a GitHub repository. You can read the spec, file issues, and follow discussions.

    Concept 14: The Relationship with WHATWG

    WHATWG maintains the "living standards" for HTML, DOM, Fetch, Streams, and many other web APIs. These are not ECMAScript, but they are part of the JavaScript platform.

    Concept 15: Current Status (2026)

    As of 2026:

    • ECMAScript 2026 (17th edition) was approved on June 30, 2026, and published in June 2026 as ECMA-262 17th edition .
    • ECMAScript 2025 (16th edition) was published in June 2025 as ECMA-262 16th edition .
    • Temporal API reached Stage 4 in March 2026 and is part of ES2026 .
    • Explicit Resource Management (using / await using) reached Stage 4 in 2025 and is part of ES2026 .
    • Iterator Sequencing (Iterator.concat) reached Stage 4 in November 2025 .

    Concept 16: Key Features by Recent Edition

    ES2025 added:

    • Iterator Helpers — .map(), .filter(), .take(), .drop() on iterators.
    • New Set methods — .union(), .intersection(), .difference().
    • JSON modules — import data from "./data.json" with { type: "json" }.
    • RegExp modifiers — inline flags like (?i:...).
    • Promise.try() — streamline promise chains.
    • Float16Array — a new typed array.
    • RegExp /v flag — upgrade to the /u flag.
    • RegExp.escape() — escape strings for regex use.

    ES2026 added:

    • Temporal API — modern, immutable date/time handling with time zones and calendars.
    • Map.prototype.getOrInsert() / getOrInsertComputed() — upsert semantics for maps .
    • Array.fromAsync() — collect async iterables into arrays .
    • Error.isError() — reliably identify error objects .
    • Math.sumPrecise() — accurate summation of floating-point numbers .
    • Iterator.concat() — lazily sequence iterators .
    • Uint8Array base64/hex methods — encode/decode binary data .
    • JSON.rawJSON() — fine control over JSON.stringify output .
    • JSON.parse reviver context — access the matched segment of JSON source .
    • Explicit Resource Management — using and await using for automatic cleanup .

    Concept 17: The Edition Numbering

    ECMAScript editions are numbered sequentially (1st, 2nd, 3rd, ..., 17th). The year name (ES2026) is the colloquial name. The edition number is the formal name in the spec.

    • Edition 17 = ES2026 = ECMA-262 17th edition.

    Concept 18: The engines Field and Conformance

    Engines report conformance via:

    • Test262 pass rates.
    • Baseline (web-platform-tests) status.
    • Can I Use and MDN compatibility tables.

    No engine is 100% conformant at all times — the spec evolves faster than any implementation can perfectly track.

    7. Internal Architecture / Under the Hood

    The Spec's Structure

    ECMA-262 is organized into:

    • Clauses — numbered sections.
    • Algorithms — numbered steps with abstract operations.
    • Grammar — BNF-style syntax rules.
    • Internal slots and methods — [[Prototype]], [[Get]], etc.

    Example algorithm (simplified):

    Array.prototype.map ( callbackfn [ , thisArg ] )
1. Let O be ? ToObject(this value).
2. Let len be ? LengthOfArrayLike(O).
3. If IsCallable(callbackfn) is false, throw a TypeError.
4. Let A be ? ArraySpeciesCreate(O, len).
5. Let k be 0.
6. Repeat, while k < len:
   a. Let Pk be ! ToString(𝔽(k)).
   b. Let kPresent be ? HasProperty(O, Pk).
   c. If kPresent is true:
      i. Let kValue be ? Get(O, Pk).
      ii. Let mappedValue be ? Call(callbackfn, thisArg, « kValue, 𝔽(k), O »).
      iii. Perform ? CreateDataPropertyOrThrow(A, Pk, mappedValue).
   d. Set k to k + 1.
7. Return A.

    This is normative — engines must follow it.

    Realms, Agents, and Jobs

    • Realm — a global environment (global object, global scope, built-ins). Each iframe has its own realm.
    • Agent — a thread of execution with its own call stack and job queues.
    • Job — a unit of asynchronous work (e.g., a promise reaction).

    These concepts define how execution proceeds across contexts.

    The Execution Model

    ┌──────────────┐
│  Call Stack  │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  Job Queue   │  ← promise jobs, host jobs
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  Event Loop  │  ← host-defined
└──────────────┘

    The spec defines the job queue semantics; the event loop is host-defined (WHATWG for browsers, Node for Node.js).

    Intrinsics and the Global Object

    Every realm has a set of intrinsic objects:

    • %Object%, %Array%, %Function%, %Promise%, %Map%, %Set%, %Math%, %JSON%, %Reflect%, %Proxy%, etc.

    These are the built-ins available to all code in that realm.

    The [[Prototype]] Chain

    Object.prototype
    ▲
    │
Array.prototype
    ▲
    │
[]

    The spec defines prototype chains and property lookup precisely.

    Test262

    The conformance suite lives at github.com/tc39/test262. Each test is a small JavaScript file with metadata:

    /*---
description: Array.prototype.at returns the last element
features: [Array.prototype.at]
---*/
assert.sameValue([1, 2, 3].at(-1), 3);

    Engines run Test262 in CI.

    9. Practical Examples

    Example 1: Using ES2026's Array.fromAsync()

    async function* fetchAllPages(url) {
    while (url) {
        const res = await fetch(url);
        const page = await res.json();
        yield* page.items;
        url = page.next;
    }
}

const allItems = await Array.fromAsync(fetchAllPages("/api/items"));
console.log(allItems.length);

    Code Breakdown:

    • Array.fromAsync collects an async iterable into an array .
    • Equivalent to for await...push, but concise.
    • Part of ECMAScript 2026 .

    Example 2: Using ES2026's Map.getOrInsert()

    const employeesByDept = new Map();

for await (const employee of employeeStream) {
    employeesByDept
        .getOrInsertComputed(employee.department, () => [])
        .push(employee);
}

    Code Breakdown:

    • getOrInsertComputed lazily creates the default value .
    • Replaces the has/set/get boilerplate.
    • Part of ECMAScript 2026 .

    Example 3: Using ES2026's Error.isError()

    try {
    riskyOperation();
} catch (err) {
    if (Error.isError(err)) {
        console.error("Real error:", err.message);
    } else {
        console.warn("Non-error thrown:", err);
    }
}

    Code Breakdown:

    • Error.isError() reliably identifies real error objects .
    • Handles the fact that JavaScript allows throwing anything.

    Example 4: Using ES2026's Temporal API

    const now = Temporal.Now.zonedDateTimeISO("America/New_York");
const meeting = now.add({ hours: 2 });
console.log(meeting.toString());

const birthday = Temporal.PlainDate.from("1990-05-15");
const age = birthday.until(Temporal.Now.plainDateISO()).years;
console.log(`Age: ${age}`);

    Code Breakdown:

    • Temporal replaces the broken Date object .
    • Immutable, time-zone-aware, calendar-aware.
    • Part of ECMAScript 2026.

    Example 5: Using ES2025's Iterator Helpers

    function* naturals() {
    let i = 0;
    while (true) yield i++;
}

const firstFiveEvens = naturals()
    .filter(n => n % 2 === 0)
    .take(5)
    .toArray();

console.log(firstFiveEvens); // [0, 2, 4, 6, 8]

    Code Breakdown:

    • Iterator Helpers add .map(), .filter(), .take(), .drop(), .toArray() to iterators.
    • Part of ECMAScript 2025 .

    Example 6: Using ES2025's Set Methods

    const a = new Set([1, 2, 3]);
const b = new Set([3, 4, 5]);

console.log(a.union(b));        // Set {1, 2, 3, 4, 5}
console.log(a.intersection(b)); // Set {3}
console.log(a.difference(b));   // Set {1, 2}

    Code Breakdown:

    • Native set operations, no library needed .
    • Part of ECMAScript 2025.

    Example 7: Using ES2026's JSON.rawJSON()

    const bigNumber = JSON.rawJSON("9007199254740993");
const json = JSON.stringify({ id: bigNumber });
console.log(json); // {"id":9007199254740993}

    Code Breakdown:

    • Preserves integers larger than Number.MAX_SAFE_INTEGER .
    • Avoids precision loss during serialization.

    11. Best Practices

    1. Know which edition introduced a feature. Why: determines engine support and transpilation needs.
    2. Check Stage 4 status before relying on a feature. Why: Stage 3 features can change.
    3. Use feature detection, not version detection. Why: engines ship features at different times.
    4. Prefer Baseline-supported features for production. Why: guaranteed cross-browser support.
    5. Transpile only what you need. Why: smaller bundles, faster builds.
    6. Follow TC39 proposals. Why: plan for upcoming features.
    7. Read the spec when behavior is surprising. Why: the spec is normative.
    8. Use Test262 to verify engine conformance. Why: catches differences early.
    9. Update TypeScript with new editions. Why: target and lib should match your runtime.
    10. Avoid polyfilling what engines already support. Why: wasted bytes.
    11. Understand backward compatibility. Why: old features never disappear — but new ones might not be everywhere.
    12. Use Intl (ECMA-402) for internationalization. Why: it's the standardized path.
    13. Follow the annual release cadence. Why: plan upgrades around June approvals.
    14. Prefer ECMAScript built-ins over libraries when available. Why: smaller dependencies.
    15. Document the ECMAScript baseline for your project. Why: teams need a shared target.

    12. Common Mistakes

    ❌ Mistake: Confusing ECMAScript with JavaScript

    "ECMAScript added fetch."

    Why it's wrong: fetch is a WHATWG API, not ECMAScript. ECMAScript does not define networking.

    ✅ Correct: Distinguish the language spec (ECMA-262) from host APIs (WHATWG, Node).

    ❌ Mistake: Assuming "ES6" Means All Modern JavaScript

    "We target ES6."

    Why it's wrong: ES6 (2015) is a decade old. ES2026 has added many features since.

    ✅ Correct: Specify the minimum edition and the target engines.

    ❌ Mistake: Using Stage 3 Features in Production Without a Plan

    Why it's wrong: Stage 3 features can change before Stage 4.

    ✅ Correct: Use Stage 3 features behind a flag or with a transpiler, and track the proposal.

    ❌ Mistake: Version Detection

    if (navigator.userAgent.includes("Chrome/120")) { /* ... */ }

    Why it's wrong: Fragile, unreliable, and doesn't reflect the actual feature set.

    ✅ Correct:

    if (typeof Array.prototype.at === "function") { /* ... */ }

    ❌ Mistake: Assuming "Latest Spec = Latest Browser"

    Why it's wrong: Engines lag the spec, and browsers lag engines.

    ✅ Correct: Check MDN / Can I Use / Baseline for actual support.

    ❌ Mistake: Ignoring Edition Numbering

    "ES2025 is the 15th edition."

    Why it's wrong: ES2025 is the 16th edition; ES2026 is the 17th.

    ✅ Correct: Know the edition numbers: ES2015 = 6th, ES2020 = 11th, ES2025 = 16th, ES2026 = 17th.

    ❌ Mistake: Thinking the Spec Defines the DOM

    Why it's wrong: The DOM is a WHATWG living standard, not ECMAScript.

    ✅ Correct: ECMAScript defines the language; WHATWG defines the DOM and other web APIs.

    ❌ Mistake: Skipping Intl (ECMA-402)

    Why it's wrong: Hand-rolled date/number formatting is error-prone and locale-insensitive.

    ✅ Correct: Use Intl.DateTimeFormat, Intl.NumberFormat, Intl.RelativeTimeFormat, etc.

    ❌ Mistake: Assuming All Engines Implement the Same Edition

    Why it's wrong: V8, SpiderMonkey, and JavaScriptCore ship features on different schedules.

    ✅ Correct: Use feature detection and Baseline.

    ❌ Mistake: Never Reading the Spec

    Why it's wrong: Surprising behaviors (coercion, prototype chains, async ordering) are explained precisely in the spec.

    ✅ Correct: Read tc39.es/ecma262 when behavior matters.

    13. Performance Considerations

    • Spec conformance is not performance. Engines optimize beyond what the spec requires.
    • Newer features are often faster. Array.fromAsync can be faster than manual loops; Math.sumPrecise is optimized.
    • Temporal is designed to be efficient compared to the legacy Date.
    • Iterator Helpers avoid intermediate arrays — lazy evaluation saves memory.
    • Set methods are optimized in engines versus userland polyfills.
    • Transpilation overhead — transpiled code can be slower than native.
    • Polyfill cost — large polyfills add parse and runtime cost.
    • JIT deoptimization — using rarely-seen syntax can deopt hot functions.
    • Spec-compliant edge cases can be slower than non-compliant shortcuts.

    Performance Tips

    1. Prefer native implementations over polyfills when available.
    2. Use Array.fromAsync over manual for await loops when collecting.
    3. Use Map.getOrInsert to avoid repeated has/get/set.
    4. Use Iterator Helpers instead of building intermediate arrays.
    5. Use Math.sumPrecise for numerically sensitive summation.
    6. Use Temporal for complex date math — it's faster and safer than hand-rolled.
    7. Avoid transpiling features your target engines already support.
    8. Check Baseline status before adding polyfills.
    9. Benchmark in the engines you ship to.
    10. Track engine conformance for performance improvements.

    14. Security Considerations

    Spec Compliance and Security

    Engines that deviate from the spec can introduce security bugs. Test262 and web-platform-tests help catch these.

    Prototype Pollution

    ECMAScript's prototype chain is powerful and dangerous. Malicious input can modify Object.prototype:

    Object.assign({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));

    Defenses: validate keys, use Object.create(null), freeze prototypes.

    eval and Function

    eval and the Function constructor execute arbitrary strings as code.

    Defenses: never evaluate untrusted input; CSP can block eval.

    Regular Expression Denial of Service (ReDoS)

    Complex regexes can cause catastrophic backtracking.

    Defenses: use safe-regex tools, limit input length, prefer linear-time patterns.

    Temporal and Time-Zone Data

    Temporal depends on the IANA time zone database, which updates periodically.

    Defenses: keep runtimes updated; don't hard-code time zone data.

    JSON Parsing

    JSON.parse is safe by design — it does not execute code. But JSON.parse on untrusted input can still produce large objects that exhaust memory.

    Defenses: limit input size; use streaming parsers for large payloads.

    Supply-Chain Risk in Polyfills

    Polyfills are packages. They can be compromised like any other dependency.

    Defenses: audit polyfills; prefer official core-js and polyfill-library; use SRI.

    Spec Ambiguity

    Some spec corners are subtle; different engines may interpret edge cases differently. This is rare but real.

    Defenses: test on multiple engines; report spec bugs to TC39.

    15. Debugging Tips

    • Read the spec. tc39.es/ecma262 is searchable and precise.
    • Check MDN for practical documentation and browser support.
    • Check Can I Use for feature support tables.
    • Check Baseline for "newly available" / "widely available" status.
    • Use Test262 to verify engine behavior.
    • Use node --version and process.versions.v8 to know your runtime.
    • Use npx browserslist to see which browsers your build targets.
    • Use Babel's REPL to see transpiled output.
    • Use console.log(Object.getOwnPropertyNames(globalThis)) to list available globals.
    • Use feature detection to verify runtime support:
    console.log(typeof Array.fromAsync); // "function" if supported
console.log(typeof Temporal);        // "object" if supported
    • Track TC39 proposals at github.com/tc39/proposals.
    • Follow ecmascript.news for weekly updates.

    16. When to Use (ECMAScript Features)

    • Whenever a native feature exists — prefer it over a library.
    • When the feature is at Stage 4 — it's guaranteed in the next edition.
    • When Baseline support covers your targets — safe for production.
    • When transpilation is acceptable — for Stage 3 / newly Stage 4 features.
    • For new projects — target the latest edition you can support.
    • For libraries — target a conservative Baseline to maximize reach.
    • For internal tools — target the latest edition your runtime supports.

    17. When Not to Use

    • Stage 0–2 features in production. Too unstable.
    • Stage 3 features without a fallback. May change.
    • Features your runtime doesn't support unless transpiled.
    • Features that add more complexity than they remove.
    • New features just because they exist — evaluate the trade-off.
    • Polyfills for features already in your Baseline.
    • Temporal in environments with outdated time-zone data.
    • eval and Function for dynamic code — security and performance risks.

    19. Did You Know?

    • ECMAScript was named after Ecma International, not the other way around.
    • Edition 4 was abandoned — it was too ambitious and nearly killed the standard.
    • ES6 took six years (2009–2015); the annual cadence was introduced to prevent that.
    • The typeof null === "object" bug is preserved for backward compatibility and will never be fixed.
    • NaN !== NaN is the only value not equal to itself — defined by IEEE-754.
    • 0.1 + 0.2 !== 0.3 — floating-point arithmetic, not a spec bug.
    • Test262 has over 50,000 tests and runs in every major engine's CI.
    • TC39 operates by consensus — any member can block a proposal.
    • Stage 2.7 was added in 2023 to bridge Stage 2 and Stage 3.
    • Temporal replaces the Date object, which has been criticized for decades.
    • Explicit Resource Management (using) was inspired by C# and Python's with.
    • Iterator Helpers bring functional programming to lazy sequences.
    • Array.fromAsync was requested by developers for years before reaching Stage 4.
    • Math.sumPrecise solves a real numerical-analysis problem.
    • Error.isError() addresses the fact that you can throw 42.
    • ECMAScript 2026 is the 17th edition, approved on June 30, 2026 .
    • ECMAScript 2025 is the 16th edition, published in June 2025 .
    • JSON modules (ES2025) let you import JSON natively.
    • RegExp /v flag (ES2025) is a superset of /u for Unicode sets.
    • Promise.try() (ES2025) simplifies promise chain error handling.
    • Float16Array (ES2025) is useful for ML and graphics workloads.
    • The spec is written in prose + algorithms, not code — engines translate it.
    • You can read the spec for free at tc39.es/ecma262.

    20. Summary

    • ECMAScript is the standardized specification of JavaScript, published as ECMA-262.
    • It defines the language: syntax, types, semantics, built-ins, and execution model.
    • It does not define host APIs — DOM, Fetch, fs, timers are separate standards.
    • TC39 evolves the language through a five-stage proposal process (0–4).
    • Since ES2015, releases are annual and named by year (ES2026, ES2025, etc.).
    • Stage 4 means a feature is finished and will be in the next edition.
    • Test262 is the official conformance test suite.
    • Backward compatibility is absolute — no feature is ever removed.
    • ECMA-402 covers internationalization (Intl); ECMA-419 covers embedded systems.
    • ES2025 added Iterator Helpers, Set methods, JSON modules, RegExp modifiers, Promise.try, and Float16Array.
    • ES2026 (17th edition, approved June 30, 2026) adds Temporal, Map.getOrInsert, Array.fromAsync, Error.isError, Math.sumPrecise, Iterator.concat, Uint8Array base64/hex, JSON.rawJSON, and Explicit Resource Management.
    • Feature detection beats version detection.
    • Baseline is the cross-browser support standard.
    • Read the spec at tc39.es/ecma262; follow proposals at github.com/tc39/proposals.
    • ECMAScript is the blueprint; JavaScript is the building.
