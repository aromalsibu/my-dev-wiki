    Runtime Environments

    1. Overview

    Definition

    A JavaScript runtime environment is the complete system that executes JavaScript code. It consists of three layers: a JavaScript engine (the core that parses and runs the language), a set of host APIs (the platform-specific interfaces the engine exposes), and the event loop (the concurrency model that orchestrates asynchronous work). The engine is the same everywhere — V8 in Chrome and Node.js, JavaScriptCore in Safari and Bun — but the host APIs and event loop differ profoundly.

    // Same language, different runtimes:

// Browser runtime:
document.querySelector("#app");       // DOM API
localStorage.setItem("key", "val");   // Storage API
window.fetch("/api");                 // Fetch API

// Node.js runtime:
const fs = require("node:fs");        // File system API
process.env.NODE_ENV;                 // Process API
fs.readFileSync("./data.json");       // Synchronous I/O

// Deno runtime:
const file = await Deno.readTextFile("./data.json"); // Deno API
Deno.env.get("HOME");                 // Environment API

// Bun runtime:
const server = Bun.serve({ fetch: () => new Response("hi") }); // Bun API
Bun.file("./data.json");              // Bun file API

    The runtime is what turns ECMAScript — a specification — into a working program that can read files, make network requests, and interact with users.

    Purpose

    Runtime environments exist because ECMAScript deliberately says nothing about I/O. The spec defines the language; it does not define how to read a file, open a network connection, or render a button. Runtimes bridge that gap:

    • Browsers provide the DOM, CSSOM, Fetch, Storage, and the rendering pipeline.
    • Node.js provides the filesystem, process, network, and CommonJS/ESM module systems.
    • Deno provides a permissioned, web-standard-first runtime with TypeScript support.
    • Bun provides an all-in-one toolchain with a built-in package manager, bundler, and test runner.
    • Edge runtimes (Cloudflare Workers, Deno Deploy, Vercel Edge) provide lightweight, globally distributed execution with restricted APIs.

    Without runtimes, JavaScript would be a language that could compute but not do anything. The runtime is what makes JavaScript a platform.

    Where It Fits

    ┌────────────────────────────────────────────────────────────┐
│                    JavaScript Runtime                       │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐  │
│  │              JavaScript Engine                        │  │
│  │   (V8, JavaScriptCore, SpiderMonkey, Hermes)          │  │
│  │                                                      │  │
│  │   Parser → Interpreter → JIT Compilers → GC          │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐  │
│  │              Host APIs                                │  │
│  │   DOM · Fetch · fs · process · crypto · net            │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐  │
│  │              Event Loop                               │  │
│  │   Microtasks · Macrotasks · Timers                    │  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘

    Every runtime embeds an engine, exposes host APIs, and implements an event loop. The differences are in which APIs, how the event loop behaves, and what constraints the runtime imposes.

    2. Why It Exists

    The Problem

    ECMAScript defines how to compute, not how to communicate. A language that can add numbers but cannot read a file, open a socket, or draw a pixel is a calculator, not a platform. The web needed a language that could:

    • React to user input in real time.
    • Fetch data from servers without reloading the page.
    • Run on servers, not just in browsers.
    • Execute in constrained environments (mobile, edge, embedded).

    Each of these requires host APIs — and each host has different capabilities, security models, and constraints.

    Previous Limitations

    Era Limitation
    1995–2008 JavaScript confined to browsers; no server-side runtime
    Pre-Node (2009) No standard server API; no package registry
    Pre-Deno (2018) Node's security model was opt-in and incomplete
    Pre-Bun (2022) Toolchains were assembled from many separate tools
    Pre-Edge (2018+) Serverless functions were slow and cold-start heavy

    Why Different Runtimes Exist

    Runtimes were not designed by committee — they were built to solve specific problems:

    • Browsers needed to execute untrusted code safely while rendering UI.
    • Node.js (2009) needed to bring JavaScript to the server with I/O and a package ecosystem.
    • Deno (2018) was created by Ryan Dahl to fix what he saw as Node's design mistakes: insecure by default, awkward module system, no TypeScript support.
    • Bun (2022) was created to offer a single, fast toolchain — runtime, package manager, bundler, and test runner in one.
    • Edge runtimes (Cloudflare Workers, Deno Deploy, Vercel Edge) were created to run code close to users with minimal cold starts.

    Each runtime solves a different problem. Choosing a runtime means choosing which problems matter most.

    Node.js Runtime

    // server.js — Node.js (ESM)
import { createServer } from "node:http";
import { readFile } from "node:fs/promises";
import process from "node:process";

const server = createServer(async (req, res) => {
    if (req.url === "/") {
        const html = await readFile("./index.html", "utf8");
        res.writeHead(200, { "Content-Type": "text/html" });
        res.end(html);
    } else {
        res.writeHead(404);
        res.end("Not found");
    }
});

server.listen(3000, () => {
    console.log(`Server running on port ${process.env.PORT ?? 3000}`);
});

    // server.ts — Deno (TypeScript directly)
const server = Deno.serve({ port: 3000 }, async (req) => {
    if (req.url.endsWith("/")) {

        return new Response(html, {
            headers: { "Content-Type": "text/html" },
        });

            });

        return new Response("Not found", { status: 404 });

    5. Core Concepts

    Concept 1: Browser Runtimes

    Browsers are the original JavaScript runtime. They provide:

    • DOM — the document object model.
    • CSSOM — the stylesheet object model.
    • Fetch API — HTTP requests.
    • Storage APIs — localStorage, sessionStorage, IndexedDB.
    • Web Workers — background threads.
    • Canvas / WebGL / WebGPU — graphics.
    • Event Loop — the WHATWG-defined task/microtask model.

    Browsers are sandboxed by origin: scripts from example.com cannot read data from bank.com.

    Concept 2: Node.js — The Incumbent

    Node.js (2009) brought JavaScript to the server. As of 2026:

    • Current LTS: Node.js 24.x ("Krypton").
    • Latest: Node.js 26.x.
    • Built-in test runner — no Jest required for basic testing.
    • Native ESM support alongside CommonJS.
    • Built-in watch mode — node --watch.
    • Permission model — still maturing, opt-in.
    • Temporal API — Node.js 26 ships with Temporal enabled by default.
    • V8 14.6 — the engine powering Node.js 26.
    • Streams iter API — new node:stream/iter implementation.
    • util.throttle() and util.debounce() — new utilities.

    Node's strengths: ecosystem depth, everywhere-supported hosting, native module compatibility. Its weakness: TypeScript still requires a build step or loader, and the toolchain is assembled rather than provided.

    Concept 3: Deno — Secure by Default

    Deno (2018) was created by Ryan Dahl to fix Node's design mistakes. As of 2026:

    • Deno 2.9 — current release.
    • Temporal API stabilized in Deno 2.7 (no --unstable-temporal flag needed).
    • Windows on ARM — official builds.
    • npm overrides in package.json.
    • Deno Desktop — build native desktop apps from web tech.
    • CSS module imports.
    • import defer — deferred imports.
    • 3.66× faster cold npm installs.
    • Node.js 26 compatibility.
    • Deny-by-default permissions — the runtime refuses filesystem, network, and environment access unless explicitly granted.
    • TypeScript runs directly — no build step.

    Deno's strengths: security model, web-standard APIs, TypeScript-first. Its weakness: smaller ecosystem than Node.

    Concept 4: Bun — The All-in-One Toolchain

    Bun (2022) is an all-in-one runtime, package manager, bundler, and test runner. As of 2026:

    • Bun 1.4 — the first release written in Rust instead of Zig.
    • 50% faster startup on Linux.
    • 35% less memory for HTTP servers.
    • 5× lower idle CPU usage.
    • Node.js 26 compatibility — 1,517 additional Node.js compatibility tests passing.
    • Bun.serve supports HTTP/2.
    • Bun.Image, Bun.WebView, Bun.markdown, Bun.cron(), Bun.Terminal — new APIs.
    • bun install is faster for packages using node-gyp.
    • bun audit fix, bun dedupe, bun prune — dependency management.
    • Uses JavaScriptCore — not V8.

    Bun's strengths: developer iteration speed, single toolchain, fast installs. Its weakness: smaller ecosystem, newer than Node.

    Concept 5: Edge Runtimes

    Edge runtimes run code close to users on globally distributed infrastructure. They are optimized for cold start speed and low latency.

    Edge Runtime Engine Notes
    Cloudflare Workers V8 (workerd) Node.js compatibility enabled by default since August 2026
    Deno Deploy V8 Generally available since February 2026; supports Deno.cron()
    Vercel Edge V8 Deprecated in Next.js; use Node.js runtime instead

    Edge runtimes do not support all Node.js APIs. They are a subset designed for web-standard compatibility.

    Concept 6: The WinterCG / WinterTC Standardization

    WinterCG (Web-interoperable Runtimes Community Group) was a W3C community group working to define a common API surface for server-side JavaScript runtimes. In 2025, it transitioned to WinterTC — an Ecma International Technical Committee — to formalize the standardization process.

    The goal: ensure that code written for one runtime (Deno, Cloudflare Workers) can run on another with minimal changes.

    Concept 7: Lightweight Runtimes

    LLRT (Low Latency Runtime) — AWS's experimental runtime built in Rust using QuickJS. Designed for fast cold starts in serverless. No JIT, so it can be slower than Node for CPU-heavy work, but ~10× faster cold starts.

    WinterJS — a JavaScript Service Workers server written in Rust using SpiderMonkey. Compliant with the WinterCG specification.

    QuickJS — a small, embeddable engine with no JIT, used in LLRT and other constrained environments.

    Concept 8: The Event Loop Across Runtimes

    The event loop is host-defined:

    Runtime Event Loop Model
    Browser WHATWG: macrotasks + microtasks + rendering
    Node.js libuv: timers, I/O, check, close callbacks
    Deno Tokio: async Rust runtime
    Bun JavaScriptCore + Bun's own event loop

    The microtask queue (promises) is drained before the next macrotask in all runtimes. But timing and ordering of I/O callbacks differ.

    Concept 9: Module Systems Across Runtimes

    Runtime CommonJS ESM TypeScript
    Browser ❌ ✅ Via bundler
    Node.js ✅ ✅ Via build step or loader
    Deno Via npm compat ✅ ✅ directly
    Bun ✅ ✅ ✅ directly

    ESM is the future, but CommonJS persists in Node's ecosystem.

    Concept 10: Package Management Across Runtimes

    Runtime Package Manager Registry
    Node.js npm, yarn, pnpm npm
    Deno Built-in, npm specifiers npm, JSR
    Bun Built-in (bun install) npm
    Edge Via bundler npm

    JSR (JavaScript Registry) is a modern, TypeScript-first registry from the Deno team.

    Concept 11: Permissions Models

    Runtime Default Permission Model
    Browser Sandboxed by origin Same-origin policy
    Node.js Full access Opt-in --permission flag
    Deno Deny by default Explicit --allow-read, --allow-net, etc.
    Bun Full access Opt-in permissions
    Edge Restricted APIs No filesystem access

    Deno's deny-by-default model is the strictest.

    Concept 12: Deployment Targets

    Target Recommended Runtime
    Chrome extension V8 (browser)
    Firefox extension SpiderMonkey (browser)
    Safari extension JavaScriptCore (browser)
    Node.js server Node.js
    Deno server Deno
    Bun server Bun
    Cloudflare Workers workerd (V8)
    Deno Deploy Deno
    Vercel Functions Node.js (recommended)
    AWS Lambda Node.js or LLRT
    React Native Hermes
    Embedded QuickJS

    6. How It Works

    Step-by-Step: Runtime Initialization (Node.js)

    1.  `node script.js` invoked.
    │
    ▼
2.  V8 engine initialized.
    │
    ▼
3.  Node.js bootstraps its host APIs (fs, net, process).
    │
    ▼
4.  libuv event loop starts.
    │
    ▼
5.  script.js is parsed, compiled, and executed.
    │
    ▼
6.  Top-level code runs to completion.
    │
    ▼
7.  Event loop waits for I/O, timers, and callbacks.
    │
    ▼
8.  Process exits when no more work is pending.

    Step-by-Step: Runtime Initialization (Deno)

    1.  `deno run --allow-net server.ts` invoked.
    │
    ▼
2.  V8 engine initialized.
    │
    ▼
3.  Deno's permission system checks granted permissions.
    │
    ▼
4.  TypeScript is transpiled (no separate build step).
    │
    ▼
5.  Tokio async runtime starts.
    │
    ▼
6.  Code executes with access only to granted APIs.
    │
    ▼
7.  Event loop processes async work.
    │
    ▼
8.  Process exits when work completes.

    Step-by-Step: Edge Runtime Execution

    1.  Request arrives at edge location.
    │
    ▼
2.  V8 isolate is spun up (cold start or warm).
    │
    ▼
3.  Worker script executes.
    │
    ▼
4.  Fetch handler processes request.
    │
    ▼
5.  Response returned to user.
    │
    ▼
6.  Isolate is kept warm or evicted.

    Step-by-Step: The Event Loop (Browser vs Node)

    Browser:                          Node.js:
┌─────────────┐                   ┌─────────────┐
│ Macrotask   │                   │ Timers      │
│ (script,    │                   │             │
│  setTimeout,│                   │ I/O         │
│  UI events) │                   │             │
└──────┬──────┘                   └──────┬──────┘
       │                                │
       ▼                                ▼
┌─────────────┐                   ┌─────────────┐
│ Microtask   │                   │ Check       │
│ (promises,  │                   │ (setImmediate)│
│  queueMicro)│                   │             │

└─────────────┘                   └─────────────┘

    Both drain microtasks before the next macrotask, but the macrotask categories differ.

    9. Practical Examples

    Example 1: Same Server, Four Runtimes

    Node.js:

    import { createServer } from "node:http";

createServer((req, res) => {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify({ runtime: "node", version: process.version }));
}).listen(3000);

    Deno:

    Deno.serve({ port: 3000 }, () =>
    Response.json({ runtime: "deno", version: Deno.version.deno })
);

    Bun:

    Bun.serve({
    port: 3000,
    fetch: () => Response.json({ runtime: "bun", version: Bun.version }),
});

    Cloudflare Workers:

    export default {
    fetch: () => Response.json({ runtime: "workers", version: "2026" }),
};

    All four run the same language — but with different APIs and deployment models.

    Example 2: Permission Model in Deno

    # ❌ Fails — no read permission
deno run server.ts

# ✅ Succeeds — read and net permissions granted
deno run --allow-read --allow-net server.ts

# ✅ Succeeds — specific domains only
deno run --allow-net=api.example.com server.ts

    Breakdown:

    • Deno denies by default.
    • Permissions are granted per-resource.
    • This prevents compromised dependencies from exfiltrating data.

    Example 3: Edge Function with Caching

    // Cloudflare Worker with KV caching
export default {
    async fetch(request, env, ctx) {
        const cacheKey = new URL(request.url).pathname;

        // Check KV cache
        const cached = await env.MY_KV.get(cacheKey);
        if (cached) {
            return new Response(cached, {
                headers: { "Content-Type": "application/json", "X-Cache": "HIT" },
            });
        }

        // Fetch from origin
        const res = await fetch(`https://api.example.com${cacheKey}`);
        const data = await res.json();

        // Store in KV
        ctx.waitUntil(env.MY_KV.put(cacheKey, JSON.stringify(data), {
            expirationTtl: 3600,
        }));

        return Response.json(data, { headers: { "X-Cache": "MISS" } });
    },
};

    Breakdown:

    • env.MY_KV — Cloudflare KV namespace.
    • ctx.waitUntil — extends the worker's lifetime for async work.
    • Edge caching reduces latency and origin load.

    Example 4: LLRT for Serverless

    // lambda.mjs — LLRT handler
export const handler = async (event) => {
    const { name = "World" } = event;

    return {
        statusCode: 200,
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
            message: `Hello, ${name}!`,
            runtime: "LLRT",
        }),
    };
};

    Breakdown:

    • LLRT uses QuickJS — no JIT.
    • Cold starts are ~10× faster than Node.
    • Best for I/O-bound, low-compute serverless functions.

    Example 5: WinterJS Service Worker

    // winterjs-worker.js
addEventListener("fetch", (event) => {
    event.respondWith(
        new Response("Hello from WinterJS", {
            headers: { "Content-Type": "text/plain" },
        })
    );
});

    Breakdown:

    • WinterJS runs Service Workers scripts on the server.
    • Powered by SpiderMonkey (Firefox's engine).
    • Compliant with the WinterCG specification.

    11. Best Practices

    1. Choose the runtime based on constraints, not hype. Why: each runtime has trade-offs.
    2. Use feature detection, not runtime detection. Why: code should be portable where possible.
    3. Prefer web-standard APIs (fetch, URL, crypto). Why: portability across runtimes.
    4. Isolate runtime-specific code behind adapters. Why: makes migration possible.
    5. Understand the security model before deploying. Why: Deno denies by default; Node grants freely.
    6. Keep dependencies minimal. Why: every dependency is a potential supply-chain risk.
    7. Use lockfiles. Why: reproducible installs across machines and runtimes.
    8. Test on the runtime you deploy to. Why: V8 and JavaScriptCore differ in edge cases.
    9. Monitor cold starts. Why: edge and serverless runtimes are sensitive to startup latency.
    10. Use the built-in tools where possible. Why: Bun and Deno ship test runners, bundlers, and formatters.
    11. Don't assume Node.js APIs exist everywhere. Why: edge runtimes are a subset.
    12. Use node: prefix for Node built-ins. Why: explicit, future-proof, works in ESM.
    13. Update runtimes regularly. Why: security patches and performance improvements ship frequently.
    14. Profile with runtime-specific tools. Why: Chrome DevTools for V8, Web Inspector for JSC.
    15. Document your runtime choice. Why: teams need to know why they chose Node vs Deno vs Bun.

    12. Common Mistakes

    ❌ Mistake: Assuming Node.js APIs Work on the Edge

    // ❌ Fails on Cloudflare Workers
import fs from "node:fs";
const data = fs.readFileSync("./data.json");

    Why it's wrong: Edge runtimes have no filesystem access.

    ✅ Correct: Use KV storage or fetch data from an origin.

    ❌ Mistake: Using process.env in Edge Runtimes

    // ❌ Fails on Cloudflare Workers
const key = process.env.API_KEY;

    Why it's wrong: process is not available in edge runtimes.

    ✅ Correct: Use env bindings:

    export default {
    async fetch(request, env) {
        const key = env.API_KEY;
    },
};

    ❌ Mistake: Ignoring Deno's Permission Model

    # ❌ Fails
deno run server.ts

# ✅ Correct
deno run --allow-net server.ts

    Why it's wrong: Deno denies by default — this is a feature, not a bug.

    ❌ Mistake: Assuming Bun Is Node

    Why it's wrong: Bun uses JavaScriptCore, not V8. Some Node APIs are missing or behave differently.

    ✅ Correct: Test your code on Bun before deploying.

    ❌ Mistake: Using require in ESM-Only Runtimes

    // ❌ Fails in browsers and Deno
const fs = require("fs");

    Why it's wrong: ESM uses import, not require.

    ✅ Correct:

    import fs from "node:fs";

    ❌ Mistake: Ignoring Runtime-Specific Event Loop Behavior

    Why it's wrong: setTimeout(0) and setImmediate ordering differs between Node and browsers.

    ✅ Correct: Understand the event loop of your target runtime.

    ❌ Mistake: Assuming All Runtimes Support TypeScript Natively

    Why it's wrong: Node.js requires a build step or loader; browsers don't support TypeScript at all.

    ✅ Correct: Use Deno or Bun for native TypeScript, or transpile for Node and browsers.

    ❌ Mistake: Overlooking Cold Start Costs

    Why it's wrong: Serverless and edge functions pay a cold start penalty. Node.js cold starts are slower than LLRT or Cloudflare Workers.

    ✅ Correct: Choose a runtime optimized for your cold-start requirements.

    ❌ Mistake: Using eval in Edge Runtimes

    // ❌ Blocked in Edge Runtime
eval("console.log('hi')");

    Why it's wrong: Edge runtimes disable eval and new Function for security.

    ✅ Correct: Avoid dynamic code execution entirely.

    ❌ Mistake: Forgetting That Edge Runtimes Are Subsets

    Why it's wrong: The Edge Runtime is a subset of Node.js APIs, not a superset.

    ✅ Correct: Check compatibility before deploying.

    13. Performance Considerations

    • Cold start — LLRT (~10× faster than Node), Cloudflare Workers (< 5ms), Node.js (~100ms+).
    • Throughput — Bun and Deno often outperform Node.js in synthetic benchmarks, but real workloads vary.
    • Memory — Bun 1.4 reduced idle memory by up to 35%.
    • Startup time — Bun 1.4 is 50% faster on Linux.
    • Concurrency — Node's libuv vs Deno's Tokio vs Bun's JavaScriptCore event loop.
    • JIT warmup — V8 and JavaScriptCore have different warmup profiles.
    • GC pauses — Orinoco (V8) vs JSC's GC vs QuickJS (no JIT, no GC tuning).
    • Network I/O — Bun's Bun.serve is highly optimized for HTTP.
    • Package install — Bun's install is up to 29% faster than npm on Node 26.

    Performance Tips

    1. Benchmark on your workload, not synthetic benchmarks.
    2. Use Bun for fast local development iteration.
    3. Use Node.js for ecosystem maturity and native modules.
    4. Use Deno for security-sensitive applications.
    5. Use LLRT for cold-start-sensitive serverless functions.
    6. Use edge runtimes for globally distributed, low-latency APIs.
    7. Profile with runtime-specific tools.
    8. Keep dependencies minimal to reduce startup cost.
    9. Use streaming APIs for large payloads.
    10. Monitor real-user metrics (RUM), not just lab tests.

    14. Security Considerations

    Deno's Permission Model

    Deno denies by default. A script cannot read files, access the network, or read environment variables without explicit permission.

    deno run --allow-read=./data --allow-net=api.example.com server.ts

    This is the strictest security model among major runtimes.

    Node.js Permission Model

    Node.js has an opt-in permission model:

    node --permission --allow-fs-read=./data server.js

    Still maturing, but available since Node 20.

    Supply-Chain Risk Across Runtimes

    All runtimes that use npm packages are vulnerable to supply-chain attacks. The 2025–2026 npm supply-chain attacks affected multiple ecosystems.

    Defenses: lockfiles, npm audit, provenance, allowlists, minimal dependencies.

    Edge Runtime Security

    Edge runtimes disable eval and new Function. They also have no filesystem access. This makes them inherently safer for running untrusted code.

    Sandboxing

    For running untrusted JavaScript, consider:

    • Deno's permission model.
    • isolated-vm (Node.js).
    • quickjs-emscripten (WASM-based QuickJS).
    • Edge runtime isolates.

    Runtime-Specific CVEs

    • V8: CVE-2026-85046 (type confusion in Array.prototype.sort, CVSS 8.8).
    • JavaScriptCore: ZDI-26-610 (use-after-free in B3 ReduceStrength).
    • JavaScriptCore: CVE-2026-20664 (WebAssembly memory bug).

    Keep runtimes updated.

    Secrets Management

    • Node.js: process.env or a secrets manager.
    • Deno: Deno.env.get() with --allow-env.
    • Cloudflare Workers: env bindings.
    • Bun: Bun.env.

    Never hard-code secrets in code.

    17. When Not to Use

    • Node.js — when you need strict security by default (use Deno).
    • Deno — when you need deep ecosystem compatibility (use Node).
    • Bun — when you need maximum ecosystem maturity (use Node).
    • Edge runtimes — when you need full Node.js API access.
    • LLRT — when you need JIT performance (use Node or Bun).
    • Hermes — when you need peak throughput (use V8).
    • QuickJS — when you need JIT performance.

    20. Summary

    • A runtime environment combines an engine, host APIs, and an event loop.
    • Browsers provide the DOM, Fetch, Storage, and the rendering pipeline.
    • Node.js (2009) is the incumbent: deep ecosystem, native modules, everywhere-supported.
    • Deno (2018) is secure by default: deny-by-default permissions, TypeScript-first, web-standard APIs.
    • Bun (2022) is an all-in-one toolchain: runtime, package manager, bundler, and test runner in one.
    • Edge runtimes (Cloudflare Workers, Deno Deploy) run code close to users with minimal cold starts.
    • WinterCG / WinterTC standardizes the API surface across server-side runtimes.
    • LLRT and WinterJS are lightweight runtimes for serverless and edge.
    • Hermes is optimized for React Native mobile apps.
    • QuickJS is a small, embeddable engine for constrained environments.
    • Security models differ: browsers are sandboxed by origin; Node grants all by default; Deno denies all by default.
    • Performance differs: Bun is fast; LLRT has fast cold starts; Node has mature ecosystem.
    • Choose based on constraints: ecosystem, security, performance, deployment target.
    • Write portable code using web-standard APIs where possible.
    • Test on the runtime you deploy to — engines and host APIs differ.
    • The runtime is the platform — it determines what your JavaScript can actually do.
