    Function Expressions

    1. Overview

    Definition

    A function expression is a function defined inside an expression — where a value is expected — rather than as a standalone statement. The function keyword can be used within any expression context, and the resulting function object can be assigned to a variable, passed as an argument, or returned from another function.

    // Assigned to a variable
const multiply = function(a, b) {
    return a * b;
};

// Passed as an argument
[1, 2, 3].map(function(n) { return n * 2; });

// Returned from a function
function createAdder(x) {
    return function(y) { return x + y; };
}

    A function expression has the same syntax as a function declaration, but the context in which it appears makes it an expression. The primary difference between a function expression and a function declaration is the function name, which can be omitted in function expressions to create anonymous functions .

    Purpose

    Function expressions exist to solve the first-class function problem: JavaScript treats functions as values. Functions can be assigned to variables, passed to other functions, and returned from functions. Function expressions are the syntax that makes this possible.

    They serve as the value-oriented function syntax of the language:

    • Assignment — store a function in a variable.
    • Arguments — pass a function to another function.
    • Returns — produce a function from another function.
    • Immediate execution — IIFEs run immediately after definition.
    • Callbacks — provide inline function logic where a function is expected.

    Where It Fits

    Functions
├── Function Declarations       ✅ done
├── Function Expressions        ← you are here
├── Arrow Functions
├── Parameters
├── Rest Parameters
├── Default Parameters
├── Closures
├── Higher-Order Functions
└── Pure Functions

    Function Expressions sit directly after Function Declarations because they are the two fundamental ways to create functions in JavaScript. The next concept, Arrow Functions, introduces a more concise syntax with different this behavior.

    2. Why It Exists

    The Problem

    JavaScript was designed from the beginning with functions as first-class values. But a function declaration is a statement — it does not produce a value that can be assigned or passed. To treat a function as a value, the language needed a different syntax form: the function expression.

    Without function expressions, you could not:

    • Assign a function to a variable.
    • Pass a function as a callback.
    • Return a function from another function.
    • Create a function inline where a value is expected.
    • Use an IIFE to create a private scope.

    Previous Limitations

    Era Limitation
    No function expressions Functions could only be declared, not used as values
    No callbacks Event handling and array methods required named functions
    No IIFEs No way to create private scopes in scripts
    No closures from expressions Returning functions from functions was impossible
    No inline functions Every callback had to be declared separately

    Why Function Expressions Were Introduced

    Function expressions were part of the original JavaScript (1995). They solved the first-class function problem by allowing the function keyword to appear in expression position — where a value is expected.

    This single design decision enabled:

    • Callbacks — passing functions to setTimeout, addEventListener, and array methods.
    • IIFEs — immediately invoked function expressions for private scoping.
    • Higher-order functions — functions that take or return functions.
    • Closures — functions that capture their lexical environment.

    Function expressions are what make JavaScript a functional programming language as well as an imperative one.

    The Block-Level Problem (Resolved by Function Expressions)

    Function declarations inside blocks had inconsistent behavior across browsers. Function expressions solved this by being block-scoped by nature — a const or let binding is block-scoped, and a function expression assigned to it inherits that scope.

    3. Syntax / Basic Usage

    Basic Syntax

    const name = function(param0, param1) {
    statements
};

    Anonymous Function Expression

    const greet = function() {
    return "Hello, world!";
};

greet(); // "Hello, world!"

    The function is anonymous — it has no name after the function keyword. It is invoked using the variable name.

    Named Function Expression

    const factorial = function calc(n) {
    if (n <= 1) return 1;
    return n * calc(n - 1);
};

factorial(5); // 120
// calc(5); // ❌ ReferenceError — name is only available inside

    The name calc is local to the function body — it is not available outside. This allows recursion without relying on the outer variable name .

    Function Expression as Argument

    [1, 2, 3].map(function(n) {
    return n * 2;
});
// [2, 4, 6]

setTimeout(function() {
    console.log("done");
}, 1000);

    Function Expression as Return Value

    function createMultiplier(factor) {
    return function(n) {
        return n * factor;
    };
}

const double = createMultiplier(2);
double(5); // 10

    IIFE — Immediately Invoked Function Expression

    (function() {
    const privateVar = "secret";
    console.log(privateVar); // "secret"
})();

// Arrow function IIFE (modern)
(() => {
    const privateVar = "secret";
    console.log(privateVar);
})();

    The parentheses around the function are required — without them, the parser treats the function keyword as the start of a declaration, not an expression .

    Async Function Expression

    const fetchData = async function(url) {
    const res = await fetch(url);
    return res.json();
};

    Generator Function Expression

    const range = function*(start, end) {
    for (let i = start; i <= end; i++) {
        yield i;
    }
};

[...range(1, 5)]; // [1, 2, 3, 4, 5]

    Async Generator Function Expression

    const streamPages = async function*(url) {
    while (url) {
        const res = await fetch(url);
        const page = await res.json();
        yield* page.items;
        url = page.next;
    }
};

    Function Expressions in Objects

    const calculator = {
    add: function(a, b) { return a + b; },
    subtract: function(a, b) { return a - b; },
};

    Function Expressions in Arrays

    const operations = [
    function(a, b) { return a + b; },
    function(a, b) { return a - b; },
];

    4. Mental Model

    The "Value Factory" Mental Model

    A function declaration is a named recipe. A function expression is a recipe you hand to someone:

    Function Declaration:               Function Expression:
┌─────────────────────┐            ┌─────────────────────┐
│ Recipe: "greet"     │            │ Here's a recipe —   │
│                     │            │ use it when you     │
│ (named, standalone) │            │ need it.            │
│                     │            │                     │
│ Saved for later.    │            │ It's a value.       │
└─────────────────────┘            └─────────────────────┘

    The "Expression Position" Mental Model

    A function is an expression when it appears where a value is expected:

    Statement position (declaration):     Expression position (expression):
┌─────────────────────────────┐       ┌─────────────────────────────┐
│ function greet() {}         │       │ const greet = function() {}; │
│                             │       │                             │
│ Top-level of script/function│       │ Right side of =             │
│                             │       │ Argument to a function      │
│                             │       │ Returned from a function    │
│                             │       │ Inside parentheses          │
└─────────────────────────────┘       └─────────────────────────────┘

    The "No Hoisting" Mental Model

    Function expressions are not hoisted — they are created when the execution reaches them:

    Function Declaration:                Function Expression:
┌─────────────────────┐              ┌─────────────────────┐
│ greet(); // ✅ works│              │ greet(); // ❌ Error│
│                     │              │                     │
│ function greet() {} │              │ const greet =       │
│                     │              │   function() {};    │
│                     │              │                     │
│ Hoisted fully.      │              │ Created at runtime. │
└─────────────────────┘              └─────────────────────┘

    Function expressions are not hoisted, unlike function declarations. You cannot use a function expression before you create it .

    The "Named vs. Anonymous" Mental Model

    Anonymous:                          Named:
┌─────────────────────┐            ┌─────────────────────┐
│ const f = function()│            │ const f = function   │
│   {};               │            │   named() {};        │
│                     │            │                      │
│ No self-reference.  │            │ Self-reference       │
│ Hard to debug.      │            │ inside the function. │
│                     │            │ Better stack traces. │
└─────────────────────┘            └─────────────────────┘

    Named function expressions provide a self-reference inside the function body — useful for recursion and debugging .

    5. Core Concepts

    Concept 1: Function Declaration vs. Function Expression

    Aspect Declaration Expression
    Position Statement Expression
    Name Required Optional
    Hoisting Fully hoisted Not hoisted
    Syntax function f() {} const f = function() {};
    Called before definition ✅ Yes ❌ No

    The primary difference is where the function keyword appears — statement position makes it a declaration; expression position makes it an expression .

    Concept 2: Anonymous Function Expressions

    const greet = function() {
    return "Hello";
};

    The function has no name after the function keyword. It is invoked using the variable name. Anonymous functions are common for callbacks and IIFEs.

    Concept 3: Named Function Expressions

    const factorial = function calc(n) {
    if (n <= 1) return 1;
    return n * calc(n - 1);
};

    The name calc is local to the function body. It is not accessible outside. This allows:

    • Recursion — the function can call itself by name.
    • Better stack traces — the name appears in error traces.
    • Self-reference — useful for event handlers that need to remove themselves.

    A named function expression can be accessed by the function name only within the function itself .

    Concept 4: No Hoisting

    console.log(notHoisted); // undefined
// Even though the variable name is hoisted, the definition isn't.
const notHoisted = function() {};

    Function expressions are not hoisted — the variable declaration is hoisted (for var), but the function assignment happens at runtime .

    Concept 5: IIFE — Immediately Invoked Function Expression

    (function() {
    // private scope
})();

    An IIFE is a function expression that is invoked immediately after definition. It creates a private scope — variables inside are not accessible outside .

    Parentheses are required around the function to make it an expression. Without them, the parser treats function as the start of a declaration.

    Concept 6: The Module Pattern (Pre-ES6)

    const Module = (function() {
    let privateVar = 0;

    return {
        increment() { privateVar++; },
        getCount() { return privateVar; },
    };
})();

    Before ES6 modules, IIFEs were the standard way to create private scopes and implement the module pattern .

    Concept 7: IIFE and Modern JavaScript

    IIFE is obsolete. While ES6 modules reduce the need for IIFEs in many cases, they are still useful in scripts, inline JavaScript, and legacy applications .

    In modern code, ES modules and block scoping (let/const) reduce the need for IIFEs. However, IIFEs remain useful for:

    • Inline scripts — no module scope available.
    • Legacy code — pre-ES6 environments.
    • Bundler output — IIFE bundles for <script> tags.
    • Async initialization — ;(async () => { ... })();.

    Concept 8: Async IIFE

    ;(async () => {
    const data = await fetch("/api");
    console.log(await data.json());
})();

    Async IIFEs allow top-level await in environments that do not support it natively.

    Concept 9: The Semicolon Prefix

    ;(function() {})();

    The leading semicolon prevents the IIFE from being interpreted as a function call on the previous expression. This is important when concatenating scripts or when the previous line does not end with a semicolon .

    Concept 10: Function Expressions in Callbacks

    button.addEventListener("click", function() {
    console.log("clicked");
});

    Function expressions are the natural syntax for callbacks — they appear exactly where a function value is expected.

    Concept 11: Function Expressions and this

    const obj = {
    name: "Ada",
    greet: function() {
        return `Hello, ${this.name}`;
    },
};

obj.greet(); // "Hello, Ada"

    When a function expression is used as a method, this refers to the object it is called on.

    Concept 12: Function Expressions and Closures

    function counter() {
    let count = 0;
    return function() {
        return ++count;
    };
}

const next = counter();
next(); // 1
next(); // 2

    Function expressions that are returned from functions capture their lexical environment, creating closures.

    Concept 13: ES2026 and Function Expressions

    ES2026 does not introduce new syntax for function expressions. The headline ES2026 features — Math.sumPrecise, Iterator.concat, Array.fromAsync, Error.isError(), Map.getOrInsert(), and using declarations — are unrelated to function expression syntax.

    The spec's InstantiateOrdinaryFunctionExpression abstract operation continues to define how function expressions create function objects and capture their environment .

    Concept 14: ESLint func-style

    ESLint's func-style rule enforces consistent use of either function declarations or function expressions:

    Option Meaning
    "expression" (default) Require function expressions
    "declaration" Require function declarations

    The rule exists because mixing the two styles inconsistently reduces readability .

    Concept 15: Best Practice — Always Name Your Function Expressions

    Providing a name for your function expression quite effectively addresses all these drawbacks, but has no tangible downsides. The best practice is to always name your function expressions .

    Naming function expressions improves stack traces, enables self-reference, and aids debugging.

    Concept 16: Function Expressions vs. Arrow Functions

    Arrow functions are a more concise form of function expression, introduced in ES6. They have different this behavior (lexical) and cannot be used as constructors. Function expressions remain necessary when you need dynamic this or a prototype property.

    Concept 17: Function Expressions in Modern Frameworks

    // React
const Button = function({ onClick, children }) {
    return <button onClick={onClick}>{children}</button>;
};

// Vue
const method = function() {
    this.count++;
};

    Function expressions are widely used in frameworks for defining components, methods, and callbacks.

    Concept 18: Performance Considerations

    Function expressions are created at runtime when execution reaches them. Creating functions inside loops or hot paths adds overhead. Move function creation outside loops when possible.

    6. How It Works

    Step-by-Step: Function Expression Evaluation

    1.  Parser encounters `function` in expression position.
    │
    ▼
2.  A FunctionExpression node is created in the AST.
    │
    ▼
3.  When execution reaches the expression:
    │   - A new function object is created.
    │   - Its [[Environment]] slot is set to the current lexical environment.
    │   - The function is assigned to the variable or passed as an argument.
    │
    ▼
4.  The function is available for calling after the assignment.

    Step-by-Step: IIFE Execution

    1.  Parser sees `(function() { ... })()`.
    │
    ▼
2.  Parentheses make the function an expression.
    │
    ▼
3.  Function object is created.
    │
    ▼
4.  The trailing `()` invokes the function immediately.
    │
    ▼
5.  The function's return value becomes the value of the expression.

    Step-by-Step: Named Function Expression Scope

    1.  `const f = function named() { ... };` is parsed.
    │
    ▼
2.  A new scope is created for the function name `named`.
    │
    ▼
3.  Inside the function, `named` refers to the function object.
    │
    ▼
4.  Outside the function, `named` is not accessible.
    │
    ▼
5.  The variable `f` refers to the function from outside.

    Step-by-Step: Hoisting Difference

    Declaration:                          Expression:
1. Parser sees function declaration.  1. Parser sees function expression.
2. Function object created at parse.  2. Variable declaration hoisted (var).
3. Binding initialized.               3. Function created at runtime.
4. Available from scope start.        4. Available after assignment line.

    Step-by-Step: InstantiateOrdinaryFunctionExpression

    The spec's InstantiateOrdinaryFunctionExpression abstract operation:

    1. Creates a new function object.
    2. Sets [[Environment]] to the current lexical environment.
    3. Sets [[FormalParameters]], [[FunctionBody]], and [[ThisMode]].
    4. Returns the function object.

    This is the same operation used for function declarations, but called from a different grammar context .

    7. Internal Architecture / Under the Hood

    The Spec's Treatment of Function Expressions

    The ECMAScript specification covers function expressions in Section 15.2 (Function Definitions). The key difference from declarations is the grammar context:

    Production Context
    FunctionDeclaration Statement position
    FunctionExpression Expression position
    GeneratorExpression Expression position
    AsyncFunctionExpression Expression position
    AsyncGeneratorExpression Expression position

    All of these use InstantiateOrdinaryFunctionExpression to create the function object.

    The [[Environment]] Slot

    Every function object has an [[Environment]] slot that references the lexical environment where the function was created. This is how closures work — the function carries a reference to its birth scope.

    Memory Layout

    Function Expression:
┌─────────────────────────────────────┐
│  Function Object                    │
│                                     │
│  [[Call]]           → bytecode      │
│  [[Environment]]    → outer scope   │
│  [[FormalParameters]] → [a, b]      │
│  [[FunctionBody]]   → AST           │
│  [[ThisMode]]       → "global"      │
│  name               → "" (anonymous)│
│  length             → 1             │
│  prototype          → object        │
└─────────────────────────────────────┘

    Function Name Inference

    When a function expression is assigned to a variable, JavaScript infers the name from the assignment:

    const greet = function() {};
console.log(greet.name); // "greet" — inferred

    This is called Function Name Inference — the spec defines it in Section 8.4.

    IIFE Compilation

    An IIFE compiles to:

    1. A function object creation.
    2. An immediate call expression.

    There is no special bytecode for IIFEs — they are just function expressions that happen to be called immediately.

    Performance in the JIT

    • Function expressions are created at runtime — each evaluation creates a new function object.
    • Function creation is expensive — avoid creating functions in hot loops.
    • JIT optimizes function calls — same as declarations.
    • Named function expressions — no performance penalty vs. anonymous.

    8. Lifecycle / Workflow

    Function Expression Lifecycle

    Parsed → Function object created at runtime → Assigned to variable → Called → GC

    IIFE Lifecycle

    Parsed → Function object created → Immediately invoked → Return value → Function object eligible for GC

    Named Function Expression Lifecycle

    Parsed → Function object created → Name binding created in function scope
    → Function available inside by name → Function available outside by variable name

    Development Workflow

    Write function expression
    │
    ▼
Lint (ESLint func-style, prefer-arrow-callback)
    │
    ▼
Type-check (TypeScript)
    │
    ▼
Run / Test
    │
    ▼
Debug (breakpoints, stack traces)

    Choosing Between Declaration and Expression

    Need hoisting?
    │
    ├── Yes → Function declaration
    │
    └── No → Need a name for debugging?
              │
              ├── Yes → Named function expression
              │
              └── No → Anonymous function expression or arrow

    9. Practical Examples

    Example 1: Basic Function Expression

    const greet = function(name) {
    return `Hello, ${name}!`;
};

console.log(greet("Ada")); // "Hello, Ada!"

    Breakdown:

    • Anonymous function expression.
    • Assigned to const greet.
    • Called using the variable name.

    Example 2: Named Function Expression with Recursion

    const factorial = function calc(n) {
    if (n <= 1) return 1;
    return n * calc(n - 1);
};

console.log(factorial(5)); // 120
// calc(5); // ❌ ReferenceError

    Breakdown:

    • calc is only available inside the function.
    • Recursion uses the local name, not the variable name.

    Example 3: IIFE for Private Scope

    const counter = (function() {
    let count = 0;

    return {
        increment() { return ++count; },
        reset() { count = 0; },
    };
})();

counter.increment(); // 1
counter.increment(); // 2
console.log(counter.count); // undefined — private

    Breakdown:

    • count is private — not accessible outside.
    • The returned object exposes public methods.

    Example 4: Async IIFE

    ;(async () => {
    try {
        const res = await fetch("/api/data");
        const data = await res.json();
        console.log(data);
    } catch (err) {
        console.error("Failed:", err);
    }
})();

    Breakdown:

    • Async IIFE enables top-level await in scripts.
    • Leading semicolon prevents concatenation issues.

    Example 5: Function Expression as Callback

    const numbers = [1, 2, 3, 4, 5];

const doubled = numbers.map(function(n) {
    return n * 2;
});

console.log(doubled); // [2, 4, 6, 8, 10]

    Example 6: Function Expression Returning a Function

    function createGreeter(greeting) {
    return function(name) {
        return `${greeting}, ${name}!`;
    };
}

const sayHello = createGreeter("Hello");
const sayHi = createGreeter("Hi");

console.log(sayHello("Ada")); // "Hello, Ada!"
console.log(sayHi("Grace"));  // "Hi, Grace!"

    Breakdown:

    • Each returned function captures its own greeting.
    • This is a closure.

    Example 7: Named Function Expression for Debugging

    const processData = function processDataImpl(data) {
    // `processDataImpl` appears in stack traces
    return data.map(function transform(item) {
        return item * 2;
    });
};

    Breakdown:

    • Naming the function improves stack traces.
    • The name is only available inside the function.

    Example 8: Function Expression in Object

    const user = {
    name: "Ada",
    greet: function() {
        return `Hello, ${this.name}`;
    },
};

console.log(user.greet()); // "Hello, Ada"

    Example 9: Generator Function Expression

    const ids = function*() {
    let id = 0;
    while (true) {
        yield id++;
    }
};

const gen = ids();
gen.next().value; // 0
gen.next().value; // 1

    Example 10: Modern Alternative to IIFE

    // Old: IIFE for private scope
var Module = (function() {
    var private = 0;
    return { get: function() { return private; } };
})();

// Modern: ES module or block scope
{
    let private = 0;
    // private is block-scoped
}

    • ES modules and block scoping reduce the need for IIFEs.
    • IIFEs remain useful for inline scripts and legacy code.

    11. Best Practices

    1. Always name your function expressions. Why: improves stack traces and debugging .
    2. Use const for function expressions. Why: prevents reassignment.
    3. Use IIFEs only when needed. Why: ES modules and block scoping reduce the need .
    4. Use a leading semicolon with IIFEs. Why: prevents concatenation issues .
    5. Prefer arrow functions for simple callbacks. Why: more concise, lexical this.
    6. Use named function expressions for recursion. Why: self-reference without outer variable.
    7. Avoid creating function expressions in loops. Why: each iteration creates a new function object.
    8. Enable ESLint func-style. Why: enforces consistent style.
    9. Use async IIFEs for top-level await in scripts. Why: enables async initialization.
    10. Keep function expressions small. Why: readability and testability.
    11. Use function expressions for object methods when this is needed. Why: dynamic this binding.
    12. Document IIFE usage. Why: future readers may not recognize the pattern.
    13. Prefer ES modules over IIFEs for new code. Why: cleaner, standard scoping.
    14. Use meaningful variable names for anonymous functions. Why: the variable name appears in stack traces.
    15. Understand the hoisting difference. Why: function expressions are not hoisted.

    12. Common Mistakes

    ❌ Mistake: Calling a Function Expression Before Definition

    greet(); // ❌ TypeError: greet is not a function
const greet = function() { return "hi"; };

    ✅ Correct:

    const greet = function() { return "hi"; };
greet(); // "hi"

    ❌ Mistake: Forgetting Parentheses for IIFE

    function() { console.log("hi"); }(); // ❌ SyntaxError

    ✅ Correct:

    (function() { console.log("hi"); })();

    ❌ Mistake: Missing Leading Semicolon for IIFE

    const x = 1
(function() {})(); // ❌ parsed as x = 1(function(){})()

    ✅ Correct:

    const x = 1;
(function() {})();

    ❌ Mistake: Using Anonymous Functions in Stack Traces

    [1, 2, 3].map(function(n) { throw new Error("oops"); });
// Stack trace: "at <anonymous>"

    ✅ Correct:

    [1, 2, 3].map(function processItem(n) { throw new Error("oops"); });
// Stack trace: "at processItem"

    ❌ Mistake: Assuming Named Function Expression Name Is Global

    const f = function named() {};
named(); // ❌ ReferenceError

    ✅ Correct: The name is only available inside the function.

    ❌ Mistake: Creating Functions in Loops

    for (let i = 0; i < 1000; i++) {
    arr.push(function() { return i; }); // creates 1000 functions
}

    ✅ Correct: Move function creation outside the loop when possible.

    ❌ Mistake: Using var for Function Expressions

    var greet = function() { return "hi"; };

    ✅ Correct:

    const greet = function() { return "hi"; };

    ❌ Mistake: Confusing Function Expression with Declaration

    // This is a declaration, not an expression
function greet() {}

    ✅ Correct: Understand the position difference.

    ❌ Mistake: IIFE Without Async for Top-Level Await

    await fetch("/api"); // ❌ SyntaxError in scripts

    ✅ Correct:

    ;(async () => { await fetch("/api"); })();

    ❌ Mistake: Overusing IIFEs in Modern Code

    (function() {
    // everything in an IIFE
})();

    ✅ Correct: Use ES modules or block scope.

    13. Performance Considerations

    • Function expressions are created at runtime — each evaluation creates a new function object.
    • Function creation is expensive — avoid in hot loops.
    • IIFEs are invoked immediately — no long-term memory cost.
    • Named function expressions — no performance penalty vs. anonymous.
    • Closures — captured variables are retained in memory.
    • JIT optimization — function expressions optimize the same as declarations.

    Performance Tips

    1. Move function expressions outside loops when possible.
    2. Use IIFEs for one-time initialization — the function is GC'd after execution.
    3. Avoid creating functions in hot paths.
    4. Use named function expressions for better stack traces without performance cost.
    5. Profile with --trace-opt / --trace-deopt if needed.

    14. Security Considerations

    IIFE for Scope Isolation

    IIFEs create private scopes — preventing global namespace pollution and variable collisions.

    Function Expressions and this

    When a function expression is used as a method, this refers to the calling object. When passed as a callback, this may be undefined (strict mode) or the global object (sloppy mode). This can lead to security issues if the function assumes a specific this.

    Defense: Use arrow functions for callbacks when this should be lexical.

    Function Name Inference and Stack Traces

    Named function expressions improve stack traces, which aids security debugging.

    IIFE and CSP

    IIFEs are compatible with strict CSP — they do not require eval or new Function.

    Async IIFE and Error Handling

    An async IIFE that throws an unhandled rejection can crash the process in Node.js.

    Defense: Always attach .catch() or use try/catch inside the IIFE.

    15. Debugging Tips

    • Name your function expressions — improves stack traces.
    • Check f.name — returns the inferred or explicit name.
    • Use debugger; — pause inside the function.
    • Chrome DevTools Sources panel — set breakpoints.
    • console.log(f) — displays the function source.
    • ESLint func-style — enforces consistent style.
    • ESLint no-loop-func — flags function expressions in loops.
    • TypeScript — catches type errors at compile time.

    17. When Not to Use

    • When hoisting is needed — use a declaration.
    • When passing a simple callback — use an arrow function.
    • When defining a class — use class.
    • When a method shorthand works — use it.
    • When the function is a value in modern code — consider arrow functions.
    • When the function is a constructor — use a class.
