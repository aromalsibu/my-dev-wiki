    Pure Functions

    1. Overview

    Definition

    A pure function is a function that satisfies two fundamental properties:

    1. Deterministic — Given the same input arguments, it always returns the same output.
    2. No observable side effects — It does not modify any state outside its own scope, and it does not depend on any external mutable state.
    // ✅ Pure — deterministic, no side effects
function add(a, b) {
    return a + b;
}

// ✅ Pure — returns a new object, does not mutate the input
function formatUser(user) {
    return {
        displayName: `${user.firstName} ${user.lastName}`,
        initials: `${user.firstName[0]}${user.lastName[0]}`,
    };
}

    A pure function is a mathematical function in the truest sense. It is a mapping from inputs to outputs with no other effects. The same input always produces the same output — no exceptions, no surprises.

    In the ECMAScript specification, there is no pure keyword. Purity is a convention and a discipline, not a language feature. It emerges from how you write the function, not from any syntax. The language does not enforce purity — the developer does.

    Purpose

    Pure functions exist to solve the predictability problem in software. Impure functions — those that depend on external state or cause side effects — are the source of the most insidious bugs in JavaScript. A function that reads from a global variable, mutates its arguments, or calls Math.random() cannot be reasoned about in isolation. Its behavior depends on when it is called and what the state of the world is at that moment.

    Pure functions eliminate this class of bug entirely:

    • Deterministic — the output depends only on the input.
    • Testable — no mocking, no setup, no teardown. Just input → output.
    • Composable — pure functions can be freely combined without worrying about hidden dependencies.
    • Cacheable — since the same input always produces the same output, results can be memoized.
    • Parallelizable — pure functions have no shared state, so they can run concurrently without race conditions.
    • Referentially transparent — any call to a pure function can be replaced by its return value without changing the program's behavior.

    As one 2026 guide puts it: "Pure functions are stable, consistent, and predictable. Given the same parameters, pure functions will always return the same result".

    Where It Fits

    Functions
├── Function Declarations       ✅ done
├── Function Expressions        ✅ done
├── Arrow Functions             ✅ done
├── Parameters                  ✅ done
├── Rest Parameters             ✅ done
├── Default Parameters          ✅ done
├── Closures                    ✅ done
├── Higher-Order Functions      ✅ done
├── Pure Functions              ← you are here

    Pure Functions are the final concept in the Functions section. They sit at the end because they represent the culmination of functional programming principles — the ideal that higher-order functions, closures, and immutability all point toward. The next section is Objects.

    2. Why It Exists

    The Problem

    Every non-trivial program needs to change state. It reads user input, fetches data, writes to the DOM, updates a database, and logs messages. These are side effects — interactions with the world outside the function. Without them, a program could compute but not do anything.

    But side effects are dangerous. A function that modifies a global variable can break another function that depends on that variable. A function that mutates its argument can corrupt the caller's data. A function that reads Date.now() returns different results on every call, making it impossible to test deterministically.

    The problem is not side effects themselves — they are necessary. The problem is side effects that are hidden inside functions that pretend to be pure. When a function's signature says (a, b) => a + b but the body also writes to localStorage, the caller has no way to know. The function is lying about what it does.

    Previous Limitations

    Era Limitation
    No pure function concept All functions could have hidden side effects
    No immutability Arrays and objects were mutated in place
    No functional programming State was modified everywhere
    No memoization Caching required global objects
    No referential transparency Functions could not be replaced by their values
    No test isolation Every test required mocking external state

    Why Pure Functions Matter

    Pure functions are the foundation of functional programming in JavaScript. They are what make the following possible:

    • React — React assumes every component is a pure function. "By strictly only writing your components as pure functions, you can avoid an entire class of baffling bugs and unpredictable behavior as your codebase grows".
    • Redux — Redux reducers must be pure functions. "The reducer does not perform side effects... does not call non-pure functions (like Date.now or Math.random)... does not mutate its arguments".
    • Memoization — caching only works for pure functions. Impure functions produce different results for the same input.
    • Testing — pure functions are trivial to test. No mocking, no setup, no teardown. Just given A → expect B.

    As the Syncfusion guide states: "Pure functions are readable because of independent behavior. Moreover, they are straightforward to debug".

    The 2026 Consensus

    In 2026, the consensus is clear: pure functions are the default for business logic; side effects should be pushed to the edges of the application. As one modern JavaScript guide puts it: "Copy instead of mutating. Keep transforms pure, push I/O to the edge".

    This does not mean every function must be pure. It means that the core of your application should be pure, and the impure shell that interacts with the outside world should be as thin as possible.

    3. Syntax / Basic Usage

    Pure Function — Deterministic, No Side Effects

    // ✅ Pure — same input, same output, no side effects
function add(a, b) {
    return a + b;
}

function formatName(first, last) {
    return `${first} ${last}`;
}

function filterEvens(numbers) {
    return numbers.filter(n => n % 2 === 0);
}

    Impure Function — External State

    // ❌ Impure — depends on external variable
let counter = 0;

function increment() {
    return ++counter; // modifies external state
}

// ❌ Impure — non-deterministic
function randomPick(arr) {
    return arr[Math.floor(Math.random() * arr.length)];
}

// ❌ Impure — side effect (I/O)
function saveUser(user) {
    localStorage.setItem("user", JSON.stringify(user));
}

    Impure Function — Mutating Arguments

    // ❌ Impure — mutates the input array
function addItem(cart, item) {
    cart.push(item);
    return cart;
}

// ✅ Pure — returns a new array
function addItem(cart, item) {
    return [...cart, item];
}

// ❌ Impure — mutates the input object
function setActive(user) {
    user.active = true;
    return user;
}

// ✅ Pure — returns a new object
function setActive(user) {
    return { ...user, active: true };
}

    Pure Function — Non-Mutating Array Operations

    const nums = [1, 2, 3, 4, 5];

const withSix = [...nums, 6];           // append
const withZero = [0, ...nums];          // prepend
const withoutThree = nums.filter(n => n !== 3); // remove by value
const withoutSecond = nums.toSpliced(1, 1);     // remove by index (ES2023)
const updated = nums.with(2, 99);       // replace at index (ES2023)
const sorted = nums.toSorted((a, b) => b - a);  // sort (ES2023)
const reversed = nums.toReversed();     // reverse (ES2023)

    ES2023 added toSorted, toReversed, with, and toSpliced — non-mutating versions of the classic array methods.

    Pure Function — Non-Mutating Object Updates

    const user = { name: "Alice", age: 30, address: { city: "NYC" } };

const older = { ...user, age: 31 };                          // update property
const withZip = { ...user, address: { ...user.address, zip: "10001" } }; // nested update
const { age, ...userWithoutAge } = user;                     // remove property
const clone = structuredClone(user);                         // deep clone

    Purifying Impure Functions — Dependency Injection

    // ❌ Impure — depends on Date.now()
function isExpired(token) {
    return token.expiresAt < Date.now();
}

// ✅ Pure — time is injected
function isExpired(token, now) {
    return token.expiresAt < now;
}
isExpired(token, Date.now()); // caller provides the time

// ❌ Impure — depends on Math.random()
function shuffle(array) {
    return array.toSorted(() => Math.random() - 0.5);
}

// ✅ Pure — randomness is injected
function shuffle(array, random = Math.random) {
    return array.toSorted(() => random() - 0.5);
}

    This dependency injection pattern purifies the function by making its dependencies explicit.

    Pure Function with Closure — Capturing Constants

    // ✅ Pure — `PI` is a constant, never changes
const PI = 3.14159;
const circleArea = (radius) => PI * radius * radius;

    A closure over a constant is still pure — the captured variable never changes. A closure over a mutable variable is impure.

    Pure Function with Destructuring

    // ✅ Pure — destructures input, returns new object
function processOrder({ items, taxRate = 0.1 }) {
    const subtotal = items.reduce((sum, item) => sum + item.price, 0);
    return {
        subtotal,
        tax: subtotal * taxRate,
        total: subtotal * (1 + taxRate),
    };
}

    Pure Function with Rest Parameters

    // ✅ Pure — collects args, returns new array
function sortNumbers(...numbers) {
    return [...numbers].sort((a, b) => a - b);
}

    4. Mental Model

    The "Mathematical Function" Mental Model

    A pure function is a mathematical function. Think of y = 2x:

    x = 2  →  y = 4     (always)
x = 3  →  y = 6     (always)
x = 3  →  y = 6     (still — not 9, not -1, not 2.5)

    There is no hidden state. There is no time dependency. There is no randomness. The output is completely determined by the input.

    ┌─────────────────────────────────────────────┐
│           Pure Function                      │
│                                             │
│  Input ──────▶ [ f(x) ] ──────▶ Output      │
│                                             │
│  No external reads                          │
│  No external writes                         │
│  No randomness                              │
│  No time dependency                         │
│                                             │
│  Same input → Same output, always.          │
└─────────────────────────────────────────────┘

    The "Reference Transparency" Mental Model

    Referential transparency means you can replace a function call with its return value without changing the program:

    const result = add(2, 3); // add(2, 3) can be replaced with 5
// The program behaves identically whether you call add(2, 3) or write 5

    This is the defining property of pure functions. If you can substitute the function call with the value it returns and nothing breaks, the function is pure.

    The "Boundary" Mental Model

    Pure functions live in the core; impure functions live at the boundaries:

    ┌─────────────────────────────────────────────────────┐
│                  Application                        │
│                                                     │

│  │  ┌─────────────────────────────────────┐    │   │
│  │  │         Pure Core                    │    │   │
│  │  │                                     │    │   │

│  │  │  transformations, validation         │    │   │
│  │  │                                     │    │   │
│  │  │  ✅ Deterministic                    │    │   │
│  │  │  ✅ No side effects                  │    │   │
│  │  │  ✅ Referentially transparent        │    │   │
│  │  │  ✅ Testable without mocks           │    │   │
│  │  └─────────────────────────────────────┘    │   │
│  └─────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘

    Push side effects to the edges. Keep the core pure.

    The "Testability" Mental Model

    Pure functions are trivial to test. Impure functions require mocking, setup, and teardown:

└─────────────────────┘            └─────────────────────┘

    As one source puts it: "The code's definitely easier to test. We don't need to mock anything".

    The "Immutable Data" Mental Model

    Pure functions require immutable data. You cannot mutate inputs — you must return new values:

    ❌ Mutation:                        ✅ Non-Mutation:

    5. Core Concepts

    Concept 1: Determinism

    A pure function is deterministic — the same input always produces the same output. There is no randomness, no time dependency, and no external state that can change the result.

    // ✅ Deterministic
function square(n) { return n * n; }

// ❌ Non-deterministic
function randomInRange(min, max) {
    return Math.random() * (max - min) + min;
}

    Concept 2: No Side Effects

    A side effect is any observable interaction with the world outside the function. Pure functions have none of the following:

    • Modifying a global or static variable.
    • Modifying any of the arguments passed to the function.
    • Making HTTP calls or database queries.
    • Writing to disk, localStorage, or the DOM.
    • Logging to the console.
    • Calling Date.now(), Math.random(), or any non-deterministic function.
    • Throwing exceptions (in the strictest definition).

    Concept 3: Referential Transparency

    A function is referentially transparent if any call to it can be replaced by its return value without changing the program.

    // Pure — referentially transparent
const area = circleArea(5); // can be replaced with 78.539...

    Concept 4: Immutability

    Pure functions do not mutate their inputs. Instead, they return new values. This is the foundation of immutable data management.

    // ✅ Pure — returns a new array
const doubled = numbers.map(n => n * 2);

// ❌ Impure — mutates the input
numbers.forEach((n, i) => { numbers[i] = n * 2; });

    Concept 5: Dependency Injection for Purity

    Impure dependencies — time, randomness, I/O — can be injected as parameters, making the function pure:

    // ❌ Impure — depends on Date.now()
function isExpired(token) { return token.expiresAt < Date.now(); }

// ✅ Pure — time is injected
function isExpired(token, now) { return token.expiresAt < now; }

    This is the dependency injection pattern for purifying impure functions.

    Concept 6: Pure Functions Enable Memoization

    Because pure functions are deterministic, their results can be cached:

    function memoize(fn) {
    const cache = new Map();
    return (...args) => {
        const key = JSON.stringify(args);
        if (cache.has(key)) return cache.get(key);
        const result = fn(...args);
        cache.set(key, result);
        return result;
    };
}

    Memoization only works for pure functions — impure functions produce different results for the same input.

    Concept 7: Pure Functions Enable Testing Without Mocks

    Pure functions can be tested with just given → expect:

    test("add returns the sum of two numbers", () => {
    expect(add(2, 3)).toBe(5);
});

    No mocking. No setup. No teardown.

    Concept 8: Pure Functions Enable Composition

    Because pure functions have no hidden state, they compose freely:

    const process = pipe(
    validateInput,
    normalizeData,
    transformData,
    formatOutput
);

    Each step is independent. Each can be tested in isolation.

    Concept 9: Pure Functions and React

    React assumes every component is a pure function. "Same inputs, same output. Given the same inputs, a pure function should always return the same result". This is why React can efficiently re-render components — if the props haven't changed, the component's output hasn't changed.

    Concept 10: Pure Functions and Redux

    Redux reducers must be pure functions. "Does not perform side effects... does not call non-pure functions... does not mutate its arguments". This is what enables Redux DevTools' time-travel debugging — replaying the same actions produces the same state.

    Concept 11: Pure Functions and ES2023 Non-Mutating Array Methods

    ES2023 added toSorted, toReversed, with, and toSpliced — non-mutating versions of sort, reverse, and index-based operations. These are the pure alternatives to their mutating counterparts.

    Mutating Non-Mutating (ES2023)
    arr.sort() arr.toSorted()
    arr.reverse() arr.toReversed()
    arr[2] = x arr.with(2, x)
    arr.splice() arr.toSpliced()

    Concept 12: Pure Functions and structuredClone

    For deep cloning without mutation, structuredClone() is the modern standard:

    const clone = structuredClone(obj); // handles circular refs, preserves types

    Concept 13: Purity Is a Spectrum

    Not every function must be pure. The goal is to maximize purity in the core and isolate impurity at the edges. As one source notes: "Pure functions are great, but realistically they represent the limit to which our code should attempt to reach and not what most of our code should look like".

    Concept 14: Pure Functions and Asynchronous Code

    Asynchronous functions are usually impure because they involve I/O — which is a side effect. However, the logic inside an async function can be pure:

    // Impure shell — handles I/O
async function fetchAndProcess(url) {
    const response = await fetch(url);
    const data = await response.json();
    return processData(data); // pure core
}

// Pure core — deterministic logic
function processData(data) {
    return data.filter(item => item.active).map(item => item.name);
}

    Concept 15: ESLint Rules for Pure Functions

    Rule Purpose
    no-param-reassign Prevent mutation of function parameters
    functional/prefer-readonly-type Enforce readonly types (TypeScript)
    functional/no-let Prefer const over let
    functional/immutable-data Prevent mutating operations

    Concept 16: Pure Functions in TypeScript

    TypeScript can enforce purity through readonly types:

    function processItems(items: readonly Item[]): readonly Item[] {
    return items.filter(item => item.active);
}

    readonly prevents mutation at compile time.

    Concept 17: Pure Functions and the V8 JIT

    V8's TurboFan compiler can inline pure functions aggressively. A function is easier to optimize when it is pure, small, and stable. Pure functions have a higher chance of inlining because they have no observable side effects that would prevent optimization.

    Concept 18: The 2026 Reality — Pragmatic Purity

    In 2026, the consensus is pragmatic purity: pure functions for business logic, impure functions at the boundaries. As one modern guide puts it: "Keep transforms pure, push I/O to the edge". The goal is not 100% purity — the goal is predictability where it matters.

    6. How It Works

    Step-by-Step: Evaluating Purity

    1.  Examine the function body.
    │
    ▼

    │   - Global variables → impure
    │   - Closure over mutable variable → impure

    ▼

    │   - Modifies global → impure
    │   - Modifies argument → impure

    │
    ▼

    │   - If no → impure
    │   - If yes → pure

    1.  Identify the impurity:
    │   - External state read
    │   - External state write
    │   - Non-deterministic dependency
    │
    ▼

    │   - Inject as parameter
    │   - Return a new value instead of mutating
    │
    ▼
3.  Verify purity:
    │   - Same input → same output
    │   - No side effects

    Step-by-Step: Testing a Pure Function

    1.  Define input and expected output.
    │
    ▼

    │
    ▼
3.  Assert the output matches.
    │
    ▼
4.  Call again with the same input.
    │
    ▼
5.  Assert the output is identical.
    │
    ▼

    Step-by-Step: Memoizing a Pure Function

    1.  Create a cache (Map or object).
    │
    ▼
2.  When the function is called:
    │   - Compute a key from the arguments.
    │   - Check if the key is in the cache.
    │   - If yes → return cached value.
    │   - If no → compute, store, return.

    7. Internal Architecture / Under the Hood

    Purity in the ECMAScript Specification

    The ECMAScript specification does not define "pure functions." There is no [[Pure]] internal slot, no pure keyword, and no purity enforcement. Purity is a convention, not a language feature.

    However, the spec does define concepts that relate to purity:

    • [[Call]] — the internal method that executes a function.
    • [[Environment]] — the slot that holds a closure's captured scope.
    • Completion Records — how functions return values or throw exceptions.

    None of these enforce purity. Purity is entirely the developer's responsibility.

    How V8 Optimizes Pure Functions

    V8's TurboFan compiler can inline pure functions more aggressively than impure ones. A pure function has a higher chance of inlining because:

    1. No observable side effects — the compiler can reorder and eliminate calls without changing behavior.
    2. Deterministic — the compiler can constant-fold repeated calls.
    3. Small and stable — pure functions tend to be small and have stable type feedback.

    V8 inlines functions that are pure, small, and stable — meeting these criteria maximizes the chance of optimization.

    The /*#__PURE__*/ Annotation

    Bundlers like Rollup and webpack recognize the /*#__PURE__*/ comment annotation. A function call marked with this annotation is treated as pure — if its result is not used, the call can be dropped during tree-shaking:

    const result = /*#__PURE__*/ expensiveCalculation();
// If `result` is unused, the entire call can be removed.

    Memory Layout of Pure Functions

    Pure functions do not retain any external state — their memory footprint is limited to their parameters and local variables:

    Pure Function:
┌─────────────────────────────────────┐
│  [[Call]]           → bytecode      │
│  [[Environment]]    → outer scope   │
│                     (read-only)     │
│  [[FormalParameters]] → [a, b]      │
│  [[FunctionBody]]   → AST           │
│                                     │
│  No mutable state retained.         │
│  No side effects.                   │
│  Safe to inline, cache, or eliminate│
└─────────────────────────────────────┘

    The Cost of Impurity

    Impure functions retain references to external state, which:

    1. Prevents garbage collection of captured variables.
    2. Prevents JIT inlining and constant folding.
    3. Prevents memoization (results change).
    4. Prevents safe parallelization.

    return token.expiresAt < Date.now();
}

// ✅ Pure — time is injected
function isExpiredPure(token, now) {
    return token.expiresAt < now;
}

console.log(isExpiredPure({ expiresAt: 1000 }, 2000)); // true

    Example 6: Memoization

    function memoize(fn) {
    const cache = new Map();
    return function(...args) {
        const key = JSON.stringify(args);
        if (cache.has(key)) return cache.get(key);
        const result = fn(...args);
        cache.set(key, result);
        return result;
    };
}

const fibonacci = memoize(function fib(n) {
    return n <= 1 ? n : fibonacci(n - 1) + fibonacci(n - 2);
});

console.log(fibonacci(40)); // fast — cached

const processUser = pipe(

    user => ({ ...user, active: true })
);

console.log(processUser({ name: "  ada  " }));
// { name: "ADA", active: true }

    11. Best Practices

    1. Default to pure functions for business logic. Why: predictable, testable, composable.
    2. Push side effects to the edges of the application. Why: keep the core pure.
    3. Use const by default. Why: prevents accidental mutation.
    4. Use spread syntax ([...arr], {...obj}) instead of mutation. Why: returns new values.
    5. Use ES2023 non-mutating array methods (toSorted, toReversed, with, toSpliced). Why: pure alternatives to mutating methods.
    6. Inject dependencies (time, randomness, I/O) as parameters. Why: purifies impure functions.
    7. Use readonly in TypeScript for input arrays and objects. Why: compile-time enforcement of purity.
    8. Use structuredClone() for deep copies. Why: avoids mutation of nested objects.
    9. Test pure functions without mocks. Why: given → expect is enough.
    10. Memoize expensive pure functions. Why: deterministic results can be cached.
    11. Use the /*#__PURE__*/ annotation for bundler tree-shaking. Why: allows dead code elimination.
    12. Keep pure functions small and focused. Why: easier to test and optimize.
    13. Use ESLint no-param-reassign. Why: prevents argument mutation.
    14. Separate pure logic from impure shells. Why: testable core, isolated I/O.
    15. Accept that not every function can be pure. Why: I/O is necessary — just isolate it.

    12. Common Mistakes

    ❌ Mistake: Mutating Arguments

    function addItem(cart, item) {
    cart.push(item); // ❌ mutates the caller's array
    return cart;
}

    ✅ Correct:

    function addItem(cart, item) {
    return [...cart, item]; // ✅ returns a new array
}

    ❌ Mistake: Reading Global State

    let taxRate = 0.1;

function calculateTotal(price) {
    return price * (1 + taxRate); // ❌ depends on external state
}

    ✅ Correct:

    function calculateTotal(price, taxRate) {
    return price * (1 + taxRate); // ✅ taxRate is a parameter
}

    ❌ Mistake: Using Date.now() or Math.random()

    function createId() {
    return Math.random().toString(36); // ❌ non-deterministic
}

    ✅ Correct:

    function createId(random = Math.random) {
    return random().toString(36); // ✅ injected — testable
}

    ❌ Mistake: Mutating Nested Objects

    function updateAddress(user, city) {
    user.address.city = city; // ❌ mutates nested object
    return user;
}

    ✅ Correct:

    function updateAddress(user, city) {
    return {
        ...user,
        address: { ...user.address, city }, // ✅ new nested object
    };
}

    ❌ Mistake: Assuming forEach Is Pure

    arr.forEach(item => {
    arr.push(item * 2); // ❌ mutates during iteration
});

    ✅ Correct:

    const doubled = arr.map(item => item * 2); // ✅ returns new array

    ❌ Mistake: Using sort() and Assuming It's Non-Mutating

    const sorted = arr.sort(); // ❌ sort() mutates the original array

    ✅ Correct:

    const sorted = arr.toSorted(); // ✅ ES2023 — non-mutating

    ❌ Mistake: Logging Inside a "Pure" Function

    function calculate(a, b) {
    console.log("calculating..."); // ❌ side effect (I/O)
    return a + b;
}

    ✅ Correct: Remove the log, or accept that the function is impure.

    ❌ Mistake: Throwing Exceptions from "Pure" Functions

    Strictly speaking, throwing is a side effect. If a function throws, it does not return a value — breaking referential transparency.

    ✅ Correct: Return a Result object instead of throwing, if strict purity is required.

    ❌ Mistake: Assuming a Function Is Pure Because It Looks Pure

    function process(data) {
    return helper(data); // ❌ helper might be impure!
}

    ✅ Correct: Trace the call chain to verify purity.

    ❌ Mistake: Mutating Date Objects

    function addDay(date) {
    date.setDate(date.getDate() + 1); // ❌ mutates the input Date
    return date;
}

    ✅ Correct:

    function addDay(date) {
    const copy = new Date(date);
    copy.setDate(copy.getDate() + 1);
    return copy; // ✅ returns a new Date
}

    13. Performance Considerations

    • Pure functions are faster to optimize — V8 can inline, constant-fold, and eliminate them.
    • Higher inlining chance — pure functions meet the "pure, small, stable" criteria for V8 inlining.
    • Memoization — pure functions can cache results, eliminating repeated computation.
    • Tree-shaking — /*#__PURE__*/ annotations allow bundlers to remove unused pure calls.
    • No hidden GC pressure — pure functions do not retain external references.
    • Non-mutating operations allocate new objects — spread and toSorted create new arrays; this has a memory cost.
    • Memoization has memory cost — caches grow; use LRU or bounded caches.
    • Impure functions block optimization — global reads and writes prevent JIT optimizations.

    Performance Tips

    1. Use pure functions in hot paths — they optimize better.
    2. Memoize expensive pure computations.
    3. Use toSorted/toReversed — they are optimized in modern engines.
    4. Avoid deep cloning in hot loops — clone once at the boundary.
    5. Use /*#__PURE__*/ for bundler dead code elimination.
    6. Profile with --trace-opt / --trace-deopt if needed.

    14. Security Considerations

    Pure Functions Are Immune to Prototype Pollution

    Pure functions do not read from or write to shared state — they are immune to prototype pollution attacks that manipulate Object.prototype.

    Side Effects as Attack Surface

    Impure functions that write to the DOM, localStorage, or the network are attack surface. A pure function cannot leak data or execute unintended I/O.

    Referential Transparency and Auditability

    Pure functions are auditable — their behavior is entirely determined by their input. This makes security review easier: no need to trace global state.

    Determinism and Replay Attacks

    Pure functions produce the same output for the same input — there is no non-determinism to exploit for replay attacks.

    Purity in Redux and Time-Travel Debugging

    Redux reducers must be pure so that replaying actions produces the same state. Impure reducers can produce inconsistent state — a security and reliability risk.

    structuredClone and Prototype Pollution

    structuredClone does not copy the prototype chain — it creates plain objects. This prevents prototype pollution via cloned objects.

    Pure Functions and CSP

    Pure functions are compatible with strict CSP — they do not require eval or new Function.

    15. Debugging Tips

    • Check for external reads — trace every variable reference.
    • Check for mutations — look for push, pop, splice, sort, reverse, and direct property assignment.
    • Check for I/O — console.log, fetch, localStorage, document.*.
    • Check for non-determinism — Date.now(), Math.random(), crypto.randomUUID().
    • Use Object.freeze() in tests — freeze inputs to catch accidental mutation.
    • Use ESLint no-param-reassign — flags parameter mutation.
    • Use structuredClone in tests — pass clones to detect mutation.
    • Test with the same input twice — assert identical output.
    • Chrome DevTools [[Scopes]] — inspect what a closure captures.
    • TypeScript readonly — compile-time mutation detection.
