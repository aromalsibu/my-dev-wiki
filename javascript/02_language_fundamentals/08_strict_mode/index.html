    Strict Mode

    1. Overview

    Definition

    Strict mode is an opt-in variant of JavaScript that changes the language's semantics to be stricter — turning silent errors into exceptions, forbidding certain legacy syntax, and fixing behaviors that hindered engine optimization. It is activated by the directive "use strict" (or 'use strict') placed at the beginning of a script or function body.

    "use strict";

// In strict mode, this throws a ReferenceError:
undeclaredVariable = 10;

    In 2026, strict mode is the default for all modern JavaScript code. Every ECMAScript module (import/export) runs in strict mode automatically. Classes are always strict. And TypeScript 6.0 (released March 2026) enabled strict mode by default, meaning new projects get stricter type-checking and runtime semantics without explicit configuration.

    Strict mode is not a subset of JavaScript — it intentionally has different semantics from sloppy (non-strict) mode. Both modes can coexist in the same program, allowing incremental adoption.

    Purpose

    Strict mode exists to solve three problems:

    1. Silent errors — JavaScript originally ignored many mistakes (typos, invalid assignments, unsafe deletions). Strict mode turns them into thrown errors.
    2. Optimization blockers — Some sloppy-mode behaviors (like with and arguments aliasing) made it hard for engines to optimize. Strict mode removes them.
    3. Future-proofing — Strict mode reserves syntax that may be used in future ECMAScript versions, preventing conflicts.

    The result is safer, faster, and more predictable code.

    Where It Fits

    Language Fundamentals
├── Variables             ✅ done
├── Data Types            ✅ done
├── Operators             ✅ done
├── Expressions           ✅ done
├── Statements            ✅ done
├── Type Conversion       ✅ done
├── Equality              ✅ done
├── Strict Mode           ← you are here

    Strict Mode is the final concept in Language Fundamentals. It is placed last because it modifies the behavior of everything that came before it — variables, functions, operators, and equality.

    2. Why It Exists

    The Problem

    JavaScript was designed in 1995 for forgiving, beginner-friendly scripting. The language silently ignored many mistakes:

    • Assigning to an undeclared variable created a global.
    • Assigning to a read-only property failed silently.
    • Deleting an undeletable property returned false without warning.
    • Duplicate function parameters were allowed (last one won).
    • with statements made scope unpredictable.
    • Octal literals (0644) were interpreted as octal in some contexts.

    This tolerance made JavaScript easy to start with — but dangerous at scale. In large applications, silent failures became hours of debugging. A single typo could create a global variable that overwrote a browser API, caused memory leaks, or introduced security vulnerabilities.

    Previous Limitations

    Problem Sloppy Mode Behavior Consequence
    Undeclared variable assignment Creates global silently Global pollution, memory leaks
    Assigning to read-only property Fails silently Data corruption
    Deleting undeletable property Returns false Silent logic errors
    Duplicate parameters Last one wins Confusing behavior
    with statement Allowed Unpredictable scope
    Octal literals Interpreted as octal Confusing for developers

    Why Strict Mode Was Introduced

    The ECMAScript committee could not simply change the default behavior — millions of existing websites depended on the lenient rules. Instead, they made strict mode opt-in so developers could adopt it file by file or function by function.

    Strict mode was introduced in ECMAScript 5 (2009) as a way to opt into a restricted variant of JavaScript — a safer, more predictable subset that eliminates footguns and enables optimization.

    Why It Still Matters in 2026

    In 2026, strict mode feels less like an option and more like seatbelts. Modern engines and bundlers hide many footguns, but mixed codebases are real — marketing snippets, analytics tags, browser extensions, userscripts, and CMS-injected HTML often bypass your build pipeline. If you debug unpredictable globals or this values in 2026, you are likely straddling strict and non-strict boundaries.

    3. Syntax / Basic Usage

    Enabling Strict Mode for an Entire Script

    Place "use strict" before any other statements:

    "use strict";

const v = "I am a strict-mode script";
// undeclaredGlobal = 10; // ❌ ReferenceError

    Placement rules: - Must be the literal first statement (comments are allowed before it, but no code). - Shebang (#!/usr/bin/env node) in Node.js is ignored and does not cancel strictness. - Any preceding statement — even const x = 1; — cancels strictness.

    Enabling Strict Mode for a Function

    Place "use strict" at the top of the function body:

    function strictFunction() {
    "use strict";
    // undeclaredVar = 10; // ❌ ReferenceError
    return "strict";
}

    Restriction: "use strict" can only be applied to functions with simple parameters. Using it in functions with rest, default, or destructured parameters is a syntax error.

    // ❌ SyntaxError
function bad({ a, b }) {
    "use strict";
}

    Strict Mode for Modules (Automatic)

    Every ECMAScript module is strict by default:

    // module.mjs — automatically strict
export function greet(name) {
    return `Hello, ${name}`;
}
// undeclaredVar = 10; // ❌ ReferenceError

    No directive needed — import and export opt you into strict mode automatically.

    Strict Mode for Classes (Automatic)

    All class bodies are strict by default:

    class User {
    constructor(name) {
        this.name = name;
    }
    // No "use strict" needed — classes are always strict
}

    Strict Mode for eval and Function

    eval code, Function constructor code, event handler attributes, and strings passed to setTimeout are treated as complete scripts or function bodies — strict mode applies if the directive is present.

    eval('"use strict"; undeclaredVar = 10;'); // ❌ ReferenceError
new Function('"use strict"; undeclaredVar = 10;')(); // ❌ ReferenceError

    Strict Mode in TypeScript 6.0 (2026)

    TypeScript 6.0 (March 2026) turned strict on by default and unconditionally emits "use strict" in non-ESM output files. New TypeScript projects now get strict runtime semantics automatically.

    // tsconfig.json — strict is now default
{
    "compilerOptions": {
        "strict": true
    }
}

    Directive Prologue

    Strict mode is part of the directive prologue — a sequence of string literal expression statements at the start of a script or function. Multiple directives are allowed:

    "use strict";
"use asm";  // another directive
// both directives are active

    4. Mental Model

    The "Seatbelts" Mental Model

    Think of strict mode as seatbelts in a car:

    • You can drive without them (sloppy mode) — but the risk is higher.
    • They don't change how the car works — they change what happens when something goes wrong.
    • They catch mistakes before they become accidents.
    • Modern cars have them on by default (ES modules, classes, TypeScript 6.0).

    The "Warnings as Errors" Mental Model

    Strict mode is like switching your code editor from "ignore all warnings" to "treat warnings as errors":

    Sloppy mode:  "You misspelled a variable — I'll just create a new one."
Strict mode:  "You misspelled a variable — ReferenceError!"

    The same code runs, but now the language actively tells you when something looks wrong.

    The "Two Worlds" Mental Model

    ┌─────────────────────────────────────────────────────────┐
│                    JavaScript                            │
│                                                         │

    The "Opt-In Ladder" Mental Model

    Level 1: No strict mode anywhere
         ↓

         ↓

         ↓

         ↓

    Adopt strictness at the smallest possible boundary while migrating legacy code.

    5. Core Concepts

    Concept 1: What Strict Mode Changes

    Strict mode makes several changes to normal JavaScript semantics:

    1. Eliminates silent errors — changes them to throw errors.
    2. Fixes optimization blockers — strict code can sometimes run faster than sloppy code.
    3. Prohibits future-reserved syntax — prevents conflicts with future ECMAScript versions.

    Concept 2: Accidental Globals Become Errors

    In sloppy mode, assigning to an undeclared variable creates a global:

    // Sloppy mode
function tally(items) {
    sum = 0; // creates global `sum`!
    for (const price of items) sum += price;
    return sum;
}

    In strict mode, this throws a ReferenceError:

    "use strict";
function tally(items) {
    sum = 0; // ❌ ReferenceError
}

    This single rule eliminates a class of production bugs.

    Concept 3: this Is undefined in Plain Function Calls

    In sloppy mode, calling a function without a receiver sets this to the global object:

    function f() { return this; }
f(); // window (browser) or globalThis (Node)

    In strict mode, this is undefined:

    "use strict";
function f() { return this; }
f(); // undefined

    This catches constructor mistakes — calling a constructor without new throws a TypeError instead of silently polluting the global object.

    Concept 4: Assignment to Read-Only Properties Throws

    "use strict";
const obj = {};
Object.defineProperty(obj, "x", { value: 1, writable: false });
obj.x = 2; // ❌ TypeError: Cannot assign to read only property 'x'

    In sloppy mode, this fails silently.

    Concept 5: Adding Properties to Non-Extensible Objects Throws

    "use strict";
const obj = Object.freeze({ a: 1 });
obj.b = 2; // ❌ TypeError: Cannot add property b, object is not extensible

    In sloppy mode, this fails silently.

    Concept 6: Deleting Undeletable Properties Throws

    "use strict";
delete Object.prototype; // ❌ TypeError: Cannot delete property 'prototype'

    In sloppy mode, this returns false and continues.

    Concept 7: Duplicate Function Parameters Are Forbidden

    "use strict";
function f(a, a) { } // ❌ SyntaxError: Duplicate parameter name

    In sloppy mode, the last parameter wins — almost never the developer's intent.

    Concept 8: Octal Literals Are Forbidden

    "use strict";
const x = 0644; // ❌ SyntaxError: Octal literals are not allowed

    In sloppy mode, 0644 is interpreted as octal (420 in decimal). Use 0o644 in strict mode if you need octal.

    Concept 9: The with Statement Is Forbidden

    "use strict";
with (obj) { } // ❌ SyntaxError: Strict mode code may not include a with statement

    with makes scope unpredictable and blocks optimization. It is forbidden in strict mode.

    Concept 10: Reserved Words in Strict Mode

    The following identifiers become reserved words in strict mode and cannot be used as variable names:

    implements, interface, let, package, private, protected, public, static, yield

    "use strict";
const let = 10; // ❌ SyntaxError: Unexpected strict mode reserved word

    Concept 11: eval and arguments Are Simplified

    In strict mode:

    • eval cannot introduce new variables into the surrounding scope.
    • arguments does not alias function parameters.
    • Assigning to eval or arguments is a syntax error.
    "use strict";
eval("var x = 10;");
console.log(typeof x); // "undefined" — x is scoped to eval

    Concept 12: arguments.callee and arguments.caller Are Forbidden

    "use strict";
function f() {
    return arguments.callee; // ❌ TypeError
}

    These were used for recursion and stack inspection but blocked optimization.

    Concept 13: Top-Level this Is undefined in Modules

    In ES modules, top-level this is undefined — not the global object.

    // module.mjs
console.log(this); // undefined

    Concept 14: TypeScript 6.0 Strict Mode (2026)

    TypeScript 6.0 (March 2026) turned strict on by default and unconditionally emits "use strict" in non-ESM files. This means:

    • New TypeScript projects get strict type-checking without configuration.
    • Emitted JavaScript includes "use strict" automatically.
    • Legacy options (target: es5, AMD, UMD) are deprecated.

    Concept 15: strict Is No Longer a Preset in TypeScript 6

    In TypeScript 6, strict is no longer a preset that enables more strict options. Instead, it is a preset that enables 9 looser type-checking options — reflecting that strict is now the baseline, and loosening is the opt-in.

    Concept 16: ES2026 Module Strictness

    Every ECMAScript module (.mjs, or .js with "type": "module") runs in strict mode by default. Classic scripts (.js without module type) still default to sloppy mode unless the directive is present.

    Concept 17: Strict Mode and Performance

    Strict mode was once rumored to slow execution, but modern engines optimize both modes. In 2026, the performance difference is negligible for typical web workloads. Strict mode's real benefit is correctness, not speed.

    Concept 18: Directives and the Directive Prologue

    Strict mode is part of the directive prologue — a sequence of string literal expression statements at the start of a script or function. Multiple directives are allowed, and strict mode is active for the entire script/function if any directive is "use strict".

    6. How It Works

    Step-by-Step: Directive Detection

    1.  Parser reads the start of a script or function body.
    │
    ▼
2.  It looks for a directive prologue:
    │   - A sequence of string literal expression statements.
    │
    ▼
3.  If "use strict" is found in the prologue:
    │   - The entire script/function is marked strict.
    │
    ▼

    │   - Strict mode is not activated.

    Step-by-Step: Accidental Global Prevention

    1.  Assignment to an undeclared variable is encountered.
    │
    ▼
2.  Engine checks the scope chain for a binding.
    │
    ▼
3.  No binding found.
    │
    ▼
4.  In strict mode → throw ReferenceError.
    │
    ▼
5.  In sloppy mode → create a global binding.

    Step-by-Step: this Binding in Strict Mode

    1.  Function is called without a receiver: f().
    │
    ▼

    │
    ▼
3.  If strict → this = undefined.
    │
    ▼

    1.  Parser sees import or export at top level.
    │
    ▼

    │
    ▼
3.  Strict mode is automatically enabled.
    │
    ▼
4.  No directive required.

    Step-by-Step: Function-Level Strictness During Migration

    1.  Legacy file remains sloppy.
    │
    ▼
2.  A critical function is wrapped with "use strict".
    │
    ▼
3.  Only that function is strict.
    │
    ▼
4.  Rest of the file remains sloppy.
    │
    ▼
5.  Migrate other functions incrementally.

    7. Internal Architecture / Under the Hood

    The Spec's Treatment of Strict Mode

    The ECMAScript specification defines strict mode in multiple sections. Key rules include:

    • Forbidden Extensions (17.1) — function objects in strict mode must not have caller or arguments own properties.
    • Octal Literals — strict mode must not extend numeric literal syntax to include octal.
    • Future Reserved Words — additional keywords are reserved in strict mode.

    The [[Strict]] Internal Slot

    Every function object has a [[Strict]] internal slot:

    • true — function was defined in strict mode.
    • false — function was defined in sloppy mode.

    This slot determines this binding, arguments behavior, and other semantics.

    How Engines Detect Strict Mode

    V8 marks scripts and functions as strict during parsing. The strict flag is stored with the function object and consulted at runtime for:

    • this binding.
    • Variable resolution.
    • eval behavior.
    • delete operations.

    Optimization Impact

    Strict mode removes optimization blockers:

    • No with → static scope resolution.
    • No arguments aliasing → simpler parameter handling.
    • No implicit globals → predictable variable resolution.

    Modern engines optimize both modes well, but strict mode gives the JIT more guarantees.

    TypeScript 6.0's Emit Behavior

    TypeScript 6.0 unconditionally emits "use strict" in non-ESM output files. For ESM output, strict mode is implicit, so the directive is not emitted. This ensures strict runtime semantics regardless of target module format.

    Module Detection

    Engines detect ES modules by:

    • .mjs file extension.
    • <script type="module"> in HTML.
    • "type": "module" in package.json (Node.js).
    • Static import/export statements.

    Once detected, strict mode is automatically enabled.

}

    "use strict";
    return function formatMoney(amount, locale = "en-US") {
        const formatter = new Intl.NumberFormat(locale, {
            style: "currency",
            currency: "USD"
        });
        return formatter.format(amount);
    };
})();

    Breakdown:

    • Only the function is strict — rest of the file remains sloppy.
    • Enables incremental migration.

    Example 10: arguments Behavior in Strict Mode

    "use strict";

function f(a) {
    arguments[0] = 99;
    return a; // 10 — arguments is not aliased
}

f(10);

    Breakdown:

    • In sloppy mode, arguments[0] = 99 would change a to 99.
    • In strict mode, arguments is a copy, not an alias.

    11. Best Practices

    1. Use ES modules for all new code. Why: strict mode is automatic, and module scope is cleaner.
    2. Enable strict: true in TypeScript 6.0. Why: it is the default — embrace it.
    3. Use "use strict" in classic scripts. Why: catches silent errors.
    4. Enable strict mode at the smallest boundary during migration. Why: function-level first, then file-level.
    5. Never use with. Why: forbidden in strict mode; blocks optimization.
    6. Always declare variables with let or const. Why: prevents accidental globals.
    7. Use const by default. Why: prevents reassignment errors.
    8. Avoid arguments in strict mode. Why: use rest parameters instead.
    9. Use 0o prefix for octal literals. Why: strict mode forbids 0644.
    10. Enable ESLint strict rules. Why: catches strict-mode violations at lint time.
    11. Test in both strict and sloppy modes during migration. Why: catch boundary issues.
    12. Check bundled output for directive placement. Why: bundlers may move "use strict".
    13. Use Object.freeze() for immutable data. Why: strict mode enforces it.
    14. Prefer undefined over null for this checks. Why: strict mode sets this to undefined.
    15. Document strict mode decisions. Why: teams need to know why a file is sloppy.

    12. Common Mistakes

    ❌ Mistake: Directive Not First Statement

    "use strict"; // ❌ cancelled by preceding statement
const x = 1;

    ✅ Correct:

    "use strict";
const x = 1;

    ❌ Mistake: Using "use strict" in a Block

    {
    "use strict"; // ❌ ignored — blocks don't have directive prologues
}

    ✅ Correct: Use at script or function level.

    ❌ Mistake: Strict Mode in Functions with Non-Simple Parameters

    function f({ a, b }) {
    "use strict"; // ❌ SyntaxError
}

    ✅ Correct: Use simple parameters, or strict mode at file level.

    ❌ Mistake: Assuming Strict Mode Slows Code

    Why it's wrong: Modern engines optimize both modes; performance difference is negligible.

    ✅ Correct: Use strict mode for correctness, not performance.

    ❌ Mistake: Forgetting Modules Are Already Strict

    // module.mjs
"use strict"; // unnecessary — already strict

    ✅ Correct: Omit the directive in modules.

    ❌ Mistake: Using arguments.callee

    "use strict";
function f() {
    return arguments.callee; // ❌ TypeError
}

    ✅ Correct: Use named function expressions for recursion.

    ❌ Mistake: Assigning to Read-Only Properties

    "use strict";
const obj = Object.freeze({ a: 1 });
obj.a = 2; // ❌ TypeError

    ✅ Correct: Check Object.isFrozen() before assignment.

    ❌ Mistake: Duplicate Parameters

    "use strict";
function f(a, a) { } // ❌ SyntaxError

    ✅ Correct: Use distinct names.

    ❌ Mistake: Octal Literals

    "use strict";
const x = 0644; // ❌ SyntaxError

    ✅ Correct:

    const x = 0o644;

    ❌ Mistake: Assuming TypeScript Strict Mode Is Only Type-Level

    Why it's wrong: TypeScript 6.0 emits "use strict" in non-ESM output — it affects runtime too.

    ✅ Correct: Understand that strict: true has both type-level and runtime effects.

    13. Performance Considerations

    • Strict mode is not slower in 2026 — modern engines optimize both modes.
    • Strict mode removes optimization blockers — no with, no arguments aliasing.
    • Module strictness is free — no directive overhead.
    • TypeScript 6.0 emits "use strict" — no performance penalty.
    • Strict mode enables JIT optimizations — predictable variable resolution.
    • Strict mode may catch errors earlier — preventing performance-degrading bugs.

    Performance Tips

    1. Use strict mode for correctness, not speed.
    2. Use ES modules — strict by default, no directive needed.
    3. Avoid eval — it deoptimizes regardless of strictness.
    4. Keep functions small and predictable.
    5. Profile with --trace-opt / --trace-deopt.

    14. Security Considerations

    Accidental Global Prevention

    Strict mode prevents global pollution — a vector for prototype pollution and cross-script interference.

    this Binding Safety

    Strict mode sets this to undefined in plain calls — preventing accidental global object mutation.

    Read-Only Property Protection

    Strict mode throws on read-only property assignment — preventing data corruption.

    Non-Extensible Object Protection

    Strict mode throws on adding properties to frozen/sealed objects — enforcing immutability.

    eval Isolation

    Strict mode prevents eval from introducing variables into the surrounding scope.

    Module Scope Isolation

    ES modules are strict and have module scope — preventing global namespace pollution.

    TypeScript 6.0 Strict Mode

    TypeScript 6.0's strict: true default catches more type errors at compile time, reducing runtime vulnerabilities.

    • TypeError: Cannot add property — non-extensible object.
    • SyntaxError: Duplicate parameter name — strict mode forbids duplicates.
    • SyntaxError: Octal literals are not allowed — use 0o prefix.
    • Check directive placement — "use strict" must be first statement.

    • ES modules — always (automatic).
    • Classes — always (automatic).

    • When you need with or octal literals — use alternatives instead.

    • TypeScript 6.0 emits "use strict" in non-ESM files automatically.
    • Strict mode is not a subset — it intentionally has different semantics.
    • "use strict" must be the literal first statement — comments are allowed, but code is not.
    • Strict mode forbids with — a major optimization blocker.
    • Strict mode reserves 9 additional keywords — including let, package, and static.
    • Duplicate parameters are a SyntaxError in strict mode.
    • Octal literals like 0644 are forbidden — use 0o644.
    • arguments.callee is forbidden in strict mode.
    • Strict mode sets this to undefined in plain calls.
    • eval cannot introduce variables into the surrounding scope in strict mode.
    • Performance difference between strict and sloppy is negligible in 2026.
    • Strict mode is "seatbelts" — not required, but highly recommended.
