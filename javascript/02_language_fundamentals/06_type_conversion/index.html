    Type Conversion

    1. Overview

    Definition

    Type conversion (also called type casting or type coercion) is the process of changing a value from one data type to another. JavaScript performs type conversion in two ways: explicitly (when you call conversion functions like Number() or String()) and implicitly (when the engine automatically converts values during operations like comparison, arithmetic, or concatenation).

    // Explicit conversion — you ask for it
const num = Number("42");        // "42" → 42
const str = String(42);          // 42 → "42"
const bool = Boolean(0);         // 0 → false

// Implicit conversion — the engine does it
const result = "5" + 3;          // 3 → "3" → "53"
const comparison = "5" == 5;     // "5" → 5 → true
const truthy = !!"hello";        // "hello" → true

    JavaScript is a weakly typed and dynamically typed language. Weak typing means it performs implicit coercion rather than throwing type errors. Dynamic typing means types are associated with values, not variables — a single variable can hold different types over its lifetime.

    Purpose

    Type conversion exists to solve the problem of mismatched types in operations. A form input arrives as a string; a calculation needs a number. A comparison needs both operands to be the same type. Without conversion, every operation would require manual type checking and explicit conversion by the developer.

    JavaScript's approach — automatic coercion — makes the language more forgiving but also more surprising. The purpose of understanding type conversion is not to embrace coercion everywhere, but to know when it happens, why it happens, and how to control it.

    Where It Fits

    Language Fundamentals
├── Variables             ✅ done
├── Data Types            ✅ done
├── Operators             ✅ done
├── Expressions           ✅ done
├── Statements            ✅ done
├── Type Conversion       ← you are here
├── Equality
└── Strict Mode

    Type conversion sits between Statements and Equality because equality (== vs ===) is the most common context where conversion rules matter. Understanding conversion first makes the equality chapter much clearer.

    2. Why It Exists

    The Problem

    JavaScript was designed for the web, where data arrives as strings. Form inputs, URL parameters, and HTML attributes are all strings. But calculations, comparisons, and logic require numbers, booleans, and objects. A language that refused to convert types would force developers to manually convert everything — tedious, error-prone, and verbose.

    JavaScript chose automatic coercion to make the language more forgiving. But this created a second problem: coercion rules are complex, asymmetric, and sometimes surprising. The goal of understanding type conversion is to know the rules so you can predict behavior and write code that is both concise and correct.

    Previous Limitations

    Era Limitation
    Pre-ES5 No Number.isNaN() — global isNaN coerces unpredictably
    No Object.is() No reliable way to compare NaN or +0/-0
    No BigInt Large numbers lost precision; no separate numeric type
    No Number.parseInt Global parseInt existed but no namespaced version
    No JSON.rawJSON No control over JSON.stringify output for primitives

    Why New Conversion Features Were Introduced

    • Number.isNaN() (ES2015) — reliable NaN check without coercion.
    • Object.is() (ES2015) — SameValue comparison for NaN and -0.
    • BigInt (ES2020) — arbitrary-precision integers with explicit conversion.
    • Number.parseInt, Number.parseFloat (ES2015) — namespaced, non-coercing versions.
    • Math.sumPrecise() (ES2026) — high-precision summation minimizing floating-point error.
    • Uint8Array base64/hex methods (ES2026) — direct conversion between binary and string encodings.
    • JSON.rawJSON() (ES2026) — fine control over JSON.stringify output for primitive values.
    • JSON.parse reviver context (ES2026) — access the matched segment of JSON source to recover exact values.

    Each new feature solves a specific conversion problem: either making an implicit conversion explicit, or providing a safer alternative to a coercing method.

    3. Syntax / Basic Usage

    Explicit Conversion — The Three Primitives

    // To Number
Number("42");         // 42
Number("");           // 0
Number("  42  ");     // 42 (whitespace trimmed)
Number("42px");       // NaN (not a valid number)
Number(true);         // 1
Number(false);        // 0
Number(null);         // 0
Number(undefined);    // NaN
Number([]);           // 0
Number([5]);          // 5
Number([1, 2]);       // NaN

// To String
String(42);           // "42"
String(true);         // "true"
String(null);         // "null"
String(undefined);    // "undefined"
String([1, 2, 3]);    // "1,2,3"
String({ a: 1 });     // "[object Object]"

// To Boolean
Boolean(0);           // false
Boolean("");          // false
Boolean(null);        // false
Boolean(undefined);   // false
Boolean(NaN);         // false
Boolean("0");         // true (non-empty string)
Boolean([]);          // true (objects are truthy)
Boolean({});          // true

    Parsing Strings to Numbers

    parseInt("42");         // 42
parseInt("42px");       // 42 (stops at first non-digit)
parseInt("ff", 16);     // 255 (explicit radix)
parseInt("");           // NaN
parseFloat("3.14");     // 3.14
parseFloat("3.14abc");  // 3.14
parseFloat("abc");      // NaN

Number.parseInt("42");  // 42 (namespaced, ES2015)
Number.parseFloat("3.14"); // 3.14

    Always pass a radix to parseInt — otherwise, strings starting with 0 may be parsed as octal (legacy behavior), and 0x strings are parsed as hex.

    Conversion with Unary Operators

    +"42";       // 42 (unary plus — same as Number())
-"42";       // -42
+true;       // 1
+false;      // 0
+null;       // 0
+undefined;  // NaN
+"";         // 0
+" 42 ";     // 42
+"42px";     // NaN

!!"hello";   // true (double negation — same as Boolean())
!!0;         // false
!![];        // true

    Implicit Conversion — Where It Happens

    // `+` operator — string concatenation takes priority
"5" + 3;       // "53" (number → string)
3 + "5";       // "35"
true + "5";    // "true5"
1 + 2 + "3";   // "33" (1+2=3, then 3+"3"="33")
"1" + 2 + 3;   // "123"

// Other arithmetic operators — numeric conversion
"5" - 3;       // 2 (string → number)
"5" * 3;       // 15
"5" / 2;       // 2.5
"5" % 2;       // 1
"5" ** 2;      // 25

// Comparison operators — numeric or string comparison
"5" > 3;       // true (string → number)
"a" > "b";     // false (lexicographic)
"10" > "9";    // false (lexicographic — "1" < "9")

// Loose equality — complex coercion rules
"5" == 5;      // true
0 == false;    // true
"" == false;   // true
null == undefined; // true
null == 0;     // false
NaN == NaN;    // false

    Conversion via Symbol.toPrimitive

    Objects can customize their conversion behavior:

    const obj = {
    [Symbol.toPrimitive](hint) {
        if (hint === "number") return 42;
        if (hint === "string") return "hello";
        return true; // "default" hint
    },
};

+obj;        // 42 (hint: "number")
`${obj}`;    // "hello" (hint: "string")
obj + "";    // "true" (hint: "default")

    Symbol.toPrimitive is called with a hint of "number", "string", or "default". If absent, JavaScript falls back to valueOf() and toString().

    ES2026 Conversion Additions

    // Math.sumPrecise — high-precision summation
Math.sumPrecise([0.1, 0.2, 0.3]); // 0.6 (not 0.6000000000000001)

// Uint8Array base64/hex conversion
const bytes = new Uint8Array([72, 101, 108, 108, 111]);
bytes.toBase64();                // "SGVsbG8="
Uint8Array.fromBase64("SGVsbG8="); // Uint8Array [72, 101, 108, 108, 111]
bytes.toHex();                   // "48656c6c6f"
Uint8Array.fromHex("48656c6c6f"); // Uint8Array [72, 101, 108, 108, 111]

// JSON.rawJSON — preserve exact primitive values
const bigNumber = JSON.rawJSON("9007199254740993");
JSON.stringify({ id: bigNumber }); // {"id":9007199254740993}

    4. Mental Model

    The "Conversion Triangle" Mental Model

    Every value can be converted to Number, String, or Boolean:

    ┌─────────────┐
│   Number    │
│             │
└──────┬──────┘
       │
       ▼
┌─────────────┐       ┌─────────────┐
│   String    │◄─────►│   Boolean   │
│             │       │             │
└─────────────┘       └─────────────┘
    • To Number — via Number(), unary +, parseInt(), parseFloat().
    • To String — via String(), template literals, + with a string.
    • To Boolean — via Boolean(), !!, logical operators, conditionals.

    The "Falsy Eight" Mental Model

    There are exactly eight falsy values:

    false        — boolean false
0            — positive zero
-0           — negative zero
0n           — BigInt zero (ES2020)
""           — empty string
null         — null
undefined    — undefined
NaN          — not a number

    Everything else is truthy — including "0", "false", [], {}, and function(){}.

    The "Two Conversion Families" Mental Model

    ┌─────────────────────────────────────────────────────┐
│                    Conversion                       │
│                                                     │
│  ┌─────────────────────┐  ┌─────────────────────┐  │
│  │   Explicit          │  │   Implicit          │  │
│  │   (you control)      │  │   (engine decides)  │  │
│  │                      │  │                      │  │
│  │  Number(x)          │  │  "5" + 3 → "53"     │  │
│  │  String(x)          │  │  "5" - 3 → 2        │  │
│  │  Boolean(x)         │  │  "5" == 5 → true    │  │
│  │  parseInt(x)        │  │  !!x → boolean      │  │
│  │  parseFloat(x)      │  │  +x → number        │  │
│  └─────────────────────┘  └─────────────────────┘  │
│                                                     │
│  Predictable, visible       Surprising, invisible   │
│  Use in production          Avoid in production     │
└─────────────────────────────────────────────────────┘

    The "ToPrimitive Pipeline" Mental Model

    When an object needs to become a primitive, JavaScript follows a pipeline:

    Object → [Symbol.toPrimitive]? → Yes → Call it → Primitive
                    │
                    ▼ No
              → [hint === "string"]? → toString() then valueOf()
                    │
                    ▼ No
              → valueOf() then toString()

    The hint determines the order:

    Hint Context Preferred Order
    "number" Arithmetic, comparison valueOf() → toString()
    "string" Template literals, String() toString() → valueOf()
    "default" +, == valueOf() → toString()

    The "Asymmetric Conversion" Mental Model

    Conversion is not symmetric:

    "5" + 3   → "53"    (number → string)
"5" - 3   → 2       (string → number)

    + prefers strings; other arithmetic operators prefer numbers. This is one of the most common sources of confusion.

    5. Core Concepts

    Concept 1: Explicit vs. Implicit Conversion

    Aspect Explicit Implicit
    Control Developer Engine
    Visibility Visible in code Invisible
    Predictability High Low
    Recommended Yes Only when intentional
    Examples Number(), String() "5" + 3, "5" == 5

    Concept 2: The Abstract Operations

    The ECMAScript spec defines conversion via abstract operations:

    Operation Purpose
    ToPrimitive Convert object to primitive
    ToBoolean Convert to boolean
    ToNumber Convert to number
    ToNumeric Convert to number or BigInt
    ToString Convert to string
    ToObject Convert primitive to object
    ToPropertyKey Convert to string or symbol
    ToInt32 Convert to 32-bit signed integer
    ToUint32 Convert to 32-bit unsigned integer
    ToBigInt Convert to BigInt

    These operations are normative — engines must follow them.

    Concept 3: ToBoolean — The Simplest Conversion

    ToBoolean never throws and never coerces objects:

    Input Type Result
    Undefined false
    Null false
    Boolean Input value
    Number false if +0, -0, or NaN; otherwise true
    String false if empty; otherwise true
    Symbol true
    BigInt false if 0n; otherwise true
    Object true

    There are exactly eight falsy values — everything else is truthy.

    Concept 4: ToNumber — String to Number Rules

    String Number
    "" 0
    " 42 " 42 (whitespace trimmed)
    "42" 42
    "42.5" 42.5
    "0x1F" 31 (hex)
    "0b101" 5 (binary)
    "0o17" 15 (octal)
    "42px" NaN
    "hello" NaN
    "Infinity" Infinity
    "-Infinity" -Infinity

    Number() is strict — it requires the entire string to be a valid number. parseInt() and parseFloat() are lenient — they parse as much as they can.

    Concept 5: ToString — Number to String Rules

    Number String
    42 "42"
    3.14 "3.14"
    0 "0"
    -0 "0"
    NaN "NaN"
    Infinity "Infinity"
    1e21 "1e+21"
    1e-7 "1e-7"

    Numbers use the shortest representation that round-trips exactly.

    Concept 6: The + Operator — Concatenation vs. Addition

    The + operator has two modes:

    1. String concatenation — if either operand is a string (after ToPrimitive).
    2. Numeric addition — if both operands are numbers (after ToPrimitive).
    1 + 2;          // 3 (both numbers)
1 + "2";        // "12" (string wins)
"1" + 2;        // "12"
1 + 2 + "3";    // "33" (left to right)
"1" + 2 + 3;    // "123"

    Concept 7: The == Operator — Loose Equality

    == performs complex coercion:

    • null == undefined → true
    • null == 0 → false
    • "5" == 5 → true (string → number)
    • 0 == false → true (boolean → number)
    • "" == false → true (both → number: 0 == 0)
    • NaN == NaN → false
    • Objects compared to primitives → ToPrimitive then compare

    Always use === unless you specifically need null/undefined coalescing.

    Concept 8: Symbol.toPrimitive — Custom Conversion

    Objects can override conversion by implementing Symbol.toPrimitive:

    const obj = {
    [Symbol.toPrimitive](hint) {
        if (hint === "number") return 42;
        if (hint === "string") return "hello";
        return true;
    },
};

    The hint is "number", "string", or "default". This is the only way to fully control object-to-primitive conversion.

    Concept 9: valueOf() and toString() — The Fallback

    If Symbol.toPrimitive is absent, JavaScript uses valueOf() and toString():

    • "number" hint — valueOf() first, then toString().
    • "string" hint — toString() first, then valueOf().
    • "default" hint — valueOf() first, then toString().

    Most objects inherit Object.prototype.valueOf() (returns the object itself) and Object.prototype.toString() (returns "[object Object]").

    Concept 10: Parsing vs. Conversion

    Number() parseInt() parseFloat()
    Strictness Strict Lenient Lenient
    Whitespace Trimmed Ignored Ignored
    Trailing chars Error → NaN Stops parsing Stops parsing
    Radix Auto (0x, 0b, 0o) Must specify N/A
    Empty string 0 NaN NaN

    Concept 11: BigInt Conversion

    BigInt(42);         // 42n
BigInt("42");       // 42n
BigInt(true);       // 1n
// BigInt(42.5);    // ❌ RangeError — no fractions
// BigInt(null);    // ❌ TypeError
// BigInt(undefined); // ❌ TypeError

Number(42n);        // 42
// 42n + 1;        // ❌ TypeError — cannot mix BigInt and Number
42n + 1n;           // 43n

    BigInt and Number cannot be mixed in arithmetic — explicit conversion is required.

    Concept 12: ES2026 Conversion Additions

    • Math.sumPrecise() — sums numbers minimizing floating-point error.
    • Uint8Array.toBase64() / fromBase64() — binary ↔ base64 string.
    • Uint8Array.toHex() / fromHex() — binary ↔ hex string.
    • JSON.rawJSON() — preserve exact primitive values in JSON.stringify.
    • JSON.parse reviver context — access the matched segment of JSON source.

    Concept 13: Object.is() — SameValue Comparison

    Object.is(NaN, NaN);   // true (unlike ===)
Object.is(0, -0);      // false (unlike ===)
Object.is(42, 42);     // true
Object.is("a", "a");   // true

    Object.is() is the SameValue algorithm — it does not coerce and treats NaN and -0 specially.

    Concept 14: Conversion in switch

    switch uses strict equality (===) for case matching — no coercion.

    switch ("5") {
    case 5: console.log("number"); break;   // ❌ not matched
    case "5": console.log("string"); break; // ✅ matched
}

    Concept 15: Conversion in Array.prototype.sort

    sort() converts elements to strings by default:

    [10, 2, 1].sort(); // [1, 10, 2] — lexicographic, not numeric
[10, 2, 1].sort((a, b) => a - b); // [1, 2, 10] — numeric

    Concept 16: Conversion in Template Literals

    Template literals convert interpolated values to strings:

    const x = 42;
`${x}`; // "42"
`${null}`; // "null"
`${undefined}`; // "undefined"
`${[1, 2]}`; // "1,2"
`${{ a: 1 }}`; // "[object Object]"

    Concept 17: Conversion in JSON.stringify

    JSON.stringify converts values to JSON-compatible types:

    JSON.stringify({ a: undefined });    // "{}"
JSON.stringify({ a: function() {} }); // "{}"
JSON.stringify({ a: NaN });          // '{"a":null}'
JSON.stringify({ a: Infinity });     // '{"a":null}'
JSON.stringify({ a: 42n });          // TypeError

    Concept 18: Conversion in JSON.parse

    JSON.parse converts JSON values to JavaScript types:

    JSON.parse("42");        // 42 (number)
JSON.parse('"42"');      // "42" (string)
JSON.parse("true");      // true (boolean)
JSON.parse("null");      // null
JSON.parse('{"a":1}');   // { a: 1 }

    ES2026 adds a reviver context parameter to access the matched segment of JSON source, useful for recovering exact values from numbers that lose precision.

    6. How It Works

    Step-by-Step: ToPrimitive Pipeline

    1.  Object needs to become a primitive.
    │
    ▼
2.  Does it have Symbol.toPrimitive?
    │   ├── Yes → call it with hint → return result
    │   └── No → continue
    │
    ▼
3.  Determine hint:
    │   - "number" (arithmetic, comparison)
    │   - "string" (template literals, String())
    │   - "default" (+, ==)
    │
    ▼
4.  For "string" hint:
    │   - try toString() → if primitive, return
    │   - try valueOf() → if primitive, return
    │
    ▼
5.  For "number" or "default" hint:
    │   - try valueOf() → if primitive, return
    │   - try toString() → if primitive, return
    │
    ▼
6.  If neither works → TypeError

    Step-by-Step: ToNumber for Strings

    1.  String is trimmed of leading/trailing whitespace.
    │
    ▼
2.  If empty → 0.
    │
    ▼
3.  If starts with "0x", "0b", "0o" → parse as hex/binary/octal.
    │
    ▼
4.  If "Infinity" or "-Infinity" → Infinity.
    │
    ▼
5.  If valid numeric string → parse as decimal.
    │
    ▼
6.  Otherwise → NaN.

    Step-by-Step: ToBoolean for Objects

    1.  Object is always truthy.
    │
    ▼
2.  No coercion occurs.
    │
    ▼
3.  Result is true.

    This is why [] and {} are truthy even though they "look empty."

    Step-by-Step: + Operator Evaluation

    1.  Evaluate left operand.
    │
    ▼
2.  Evaluate right operand.
    │
    ▼
3.  Apply ToPrimitive to both.
    │
    ▼
4.  If either result is a string → string concatenation.
    │
    ▼
5.  Otherwise → numeric addition.

    Step-by-Step: == Loose Equality

    1.  If both operands are same type → strict comparison.
    │
    ▼
2.  If one is null and other is undefined → true.
    │
    ▼
3.  If one is number and other is string → string → number.
    │
    ▼
4.  If one is boolean → boolean → number.
    │
    ▼
5.  If one is object and other is primitive → object → primitive.
    │
    ▼
6.  Otherwise → false.

    Step-by-Step: ES2026 Math.sumPrecise

    1.  Iterable of numbers is consumed.
    │
    ▼
2.  Numbers are summed using a high-precision algorithm.
    │
    ▼
3.  Floating-point errors are minimized.
    │
    ▼
4.  Result is returned as a single Number.

    7. Internal Architecture / Under the Hood

    The Abstract Operations in ECMA-262

    The spec defines conversion in Section 7.1:

    7.1.1  ToPrimitive ( input [, preferredType ] )
7.1.2  ToBoolean ( argument )
7.1.3  ToNumeric ( value )
7.1.4  ToNumber ( argument )
7.1.5  ToIntegerOrInfinity ( argument )
7.1.6  ToInt32 ( argument )
7.1.7  ToUint32 ( argument )
7.1.13 ToBigInt ( argument )
7.1.17 ToString ( argument )
7.1.18 ToObject ( argument )
7.1.19 ToPropertyKey ( argument )

    These are normative — engines must follow them exactly.

    ToPrimitive in Detail

    ToPrimitive(input, preferredType):
1.  If input is not an Object → return input.
2.  Let exoticToPrim = GetMethod(input, @@toPrimitive).
3.  If exoticToPrim is not undefined:
    a.  Let hint be preferredType (or "default").
    b.  Let result = Call(exoticToPrim, input, « hint »).
    c.  If result is not an Object → return result.
    d.  Throw TypeError.
4.  If preferredType is not present → hint = "default".
5.  Return OrdinaryToPrimitive(input, hint).

    OrdinaryToPrimitive

    OrdinaryToPrimitive(O, hint):
1.  If hint is "string":
    a.  methodNames = « "toString", "valueOf" ».
2.  Else:
    a.  methodNames = « "valueOf", "toString" ».
3.  For each name in methodNames:
    a.  Let method = Get(O, name).
    b.  If IsCallable(method):
        i.   Let result = Call(method, O).
        ii.  If result is not an Object → return result.
4.  Throw TypeError.

    The hint Values

    Hint When Used
    "number" Arithmetic operators (-, *, /, %, **), relational comparison
    "string" String(), template literals, alert()
    "default" +, ==, !=

    Conversion in the Engine

    V8 optimizes conversion with type feedback:

    function add(a, b) { return a + b; }
add(1, 2);   // feedback: both numbers → fast integer add
add("a", "b"); // guard fails → deoptimize → string concat

    Each call site records the types it has seen. The JIT compiles speculative code based on that feedback. If a new type appears, the guard fails and the function deoptimizes.

    Memory and Performance

    • SMIs (small integers) convert inline — fast.
    • HeapNumbers convert with boxing — slower.
    • String parsing — Number() uses a fast path for simple numeric strings.
    • parseInt() — slower than Number() because it scans character by character.
    • Symbol.toPrimitive — function call overhead.

    8. Lifecycle / Workflow

    Conversion Lifecycle

    Value → Determine target type → Apply conversion rules → Result

    Explicit Conversion Workflow

    Developer calls Number(x) → ToNumber algorithm → Result
Developer calls String(x) → ToString algorithm → Result
Developer calls Boolean(x) → ToBoolean algorithm → Result

    Implicit Conversion Workflow

    Operation encounters mismatched types
    │
    ▼
Engine determines required conversion
    │
    ▼
Applies ToPrimitive / ToNumber / ToString / ToBoolean
    │
    ▼
Operation proceeds with converted values

    ToPrimitive Workflow

    Object → Symbol.toPrimitive? → Yes → Call with hint → Primitive
                    │
                    ▼ No
              Hint determines order
                    │
                    ▼
              toString() / valueOf()
                    │
                    ▼
              Primitive or TypeError

    ES2026 Conversion Workflow

    Uint8Array → toBase64() → string
Uint8Array → toHex() → string
Uint8Array.fromBase64(string) → Uint8Array
Uint8Array.fromHex(string) → Uint8Array

JSON.stringify({ id: JSON.rawJSON("...") }) → exact primitive
JSON.parse(source, reviver) → reviver receives context

    9. Practical Examples

    Example 1: Explicit Conversion — The Safe Path

    const input = "42";
const num = Number(input);        // 42
const str = String(num);          // "42"
const bool = Boolean(input);      // true

console.log(typeof num, typeof str, typeof bool);
// "number" "string" "boolean"

    Breakdown:

    • Number() is strict — it returns NaN for invalid strings.
    • String() never throws.
    • Boolean() follows the falsy-eight rule.

    Example 2: Implicit Conversion — String Concatenation

    const a = 1 + 2 + "3";    // "33"
const b = "1" + 2 + 3;    // "123"

console.log(a); // "33"
console.log(b); // "123"

    Breakdown:

    • Left to right: 1 + 2 = 3, then 3 + "3" = "33".
    • "1" + 2 = "12", then "12" + 3 = "123".

    Example 3: Implicit Conversion — Numeric

    const a = "5" - 3;        // 2
const b = "5" * 3;        // 15
const c = "5" / 2;        // 2.5
const d = "5" % 2;        // 1

console.log(a, b, c, d); // 2 15 2.5 1

    Breakdown:

    • All arithmetic operators except + convert strings to numbers.

    Example 4: Loose vs. Strict Equality

    console.log("5" == 5);    // true
console.log("5" === 5);   // false
console.log(null == undefined); // true
console.log(null === undefined); // false
console.log(NaN == NaN);  // false
console.log(NaN === NaN); // false
console.log(Object.is(NaN, NaN)); // true

    Breakdown:

    • == coerces; === does not.
    • Object.is() treats NaN as equal to itself.

    Example 5: Symbol.toPrimitive — Custom Conversion

    class Temperature {
    constructor(celsius) {
        this.celsius = celsius;
    }

    [Symbol.toPrimitive](hint) {
        if (hint === "number") return this.celsius;
        if (hint === "string") return `${this.celsius}°C`;
        return this.celsius;
    }
}

const temp = new Temperature(25);

console.log(+temp);        // 25
console.log(`${temp}`);    // "25°C"
console.log(temp + 5);     // 30

    Breakdown:

    • Symbol.toPrimitive controls conversion for all hints.
    • Without it, temp + 5 would produce "[object Object]5".

    Example 6: parseInt vs. Number

    console.log(parseInt("42px"));    // 42
console.log(Number("42px"));      // NaN
console.log(parseInt(""));        // NaN
console.log(Number(""));          // 0
console.log(parseInt("ff", 16));  // 255
console.log(Number("0xff"));      // 255

    Breakdown:

    • parseInt is lenient; Number is strict.
    • Always pass a radix to parseInt.

    Example 7: Math.sumPrecise (ES2026)

    const sum = 0.1 + 0.2;           // 0.30000000000000004
const precise = Math.sumPrecise([0.1, 0.2]); // 0.3

console.log(sum);     // 0.30000000000000004
console.log(precise); // 0.3

    Breakdown:

    • Math.sumPrecise minimizes floating-point error.
    • Part of ES2026.

    Example 8: Uint8Array Base64/Hex (ES2026)

    const bytes = new Uint8Array([72, 101, 108, 108, 111]); // "Hello"

console.log(bytes.toBase64());  // "SGVsbG8="
console.log(bytes.toHex());     // "48656c6c6f"

const decoded = Uint8Array.fromBase64("SGVsbG8=");
console.log(decoded); // Uint8Array [72, 101, 108, 108, 111]

    Breakdown:

    • Direct conversion between binary and string encodings.
    • Part of ES2026.

    Example 9: JSON.rawJSON (ES2026)

    const bigNumber = JSON.rawJSON("9007199254740993");
const json = JSON.stringify({ id: bigNumber });
console.log(json); // {"id":9007199254740993}

    Breakdown:

    • Preserves integers larger than Number.MAX_SAFE_INTEGER.
    • Part of ES2026.

    Example 10: Conversion in sort

    const nums = [10, 2, 1];
console.log(nums.sort());              // [1, 10, 2] — lexicographic!
console.log(nums.sort((a, b) => a - b)); // [1, 2, 10] — numeric

    Breakdown:

    • Default sort() converts to strings.
    • Always provide a comparator for numbers.

    11. Best Practices

    1. Default to explicit conversion in production code. Why: makes type changes visible and intentional.
    2. Use Number(), String(), Boolean() over shorthand (+x, !!x, `${x}). Why: clarity over cleverness.
    3. Always use === and !==. Why: avoids coercion surprises.
    4. Use Number.isNaN() not global isNaN(). Why: global isNaN coerces.
    5. Always pass a radix to parseInt(). Why: avoids legacy octal and hex parsing.
    6. Use Number() for strict parsing, parseInt() for lenient parsing. Why: different tools for different jobs.
    7. Convert at system boundaries (API, input, storage). Why: keep internal data in the right types.
    8. Use Symbol.toPrimitive for custom object conversion. Why: full control over all hints.
    9. Use Object.is() for SameValue comparison. Why: handles NaN and -0 correctly.
    10. Provide a comparator to Array.prototype.sort(). Why: default converts to strings.
    11. Use Math.sumPrecise() for floating-point summation. Why: minimizes precision loss (ES2026).
    12. Use Uint8Array base64/hex methods for binary data. Why: native, efficient (ES2026).
    13. Use JSON.rawJSON() when exact primitive preservation matters. Why: avoids precision loss (ES2026).
    14. Enable ESLint eqeqeq and no-implicit-coercion. Why: enforces safe conversion practices.
    15. Understand the falsy eight. Why: predicts conditional behavior.

    12. Common Mistakes

    ❌ Mistake: Using == Instead of ===

    0 == "";    // true
0 == false; // true
"" == false; // true

    ✅ Correct:

    0 === "";    // false
0 === false; // false
"" === false; // false

    ❌ Mistake: Forgetting parseInt Radix

    parseInt("08"); // 8 in modern engines, but legacy risk

    ✅ Correct:

    parseInt("08", 10); // 8

    ❌ Mistake: Assuming Number("") Is NaN

    Number(""); // 0, not NaN

    ✅ Correct: Use parseInt("") for NaN, or check for empty strings first.

    ❌ Mistake: Using || for Numeric Defaults

    const count = userCount || 10; // 0 becomes 10

    ✅ Correct:

    const count = userCount ?? 10; // only null/undefined become 10

    ❌ Mistake: sort() Without Comparator

    [10, 2, 1].sort(); // [1, 10, 2] — wrong!

    ✅ Correct:

    [10, 2, 1].sort((a, b) => a - b); // [1, 2, 10]

    ❌ Mistake: Mixing BigInt and Number

    1n + 1; // ❌ TypeError

    ✅ Correct:

    1n + 1n; // 2n
Number(1n) + 1; // 2

    ❌ Mistake: Assuming typeof null Is "null"

    typeof null; // "object" — historical bug

    ✅ Correct: value === null.

    ❌ Mistake: Global isNaN

    isNaN("hello"); // true — coerces

    ✅ Correct:

    Number.isNaN("hello"); // false — does not coerce

    ❌ Mistake: Using + for Conversion Ambiguously

    +"42"; // 42 — but could be string concatenation if not careful

    ✅ Correct: Use Number("42") for clarity.

    ❌ Mistake: Forgetting Template Literal Conversion

    `${[1, 2]}`; // "1,2"
`${{ a: 1 }}`; // "[object Object]"

    ✅ Correct: Use JSON.stringify() for objects.

    13. Performance Considerations

    • Number() vs parseInt() — Number() is faster for strict parsing.
    • Unary + vs Number() — similar performance; Number() is clearer.
    • String() vs template literals — template literals are slightly slower.
    • Symbol.toPrimitive — adds function call overhead per conversion.
    • String concatenation — ConsString lazy evaluation; flattening costs.
    • Math.sumPrecise() — slower than + but accurate for floating-point.
    • JSON.parse — fast for valid JSON; reviver adds overhead.
    • sort() comparator — required for numeric sort; adds function call cost.
    • Type stability — keep types stable in hot loops for JIT optimization.

    Performance Tips

    1. Convert once at boundaries, not in hot loops.
    2. Use Number() for strict numeric parsing.
    3. Keep operand types stable in arithmetic.
    4. Use Math.sumPrecise() only when precision matters.
    5. Use Uint8Array base64/hex methods for binary data.
    6. Profile with --trace-opt / --trace-deopt.

    14. Security Considerations

    Coercion Attacks

    if (input == 1) { /* bypassed with "1" or [1] */ }

    Defense: Always use ===.

    Prototype Pollution

    Malicious input can modify Object.prototype, affecting all objects.

    Defense: Validate keys, use Object.create(null), freeze prototypes.

    eval and Implicit Conversion

    Never pass untrusted strings to eval() or new Function().

    parseInt and Radix

    Omitting the radix can lead to unexpected parsing (octal in legacy engines).

    Defense: Always pass 10 for decimal.

    Symbol.toPrimitive Abuse

    Objects can override conversion to return unexpected values. Never trust objects from untrusted sources without validation.

    JSON Parsing

    JSON.parse is safe by design — it does not execute code. But parsing large payloads can exhaust memory.

    Defense: Limit input size.

    BigInt and Denial of Service

    Huge BigInt operations can block the event loop.

    Defense: Validate input size; avoid BigInt arithmetic on untrusted values.

    Uint8Array Base64/Hex

    These methods are safe, but ensure you validate decoded data before use.

    17. When Not to Use

    • == — never; use ===.
    • || for defaults — when 0, "", false are valid.
    • Global isNaN() — use Number.isNaN().
    • parseInt() without radix — always pass 10.
    • Implicit coercion in production — prefer explicit conversion.
    • eval() for conversion — never.
    • new Number() / new String() — creates objects, not primitives.
    • Mixing BigInt and Number — explicit conversion required.
