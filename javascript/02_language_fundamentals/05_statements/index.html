    Statements

    1. Overview

    Definition

    A statement is a syntactic unit that expresses an action to be performed. Statements are the instructions of a JavaScript program — they declare variables, control flow, handle errors, and manage resources. Unlike expressions, statements do not produce values; they direct the engine to do something.

    let x = 10;                      // declaration statement
if (x > 5) { x--; }             // conditional statement
for (let i = 0; i < 3; i++) {}  // iteration statement
try { risky(); } catch (e) {}   // exception handling statement
using file = openFile("a.txt");  // resource management (ES2026)
debugger;                        // debugger statement

    The ECMAScript 2026 specification (17th edition, approved June 30, 2026) organizes statements into a formal StatementList grammar. Every program is a sequence of statements.

    Purpose

    Statements exist to solve the fundamental problem of directing execution. A program that only produces values is a calculator; a program that can decide, repeat, handle errors, and manage resources is a program. Statements provide that control.

    They serve as the action layer of the language:

    • Declarations — create bindings (let, const, using).
    • Control flow — decide what runs next (if, switch, loops).
    • Jumps — alter execution order (break, continue, return, throw).
    • Error handling — recover from failures (try/catch/finally).
    • Resource management — deterministic cleanup (using, await using).
    • Debugging — pause execution (debugger).

    Where It Fits

    Language Fundamentals
├── Variables             ✅ done
├── Data Types            ✅ done
├── Operators             ✅ done
├── Expressions           ✅ done
├── Statements            ← you are here
├── Type Conversion
├── Equality
└── Strict Mode

    Statements sit after Expressions because expressions are the values that statements act upon. A statement is a command; an expression is a value. The distinction is fundamental.

    2. Why It Exists

    The Problem

    A programming language that can only compute values cannot do anything. It cannot choose between alternatives, repeat work, handle failure, or clean up resources. Statements solve the control problem: they give programs the ability to direct their own execution.

    But statements create a second problem: where does a statement end? JavaScript answers this with semicolons — and Automatic Semicolon Insertion (ASI), which allows omitting semicolons in many cases but creates subtle pitfalls.

    Previous Limitations

    Era Limitation
    Pre-ES2015 No let/const statements — only var
    No resource management Cleanup required manual try/finally
    No async iteration for...of could not handle async iterables
    No using File handles, connections leaked on exceptions
    Complex conditionals Deep if/else chains for structural matching

    Why New Statement Forms Were Introduced

    • for await...of (ES2018) — iterate async iterables natively.
    • using / await using (ES2026) — deterministic resource cleanup with Symbol.dispose and Symbol.asyncDispose.
    • Pattern matching (Stage 3, ES2026) — declarative structural selection to replace complex if/else and switch chains.

    Each new statement form solves a readability, correctness, or resource-safety problem.

    3. Syntax / Basic Usage

    Declaration Statements

    let x = 10;              // let declaration
const PI = 3.14159;      // const declaration
var legacy = "old";      // var declaration (legacy)
using file = openFile("data.txt");        // ES2026 resource management
await using conn = await openConnection(); // ES2026 async resource management
function greet() {}      // function declaration
class User {}            // class declaration

    Conditional Statements

    // if / else if / else
if (age >= 18) {
    console.log("adult");
} else if (age >= 13) {
    console.log("teen");
} else {
    console.log("child");
}

// switch
switch (status) {
    case "active":
        console.log("Active");
        break;
    case "inactive":
        console.log("Inactive");
        break;
    default:
        console.log("Unknown");
}

    Iteration Statements

    // for
for (let i = 0; i < 3; i++) { console.log(i); }

// for...in — iterates keys
for (const key in obj) { console.log(key); }

// for...of — iterates values
for (const value of arr) { console.log(value); }

// for await...of — iterates async iterables (ES2018)
for await (const chunk of asyncIterable) { console.log(chunk); }

// while
let n = 0;
while (n < 3) { n++; }

// do...while — runs at least once
let m = 0;
do { m++; } while (m < 3);

    for await...of creates a loop iterating over async iterable objects as well as sync iterables. It can only be used in contexts where await can be used — inside an async function body or in a module.

    Jump Statements

    break;              // exit loop or switch
continue;           // skip to next iteration
return value;       // exit function with value
throw new Error();  // throw an exception

    Exception Handling Statements

    try {
    riskyOperation();
} catch (error) {
    console.error(error);
} finally {
    cleanup();
}

    Labelled Statements

    outer: for (let i = 0; i < 3; i++) {
    inner: for (let j = 0; j < 3; j++) {
        if (j === 1) continue outer;
        if (i === 2) break outer;
        console.log(i, j);
    }
}

    A labeled statement is any statement prefixed with an identifier. You can jump to this label using a break or continue statement nested within the labeled statement. break can be used within any labeled statement, and continue can be used within labeled looping statements. JavaScript has no goto — labels can only be used with break or continue.

    Resource Management Statements (ES2026)

    {
    using file = openFile("data.txt");
    // use file
} // file[Symbol.dispose]() called automatically

{
    await using conn = await openConnection();
    // use conn
} // await conn[Symbol.asyncDispose]() called automatically

    Explicit Resource Management reached Stage 4 and is part of ECMAScript 2026. Babel's @babel/plugin-transform-explicit-resource-management transforms using declarations into try/catch/finally patterns.

    Other Statements

    debugger;           // pause execution in DevTools
;                   // empty statement
{ }                 // block statement
"use strict";       // directive (not a statement)

    Automatic Semicolon Insertion (ASI)

    JavaScript automatically inserts semicolons in many cases. However, certain lines require a semicolon if the following line begins with:

    • An opening parenthesis ( — would be treated as a call expression.
    • An opening square bracket [ — would be treated as property access.
    • A template literal ` — would be treated as a tagged template.
    • Unary + or - — would be treated as a binary operator.
    • A RegExp literal — could be parsed as a division operator.
    // ❌ ASI pitfall
const a = 1
const b = 2
[1, 2].forEach(console.log) // parsed as 2[1,2].forEach(...)

    Always use semicolons to avoid ASI pitfalls.

    4. Mental Model

    The "Command vs. Value" Mental Model

    • An expression is a question: "What is 2 + 3?" → 5.
    • A statement is a command: "Add 2 to x and store it."
    Expression: 2 + 3           → value (5)
Statement:  let x = 2 + 3;  → action (bind x to 5)

    If you can put it on the right side of =, it is an expression. If it ends with ; and performs an action, it is a statement.

    The "Control Flow Graph" Mental Model

    Statements form a control flow graph — nodes are statements, edges are possible execution paths:

    [let x = 10] → [if (x > 5)] → true → [x--]
                    ↓
                  false → [console.log(x)]

    Conditionals create branches; loops create cycles; jumps create edges to other nodes.

    The "Block Scope" Mental Model

    Blocks ({ }) create scope:

    {
    let x = 10;  // scoped to this block
    const y = 20;
    using z = resource(); // disposed at block exit
}
// x, y, z not accessible here

    var ignores block scope; let, const, and using respect it.

    The "Statement Ladder" Mental Model

    Statements are organized by purpose:

    Declarations    → create bindings
Control flow    → decide what runs
Iteration       → repeat work
Jumps           → alter order
Exceptions      → handle failures
Resources       → manage cleanup
Debugging       → pause execution

    The "Pipeline of Execution" Mental Model

    Statements execute sequentially by default:

    Statement 1 → Statement 2 → Statement 3 → ...

    Control flow statements alter this sequence:

    • if — skip or execute.
    • Loops — repeat.
    • break — exit early.
    • return — exit function.
    • throw — jump to catch.

    5. Core Concepts

    Concept 1: Statement Categories

    Category Statements
    Declarations let, const, var, using, await using, function, class
    Conditionals if, else, switch
    Loops for, for...in, for...of, for await...of, while, do...while
    Jumps break, continue, return, throw
    Exceptions try, catch, finally
    Labels label:
    Blocks { }
    Empty ;
    Debugger debugger
    Directives "use strict"

    Concept 2: Expression Statements

    An expression becomes a statement when terminated with ;:

    console.log("hello");  // expression statement
x = 10;                // expression statement

    Not all expressions can be statements — object literals need parentheses:

    ({ a: 1 });  // expression statement with object literal

    Concept 3: Block Statements

    {
    let x = 10;
    const y = 20;
}
// x, y not accessible here

    Blocks create scope and group statements. They are required for let/const/using to be block-scoped.

    Concept 4: Conditional Statements

    if — executes a statement if a condition is truthy.

    switch — compares one expression against multiple case values using strict equality (===). Each case should end with break to prevent unintentional fall-through. The default case runs when no other case matches.

    switch (value) {
    case 1:
    case 2:
        // grouped cases — both 1 and 2 run this
        break;
    default:
        break;
}

    Concept 5: Iteration Statements

    Loop Iterates Over Use Case
    for Counter Known iterations
    for...in Enumerable keys Object keys
    for...of Iterable values Arrays, strings, Maps, Sets
    for await...of Async iterables Streams, async generators
    while Condition Unknown iterations
    do...while Condition (runs at least once) Guaranteed first run

    Concept 6: Jump Statements

    break — exits the innermost loop or switch.

    continue — skips to the next iteration.

    return — exits the current function with a value.

    throw — throws an exception.

    for (const x of items) {
    if (x === null) continue;  // skip null
    if (x < 0) break;          // exit loop
    process(x);
}

    Concept 7: Exception Handling

    try {
    risky();
} catch (error) {
    handle(error);
} finally {
    cleanup(); // always runs
}

    finally runs regardless of whether an exception was thrown or caught. It is the primary mechanism for cleanup before using.

    Concept 8: Labelled Statements

    Labels identify statements for break or continue:

    outer: for (let i = 0; i < 3; i++) {
    for (let j = 0; j < 3; j++) {
        if (j > i) continue outer;
        console.log(i, j);
    }
}

    break label; exits the labeled statement; continue label; continues the labeled loop. A statement can have multiple labels, all functionally equivalent.

    Concept 9: Resource Management with using (ES2026)

    {
    using file = openFile("data.txt");
    // file[Symbol.dispose]() called at block exit
}
    • using — synchronous disposal via Symbol.dispose.
    • await using — asynchronous disposal via Symbol.asyncDispose.
    • Disposal happens in reverse order (LIFO).
    • Works with try/catch — disposal runs even on exceptions.

    Concept 10: for await...of (ES2018)

    async function* fetchPages() {
    yield await fetch("/page/1");
    yield await fetch("/page/2");
}

for await (const page of fetchPages()) {
    console.log(page);
}

    for await...of first gets the iterable's [Symbol.asyncIterator]() method. If it does not exist, it falls back to [Symbol.iterator](). It can only be used inside async functions or modules.

    Concept 11: switch vs. Pattern Matching (Stage 3, ES2026)

    switch compares one value against multiple cases using ===. Pattern matching (Stage 3) extends this with destructuring, type checks, and guard conditions:

    // switch (current)
switch (status) {
    case "active": return true;
    default: return false;
}

// Pattern matching (proposed)
return status match {
    "active" => true,
    _ => false,
};

    Pattern matching is a cleaner and more expressive way to replace complex if...else and switch statements. It is Stage 3 — not yet standard.

    Concept 12: Automatic Semicolon Insertion (ASI)

    JavaScript inserts semicolons at line breaks in many cases. But ASI has restricted productions — contexts where a line terminator is not allowed:

    • return followed by a newline.
    • throw followed by a newline.
    • Postfix ++/-- followed by a newline.
    • continue/break followed by a newline.
    • Arrow function => followed by a newline.
    // ❌ ASI pitfall — returns undefined
function f() {
    return
        { value: 10 };
}

// ✅ Correct
function f() {
    return { value: 10 };
}

    Concept 13: Directives

    "use strict";  // strict mode directive

    Directives are expression statements that appear at the start of a script or function. They are not string literals — they are syntax with special meaning. ES modules and classes are strict by default.

    Concept 14: Empty Statement

    ;  // does nothing

    Used when a statement is syntactically required but no action is needed:

    for (let i = 0; i < 3; i++);  // empty body

    Concept 15: debugger Statement

    debugger;  // pauses execution when DevTools is open

    No effect when DevTools is closed. Essential for interactive debugging.

    6. How It Works

    Step-by-Step: Statement Execution

    1.  Parser reads statement text.
    │
    ▼
2.  AST node is created.
    │
    ▼
3.  Engine evaluates the statement.
    │
    ▼
4.  Control flow determines next statement.
    │
    ▼
5.  Repeat until program ends.

    Step-by-Step: if Execution

    1.  Condition expression is evaluated.
    │
    ▼
2.  Result is coerced to boolean.
    │
    ▼
3.  If truthy → execute consequent.
    │
    ▼
4.  If falsy and `else` exists → execute alternate.
    │
    ▼
5.  Continue to next statement.

    Step-by-Step: switch Execution

    1.  Discriminant expression is evaluated.
    │
    ▼
2.  Each case value is compared using ===.
    │
    ▼
3.  First matching case is entered.
    │
    ▼
4.  Execution continues until break or end.
    │
    ▼
5.  If no match and default exists → default runs.

    Step-by-Step: try/catch/finally Execution

    1.  `try` block executes.
    │
    ▼
2.  If exception thrown → `catch` block executes.
    │
    ▼
3.  If no exception → `catch` skipped.
    │
    ▼
4.  `finally` always executes.
    │
    ▼
5.  Control resumes after `try` statement.

    Step-by-Step: using Disposal (ES2026)

    1.  `using x = acquire()` executes.
    │
    ▼
2.  Resource is registered with block's disposal list.
    │
    ▼
3.  Block body executes.
    │
    ▼
4.  Block exits (normal or exception).
    │
    ▼
5.  Resources disposed in reverse order.
    │
    ▼
6.  Scope exits.

    Step-by-Step: for await...of Execution

    1.  Iterable's [Symbol.asyncIterator]() is called.
    │
    ▼
2.  If not present, [Symbol.iterator]() is used.
    │
    ▼
3.  `next()` is called and awaited.
    │
    ▼
4.  If done → loop ends.
    │
    ▼
5.  If not done → value is assigned, body executes.
    │
    ▼
6.  Repeat from step 3.

    7. Internal Architecture / Under the Hood

    Statement Compilation

    V8 compiles statements into bytecode in Ignition. Control flow statements compile to conditional jumps and loops in the bytecode. Hot loops are optimized by Sparkplug, Maglev, and TurboFan.

    The AST

    Statements become statements nodes in the AST:

    Program
├── VariableDeclaration
│   └── VariableDeclarator
├── IfStatement
│   ├── test (expression)
│   ├── consequent (statement)
│   └── alternate (statement)
├── ForStatement
│   ├── init
│   ├── test
│   ├── update
│   └── body
└── TryStatement
    ├── block
    ├── handler
    └── finalizer

    Completion Records

    Every statement returns a Completion Record:

    {
    [[Type]]: normal | break | continue | return | throw,
    [[Value]]: any,
    [[Target]]: label
}

    This is how the engine tracks control flow — whether execution continues normally, jumps, returns, or throws.

    using in the Spec

    using is implemented via DisposableStack and AsyncDisposableStack — internal data structures that track resources and dispose them in reverse order. Babel transforms using into try/catch/finally patterns with _usingCtx helpers.

    for await...of in the Spec

    for await...of uses AsyncIteratorClose and IteratorClose abstract operations to ensure cleanup. It awaits each next() call and handles both sync and async iterables.

    ASI in the Parser

    ASI is applied during parsing. When a line terminator is encountered and the next token cannot continue the statement, a semicolon is inserted. Restricted productions (return, throw, break, continue, postfix ++/--) have special rules.

    8. Lifecycle / Workflow

    Statement Execution Lifecycle

    Parse → Build AST → Compile to bytecode → Execute → Completion Record → Next statement

    Control Flow Lifecycle

    Sequential → Condition evaluated → Branch taken → Statements execute → Continue

    Loop Lifecycle

    Initialize → Test condition → Execute body → Update → Test condition → ... → Exit

    Exception Lifecycle

    try executes → Exception thrown → Unwind stack → catch executes → finally executes → Resume

    using Lifecycle

    using x = acquire() → Register resource → Execute block → Dispose in reverse order → Exit

    Development Workflow

    Write statements → Lint (ESLint) → Type-check (TypeScript) → Run → Debug

    ESLint rules like no-fallthrough, no-unreachable, and no-constant-condition catch statement mistakes.

    9. Practical Examples

    Example 1: Conditional Statement

    function getAccess(role) {
    if (role === "admin") return "full";
    if (role === "editor") return "edit";
    return "read";
}

    Example 2: switch with Grouped Cases

    function getDayType(day) {
    switch (day) {
        case "sat":
        case "sun":
            return "weekend";
        case "mon":
        case "tue":
        case "wed":
        case "thu":
        case "fri":
            return "weekday";
        default:
            return "invalid";
    }
}

    Example 3: for...of with break and continue

    for (const item of items) {
    if (!item.active) continue;
    if (item.critical) break;
    process(item);
}

    Example 4: Labelled Loops

    search: for (let i = 0; i < grid.length; i++) {
    for (let j = 0; j < grid[i].length; j++) {
        if (grid[i][j] === target) {
            console.log(`Found at ${i},${j}`);
            break search;
        }
    }
}

    Example 5: try/catch/finally

    function readConfig(path) {
    let file;
    try {
        file = openFile(path);
        return JSON.parse(file.read());
    } catch (err) {
        console.error("Failed to read config:", err);
        return null;
    } finally {
        file?.close();
    }
}

    Example 6: Resource Management with using (ES2026)

    function processData(path) {
    using file = openFile(path);
    const data = file.read();
    return JSON.parse(data);
    // file is disposed automatically — even on parse error
}

    Example 7: for await...of (ES2018)

    async function* streamPages(url) {
    while (url) {
        const res = await fetch(url);
        const page = await res.json();
        yield* page.items;
        url = page.next;
    }
}

const allItems = [];
for await (const item of streamPages("/api/items")) {
    allItems.push(item);
}

    Example 8: Pattern Matching (Stage 3, Proposed)

    function describe(value) {
    return value match {
        0 => "zero",
        n when n > 0 => `positive: ${n}`,
        n when n < 0 => `negative: ${n}`,
        _ => "unknown",
    };
}

    Pattern matching is Stage 3 — not yet standard. It provides a cleaner alternative to complex if/else and switch chains.

    Example 9: ASI Pitfall

    // ❌ ASI inserts semicolon after `return`
function f() {
    return
        { value: 10 };
}
console.log(f()); // undefined

// ✅ Correct
function f() {
    return { value: 10 };
}
console.log(f()); // { value: 10 }

    11. Best Practices

    1. Use const by default, let when reassigning. Why: prevents accidental mutation.
    2. Always use braces with if/for/while. Why: prevents dangling-else and scope bugs.
    3. Always use break in switch cases. Why: prevents unintentional fall-through.
    4. Use for...of over for...in for arrays. Why: for...in iterates keys and inherited properties.
    5. Use for await...of for async iterables. Why: native async iteration (ES2018).
    6. Use using for resources needing cleanup. Why: deterministic disposal even on exceptions (ES2026).
    7. Use labels sparingly. Why: they can make code harder to follow.
    8. Always use semicolons. Why: avoids ASI pitfalls.
    9. Never use return with a newline before the value. Why: ASI inserts a semicolon, returning undefined.
    10. Use try/catch for recoverable errors only. Why: not all errors should be caught.
    11. Use finally for cleanup that must always run. Why: guaranteed execution.
    12. Prefer pattern matching when it reaches Stage 4. Why: declarative and concise (currently Stage 3).
    13. Use debugger instead of console.log for complex debugging. Why: interactive inspection.
    14. Lint with no-fallthrough, no-unreachable, no-constant-condition. Why: catches statement mistakes.
    15. Keep statements small and focused. Why: readability and testability.

    12. Common Mistakes

    ❌ Mistake: Missing break in switch

    switch (x) {
    case 1:
        console.log("one");
    case 2:
        console.log("two"); // runs for x === 1 too!
}

    ✅ Correct:

    switch (x) {
    case 1:
        console.log("one");
        break;
    case 2:
        console.log("two");
        break;
}

    ❌ Mistake: return with Newline

    function f() {
    return
        { value: 10 }; // ASI inserts semicolon → returns undefined
}

    ✅ Correct:

    function f() {
    return { value: 10 };
}

    ❌ Mistake: for...in on Arrays

    for (const i in arr) { console.log(arr[i]); } // iterates inherited properties too

    ✅ Correct:

    for (const value of arr) { console.log(value); }

    ❌ Mistake: Missing Braces

    if (x > 5)
    console.log("big");
    console.log("always"); // NOT part of the if!

    ✅ Correct:

    if (x > 5) {
    console.log("big");
    console.log("always");
}

    ❌ Mistake: continue in switch

    switch (x) {
    case 1:
        continue; // ❌ SyntaxError outside loop
}

    ✅ Correct: Use break in switch.

    ❌ Mistake: Forgetting await in for await...of

    for (const x of asyncIterable) {} // ❌ not async

    ✅ Correct:

    for await (const x of asyncIterable) {}

    ❌ Mistake: Using using Outside a Block

    using file = openFile("a.txt"); // at top level — disposes at module exit

    Why it's wrong: Top-level using disposes at module exit, not immediately.

    ✅ Correct: Use using inside a block for deterministic disposal.

    ❌ Mistake: Assuming Pattern Matching Is Standard

    Pattern matching is Stage 3 — not standard.

    ✅ Correct: Use with a transpiler and track the proposal.

    ❌ Mistake: Unreachable Code After return

    function f() {
    return 1;
    console.log("never"); // unreachable
}

    ✅ Correct: Remove unreachable code.

    ❌ Mistake: Constant Conditions

    if (false) { /* never runs */ }

    ✅ Correct: Remove dead code.

    13. Performance Considerations

    • Loop overhead — for loops are generally fastest; for...of has iterator overhead.
    • for...in — slowest; iterates inherited properties.
    • switch — optimized by engines; can be faster than if/else chains for many cases.
    • try/catch — deoptimizes functions in some engines; avoid in hot paths.
    • using — adds disposal registry; overhead proportional to resource count.
    • for await...of — async overhead per iteration; use for I/O, not CPU-bound loops.
    • ASI — parser-level; no runtime cost.
    • Labels — no runtime cost; purely syntactic.

    Performance Tips

    1. Use for for counter-based loops in hot paths.
    2. Use for...of for readability — optimize later if needed.
    3. Avoid try/catch in hot loops.
    4. Use switch for multi-way branching.
    5. Keep loop bodies small.
    6. Profile with --trace-opt / --trace-deopt.

    14. Security Considerations

    eval and Function

    Never evaluate untrusted strings as statements. Use JSON.parse for data.

    Prototype Pollution in for...in

    for...in iterates inherited properties — including polluted ones.

    Defense: Use Object.hasOwn() or for...of with Object.keys().

    try/catch and Error Masking

    Catching all errors can hide security-relevant failures.

    Defense: Catch specific errors; re-throw unexpected ones.

    using and Resource Exhaustion

    using guarantees disposal — preventing file handle and connection leaks.

    Label Injection

    Labels are syntactic — no injection risk.

    ASI and Security

    ASI can cause unexpected parsing — a potential source of bugs with security implications.

    Defense: Always use semicolons.

    15. Debugging Tips

    • debugger; — pause in DevTools.
    • console.log — print values.
    • console.trace — print stack trace.
    • ESLint no-fallthrough — flags missing break.
    • ESLint no-unreachable — flags dead code.
    • ESLint no-constant-condition — flags always-true/false conditions.
    • Chrome DevTools Sources panel — set breakpoints on statements.
    • Node.js --inspect-brk — debug statements in Node.
    • try/catch with console.error — log exceptions.

    17. When Not to Use

    • var — never in new code.
    • for...in on arrays — use for...of.
    • switch without break — unless fall-through is intentional.
    • try/catch for control flow — use conditionals.
    • Labels — when simpler structure suffices.
    • debugger in production — remove before deploy.
    • Pattern matching in production — Stage 3; may change.
    • using at top level — disposes at module exit, not immediately.

    20. Summary

    • A statement expresses an action; an expression produces a value.
    • Declaration statements — let, const, var, using, await using, function, class.
    • Conditional statements — if/else, switch.
    • Iteration statements — for, for...in, for...of, for await...of, while, do...while.
    • Jump statements — break, continue, return, throw.
    • Exception handling — try/catch/finally.
    • Labelled statements — break label;, continue label; — no goto.
    • Resource management — using / await using (ES2026) with Symbol.dispose / Symbol.asyncDispose.
    • for await...of — async iteration (ES2018).
    • Pattern matching — Stage 3 proposal, cleaner than switch.
    • ASI — automatic semicolon insertion; always use semicolons to avoid pitfalls.
    • Best practices — const by default, braces always, break in switch, for...of over for...in.
    • ES2026 added using, await using, Array.fromAsync, Error.isError, Math.sumPrecise, and more.
    • Statements are the control layer — they decide what happens, when, and in what order.
