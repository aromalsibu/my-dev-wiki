# Setting Up a Database

Create a database class that manages your tables, database connection, and schema.

---

# What is it?

A Drift database is the central class that represents your application's SQLite database. It defines which tables belong to the database, manages the connection to SQLite, and provides the entry point for performing queries.

Every interaction with your database—whether inserting, updating, deleting, or querying data—starts from this class.

---

# Why does it exist?

Instead of interacting with SQLite directly, Drift uses a database class to:

* Group related tables into a single database.
* Provide a type-safe API for queries.
* Manage the database connection.
* Track the database schema version.
* Generate helper methods and data classes.

This gives your application a single, organized interface for working with the database.

---

# Syntax

## Define a Database Class

```dart
import 'package:drift/drift.dart';

part 'app_database.g.dart';

@DriftDatabase(tables: [Users, Todos])
class AppDatabase extends _$AppDatabase {
  AppDatabase(super.executor);

  @override
  int get schemaVersion => 1;
}
```

Explanation:

* `part 'app_database.g.dart'` includes the generated code.
* `@DriftDatabase` marks the class as a Drift database.
* `tables` lists every table managed by this database.
* `_$AppDatabase` is generated by Drift.
* `super.executor` provides the database connection.
* `schemaVersion` identifies the current database schema version.

---

## Create a Database Instance

```dart
final database = AppDatabase(databaseConnection);
```

Explanation:

* `databaseConnection` is a database executor that opens and communicates with SQLite.
* Once created, the database instance can be reused throughout your application.

---

# Mental Model

Think of the database class as the application's database manager.

```text
App
 │
 ▼
AppDatabase
 │
 ├── Users Table
 ├── Todos Table
 ├── Posts Table
 │
 ▼
SQLite Database
```

Instead of each table connecting to SQLite independently, the database class manages them all through a single connection.

# Examples

## Simple Example

A database with a single table.

```dart
@DriftDatabase(tables: [Users])
class AppDatabase extends _$AppDatabase {
  AppDatabase(super.executor);

  @override
  int get schemaVersion => 1;
}
```

Explanation:

* The database contains only the `Users` table.
* Drift generates APIs for querying and modifying users.

---

## Real-World Example

A task management application might have:

```dart
@DriftDatabase(
  tables: [
    Users,
    Projects,
    Tasks,
    Comments,
    Labels,
  ],
)
class AppDatabase extends _$AppDatabase {
  AppDatabase(super.executor);

  @override
  int get schemaVersion => 3;
}
```

Explanation:

* Multiple related tables are grouped into a single database.
* Increasing `schemaVersion` indicates that the database structure has changed.

---

# When to Use

Create a database class when:

* Starting a new Drift project.
* Managing one or more tables.
* Organizing your application's local storage.
* Providing a central API for database operations.

---

# When NOT to Use

Avoid creating multiple database classes unless your application genuinely requires separate databases.

For most applications, a single database containing multiple tables is easier to manage and maintain.

---

# Best Practices

* Keep a single database class for most applications.
* Organize table definitions into separate files.
* Register all tables inside the `@DriftDatabase` annotation.
* Keep the database class focused on configuration.
* Move complex queries into DAOs instead of placing them directly in the database class.

---

# Common Mistakes

## Forgetting the generated part file

**Wrong**

```dart
@DriftDatabase(tables: [Users])
class AppDatabase extends _$AppDatabase {}
```

Explanation:

* Without the `part` directive, the generated code cannot be linked.

**Correct**

```dart
part 'app_database.g.dart';
```

Explanation:

* Includes the generated implementation.

---

## Not registering a table

**Wrong**

```dart
@DriftDatabase(tables: [])
```

Explanation:

* Drift won't generate APIs for tables that aren't registered.

**Correct**

```dart
@DriftDatabase(tables: [Users])
```

Explanation:

* Every table used by the database should be listed here.

---

## Placing business logic inside the database

**Wrong**

```dart
class AppDatabase extends _$AppDatabase {
  Future<void> completeProjectAndNotifyUsers() async {
    // Large amount of application logic...
  }
}
```

Explanation:

* Mixing business logic with database configuration makes the class harder to maintain.

**Correct**

* Keep the database responsible for persistence.
* Place complex query logic in DAOs and business logic in repositories or services.
