# Custom Data Classes

Custom data classes let you use your own Dart classes instead of Drift's generated data classes.

---

# What is it?

By default, Drift generates a data class for every table.

For example:

```text
Users Table
      │
      ▼
Generated User class
```

However, Drift also allows you to use your own Dart class to represent rows from a table.

This gives you complete control over the structure, behavior, and APIs of your data objects.

---

# Why does it exist?

Generated data classes are suitable for most applications, but sometimes you need more control.

For example, you might want to:

* Use an existing domain model.
* Add custom methods.
* Add computed properties.
* Integrate with another architecture.
* Share models between different data sources.

Custom data classes let you keep your application's models independent from Drift's generated code.

---

# Syntax

## Using a Custom Data Class

```dart
class User {
  final int id;
  final String name;

  const User({
    required this.id,
    required this.name,
  });
}
```

Explanation:

* This is your own Dart class.
* It is not generated by Drift.
* You decide its fields, constructors, and methods.

> **Note:** Configuring Drift to use custom row classes requires additional annotations and mapping, which are covered in the official Drift documentation and advanced configuration guides.

---

# Mental Model

Think of the data class as the object your application works with.

```text
Database Row
      │
      ▼
Mapping
      │
      ▼
Your User Class
```

Instead of using Drift's generated object, the row is represented by your own class.

---

# Examples

## Simple Example

A custom product model.

```dart
class Product {
  final int id;
  final String name;
  final double price;

  const Product({
    required this.id,
    required this.name,
    required this.price,
  });
}
```

Explanation:

* The class is completely independent of Drift.
* Additional methods or properties can be added as needed.

---

## Real-World Example

A richer domain model.

```dart
class User {
  final int id;
  final String firstName;
  final String lastName;

  const User({
    required this.id,
    required this.firstName,
    required this.lastName,
  });

  String get fullName => '$firstName $lastName';
}
```

Explanation:

* The class includes computed properties.
* Business-related behavior can live alongside the data.

---

# When to Use

Use custom data classes when:

* Your project already has domain models.
* You follow Clean Architecture.
* You want additional methods or computed properties.
* Models are shared across multiple layers.
* You need complete control over your data objects.

---

# When NOT to Use

Avoid custom data classes when:

* You're building a small application.
* Drift's generated data classes meet your needs.
* You don't need custom behavior.

Generated data classes are simpler and require less configuration.

---

# Best Practices

* Prefer generated data classes unless customization is necessary.
* Keep custom models focused on your application's domain.
* Avoid duplicating generated classes without a clear reason.
* Separate persistence concerns from business logic when appropriate.
* Use meaningful methods and computed properties instead of duplicating data.

---

# Common Mistakes

## Creating custom classes unnecessarily

**Wrong**

Creating custom classes that contain exactly the same fields as the generated data classes without adding any new behavior.

Explanation:

* This increases maintenance without providing additional value.

**Correct**

Use generated data classes unless your application benefits from custom models.

---

## Mixing generated and custom models inconsistently

**Wrong**

Using generated data classes in some parts of the application and custom models in others without a clear conversion strategy.

Explanation:

* This can make the codebase harder to understand and maintain.

**Correct**

Choose a consistent approach and map between models when necessary.

---

## Putting database-specific logic in domain models

**Wrong**

Adding Drift-specific APIs or persistence logic directly to your custom data classes.

Explanation:

* This tightly couples your models to the database implementation.

**Correct**

Keep custom data classes focused on representing your application's data and behavior.

# Summary

Custom data classes allow you to replace Drift's generated row classes with your own Dart models. They are useful when your application requires richer domain models, shared business objects, or additional behavior. For most applications, however, the generated data classes are sufficient and provide the simplest development experience.
