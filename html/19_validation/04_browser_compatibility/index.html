    Browser Compatibility

    1. Overview

    Definition

    Browser compatibility is the practice of building web pages and applications that function correctly — structurally, visually, and behaviorally — across all browsers and devices that a target audience uses. It is the discipline of understanding what works where, what degrades gracefully, and what requires a fallback.

    <!-- Works everywhere: progressive enhancement -->
<button type="button">Save</button>

<!-- Works in modern browsers; older browsers ignore unknown attributes -->
<input type="text" autocomplete="off" inputmode="numeric" enterkeyhint="done">

<!-- Feature-detected enhancement -->
<script>
    if ('IntersectionObserver' in window) {
        // Use IntersectionObserver
    } else {
        // Fallback to scroll listener
    }
</script>

    Browser compatibility is not about supporting every browser ever made. It is about deliberately choosing which browsers to support, understanding the feature landscape for those browsers, and implementing the right fallbacks where needed.

    The question is no longer "does this work in IE?" — Internet Explorer was officially retired on June 15, 2022 [9†L40-L42]. The question in 2026 is: "What is Baseline for this feature, and does my target audience fall within Baseline?"

    Purpose

    Browser compatibility serves several essential purposes:

    • Universal access — users on any browser can access content.
    • Consistent experience — the page works predictably across engines.
    • Progressive enhancement — modern features enhance; core functionality works everywhere.
    • Graceful degradation — older browsers get a functional fallback.
    • Cost management — supporting too many browsers is expensive.
    • Legal compliance — some regulations require compatibility with specific browsers.
    • Performance — modern browsers get optimized experiences.
    • Future-proofing — the site works in browsers that do not exist yet.

    Where It Fits

    Validation
│
├── HTML Validator          ← markup correctness
├── Common Errors           ← frequent validation errors
├── Accessibility Validation ← automated a11y checks
├── Browser Compatibility   ← cross-browser testing (THIS CHAPTER)
└── Debugging HTML          ← tools and techniques

    Browser Compatibility is the final validation layer. Valid HTML, accessible markup, and error-free pages all mean nothing if the page does not work in the user's browser.

    2. Why It Exists

    The Problem

    The web is not a single platform. It is a collection of engines — Blink (Chrome, Edge, Opera, Brave), Gecko (Firefox), WebKit (Safari, iOS browsers) — each with its own implementation of the standards. When a new feature ships in Chrome, it may take months or years to reach Safari. When Safari implements a feature differently, code that works in one browser breaks in another.

    ┌─────────────────────────────────────────────┐
│  BLINK (Chrome, Edge, Opera, Brave)          │
│  └── Largest market share                    │
│  └── Fastest feature adoption                │
├─────────────────────────────────────────────┤
│  GECKO (Firefox)                             │
│  └── Independent implementation              │
│  └── Strong standards focus                  │
├─────────────────────────────────────────────┤
│  WEBKIT (Safari, iOS browsers)               │
│  └── iOS requires WebKit for all browsers    │
│  └── Slower feature adoption historically    │
│  └── Unique iOS-specific constraints         │
└─────────────────────────────────────────────┘

    A developer writing code in Chrome cannot assume it works in Safari. A feature that is "widely supported" may have subtle implementation differences. Cross-browser compatibility exists to manage these differences deliberately.

    Previous Limitations

    Limitation Consequence
    No feature support data Developers guessed what worked
    No market share data Hard to prioritize which browsers to support
    No baseline standard Every feature required manual research
    Vendor prefixes -webkit-, -moz-, -ms- everywhere
    No polyfill ecosystem Every feature required custom fallback code
    No testing infrastructure Real-device testing was manual and slow
    IE legacy Years of hacks for a single browser

    Why It Was Introduced

    Browser compatibility has been a concern since the first browser wars of the 1990s. But the modern approach was shaped by:

    • 2006 — jQuery launched, abstracting away browser differences.
    • 2008 — Can I Use launched, providing feature support data.
    • 2015 — Autoprefixer automated vendor prefixing.
    • 2019 — Babel and @babel/preset-env made transpilation standard.
    • 2023 — Baseline launched, providing a unified compatibility standard.
    • 2024–2026 — Baseline adopted by GitLab, MDN, and major frameworks.

    Baseline, maintained by the W3C WebDX Community Group, defines two tiers:

    Tier Meaning Adoption
    Baseline Newly available Interoperable across Chrome, Edge, Firefox, and Safari 13.9% of users
    Baseline Widely available Interoperable for 30+ months 98.0% of users

    A feature that is Baseline Newly available works in all current browsers but may not work in older versions. A feature that is Baseline Widely available has been stable for at least 30 months and is safe to use without fallbacks in most production environments.

    In 2026, browser compatibility is not about checking every feature manually. It is about knowing the Baseline status of each feature and choosing a support target for your audience.

    4. Mental Model

    The "Three Engines" Mental Model

    In 2026, there are three major browser engines:

    ┌─────────────────────────────────────────────┐
│  BLINK                                       │
│  ├── Chrome (desktop, Android)               │
│  ├── Edge                                    │
│  ├── Opera                                   │
│  ├── Brave                                   │
│  ├── Vivaldi                                 │
│  └── Arc                                     │
├─────────────────────────────────────────────┤
│  GECKO                                       │
│  └── Firefox (desktop, Android)              │
├─────────────────────────────────────────────┤
│  WEBKIT                                      │
│  ├── Safari (macOS, iOS)                     │
│  └── All iOS browsers (required)             │
└─────────────────────────────────────────────┘

    If a feature works in all three engines, it is Baseline. If it works in only one or two, it is limited availability.

    The "Baseline Decision" Mental Model

    ┌─────────────────────────────────────────────┐
│  IS THE FEATURE BASELINE?                    │
│                                              │
│  YES → Use it. No fallback needed.           │
│                                              │
│  NO → Is it critical to functionality?       │
│       │                                      │
│       ├── YES → Use a polyfill or fallback   │
│       │                                      │
│       └── NO  → Progressive enhancement      │
│                  (use where supported)        │
└─────────────────────────────────────────────┘

    The Baseline standard gives a clear answer to the compatibility question.

    The "Progressive Enhancement" Mental Model

    ┌─────────────────────────────────────────────┐
│  LAYER 1: CORE FUNCTIONALITY                 │
│  └── Works in every browser                  │
│  └── HTML, basic CSS, basic JS               │
│  └── Always present                          │
├─────────────────────────────────────────────┤
│  LAYER 2: ENHANCED EXPERIENCE                │
│  └── Works in modern browsers                │
│  └── CSS Grid, Flexbox, modern APIs          │
│  └── Applied via @supports or feature detection │
├─────────────────────────────────────────────┤
│  LAYER 3: OPTIONAL EXTRAS                    │
│  └── Works in cutting-edge browsers          │
│  └── View Transitions, Anchor Positioning    │
│  └── Bonus for users who have them           │
└─────────────────────────────────────────────┘

    Build for Layer 1. Enhance for Layer 2. Experiment with Layer 3.

    ┌─────────────────────────────────────────────┐
│  MARKET SHARE (2026)                         │

└─────────────────────────────────────────────┘

    Market share tells you who is using which browser. Baseline tells you whether a feature works in all browsers. You need both to make good decisions.

    The "Fallback Strategy" Mental Model

    ┌─────────────────────────────────────────────┐
│  FEATURE IS BASELINE                         │
│  └── No fallback needed                      │
├─────────────────────────────────────────────┤

    Not every non-Baseline feature needs a fallback. Some features are enhancements — if they do not work, the page still functions.

    ┌─────────────────────────────────────────────┐
│  QUESTION: Which browsers must work?         │
│                                              │

    There is no universal answer. The support target is a business decision, not a technical one.

    5. Core Concepts

    Concept 1: Baseline

    The Web Platform Baseline defines whether a feature is interoperable across Chrome, Edge, Firefox, and Safari. Maintained by the W3C WebDX Community Group.

    Concept 2: Baseline Newly Available

    The feature works in all current browsers. 13.9% of users have a browser that supports the full Baseline Newly available set.

    Concept 3: Baseline Widely Available

    The feature has been interoperable for 30+ months. 98.0% of users have a browser that supports the full Baseline Widely available set.

    Concept 4: The Three Engines

    Blink (Chrome, Edge), Gecko (Firefox), WebKit (Safari). A feature is Baseline if it works in all three.

    Concept 5: Market Share

    Google Chrome dominates with ~65% global share. Safari is second at ~18%. Edge and Firefox are smaller.

    Concept 6: The Recommended Support Target

    Latest 2 versions of Chrome, Edge, Firefox, Safari; current and previous iOS version; current Chrome for Android.

    Concept 7: Feature Detection

    Checking at runtime whether a feature exists before using it. 'IntersectionObserver' in window, CSS.supports().

    Concept 8: CSS @supports

    A CSS feature query that applies styles only if the browser supports a given property-value pair.

    Concept 9: Polyfills

    JavaScript code that implements a feature in browsers that do not support it natively. Polyfills should be loaded conditionally.

    Concept 10: Transpilation

    Converting modern JavaScript (ES2020+) to older syntax (ES5) using tools like Babel.

    Concept 11: Autoprefixer

    A tool that adds vendor prefixes to CSS based on the target browsers.

    Concept 12: browserslist

    A configuration format for specifying target browsers, used by Babel, Autoprefixer, and other tools.

    Concept 13: Can I Use

    The primary database of browser feature support.

    Concept 14: MDN Baseline Badges

    MDN shows Baseline status for every feature page.

    Concept 15: Web Platform Status

    The webstatus.dev dashboard shows Baseline status for every feature.

    Concept 16: Internet Explorer Is Retired

    IE 11 was officially retired on June 15, 2022. It is no longer a supported browser.

    Concept 17: Edge (EdgeHTML) Is Retired

    The original EdgeHTML engine was replaced by Chromium in Edge 79 (2020).

    Concept 18: Safari on iOS

    All browsers on iOS must use WebKit. This means Chrome on iOS is effectively Safari.

    Concept 19: Container Queries

    Container Queries became Baseline Widely available on August 14, 2025.

    Concept 20: Subgrid

    Subgrid became Baseline Widely available in June 2026.

    Concept 21: Temporal API

    Firefox 139 shipped Temporal unflagged in May 2025. Chrome 144 and Edge 144 shipped Temporal in 2026. Safari's support was still pending as of mid-2026.

    Concept 22: WebGPU

    WebGPU's Baseline availability was blocked since January 2026 by Firefox, with an 8-month gap.

    Concept 23: Feature Queries in CSS

    @supports allows conditional CSS based on feature support. Example: @supports (grid-template-columns: subgrid) { ... }.

    Concept 24: Polyfill Caveats

    The perfect polyfill is hard to find. Most have caveats, performance impacts, or maintenance risks. Understand the polyfill before using it.

    Concept 25: Baseline Year

    Instead of targeting "Widely available," you can target a specific Baseline year (e.g., 2023, 2024). This allows you to use features from that year and later without fallbacks.

    7. Internal Architecture / Under the Hood

    The Baseline Algorithm

    Baseline is determined by the W3C WebDX Community Group:

    1. A feature is proposed.
    2. Browser vendors implement it.
    3. When Chrome, Edge, Firefox, and Safari all ship it, it becomes Baseline Newly available.
    4. After 30 months of stable support, it becomes Baseline Widely available.

    The 30-month window ensures that users on older browser versions are not left behind.

    The Market Share Data

    Global browser market share (2026):

    Browser Share
    Chrome ~65%
    Safari ~18%
    Edge ~5%
    Firefox ~3%
    Samsung Internet ~3%
    Other ~6%

    On Windows, Chrome accounts for 69.3%, Edge 18.5%, Firefox 6.6%, Opera 2.7%, Brave 1.6%.

    The Three Engines

    Engine Browsers Market Share
    Blink Chrome, Edge, Opera, Brave, Vivaldi, Arc ~73%
    WebKit Safari (macOS, iOS) ~18%
    Gecko Firefox ~3%

    The Polyfill Architecture

    Polyfills typically:

    1. Detect whether the feature is missing.
    2. Provide a JavaScript implementation.
    3. Patch the global scope (e.g., window.IntersectionObserver).

    Polyfills are loaded conditionally — only when the feature is missing.

    The CSS @supports Architecture

    @supports is a conditional group rule in CSS:

    @supports (condition) {
    /* Applied only if condition is true */
}

    The condition can be:

    • A property-value pair: (display: grid).
    • A conjunction: (display: grid) and (gap: 1rem).
    • A disjunction: (display: grid) or (display: flex).
    • A negation: not (display: grid).

    9. Practical Examples

    Example 1: Checking Baseline on MDN

    1.  Visit developer.mozilla.org/en-US/docs/Web/CSS/CSS_grid_layout
2.  Look for the Baseline badge:
    ✅ Baseline Widely available
3.  The feature is safe to use.

    Code Breakdown:

    • MDN shows Baseline status for every feature.
    • ✅ Widely available — safe to use.
    • ⚠️ Newly available — use with caution.
    • ❌ Limited availability — use with fallback.

    Example 2: The @supports Fallback

    /* Base: Flexbox (works everywhere) */
.card-grid {
    display: flex;
    flex-wrap: wrap;
    gap: 1rem;
}

.card {
    flex: 1 1 300px;
}

/* Enhanced: CSS Grid (Baseline Widely available) */
@supports (display: grid) {
    .card-grid {
        display: grid;
        grid-template-columns: repeat(auto-fit, minmax(300px, 1fr));
    }
}

    Code Breakdown:

    • Base styles work in every browser.
    • @supports applies Grid styles only where supported.
    • Grid is Baseline Widely available, so the fallback is rarely used.

    Example 3: Feature Detection with Fallback

    // Check for IntersectionObserver
if ('IntersectionObserver' in window) {
    const observer = new IntersectionObserver((entries) => {
        entries.forEach((entry) => {
            if (entry.isIntersecting) {
                entry.target.classList.add('visible');
            }
        });
    });

    document.querySelectorAll('.animate').forEach((el) => {
        observer.observe(el);
    });
} else {
    // Fallback: show everything
    document.querySelectorAll('.animate').forEach((el) => {
        el.classList.add('visible');
    });
}

    Code Breakdown:

    • Modern browsers get the animation.
    • Older browsers get the fallback.
    • No polyfill required.

    Example 4: Polyfill with Dynamic Import

    <script type="module">
    // Check for a feature and load the polyfill only if needed
    if (!('IntersectionObserver' in window)) {
        await import('/polyfills/intersection-observer.js');
    }

    // Now the feature is available
    const observer = new IntersectionObserver(/* ... */);
</script>

    Code Breakdown:

    • The polyfill is loaded only when needed.
    • import() is dynamic — modern browsers only.
    • The polyfill patches the missing feature.

    11. Best Practices

    1. Adopt Baseline as your compatibility standard. Why: it is the 2026 industry standard.
    2. Choose a support target based on your audience. Why: there is no universal answer.
    3. Use feature detection over browser sniffing. Why: browser sniffing is unreliable.
    4. Use @supports for CSS fallbacks. Why: clean, declarative, native.
    5. Use browserslist for tooling configuration. Why: single source of truth.
    6. Use @babel/preset-env for transpilation. Why: automatic target-based transforms.
    7. Use Autoprefixer for vendor prefixes. Why: no more manual prefixes.
    8. Load polyfills conditionally. Why: do not ship polyfills to browsers that do not need them.
    9. Test across Chromium, Firefox, and WebKit. Why: the three engines cover all browsers.
    10. Test on real devices for mobile. Why: emulators do not catch all issues.
    11. Use Playwright for local cross-browser testing. Why: fast, free, reliable.
    12. Use BrowserStack or Sauce Labs for cloud testing. Why: real devices and OS combinations.
    13. Monitor browser analytics. Why: know which browsers your users actually use.
    14. Set Baseline alerts in CI. Why: prevent compatibility regressions.
    15. Use progressive enhancement. Why: core functionality works everywhere.
    16. Use graceful degradation where progressive enhancement is not possible. Why: fallbacks for older browsers.
    17. Do not use browser-specific hacks. Why: they are fragile and hard to maintain.
    18. Do not support Internet Explorer. Why: it was retired in June 2022.
    19. Do not support EdgeHTML. Why: it was replaced by Chromium in 2020.
    20. Do not assume Chrome behavior applies to Safari. Why: WebKit has unique constraints.
    21. Do not ship polyfills for Baseline Widely available features. Why: they are unnecessary.
    22. Evaluate polyfills carefully. Why: most have caveats, performance impacts, or maintenance risks.
    23. Test accessibility across browsers. Why: engine differences affect a11y.
    24. Keep your target browsers up to date. Why: the landscape changes annually.
    25. Document your browser support policy. Why: consistency across the team.

    12. Common Mistakes

    ❌ Mistake: Supporting Internet Explorer

    // IE-specific hacks
if (navigator.userAgent.indexOf('MSIE') !== -1) { ... }

    Why it's wrong: IE 11 was retired on June 15, 2022. No modern site should support it.

    ✅ Correct: Remove IE support from your browserslist and code.

    ❌ Mistake: Using Browser Sniffing

    if (navigator.userAgent.indexOf('Safari') !== -1) {
    // Safari-specific code
}

    Why it's wrong: User agent strings are unreliable and easily spoofed.

    ✅ Correct: Use feature detection.

    ❌ Mistake: Assuming Chrome = Safari

    /* Works in Chrome, not in Safari */
.example { position: sticky; }

    Why it's wrong: Safari has unique implementation differences.

    ✅ Correct: Test in both and use @supports.

    ❌ Mistake: Shipping Polyfills to Everyone

    <script src="/polyfills/all.js"></script>

    Why it's wrong: Wastes bandwidth on browsers that do not need it.

    ✅ Correct: Load polyfills conditionally.

    ❌ Mistake: Not Testing in Firefox

    // Only tested in Chrome

    Why it's wrong: Gecko has different behavior for some APIs.

    ✅ Correct: Test in all three engines.

    ❌ Mistake: Not Testing on Real iOS Devices

    // Tested only in Chrome DevTools

    Why it's wrong: iOS Safari has unique constraints (no beforeunload, limited requestAnimationFrame, etc.).

    ✅ Correct: Test on real iOS devices or BrowserStack.

    ❌ Mistake: Using Non-Baseline Features Without Fallback

    /* Not Baseline yet */
.view-transition { view-transition-name: card; }

    Why it's wrong: Browsers without support see a broken layout.

    ✅ Correct: Use @supports or progressive enhancement.

    ❌ Mistake: No Browser Support Policy

    <!-- No documented target browsers -->

    Why it's wrong: Inconsistent decisions across the team.

    ✅ Correct: Document the support target in .browserslistrc.

    ❌ Mistake: Manual Vendor Prefixes

    .example {
    -webkit-transform: translateX(10px);
    -moz-transform: translateX(10px);
    -ms-transform: translateX(10px);
    transform: translateX(10px);
}

    Why it's wrong: Error-prone and unnecessary.

    ✅ Correct: Use Autoprefixer.

    ❌ Mistake: Not Monitoring Browser Analytics

    <!-- No idea which browsers users use -->

    Why it's wrong: The support target may not match the actual audience.

    ✅ Correct: Review analytics quarterly.

    13. Performance Considerations

    • Transpiled code is larger — ES5 output is larger than ES2020 input.
    • Polyfills add weight — load them conditionally.
    • Feature detection is cheap — a simple in check.
    • @supports is parsed once — negligible cost.
    • Multiple browser builds — module/nomodule doubles the build output.
    • Cloud testing is slower than local — use Playwright for fast feedback.

    Performance Tips

    1. Use module/nomodule to avoid shipping modern code to older browsers.
    2. Load polyfills conditionally with dynamic import.
    3. Use Babel with useBuiltIns: "usage" for automatic polyfill injection.
    4. Prefer feature detection over polyfills where possible.
    5. Test on low-end devices in target browsers.
    6. Monitor Core Web Vitals by browser.

    14. Security Considerations

    Polyfill Supply Chain Risk

    Polyfills are third-party JavaScript. A compromised polyfill can inject malicious code.

    Defense: Use well-maintained polyfills; pin versions; use SRI where possible.

    Browser-Specific Security Bugs

    Different engines have different security bugs. A feature that is safe in Chrome may be vulnerable in Safari.

    Defense: Test security-critical features in all target browsers.

    CSP and Polyfills

    Polyfills may use eval() or new Function(), which require 'unsafe-eval' in CSP.

    Defense: Use polyfills that do not require 'unsafe-eval'.

    Autoprefixer and Security

    Autoprefixer only adds CSS properties. It does not introduce security risks.

    Feature Detection and Security

    Feature detection is safe — it only checks for the presence of APIs.

    User Agent Sniffing and Security

    User agent strings are spoofable. Do not use them for security decisions.
