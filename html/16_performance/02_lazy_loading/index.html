    Lazy Loading

    1. Overview

    Definition

    Lazy loading is the practice of deferring the loading of non-critical resources — images, iframes, videos, scripts, and below-the-fold content — until they are actually needed, typically when they enter or approach the viewport. Instead of loading everything upfront, the browser loads only what the user is likely to see, then loads the rest on demand.

    <!-- Native lazy loading: the browser defers the image until it nears the viewport -->
<img src="photo.jpg" alt="Photo" loading="lazy" width="800" height="600">

<!-- Eager loading: the LCP image loads immediately -->
<img src="hero.jpg" alt="Hero" fetchpriority="high" width="1200" height="600">

    Lazy loading is not one technique — it is a family of techniques that apply across resource types:

    • Native HTML — loading="lazy" on <img> and <iframe>.
    • JavaScript APIs — IntersectionObserver for custom lazy-loading logic.
    • Framework primitives — next/image, <Suspense>, React.lazy, dynamic imports.
    • CSS — content-visibility: auto for skipping off-screen rendering.
    • Dynamic imports — import() for loading JavaScript modules on demand.

    The goal is always the same: load less upfront, load more later, and never load what the user will never see.

    Purpose

    Lazy loading serves several essential purposes:

    • Faster initial page load — fewer bytes downloaded before the first paint.
    • Lower bandwidth consumption — users on metered connections download only what they see.
    • Reduced memory usage — fewer DOM nodes, decoded images, and parsed scripts in memory.
    • Better Core Web Vitals — faster LCP, lower TBT, and lower INP.
    • Lower server costs — fewer image requests, less CDN traffic, less bandwidth billed.
    • Improved UX on long pages — content loads progressively as the user scrolls.
    • Accessibility for slow connections — users on 3G/4G see the important content first.
    • Scalable content delivery — galleries, feeds, and product lists can be arbitrarily long.

    The primary metric lazy loading targets is LCP — but only if applied correctly. Misapplied lazy loading makes LCP worse, not better.

    Where It Fits

    Performance Stack
│
├── Critical HTML        ← minimum markup for first paint
├── Lazy Loading         ← defer non-critical resources
├── Resource Hints       ← preload, preconnect, prefetch
├── Preload              ← high-priority fetch for critical assets
├── Prefetch             ← low-priority fetch for next navigation
├── DNS Prefetch         ← resolve third-party origins early
├── Script Loading       ← defer, async, module
└── Rendering Impact     ← layout shift, paint, compositing

    Lazy loading sits after critical HTML in the performance stack. Critical HTML determines what arrives first; lazy loading determines what arrives later. Together they shape the loading timeline of the page.

    2. Why It Exists

    The Problem

    A page with 30 images does not need all 30 images to render its first frame. A page with 5 iframes — analytics, chat widget, social embed, map, ad — does not need all 5 loaded before the user can read the first paragraph. Yet for decades, browsers loaded every resource in the HTML as soon as the parser encountered it.

    On a fast fiber connection, this is invisible. On a slow 3G connection, on a low-end Android phone, or in a country where bandwidth is expensive — it is the difference between a page that loads in 2 seconds and one that loads in 15 seconds.

    The 2026 reality: the median web page weighs over 2.5 MB, with images accounting for 1.2 MB of that. Loading every byte upfront wastes bandwidth, memory, and CPU on content the user may never scroll to.

    Previous Limitations

    Limitation Consequence
    No native lazy loading All images loaded upfront, regardless of visibility
    Manual JavaScript hacks scroll listeners with getBoundingClientRect() — janky and expensive
    No iframe deferral Analytics, chat, and ad iframes blocked the critical path
    No below-the-fold deferral Full-page rendering cost paid at load time
    No framework primitives Every team reinvented lazy loading badly
    No CSS containment Off-screen content still rendered and composited

    Why It Was Introduced

    Native lazy loading (loading="lazy") shipped in Chrome 76 (July 2019) and Firefox 75 (April 2020). Safari added support in 15.4 (March 2022). It replaced the JavaScript scroll-listener pattern that had dominated for years.

    The IntersectionObserver API shipped in 2016 and became the standard for detecting when an element enters the viewport. It replaced scroll listeners and getBoundingClientRect(), which ran on the main thread and caused jank.

    content-visibility: auto shipped in Chrome 85 (2020) and became baseline across browsers by 2024. It allows the browser to skip rendering of off-screen content, reducing layout and paint cost.

    Framework primitives — next/image, Nuxt Image, Gatsby Image, Angular NgOptimizedImage — automated lazy loading and responsive image handling. React's lazy() and Suspense brought code-splitting to components.

    AVIF and WebP reduced per-image bytes by 30–60% compared to JPEG, making lazy loading more effective (fewer bytes to defer, but larger savings when deferred).

    In 2026, lazy loading is baseline and expected — not an optimization, but a default. Browsers ship it natively; frameworks automate it; the only question is whether you are applying it correctly.

    3. Syntax / Basic Usage

    Native Image Lazy Loading

    <!-- Lazy: browser defers loading until the image nears the viewport -->
<img src="photo.jpg" alt="Photo" loading="lazy" width="800" height="600">

<!-- Eager: browser loads immediately (default for most browsers) -->
<img src="hero.jpg" alt="Hero" fetchpriority="high" width="1200" height="600">

    Code Breakdown

    Attribute Value Effect
    loading lazy Defer until the image nears the viewport
    loading eager Load immediately (default)
    fetchpriority high Fetch at highest priority (for LCP images)
    fetchpriority low Fetch at low priority (for below-the-fold)
    width / height pixel values Reserve space to prevent layout shift

    Critical rule: Never lazy-load the LCP element. If the largest visible element is an image, add fetchpriority="high" and leave it eager. Lazy-loading the LCP image delays LCP by hundreds of milliseconds.

    Native Iframe Lazy Loading

    <!-- Lazy: iframe loads when near the viewport -->
<iframe src="https://www.youtube.com/embed/xyz"
        loading="lazy"
        width="560"
        height="315"
        title="Product demo">
</iframe>

    Code Breakdown:

    • loading="lazy" — defers the iframe until it nears the viewport.
    • Off-screen iframes (footer chat widgets, below-the-fold embeds) do not load until needed.
    • Supported in all modern browsers.

    The IntersectionObserver API

    const images = document.querySelectorAll('img[data-src]');

const observer = new IntersectionObserver((entries) => {
    entries.forEach((entry) => {
        if (entry.isIntersecting) {
            const img = entry.target;
            img.src = img.dataset.src;
            img.removeAttribute('data-src');
            observer.unobserve(img);
        }
    });
}, {
    rootMargin: '200px 0px',  // start loading 200px before viewport
    threshold: 0.01
});

images.forEach((img) => observer.observe(img));

    Code Breakdown

    Line Purpose
    document.querySelectorAll('img[data-src]') Select images with placeholder data-src
    new IntersectionObserver(callback, options) Create an observer
    rootMargin: '200px 0px' Start loading 200px before the image enters the viewport
    threshold: 0.01 Trigger when at least 1% of the element is visible
    observer.observe(img) Register each image for observation
    observer.unobserve(img) Stop observing once loaded

    The content-visibility: auto Pattern

    .below-fold-section {
    content-visibility: auto;
    contain-intrinsic-size: 0 500px;
}

    Code Breakdown:

    • content-visibility: auto — the browser skips rendering the element until it nears the viewport.
    • contain-intrinsic-size — provides a placeholder size to prevent layout shift.
    • Reduces initial rendering cost on long pages by 20–50%.

    Dynamic Imports (Code Splitting)

    // Static import: always loaded
import { heavyFunction } from './heavy-module.js';

// Dynamic import: loaded on demand
button.addEventListener('click', async () => {
    const { heavyFunction } = await import('./heavy-module.js');
    heavyFunction();
});

    Code Breakdown:

    • Dynamic import() returns a Promise that resolves when the module loads.
    • Used for route-level code splitting, modal content, and rarely-used features.
    • Bundlers (Webpack, Vite, Rollup, esbuild) automatically split dynamic imports into separate chunks.

    React.lazy and Suspense

    import { lazy, Suspense } from 'react';

const HeavyChart = lazy(() => import('./HeavyChart'));

function Dashboard() {
    return (
        <main>
            <h1>Dashboard</h1>
            <Suspense fallback={<ChartSkeleton />}>
                <HeavyChart />
            </Suspense>
        </main>
    );
}

    Code Breakdown:

    • lazy(() => import('./HeavyChart')) — the component is loaded only when rendered.
    • <Suspense fallback={...}> — shows a placeholder while the component loads.
    • The above-the-fold content renders immediately; the chart loads when its chunk arrives.

    The next/image Component

    import Image from 'next/image';

<Image
    src="/hero.jpg"
    alt="Hero"
    width={1200}
    height={600}
    priority  // disables lazy loading for LCP images
/>

    Code Breakdown:

    • next/image automatically lazy-loads by default.
    • priority disables lazy loading for the LCP element.
    • Automatically serves AVIF/WebP, generates srcset, and prevents layout shift.

    4. Mental Model

    The "Restaurant Menu" Mental Model

    Think of a page as a restaurant menu:

    ┌─────────────────────────────────────────────┐
│  APPETIZER (Critical, eager)                 │
│  └── Hero image, above-the-fold content      │
│  └── Load immediately                        │
├─────────────────────────────────────────────┤
│  MAIN COURSE (Below-the-fold, lazy)          │
│  └── Product images, sections further down   │
│  └── Load when the user scrolls to them      │
├─────────────────────────────────────────────┤
│  DESSERT (Deep content, lazy)                │
│  └── Footer images, related content          │
│  └── Load only if the user reaches them      │
└─────────────────────────────────────────────┘

    The user should never wait for the dessert to enjoy the appetizer.

    The "Just-in-Time Delivery" Mental Model

    Traditional loading is a truck that delivers all goods before the store opens. Lazy loading is a just-in-time supply chain — goods arrive as the shelves empty.

    Traditional:
  Load → Everything arrives → Store opens

Lazy:
  Load → First shelves fill → Store opens
         → As user browses, more shelves fill

    The store opens faster, but the user never notices the difference — except that the page feels instant.

    The "Viewport as Trigger" Mental Model

    The viewport is the boundary between "load now" and "load later":

    ┌─────────────────────────────────────────────┐
│  VIEWPORT                                    │
│  ├── Above the fold: EAGER                   │
│  └── LCP element: fetchpriority="high"       │
│                                              │
│  ← Below the fold: LAZY                      │
│                                              │
│  ← Far below: content-visibility: auto       │
│                                              │
│  ← Never scrolled to: NEVER LOADED           │
└─────────────────────────────────────────────┘

    The rootMargin in IntersectionObserver and the browser's native lazy loading both use the viewport as the trigger. Content enters the loading queue as it approaches the viewport.

    The "LCP Trap" Mental Model

    The single most important rule of lazy loading:

    ┌─────────────────────────────────────────────┐
│  ⚠️  NEVER LAZY-LOAD THE LCP ELEMENT ⚠️     │
│                                              │
│  If the LCP element is an image:             │
│    ❌ loading="lazy"          → slows LCP    │
│    ✅ fetchpriority="high"    → fast LCP     │
│                                              │
│  If the LCP element is a background image:   │
│    ❌ background-image with lazy loading     │
│    ✅ <img> with fetchpriority="high"        │
│                                              │
│  If the LCP element is a text element:       │
│    ✅ Ensure the font loads fast             │
└─────────────────────────────────────────────┘

    Lazy loading is a trade-off. It speeds up below-the-fold loading at the cost of delaying above-the-fold loading. Get the boundary wrong, and you make LCP worse, not better.

    The "Progressive vs. Deferred" Mental Model

    Two related but distinct techniques:

    ┌─────────────────────────────────────────────┐
│  PROGRESSIVE LOADING                         │
│  └── Load low-quality first, then high-quality│
│  └── Examples: LQIP, BlurHash, progressive JPEG
│  └── Goal: perceived performance             │
├─────────────────────────────────────────────┤
│  LAZY LOADING                                │
│  └── Defer loading until needed              │
│  └── Examples: loading="lazy", IntersectionObserver
│  └── Goal: total bytes downloaded            │
└─────────────────────────────────────────────┘

    Both can be combined: lazy-load the image, but show a low-quality placeholder (LQIP) while it loads.

    5. Core Concepts

    Concept 1: loading="lazy"

    The native HTML attribute for lazy loading images and iframes. Supported in all modern browsers since 2022. The browser decides exactly when to load the resource based on network conditions, viewport size, and scroll speed.

    Concept 2: The loading="eager" Default

    If loading is not specified, browsers use eager for images in the initial viewport and may still load below-the-fold images immediately. Adding loading="lazy" explicitly is the only reliable way to defer below-the-fold images.

    Concept 3: fetchpriority

    The fetchpriority attribute controls the browser's fetch priority for a resource:

    Value Effect
    high Fetch at highest priority (LCP images)
    low Fetch at low priority (below-the-fold images)
    auto Default priority

    Concept 4: IntersectionObserver

    The modern API for detecting when an element enters or exits the viewport. Replaces scroll listeners and getBoundingClientRect(). Runs off the main thread and is efficient even with hundreds of observed elements.

    Concept 5: rootMargin

    The rootMargin option in IntersectionObserver expands or shrinks the intersection area:

    {
    rootMargin: '200px 0px'  // start loading 200px before the viewport
}

    A positive rootMargin loads resources earlier — a common optimization to prevent visible pop-in on slow connections.

    Concept 6: content-visibility: auto

    A CSS property that allows the browser to skip rendering of off-screen content. Reduces initial rendering cost by 20–50% on long pages. Requires contain-intrinsic-size to prevent layout shift.

    Concept 7: Dynamic Imports

    const module = await import('./module.js');

    Loads a JavaScript module on demand. Bundlers split dynamic imports into separate chunks. Used for route-level code splitting, rarely-used features, and modal content.

    Concept 8: Route-Level Code Splitting

    The most impactful code-splitting strategy: each route loads only the JavaScript needed for that route. Frameworks like Next.js, Remix, SvelteKit, and Nuxt do this automatically.

    Concept 9: Component-Level Code Splitting

    Splitting JavaScript at the component level — used for large charts, editors, and modals that are not needed on initial load.

    const HeavyEditor = lazy(() => import('./HeavyEditor'));

    Concept 10: The LCP Trap

    Never lazy-load the LCP element. Lazy loading delays LCP by hundreds of milliseconds. Use fetchpriority="high" and leave it eager.

    Concept 11: The Layout Shift Trap

    Lazy loading without width/height causes layout shift (CLS). Always specify dimensions or use aspect-ratio in CSS.

    <img src="photo.jpg" alt="Photo" loading="lazy" width="800" height="600">

    Concept 12: decoding="async"

    Tells the browser to decode the image asynchronously, off the main thread. Prevents the image decode from blocking other work.

    <img src="photo.jpg" alt="Photo" loading="lazy" decoding="async" width="800" height="600">

    Concept 13: LQIP (Low-Quality Image Placeholder)

    A technique that shows a tiny, blurred version of the image while the full-resolution version loads. Improves perceived performance.

    <img src="photo-tiny.jpg"
     data-src="photo.jpg"
     class="lazy"
     style="filter: blur(20px);"
     alt="Photo">

    Concept 14: The srcset and sizes Attributes

    Combine lazy loading with responsive images to load the smallest sufficient image:

    <img src="photo-800.jpg"
     srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1600.jpg 1600w"
     sizes="(max-width: 600px) 400px, (max-width: 1200px) 800px, 1600px"
     loading="lazy"
     width="800"
     height="600"
     alt="Photo">

    Concept 15: Iframe Lazy Loading

    Iframes are the second-biggest performance drain on most pages (after images). loading="lazy" defers them until they near the viewport.

    <iframe src="https://www.youtube.com/embed/xyz" loading="lazy" title="Video"></iframe>

    Concept 16: Video Lazy Loading

    Videos should never autoplay-load. Use preload="none" on <video> elements and load them on click.

    <video preload="none" controls poster="poster.jpg">
    <source src="video.mp4" type="video/mp4">
</video>

    Concept 17: The Facade Pattern

    For heavy third-party embeds (YouTube, Google Maps, Twitter), use a facade — a lightweight placeholder (often an image) that looks like the embed. Load the real iframe only when the user clicks.

    <!-- Facade: a lightweight image -->
<div class="youtube-facade" data-video-id="xyz">
    <img src="youtube-thumbnail.jpg" alt="Video: Product demo">
    <button>Play</button>
</div>

    Libraries: lite-youtube-embed, @justinribeiro/lite-youtube, react-lite-youtube-embed.

    Concept 18: Framework Primitives

    Framework Lazy Loading Primitive
    Next.js next/image, next/dynamic
    Nuxt <NuxtImg>, defineAsyncComponent
    SvelteKit Native, {#await}
    Astro Built-in by default
    Angular NgOptimizedImage, @defer
    Gatsby gatsby-plugin-image
    Remix Native <img>, lazy routes

    Concept 19: The loading Attribute and CSP

    Lazy loading does not affect CSP directly, but the resources being lazy-loaded must still satisfy CSP directives (img-src, frame-src, script-src).

    Concept 20: Measuring Lazy Loading Effectiveness

    • Lighthouse — audits for offscreen images.
    • Chrome DevTools → Coverage — shows unused bytes.
    • Network panel — verify resources are loaded on scroll.
    • WebPageTest filmstrip — visualize loading over time.
    • CrUX — real-world LCP data.

    7. Internal Architecture / Under the Hood

    How Native Lazy Loading Works

    The browser's lazy loading implementation uses:

    • IntersectionObserver internally — the browser uses an efficient viewport-intersection check.
    • Network-aware thresholds — the browser may load earlier on slow connections to compensate for latency.
    • Scroll velocity — fast scrolling triggers earlier loading.
    • Viewport distance — the browser may load images within a certain distance of the viewport.

    The exact thresholds are implementation-specific and not standardized, which is why behavior varies between Chrome, Firefox, and Safari.

    The Preload Scanner vs. Lazy Loading

    The preload scanner runs ahead of the main parser and discovers resources early. Lazy-loaded images are not discovered by the preload scanner because the browser defers their fetch until intersection. This is the desired behavior — it removes them from the critical path.

    The IntersectionObserver Architecture

    IntersectionObserver runs on a separate thread, so it does not compete with the main thread for layout and paint. This is what makes it superior to scroll listeners, which run on the main thread and cause jank.

    Main thread:           Separate thread:
  ─ Layout               ─ IntersectionObserver
  ─ Paint                  ├── Watches elements
  ─ JS execution           └── Fires callbacks

    The content-visibility Rendering Skip

    content-visibility: auto tells the browser:

    1. Skip layout and paint for off-screen content.
    2. Render the element when it nears the viewport.
    3. Use contain-intrinsic-size as a placeholder size.

    The browser maintains the DOM but skips the rendering cost until the element is needed.

    The Chunk Splitting Algorithm

    Bundlers (Webpack, Vite, Rollup, esbuild) detect dynamic imports and split them into separate chunks:

    main.js         ← always loaded
  ├── route-a.js   ← dynamic import on /a
  ├── route-b.js   ← dynamic import on /b
  └── chart.js     ← dynamic import when chart renders

    Chunk names are content-hashed for cache-busting. Chunks are loaded on demand via <script> injection or fetch().

    The Next.js Image Pipeline

    next/image:

    1. Detects the image dimensions.
    2. Generates a srcset at build time or on demand.
    3. Serves AVIF/WebP with JPEG fallback.
    4. Applies loading="lazy" by default.
    5. Adds fetchpriority="high" when priority is set.
    6. Prevents layout shift via width/height attributes.

    Code Breakdown:

    • Hero image: eager, fetchpriority="high", no lazy loading.
    • Below-the-fold images: loading="lazy", decoding="async".
    • All images have width and height to prevent layout shift.
    • Browser loads feature images only when the user scrolls.

    Example 2: IntersectionObserver with rootMargin

    const images = document.querySelectorAll('img[data-src]');

const observer = new IntersectionObserver((entries) => {
    entries.forEach((entry) => {
        if (!entry.isIntersecting) return;

        const img = entry.target;
        img.src = img.dataset.src;
        img.removeAttribute('data-src');
        observer.unobserve(img);
    });
}, {
    rootMargin: '300px 0px',  // load 300px before viewport
    threshold: 0
});

images.forEach((img) => observer.observe(img));

    Code Breakdown:

    • rootMargin: '300px 0px' — starts loading 300px before the image enters the viewport.
    • threshold: 0 — fires when any part of the image touches the root.
    • observer.unobserve(img) — stops observing after loading.
    • The 300px margin prevents visible pop-in on slow connections.

    Example 3: content-visibility for Long Pages

    .below-fold-section {
    content-visibility: auto;
    contain-intrinsic-size: auto 500px;
}

    <main>
    <section class="hero">...</section>
    <section class="below-fold-section">
        <!-- This section is not rendered until near viewport -->
    </section>
    <section class="below-fold-section">
        <!-- Same here -->
    </section>
</main>

    Code Breakdown:

    • content-visibility: auto — skips rendering until the section nears the viewport.
    • contain-intrinsic-size: auto 500px — placeholder size to prevent layout shift.
    • auto in the first position tells the browser to remember the actual size once rendered.

    Example 4: Lazy Loading with LQIP

    <img src="photo-tiny.jpg"
     data-src="photo-full.jpg"
     alt="Photo"
     width="800"
     height="600"
     class="lazy"
     style="filter: blur(20px); transition: filter 0.3s;">

    const observer = new IntersectionObserver((entries) => {
    entries.forEach((entry) => {
        if (!entry.isIntersecting) return;

        const img = entry.target;
        img.src = img.dataset.src;
        img.style.filter = 'none';
        observer.unobserve(img);
    });
}, { rootMargin: '200px' });

document.querySelectorAll('.lazy').forEach((img) => observer.observe(img));

    Code Breakdown:

    • Tiny placeholder image loads immediately (small bytes).
    • Full image loads when near the viewport.
    • Blur filter is removed on load, creating a smooth transition.

    Example 5: Lazy Loading Iframes with Facade

    <!-- Facade: lightweight, loads immediately -->
<div class="video-facade" data-video-id="xyz">
    <img src="thumbnail.jpg" alt="Video: Product demo" loading="lazy" width="560" height="315">
    <button type="button" aria-label="Play video">Play</button>
</div>

<script>
    document.querySelectorAll('.video-facade').forEach((facade) => {
        facade.addEventListener('click', () => {
            const iframe = document.createElement('iframe');
            iframe.src = `https://www.youtube.com/embed/${facade.dataset.videoId}?autoplay=1`;
            iframe.width = '560';
            iframe.height = '315';
            iframe.title = 'Product demo';
            iframe.allow = 'autoplay; fullscreen';
            facade.replaceWith(iframe);
        });
    });
</script>

    Code Breakdown:

    • The facade is a lightweight image and button.
    • On click, the facade is replaced with the real iframe.
    • Saves hundreds of KB and multiple HTTP requests on initial load.
    • Improves LCP by removing the iframe from the critical path.

document.getElementById('show-chart').addEventListener('click', async () => {
    const { renderChart } = await import('./chart.js');
    renderChart(document.getElementById('chart-container'));
});

    Code Breakdown:

    • The chart library is loaded only when the user clicks the button.
    • The initial bundle stays small.
    • Bundlers automatically split chart.js into a separate chunk.

    Example 7: Route-Level Code Splitting (React)

    import { lazy, Suspense } from 'react';
import { Routes, Route } from 'react-router-dom';

const Dashboard = lazy(() => import('./pages/Dashboard'));
const Settings = lazy(() => import('./pages/Settings'));
const Reports = lazy(() => import('./pages/Reports'));

function App() {
    return (
        <Suspense fallback={<PageSkeleton />}>
            <Routes>
                <Route path="/" element={<Dashboard />} />
                <Route path="/settings" element={<Settings />} />
                <Route path="/reports" element={<Reports />} />
            </Routes>
        </Suspense>
    );
}

    Code Breakdown:

    • Each route is loaded only when navigated to.
    • The initial bundle contains only the shared code.
    • <Suspense> shows a skeleton while the route loads.
    • Route-level splitting is the most impactful code-splitting strategy.

    11. Best Practices

    1. Never lazy-load the LCP element. Why: it delays LCP by hundreds of milliseconds.
    2. Add fetchpriority="high" to the LCP element. Why: tells the browser to fetch it at highest priority.
    3. Lazy-load all below-the-fold images. Why: reduces initial bytes and improves FCP/LCP.
    4. Always specify width and height. Why: prevents layout shift (CLS).
    5. Use decoding="async". Why: prevents image decode from blocking the main thread.
    6. Lazy-load iframes. Why: iframes are heavy and often below the fold.
    7. Use facades for third-party embeds. Why: saves hundreds of KB.
    8. Use content-visibility: auto for long sections. Why: skips off-screen rendering.
    9. Use contain-intrinsic-size with content-visibility. Why: prevents layout shift.
    10. Code-split at the route level. Why: the most impactful code-splitting strategy.
    11. Use dynamic imports for heavy components. Why: keep initial bundle small.
    12. Use preload="none" for videos. Why: videos should not preload.
    13. Use srcset and sizes with lazy loading. Why: load the smallest sufficient image.
    14. Use IntersectionObserver instead of scroll listeners. Why: runs off the main thread; no jank.
    15. Add rootMargin to prevent pop-in. Why: load before the element is visible.
    16. Use loading="lazy" instead of JavaScript when possible. Why: native implementation is more efficient.
    17. Use LQIP for large hero images below the fold. Why: improves perceived performance.
    18. Test on slow networks (3G/4G) and low-end devices. Why: performance gaps are invisible on fast connections.
    19. Measure with Lighthouse, WebPageTest, and CrUX. Why: lab + field data reveals different issues.
    20. Audit lazy loading after every major framework upgrade. Why: framework behavior changes.
    21. Lazy-load only what is truly non-critical. Why: over-lazy-loading delays content the user needs.
    22. Do not lazy-load images in the initial viewport. Why: they are part of the LCP.
    23. Do not lazy-load fonts. Why: font loading affects FOUT/FOIT and should be preloaded.
    24. Do not lazy-load critical CSS. Why: CSS is render-blocking and must load first.
    25. Monitor Core Web Vitals continuously. Why: LCP, INP, and CLS drive SEO and UX.

    12. Common Mistakes

    ❌ Mistake: Lazy-Loading the LCP Image

    <img src="/hero.jpg" alt="Hero" loading="lazy" width="1200" height="600">

    Why it's wrong: Delays LCP by hundreds of milliseconds. Lazy loading the LCP element is the single most common lazy-loading mistake.

    ✅ Correct:

    <img src="/hero.jpg" alt="Hero" fetchpriority="high" width="1200" height="600">

    ❌ Mistake: No width and height on Lazy-Loaded Images

    <img src="photo.jpg" alt="Photo" loading="lazy">

    Why it's wrong: The browser doesn't know the image dimensions, causing layout shift (CLS) when the image loads.

    ✅ Correct:

    <img src="photo.jpg" alt="Photo" loading="lazy" width="800" height="600">

    ❌ Mistake: Using scroll Listeners Instead of IntersectionObserver

    window.addEventListener('scroll', () => {
    document.querySelectorAll('img[data-src]').forEach((img) => {
        if (img.getBoundingClientRect().top < window.innerHeight) {
            img.src = img.dataset.src;
        }
    });
});

    Why it's wrong: Runs on the main thread on every scroll event, causing jank and poor INP.

    ✅ Correct: Use IntersectionObserver.

    ❌ Mistake: Lazy-Loading Above-the-Fold Images

    <img src="logo.jpg" alt="Logo" loading="lazy" width="200" height="50">
<img src="hero.jpg" alt="Hero" loading="lazy" width="1200" height="600">

    Why it's wrong: Both images are in the initial viewport. Lazy loading them delays the first paint.

    ✅ Correct:

    <img src="logo.jpg" alt="Logo" width="200" height="50">
<img src="hero.jpg" alt="Hero" fetchpriority="high" width="1200" height="600">

    ❌ Mistake: No loading="lazy" on Below-the-Fold Images

    <img src="feature-1.jpg" alt="Feature 1" width="800" height="600">
<img src="feature-2.jpg" alt="Feature 2" width="800" height="600">

    Why it's wrong: All images load upfront, wasting bandwidth and delaying LCP.

    ✅ Correct:

    <img src="feature-1.jpg" alt="Feature 1" loading="lazy" decoding="async" width="800" height="600">
<img src="feature-2.jpg" alt="Feature 2" loading="lazy" decoding="async" width="800" height="600">

    ❌ Mistake: Lazy-Loading Critical Fonts

    <link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>

    Why it's wrong: Fonts are critical for text rendering. Preloading is correct; lazy loading is not.

    ✅ Correct: Preload critical fonts.

    ❌ Mistake: No Facade for Third-Party Embeds

    <iframe src="https://www.youtube.com/embed/xyz" width="560" height="315"></iframe>

    Why it's wrong: The iframe loads immediately, blocking the critical path.

    ✅ Correct:

    <div class="video-facade" data-video-id="xyz">
    <img src="thumbnail.jpg" alt="Video thumbnail" loading="lazy">
    <button>Play</button>
</div>

    ❌ Mistake: content-visibility Without contain-intrinsic-size

    section {
    content-visibility: auto;
}

    Why it's wrong: The browser doesn't know the section's size, causing layout shift.

    ✅ Correct:

    section {
    content-visibility: auto;
    contain-intrinsic-size: 0 500px;
}

    ❌ Mistake: Lazy-Loading All Scripts

    <script src="/js/critical.js" defer></script>

    Why it's wrong: Critical scripts should load and execute early; lazy loading them delays interactivity.

    ✅ Correct: Lazy-load non-critical scripts; defer critical scripts.

    ❌ Mistake: Assuming loading="lazy" Is Universal

    Why it's wrong: Older browsers (IE 11, Safari < 15.4) do not support native lazy loading.

    ✅ Correct: Use IntersectionObserver as a fallback, or accept that older browsers will load eagerly.

    14. Security Considerations

    Lazy Loading and CSP

    Lazy-loaded resources must satisfy the same CSP directives as eagerly-loaded resources:

    Content-Security-Policy:
    img-src 'self' https://cdn.example.com;
    frame-src https://www.youtube.com

    Lazy Loading and Subresource Integrity

    Lazy-loaded scripts and styles should use SRI where possible:

    <script src="https://cdn.example.com/lib.js"
        integrity="sha384-..."
        crossorigin="anonymous"
        defer></script>

    Facade Pattern and Clickjacking

    Facades replace iframes with custom UI. Ensure that the facade does not introduce clickjacking or UI redressing vulnerabilities.

    Lazy Loading and Third-Party Scripts

    Lazy-loaded third-party scripts still execute in your origin's context. Apply the same security review as eager-loaded scripts.

    Deferred Loading and Ad Blockers

    Some ad blockers may block lazy-loaded ad iframes. Ensure your page functions correctly when ad iframes fail to load.

    • Chrome DevTools → Lighthouse — audits for offscreen images.
    • Lighthouse → offscreen-images audit — flags images that should be lazy-loaded.
    • Lighthouse → lcp-lazy-loaded audit — flags LCP images that are incorrectly lazy-loaded.
    • WebPageTest filmstrip — visualize loading over time.
    • Network throttling (Slow 3G) — reveals loading issues invisible on fast connections.
    • Disable cache — verify lazy loading works on first load.
    • document.querySelectorAll('img[loading="lazy"]') — count lazy-loaded images.
    • Scroll through the page — verify images load on scroll.
    • Check for pop-in — if images pop in visibly, rootMargin should be increased.
