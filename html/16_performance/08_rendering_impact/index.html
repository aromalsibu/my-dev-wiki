    Rendering Impact

    1. Overview

    Definition

    Rendering impact is the cost a web page imposes on the browser's rendering pipeline — the sequence of steps the browser takes to convert HTML, CSS, and JavaScript into pixels on the screen. It encompasses layout (computing geometry), paint (filling pixels), composite (assembling layers), and the events that trigger them: reflow (layout invalidation) and repaint (paint invalidation).

    /* Low rendering impact: transform + opacity */
.card:hover {
    transform: translateY(-4px);
    opacity: 0.9;
}

/* High rendering impact: layout-triggering properties */
.card:hover {
    top: -4px;
    width: 220px;
    height: 110px;
}

    Both examples visually move the card. The first is handled by the compositor thread — the second forces the browser to recalculate layout, re-layout surrounding elements, repaint, and recomposite. The visual result may look identical; the cost is not.

    Rendering impact is measured in milliseconds of main-thread work and frames dropped. It directly affects Interaction to Next Paint (INP), Cumulative Layout Shift (CLS), and the smoothness of animations and scrolling.

    Purpose

    Understanding rendering impact serves several essential purposes:

    • Smooth animations — 60fps (16.7ms per frame) requires rendering work under budget.
    • Fast interaction response — INP measures how quickly the browser responds to user input.
    • Stable layout — CLS measures unexpected layout shifts.
    • Jank-free scrolling — long paint and composite tasks cause visible stutter.
    • Battery efficiency — unnecessary rendering wastes CPU and battery on mobile.
    • Frame budget discipline — every render must fit within the 16.7ms (or 8.3ms for 120Hz) frame budget.
    • Predictable behavior — developers know which CSS properties are cheap and which are expensive.

    Rendering impact is the last mile of performance. Every optimization above it — critical HTML, lazy loading, resource hints, script loading — is undermined if the page then janks on every scroll, hover, or animation.

    Where It Fits

    Performance Stack
│
├── Critical HTML        ← minimum markup for first paint
├── Lazy Loading         ← defer non-critical resources
├── Resource Hints       ← preload, preconnect, prefetch
├── Preload              ← high-priority fetch for critical assets
├── Prefetch             ← low-priority fetch for next navigation
├── DNS Prefetch         ← resolve third-party origins early
├── Script Loading       ← defer, async, module
└── Rendering Impact     ← layout, paint, composite, frame budget

    Rendering impact is the bottom of the performance stack — the layer closest to the user's eyes. It is where the browser either paints a smooth 60fps or stutters at 20fps.

    2. Why It Exists

    The Problem

    A browser does not paint pixels directly from HTML. It must:

    1. Parse HTML → build the DOM.
    2. Parse CSS → build the CSSOM.
    3. Combine DOM + CSSOM → build the render tree.
    4. Compute layout → determine the position and size of every element.
    5. Paint → fill in the pixels for every element.
    6. Composite → assemble the painted layers into the final image.

    Steps 4–6 are the rendering pipeline. Every DOM change that affects geometry triggers layout. Every change that affects appearance triggers paint. Every change that affects the visual stack triggers composite.

    The problem: not all CSS properties are equally expensive. Some are cheap (handled by the compositor). Some are catastrophically expensive (force a full layout recalculation). Developers who do not understand the difference write code that janks on every frame.

    Previous Limitations

    Limitation Consequence
    No separation of layout/paint/composite Every change forced full rendering
    No compositor thread Main thread did all the work — jank on every scroll
    No transform / opacity optimization Animations forced layout + paint
    No will-change hint Browser could not pre-optimize layers
    No contain property Changes in one subtree affected the whole page
    No content-visibility Off-screen content still laid out and painted
    No Layout Instability API CLS was invisible to developers

    Why It Was Introduced

    The modern rendering pipeline evolved in stages:

    • 2010s — browsers introduced compositor threads — separate threads for painting and compositing, freeing the main thread for JavaScript.
    • 2013 — transform and opacity were identified as compositor-only properties — they could be animated without touching the main thread.
    • 2015 — the will-change property shipped, letting developers hint which elements would animate.
    • 2019 — contain shipped, allowing developers to isolate subtrees from the rest of the layout.
    • 2020 — content-visibility shipped, skipping rendering for off-screen content.
    • 2020 — Cumulative Layout Shift (CLS) became a Core Web Vital.
    • 2024 — Interaction to Next Paint (INP) replaced First Input Delay (FID) as a Core Web Vital.

    In 2026, the rendering pipeline is fully specified and observable. Chrome DevTools, Firefox DevTools, and Safari Web Inspector all expose the rendering pipeline in detail. The question is not whether the tools exist — it is whether developers are using them.

    The Cost Hierarchy of CSS Properties

    ┌─────────────────────────────────────────────┐
│  CHEAPEST — Composite only                   │
│  └── transform                               │
│  └── opacity                                 │
│  └── filter (in some cases)                  │
├─────────────────────────────────────────────┤

├─────────────────────────────────────────────┤

    The Composable Animation Pattern

    /* ✅ Cheap: composite-only */
.card {
    transition: transform 200ms ease, opacity 200ms ease;
}
.card:hover {
    transform: translateY(-4px);
    opacity: 0.9;
}

    Code Breakdown

    • transform: translateY(-4px) — moves the element without triggering layout.
    • opacity: 0.9 — changes transparency without triggering layout.
    • The animation runs on the compositor thread — the main thread is free.
    • The visual result is identical to animating top, but the cost is dramatically lower.

    The will-change Hint

    .card {
    will-change: transform, opacity;
}

    Code Breakdown

    • will-change — hints to the browser that the element will animate.
    • The browser promotes the element to its own compositing layer.
    • The animation runs on the compositor thread.
    • Use sparingly — too many layers waste memory and GPU resources.

    The contain Property

    .card {
    contain: layout paint;
}

    Code Breakdown

    Value Effect
    layout Isolates the element's layout from its surroundings
    paint Clips paint to the element's bounds
    size Isolates size computation
    style Isolates style changes
    strict Applies size layout paint
    content Applies layout paint style

    Isolating a subtree prevents changes inside it from triggering layout on the whole page.

    The content-visibility Property

    .below-fold-section {
    content-visibility: auto;
    contain-intrinsic-size: 0 500px;
}

    Code Breakdown

    • content-visibility: auto — skips rendering until the element nears the viewport.
    • contain-intrinsic-size — provides a placeholder size to prevent layout shift.
    • Reduces initial rendering cost by 20–50% on long pages.

    The aspect-ratio Property

    .image-container {
    aspect-ratio: 16 / 9;
}

    Code Breakdown

    • aspect-ratio — reserves space based on the aspect ratio.
    • Prevents layout shift when the image loads.
    • Replaces the old padding-hack technique.

    The transform and opacity Animation

    @keyframes slide-in {
    from {
        transform: translateX(-100%);
        opacity: 0;
    }
    to {
        transform: translateX(0);
        opacity: 1;
    }
}
.slide-in {
    animation: slide-in 300ms ease-out;
}

    Code Breakdown

    • Animations using transform and opacity run entirely on the compositor thread.
    • The main thread is not involved — the animation stays smooth even during heavy JavaScript.
    • This is the single most important pattern for smooth animation.

    4. Mental Model

    The "Painting a Room" Mental Model

    Think of the rendering pipeline as painting a room:

    ┌─────────────────────────────────────────────┐
│  LAYOUT      → Where does the furniture go?  │
│  PAINT       → What color is each object?    │
│  COMPOSITE   → How do the layers stack?      │
└─────────────────────────────────────────────┘

    Changing the position of furniture (layout) forces a full rearrangement. Changing the color of a wall (paint) forces a repaint but no rearrangement. Changing the order of hanging pictures (composite) is quick and does not affect the room.

    The goal: make changes that only affect the composite layer, not the layout.

    The "Three Costs" Mental Model

    Every rendering change has one of three costs:

    ┌─────────────────────────────────────────────┐
│  LAYOUT CHANGE (most expensive)              │
│  └── Recalculate geometry                    │
│  └── Re-layout surrounding elements          │
│  └── Repaint                                 │
│  └── Recomposite                             │
│                                              │
│  Triggered by: width, height, top, left,     │
│  margin, padding, font-size, display         │
├─────────────────────────────────────────────┤
│  PAINT CHANGE (medium)                       │
│  └── Repaint affected region                 │
│  └── Recomposite                             │
│                                              │
│  Triggered by: color, background, shadow,    │
│  border-radius                               │
├─────────────────────────────────────────────┤
│  COMPOSITE CHANGE (cheapest)                 │
│  └── Recomposite                             │
│                                              │
│  Triggered by: transform, opacity            │
└─────────────────────────────────────────────┘

    The "Frame Budget" Mental Model

    A smooth animation runs at 60 frames per second — one frame every 16.7ms. On high-refresh displays (120Hz), the budget is 8.3ms per frame.

    ┌─────────────────────────────────────────────┐
│  FRAME BUDGET (60fps)                        │
│  ├── JavaScript:  ~5ms                       │
│  ├── Style:       ~1ms                       │
│  ├── Layout:      ~2ms                       │
│  ├── Paint:       ~2ms                       │
│  └── Composite:   ~2ms                       │
│                                              │
│  Total: 16.7ms — exceed it, and you drop    │
│  a frame.                                    │
└─────────────────────────────────────────────┘

    Every layout that runs inside an animation frame eats into this budget. Layout-triggering animations blow the budget on slow devices.

    The "Compositor Thread" Mental Model

    The browser has two threads:

    ┌─────────────────────────────────────────────┐
│  MAIN THREAD                                 │
│  ├── JavaScript                              │
│  ├── HTML parsing                            │
│  ├── CSS parsing                             │
│  ├── Layout                                  │
│  ├── Paint                                   │
│  └── Event handling                          │
├─────────────────────────────────────────────┤
│  COMPOSITOR THREAD                           │
│  ├── Layer compositing                       │
│  ├── Transform animations                    │
│  ├── Opacity animations                      │
│  └── Scrolling                               │
└─────────────────────────────────────────────┘

    Animations on the compositor thread stay smooth even when the main thread is busy. Animations on the main thread jank whenever JavaScript runs.

    The "Layer Explosion" Mental Model

    Promoting too many elements to their own layers has a cost:

    ┌─────────────────────────────────────────────┐
│  LAYER PROMOTION (will-change, transform)   │
│  ├── ✅ Smooth animation                    │
│  ├── ❌ More GPU memory                     │
│  ├── ❌ More compositing work               │
│  └── ❌ Potential jank on low-end devices   │
└─────────────────────────────────────────────┘

    Promote only what you animate. Remove will-change after the animation ends.

    The "Reflow vs Repaint" Mental Model

    ┌─────────────────────────────────────────────┐
│  REFLOW (layout)                             │
│  └── Triggered by geometry changes           │
│  └── Recomputes positions and sizes          │
│  └── Cascades to children and siblings       │
│  └── Most expensive                          │
├─────────────────────────────────────────────┤
│  REPAINT                                     │
│  └── Triggered by visual changes             │
│  └── Fills in pixels                         │
│  └── Does not affect layout                  │
│  └── Medium cost                             │
├─────────────────────────────────────────────┤
│  COMPOSITE                                   │
│  └── Triggered by layer changes              │
│  └── Assembles layers                        │
│  └── Cheapest                                 │
└─────────────────────────────────────────────┘

    5. Core Concepts

    Concept 1: The Rendering Pipeline

    The sequence of steps the browser takes to convert HTML, CSS, and JavaScript into pixels: DOM → CSSOM → Render Tree → Layout → Paint → Composite.

    Concept 2: Layout (Reflow)

    Computing the geometry of every element — position, size, and relationship to siblings. Triggered by changes to width, height, top, left, margin, padding, font-size, display, and more.

    Concept 3: Paint (Repaint)

    Filling in the pixels for each element. Triggered by changes to color, background, box-shadow, border-radius, and more. Does not affect layout.

    Concept 4: Composite

    Assembling layers into the final image. Triggered by changes to transform, opacity, and layer order. Handled by the compositor thread.

    Concept 5: The Cost Hierarchy

    transform, opacity     → composite (cheapest)
color, background      → paint + composite
width, height, top     → layout + paint + composite (most expensive)

    Concept 6: The Frame Budget

    60fps = 16.7ms per frame. 120fps = 8.3ms per frame. Exceeding the budget drops frames and causes visible jank.

    Concept 7: The Compositor Thread

    A separate thread that handles transform, opacity, and scroll animations. Freeing the main thread for JavaScript.

    Concept 8: Layout Thrashing

    Reading layout properties (e.g., offsetHeight) forces the browser to flush pending layout changes. Writing layout properties then reading again forces another flush. This read-write-read-write pattern is called layout thrashing or forced synchronous layout.

    // ❌ Layout thrashing: forces layout on every iteration
for (const el of elements) {
    el.style.width = el.offsetWidth + 10 + 'px'; // read → write → read
}

    Concept 9: Forced Synchronous Layout

    When JavaScript reads a layout property after a DOM mutation, the browser must synchronously compute layout to return the correct value. This is a forced synchronous layout — expensive and janky.

    Concept 10: will-change

    A CSS property that hints the browser to promote an element to its own compositing layer. Use sparingly — too many layers waste memory.

    Concept 11: Layer Promotion

    An element becomes its own compositing layer when it has certain properties: transform: translateZ(0), will-change: transform, position: fixed, opacity < 1, etc. Promoted layers animate on the compositor thread.

    Concept 12: The contain Property

    Isolates a subtree from the rest of the page. Values: layout, paint, size, style, strict, content. Prevents changes inside the subtree from triggering layout on the whole page.

    Concept 13: content-visibility

    Skips rendering of off-screen content until it nears the viewport. Reduces initial rendering cost by 20–50% on long pages. Requires contain-intrinsic-size to prevent layout shift.

    Concept 14: Cumulative Layout Shift (CLS)

    Measures unexpected layout shifts — content that moves after the user has already started interacting. A Core Web Vital. Target: < 0.1.

    Concept 15: Interaction to Next Paint (INP)

    Measures the responsiveness of the page to user input. Replaced FID in March 2024. Target: < 200ms.

    Concept 16: Long Tasks

    Any JavaScript task over 50ms is a long task. Long tasks block the main thread and delay rendering. Break long tasks into smaller chunks.

    Concept 17: The Layout Instability API

    A browser API that reports layout shifts:

    new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        if (!entry.hadRecentInput) {
            console.log('Layout shift:', entry.value);
        }
    }
}).observe({ type: 'layout-shift', buffered: true });

    Concept 18: Paint Flashing

    A Chrome DevTools feature that highlights painted regions. Green flashes indicate painted areas. Use it to identify unnecessary paints.

    Concept 19: Layer Borders

    A Chrome DevTools feature that outlines compositing layers. Use it to identify excessive layer promotion.

    Concept 20: The Rendering Waterfall

    The sequence of rendering events for a single frame: requestAnimationFrame → Style → Layout → Paint → Composite. Each stage must fit within the frame budget.

    7. Internal Architecture / Under the Hood

    The Render Tree

    The browser combines the DOM and CSSOM into a render tree — a tree of visible elements with their computed styles.

    DOM + CSSOM → Render Tree
    │
    └── Only visible elements
    └── Each node has computed styles

    Elements with display: none are excluded. Elements with visibility: hidden are included but not painted.

    The Layout Engine

    The layout engine walks the render tree and computes the geometry of every element:

    Render Tree → Layout Tree
    │
    ├── Position (x, y)
    ├── Size (width, height)
    └── Relationship to siblings

    Layout is a single-pass algorithm on the tree. Changing any element's geometry may cascade to its children and siblings.

    The Paint Engine

    The paint engine walks the layout tree and generates paint records — a list of drawing operations for each region of the screen.

    Layout Tree → Paint Records
    │
    └── Draw rect at (x, y)
    └── Draw text at (x, y)
    └── Draw image at (x, y)

    Paint records are sorted by stacking context (z-index, position, etc.).

    The Compositor

    The compositor assembles painted layers into the final image. Layers are composited on the GPU — fast and parallel.

    Paint Records → Layers → Composite → GPU → Screen

    The Compositing Layer Model

    ┌─────────────────────────────────────────────┐
│  COMPOSITING LAYERS                          │
│                                              │
│  Layer 1 (document)                          │
│  ├── Layer 2 (fixed header)                 │
│  ├── Layer 3 (animated card)                │
│  └── Layer 4 (video)                        │
│                                              │
│  Each layer is composited independently.    │
│  Animating a layer does not affect others.  │
└─────────────────────────────────────────────┘

    The Layout Invalidation Algorithm

    When a property changes, the browser:

    1. Marks the element as layout-dirty.
    2. Walks up the tree to find the nearest layout boundary.
    3. Invalidates layout from that boundary down.
    4. Recomputes layout when needed (before paint).

    The Forced Synchronous Layout Engine

    Reading a layout property (e.g., offsetWidth) triggers a synchronous layout flush — the browser must compute layout immediately to return a value.

    el.style.width = '100px'    // write (marks layout dirty)
el.offsetWidth              // read → forces layout flush
el.style.width = '200px'    // write
el.offsetWidth              // read → forces layout flush AGAIN

    The Layout Instability API

    The browser reports layout shifts via the layout-shift performance entry type. Each entry has:

    • value — the CLS score for that shift.
    • hadRecentInput — whether the shift occurred within 500ms of user input.
    • sources — the elements that shifted.

    The INP Pipeline

    INP measures the time from the first user input to the next paint. It includes:

    1. Event handler execution.
    2. Style recalculation.
    3. Layout.
    4. Paint.
    5. Composite.

    Long event handlers block the main thread and increase INP.

    9. Practical Examples

    Example 1: Composite-Only Animation

    .card {
    transition: transform 200ms ease, opacity 200ms ease;
    will-change: transform, opacity;
}
.card:hover {
    transform: translateY(-4px);
    opacity: 0.9;
}
.card:not(:hover) {
    will-change: auto;
}

    Code Breakdown:

    • transform and opacity are compositor-only properties — no layout or paint.
    • will-change promotes the element to its own layer.
    • will-change: auto removes the promotion after the animation — prevents layer bloat.

    Example 2: Fixing Layout Thrashing

    // ❌ Layout thrashing
for (const el of elements) {
    el.style.height = el.offsetHeight + 10 + 'px';
}

// ✅ Batched reads and writes
const heights = elements.map(el => el.offsetHeight);
elements.forEach((el, i) => {
    el.style.height = heights[i] + 10 + 'px';
});

    Code Breakdown:

    • The first version interleaves reads and writes — each read forces a layout flush.
    • The second version batches all reads first, then all writes — one layout flush.
    • Use requestAnimationFrame for even better performance.

    Example 3: content-visibility for Long Pages

    .below-fold-section {
    content-visibility: auto;
    contain-intrinsic-size: 0 500px;
}

    <main>
    <section class="hero">...</section>
    <section class="below-fold-section">...</section>
    <section class="below-fold-section">...</section>
</main>

    Code Breakdown:

    • content-visibility: auto — skips rendering until the section nears the viewport.
    • contain-intrinsic-size: 0 500px — placeholder size to prevent layout shift.
    • Reduces initial rendering cost by 20–50% on long pages.

    Example 4: contain for Isolated Subtrees

    .widget {
    contain: layout paint;
}

    Code Breakdown:

    • contain: layout — changes inside the widget do not affect the rest of the page.
    • contain: paint — the widget's paint is clipped to its bounds.
    • Prevents a widget update from triggering full-page layout.

    Example 5: Reserving Space for Images

    <img src="photo.jpg"
     alt="Photo"
     width="800"
     height="600"
     loading="lazy">

    /* Alternative: use aspect-ratio */
.image-container {
    aspect-ratio: 4 / 3;
    width: 100%;
}

    Code Breakdown:

    • width and height on <img> reserve space before the image loads — no layout shift.
    • aspect-ratio on the container reserves space based on the ratio.
    • CLS target: < 0.1.

    Example 6: Reserving Space for Ads

    <div class="ad-slot" style="min-height: 250px;">
    <!-- Ad loads here -->
</div>

    Code Breakdown:

    • min-height reserves space for the ad.
    • The ad loads into the reserved space — no layout shift.
    • Use fixed dimensions where possible.

    Example 7: Breaking Long Tasks

    // ❌ Long task: blocks the main thread for 200ms
function processItems(items) {
    items.forEach(item => {
        heavyComputation(item);
    });
}

// ✅ Yielding to the browser
async function processItems(items) {
    for (const item of items) {
        heavyComputation(item);
        await scheduler.yield(); // yields to the browser
    }
}

    Code Breakdown:

    • The first version blocks the main thread for the entire loop — jank.
    • The second version yields after each item — the browser can paint between iterations.
    • scheduler.yield() is the modern API (Chrome 129+).

    Example 8: Using requestAnimationFrame for Visual Updates

    // ❌ Visual update outside rAF — may cause jank
el.style.transform = `translateX(${x}px)`;

// ✅ Visual update inside rAF
requestAnimationFrame(() => {
    el.style.transform = `translateX(${x}px)`;
});

    Code Breakdown:

    • Visual updates should be batched into requestAnimationFrame.
    • The browser schedules the update at the next frame boundary.
    • Prevents layout thrashing and jank.

    Example 9: Monitoring Layout Shifts

    new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        if (!entry.hadRecentInput) {
            console.log('Layout shift:', {
                value: entry.value,
                sources: entry.sources
            });
        }
    }
}).observe({ type: 'layout-shift', buffered: true });

    Code Breakdown:

    • layout-shift entries report CLS.
    • hadRecentInput: true — shifts within 500ms of user input are excluded from CLS.
    • sources — identifies the elements that shifted.

    Example 10: Complete Rendering-Optimized Component

    .card {
    /* Isolate from surroundings */
    contain: layout paint;

    /* Reserve space */
    aspect-ratio: 4 / 3;

    /* Animate cheaply */
    transition: transform 200ms ease, opacity 200ms ease;
}

.card:hover {
    transform: translateY(-4px);
    opacity: 0.9;
}

/* Skip rendering off-screen cards */
.card-list .card {
    content-visibility: auto;
    contain-intrinsic-size: 0 300px;
}

    Code Breakdown:

    • contain — isolates each card from its neighbors.
    • aspect-ratio — reserves space for the card.
    • transform + opacity — composite-only hover animation.
    • content-visibility: auto — skips rendering off-screen cards.

    11. Best Practices

    1. Animate only transform and opacity. Why: they run on the compositor thread; no layout or paint.
    2. Never animate width, height, top, left, margin, or padding. Why: they trigger layout and jank.
    3. Use will-change sparingly. Why: too many layers waste memory and GPU.
    4. Remove will-change after the animation. Why: prevents layer bloat.
    5. Use contain to isolate subtrees. Why: prevents changes from cascading to the whole page.
    6. Use content-visibility: auto for long pages. Why: skips off-screen rendering.
    7. Always specify width and height on images. Why: prevents layout shift (CLS).
    8. Use aspect-ratio for containers. Why: reserves space without explicit dimensions.
    9. Batch DOM reads and writes. Why: prevents forced synchronous layout.
    10. Use requestAnimationFrame for visual updates. Why: batches updates to the next frame.
    11. Break long tasks into chunks. Why: prevents main-thread blocking.
    12. Use scheduler.yield() to yield to the browser. Why: allows paint between tasks.
    13. Use the Layout Instability API to measure CLS. Why: identifies shifting elements.
    14. Use the Performance panel to profile rendering. Why: identifies bottlenecks.
    15. Avoid layout thrashing in loops. Why: forces layout on every iteration.
    16. Use transform: translate() instead of top/left for positioning. Why: composite-only.
    17. Use transform: scale() instead of width/height for size changes. Why: composite-only.
    18. Reserve space for ads, embeds, and iframes. Why: prevents CLS.
    19. Avoid inserting content above existing content. Why: causes layout shift.
    20. Test on low-end devices. Why: rendering gaps are invisible on fast hardware.
    21. Monitor INP and CLS in production. Why: real user metrics reveal issues lab data misses.
    22. Use View Transitions API for page transitions. Why: native, smooth, compositor-driven.
    23. Prefer content-visibility over manual visibility toggling. Why: native rendering skip.
    24. Avoid position: fixed on animating elements. Why: forces layer promotion and repaint.
    25. Audit rendering performance after every significant UI change. Why: regressions are common.

    12. Common Mistakes

    ❌ Mistake: Animating top / left

    .card:hover {
    top: -4px;
}

    Why it's wrong: top triggers layout on every frame — jank.

    ✅ Correct:

    .card:hover {
    transform: translateY(-4px);
}

    ❌ Mistake: Animating width / height

    .card:hover {
    width: 220px;
}

    Why it's wrong: width triggers layout — jank.

    ✅ Correct:

    .card:hover {
    transform: scale(1.1);
}

    ❌ Mistake: Layout Thrashing in Loops

    for (const el of elements) {
    el.style.height = el.offsetHeight + 10 + 'px';
}

    Why it's wrong: Interleaves reads and writes — forces layout on every iteration.

    ✅ Correct:

    const heights = elements.map(el => el.offsetHeight);
elements.forEach((el, i) => el.style.height = heights[i] + 10 + 'px');

    ❌ Mistake: Permanent will-change

    .card {
    will-change: transform;
}

    Why it's wrong: The element is always promoted to a layer — wasted memory.

    ✅ Correct:

    .card:hover {
    will-change: transform;
}
.card:not(:hover) {
    will-change: auto;
}

    ❌ Mistake: Images Without Dimensions

    <img src="photo.jpg" alt="Photo">

    Why it's wrong: The browser does not know the image dimensions, causing layout shift (CLS).

    ✅ Correct:

    <img src="photo.jpg" alt="Photo" width="800" height="600">

    ❌ Mistake: No Space Reserved for Ads

    <div class="ad-slot">
    <!-- Ad loads here -->
</div>

    Why it's wrong: The ad loads and pushes content down — layout shift.

    ✅ Correct:

    <div class="ad-slot" style="min-height: 250px;"></div>

    ❌ Mistake: Long Tasks

    function processAll(items) {
    items.forEach(item => heavyWork(item));
}

    Why it's wrong: Blocks the main thread — jank and high INP.

    ✅ Correct:

    async function processAll(items) {
    for (const item of items) {
        heavyWork(item);
        await scheduler.yield();
    }
}

    ❌ Mistake: Visual Updates Outside requestAnimationFrame

    el.style.transform = `translateX(${x}px)`;

    Why it's wrong: Updates may not be batched to the next frame.

    ✅ Correct:

    requestAnimationFrame(() => {
    el.style.transform = `translateX(${x}px)`;
});

    ❌ Mistake: No contain on Self-Contained Widgets

    .widget {
    /* No contain */
}

    Why it's wrong: Changes inside the widget trigger layout on the whole page.

    ✅ Correct:

    .widget {
    contain: layout paint;
}

    ❌ Mistake: Excessive Layer Promotion

    .card {
    will-change: transform;
    transform: translateZ(0);
    backface-visibility: hidden;
}

    Why it's wrong: Every card is promoted — layer bloat and GPU memory exhaustion.

    ✅ Correct: Promote only the elements that animate.

    13. Performance Considerations

    • Composite-only animations are 5–10× cheaper than layout animations.
    • Layout thrashing can block the main thread for hundreds of milliseconds.
    • content-visibility: auto reduces initial rendering by 20–50%.
    • contain: layout paint isolates subtrees.
    • Long tasks over 50ms delay rendering.
    • 60fps requires 16.7ms per frame; 120fps requires 8.3ms.
    • Layer promotion costs GPU memory.
    • CLS target: < 0.1.
    • INP target: < 200ms.
    • Every layout, paint, and composite eats into the frame budget.

    Performance Tips

    1. Animate transform and opacity.
    2. Use will-change sparingly.
    3. Use contain for isolated widgets.
    4. Use content-visibility: auto for long pages.
    5. Reserve space for images and ads.
    6. Batch DOM reads and writes.
    7. Break long tasks.
    8. Use requestAnimationFrame for visual updates.
    9. Measure with Lighthouse, Performance panel, and RUM.
    10. Test on low-end devices.

    14. Security Considerations

    Rendering Impact and CSP

    CSP does not directly affect rendering. But inline styles used for animations require 'unsafe-inline' in style-src unless nonces or hashes are used.

    Rendering Impact and Layout Leaks

    Ad and widget iframes can read the parent page's layout in some cases. Use contain to isolate them.

    Layer Promotion and Security

    Promoting an element to its own layer can leak information via timing side channels. Modern browsers mitigate this with cross-origin isolation.

    View Transitions and Security

    The View Transitions API captures a snapshot of the page — ensure that sensitive data is not exposed during the transition.

    Long Tasks and Side Channels

    Long tasks can leak information via timing side channels. Modern browsers mitigate this with high-resolution timer restrictions.

    16. When to Use

    • Every animation — use transform and opacity.
    • Every long page — use content-visibility: auto.
    • Every self-contained widget — use contain.
    • Every image — specify width and height.
    • Every ad slot — reserve space.
    • Every long task — break it up.
    • Every visual update — batch in requestAnimationFrame.

    17. When Not to Use

    • Do not animate width, height, top, left, margin, or padding. Use transform.
    • Do not use will-change permanently. Remove it after the animation.
    • Do not promote every element to a layer. It wastes memory.
    • Do not read layout in a loop. Batch reads first.
    • Do not insert content above existing content. It causes CLS.
    • Do not leave long tasks on the main thread. Break them up.
    • Do not use position: fixed for animating elements. Use transform.
