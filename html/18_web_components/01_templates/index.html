    Templates

    1. Overview

    Definition

    The <template> element is an HTML element that holds markup that is parsed but not rendered. Its content is stored in a separate DocumentFragment — not in the main DOM tree — and remains inert until cloned and inserted by JavaScript. It is the standard primitive for defining reusable HTML fragments declaratively.

    <template id="user-card">
    <article class="card">
        <img class="avatar" alt="">
        <h2 class="name"></h2>
        <p class="bio"></p>
    </article>
</template>

<script>
    const template = document.getElementById('user-card');
    const clone = template.content.cloneNode(true);

    clone.querySelector('.avatar').src = 'alice.jpg';
    clone.querySelector('.name').textContent = 'Alice';
    clone.querySelector('.bio').textContent = 'Software engineer.';

    document.body.appendChild(clone);
</script>

    The <template> element behaves unlike every other HTML element:

    • Its content is not a child — template.children is empty.
    • Its content is not rendered — no layout, no paint.
    • Its content is not in the accessibility tree.
    • Its content is not matched by page CSS selectors.
    • Its content is inert — scripts do not run, images do not load, iframes do not fetch.

    The content lives in template.content — a DocumentFragment — and is instantiated by cloning.

    Templates are the foundation of Web Components. They define the initial shadow tree, provide the markup for custom elements, and pair with slots to project consumer content. Every modern component — from Lit to FAST to Stencil — begins with a template.

    Purpose

    The <template> element serves several essential purposes:

    • Deferred parsing — HTML is parsed once, rendered on demand.
    • Reusable markup — a single declaration, unlimited instances.
    • Inert content — scripts and network requests do not fire until instantiation.
    • Client-side templating — replace fragile string concatenation with parsed markup.
    • Web Components — define the shadow DOM structure of custom elements.
    • Performance — parse once, clone cheaply.
    • Security — safe container for markup that has not yet been vetted for insertion.
    • Declarative Shadow DOM — server-render shadow roots via shadowrootmode.

    The template element is the only HTML element with a separate content document. It is a unique platform primitive designed for component-oriented architecture.

    Where It Fits

    Web Components
│
├── Templates              ← reusable markup (THIS CHAPTER)
├── Slots                  ← content projection
├── Shadow DOM             ← style and structure encapsulation
├── Custom Elements        ← reusable component definitions
└── Declarative Shadow DOM ← server-rendered shadow roots

    Templates sit at the base of the Web Components stack. They define the markup; slots project content into it; Shadow DOM encapsulates it; custom elements bind it to a tag.

    2. Why It Exists

    The Problem

    Before <template>, developers had no native way to hold reusable HTML. Every workaround was broken:

    • Hidden <div> elements — parsed, laid out (then hidden), part of the DOM, affected by CSS, exposed to assistive technology.
    • <script type="text/template"> — a hack that abused the script element to hide markup; the content was a string, not a DOM tree.
    • JavaScript string concatenation — XSS-prone, slow to parse on every use, no static analysis.
    • innerHTML with embedded markup — re-parsed on every instance; no parse-time validation.

    Each of these approaches had a fundamental flaw: they were not designed for reusable markup. They were borrowed from other purposes and produced side effects — rendering, DOM pollution, style leakage, or security risks.

    <!-- Old approach: hidden div -->
<div id="template" style="display: none;">
    <article class="card">...</article>
</div>

<!-- Problems:
  - Parsed, laid out, then hidden (wasted work)
  - Part of the DOM (visible to querySelector, accessibility tools)
  - Subject to CSS rules targeting .card
  - Scripts and images inside still execute/load
-->

    // Old approach: string concatenation
const html = `<article class="card"><h2>${userInput}</h2></article>`;
container.innerHTML = html;

// Problems:
  - XSS if userInput is untrusted
  - Re-parses HTML on every use
  - No syntax highlighting, no linting
  - Errors discovered at runtime

    Previous Limitations

    Limitation Consequence
    No native template element No declarative way to hold reusable markup
    Hidden divs were rendered Wasted layout and paint
    Hidden divs were in the DOM CSS selectors and accessibility tools matched them
    Hidden divs were not inert Scripts executed, images loaded
    String concatenation XSS risks, poor performance, no static analysis
    No parse-time validation Errors discovered only at runtime
    No encapsulation Templates leaked styles and structure into the page

    Why It Was Introduced

    The <template> element was introduced as part of the Web Components specification, which was proposed by Google around 2011 and standardized in the HTML Living Standard. It shipped in Chrome 26 (2013), Firefox 22 (2013), Safari 8 (2014), and Edge 13 (2015).

    The key innovation was the separate content document: rather than storing the template's markup as children (which would render them), the browser parses the content into a DocumentFragment owned by a template contents owner document. This makes the content:

    • Parsed — a valid DOM tree, not a string.
    • Inert — scripts do not run, resources do not load.
    • Not rendered — no layout, no paint.
    • Not in the DOM — not matched by page selectors.
    • Not accessible — not in the accessibility tree.

    The template element is the only HTML element with these properties. It is a genuine platform primitive.

    Since HTML5 shipped templates, they have become the foundation of:

    • Lit — HTML tagged template literals.
    • FAST — templates as the component markup.
    • Stencil — compiled templates.
    • Vue — <template> in Single File Components.
    • Angular — <ng-template>.
    • Svelte — compiled templates to JavaScript.
    • React — JSX (not <template>, but the same concept).

    In 2026, the <template> element is baseline and universally supported. It is the declarative foundation of Web Components and the standard answer to "how do I hold reusable markup in HTML?"

    3. Syntax / Basic Usage

    The Minimal Template

    <template id="greeting">
    <p class="message">Hello!</p>
</template>

    Code Breakdown

    • <template> — the template element.
    • id="greeting" — standard id for JavaScript access.
    • <p class="message">Hello!</p> — the template content.

    Critical detail: template.children is empty. The content is not a child of the template — it is stored in template.content.

    Accessing the Content

    const template = document.getElementById('greeting');

console.log(template.children.length);    // 0 — no children!
console.log(template.childNodes.length);  // 0 — no child nodes!
console.log(template.innerHTML);          // "" — empty string!
console.log(template.content);            // #document-fragment (the actual content)
console.log(template.content.children.length); // 1 — the actual count

    Cloning the Content

    const template = document.getElementById('greeting');
const clone = template.content.cloneNode(true);

document.body.appendChild(clone);

// The clone is now part of the DOM and rendered

    Code Breakdown

    • template.content — the DocumentFragment holding the template's parsed content.
    • .cloneNode(true) — deep clone of the entire content subtree.
    • document.body.appendChild(clone) — inserts the clone into the DOM.

    The Two-Step Pattern

    Every template use follows the same two steps:

    // 1. Clone
const clone = template.content.cloneNode(true);

// 2. Insert
container.appendChild(clone);

    Between the two steps, the clone can be customized — text set, attributes changed, event listeners attached — before it is rendered.

    The Full Production Example

    <template id="product-card-template">
    <style>
        .card {
            display: grid;
            grid-template-columns: 80px 1fr;
            gap: 1rem;
            padding: 1rem;
            border: 1px solid #e0e0e0;
            border-radius: 8px;
        }
        .image {
            width: 80px;
            height: 80px;
            object-fit: cover;
            border-radius: 4px;
        }
        .name { font-weight: bold; margin: 0; }
        .price { color: #2c7a2c; font-weight: bold; }
    </style>
    <div class="card">
        <img class="image" alt="">
        <div>
            <h3 class="name"></h3>
            <p class="price"></p>
        </div>
    </div>
</template>

<ul id="products"></ul>

<script>
    const products = [
        { name: 'Nike Pegasus 41', price: '$139.99', image: '/nike.jpg' },
        { name: 'Adidas Ultraboost', price: '$179.99', image: '/adidas.jpg' },
        { name: 'Brooks Ghost 16', price: '$149.99', image: '/brooks.jpg' }
    ];

    const template = document.getElementById('product-card-template');
    const list = document.getElementById('products');

    • The template holds a complete card structure with styles.
    • Each clone is customized with product data.
    • Clones are batched into a DocumentFragment for a single DOM insertion.
    • The template is parsed once at page load; cloning is cheap.

    Declarative Shadow DOM

    <my-element>
    <template shadowrootmode="open">
        <style>
            p { color: blue; }
        </style>
        <p>Shadow content</p>
    </template>
</my-element>

    Code Breakdown

    • shadowrootmode="open" — declares the template as a shadow root.
    • The content becomes the shadow tree of <my-element>.
    • The template element is removed from the DOM after parsing.
    • Supported in Chrome 90+, Edge 90+, Safari 16.4+, Firefox 123+.

    The Three Declarative Shadow DOM Attributes

    <!-- Basic declarative shadow root -->
<template shadowrootmode="open">...</template>

<!-- Focus delegation: host focus goes to the first focusable element -->
<template shadowrootmode="open" shadowrootdelegatesfocus>...</template>

<!-- Clonable: the shadow root can be cloned via cloneNode() -->
<template shadowrootmode="open" shadowrootclonable>...</template>

<!-- Serializable: the shadow root can be serialized via getHTML() -->
<template shadowrootmode="open" shadowrootserializable>...</template>

    Code Breakdown

    Attribute Purpose
    shadowrootmode "open" or "closed"
    shadowrootdelegatesfocus Delegates focus to the first focusable element
    shadowrootclonable Allows cloning via cloneNode()
    shadowrootserializable Allows serialization via getHTML()

    4. Mental Model

    The "Blueprint" Mental Model

    A template is a blueprint, not a rendered element:

    ┌─────────────────────────────────────────────┐
│  TEMPLATE (blueprint)                        │
│  └── Parsed but not rendered                 │
│  └── Stored in a DocumentFragment            │
│  └── Inert                                    │
│  └── Not in the DOM                           │
│                                              │
│  CLONE (instance)                            │
│  └── Created via cloneNode(true)             │
│  └── Inserted into the DOM                    │
│  └── Rendered and interactive                 │
└─────────────────────────────────────────────┘

    A blueprint is not a building. A template is not a rendered element. It is the source from which instances are created.

    The "Two-Tree" Mental Model

    The template element creates two separate trees:

    ┌─────────────────────────────────────────────┐
│  MAIN DOM TREE                                │
│  └── The document body                        │
│  └── Rendered, interactive, accessible        │
│                                              │
│  TEMPLATE CONTENT TREE                        │
│  └── template.content (DocumentFragment)      │
│  └── Parsed but not rendered                  │
│  └── Inert                                    │
│  └── Not in the accessibility tree            │
└─────────────────────────────────────────────┘

    The template's content is a separate tree from the main DOM. It is parsed but isolated.

    The "Children Are Empty" Mental Model

    The most counterintuitive aspect of the template element:

    const template = document.querySelector('template');

template.children.length;    // 0
template.childNodes.length;  // 0
template.innerHTML;          // "" (empty!)

template.content.children.length;    // 1 (the actual content)
template.content.childNodes.length;  // 1

    The template element has no children in the normal sense. Its content is in a separate DocumentFragment. This is why template.innerHTML returns an empty string — the content is not in the template element itself.

    This is not a bug. It is the defining characteristic of the template element.

    The "Inert Content" Mental Model

    The template's content is inert. Nothing in it executes or loads until cloned and inserted:

    ┌─────────────────────────────────────────────┐
│  INSIDE A TEMPLATE                           │
│  ├── Scripts do not run                       │
│  ├── Images do not load                       │
│  ├── Styles do not apply                      │
│  ├── Videos do not preload                    │
│  ├── Iframes do not load                      │
│  └── Event handlers do not attach             │
├─────────────────────────────────────────────┤
│  AFTER CLONING AND INSERTION                  │
│  ├── Scripts run                              │
│  ├── Images load                              │
│  ├── Styles apply                             │
│  ├── Videos preload                           │
│  ├── Iframes load                             │
│  └── Event handlers attach                    │
└─────────────────────────────────────────────┘

    This is why templates are safe — you can put anything inside, and nothing will happen until you clone it.

    The "Parse Once, Clone Many" Mental Model

    The template's content is parsed once when the page loads. Cloning is cheap — it copies the parsed tree, not the HTML string:

    ┌─────────────────────────────────────────────┐
│  WITHOUT TEMPLATE (string concatenation)     │
│  └── innerHTML = '...'                       │
│  └── Parses the HTML string on every use      │
│  └── Repeats parsing for each instance        │
├─────────────────────────────────────────────┤
│  WITH TEMPLATE                               │
│  └── Parsed once at page load                 │
│  └── cloneNode(true) copies the parsed tree  │
│  └── Cheap for each instance                  │
└─────────────────────────────────────────────┘

    Templates are dramatically faster than string concatenation for repeated markup.

    The "Foundation of Web Components" Mental Model

    The template element is the first building block of Web Components:

    ┌─────────────────────────────────────────────┐
│  TEMPLATE                                    │
│  └── Holds the markup                         │
│                                              │
│  SLOT                                        │
│  └── Projects content into the markup         │
│                                              │
│  SHADOW DOM                                  │
│  └── Encapsulates the markup                  │
│                                              │
│  CUSTOM ELEMENTS                             │
│  └── Instantiates the markup                  │
│                                              │
│  DECLARATIVE SHADOW DOM                      │
│  └── Server-renders the shadow root           │
└─────────────────────────────────────────────┘

    Every Web Component starts with a template.

    5. Core Concepts

    Concept 1: The <template> Element

    An HTML element whose content is parsed but not rendered. The content is stored in a separate DocumentFragment accessible via template.content.

    Concept 2: The content Property

    A read-only DocumentFragment containing the template's parsed content. This is where the template's markup actually lives. Not in template.children or template.innerHTML.

    Concept 3: The Empty Children

    The template element's children, childNodes, and innerHTML are empty. The content is not in the template element itself.

    Concept 4: The Inert Content

    Template content is inert — scripts do not run, images do not load, styles do not apply, iframes do not load. Nothing happens until the content is cloned and inserted.

    Concept 5: The cloneNode(true) Pattern

    Templates are instantiated by deep-cloning the content:

    const clone = template.content.cloneNode(true);

    Deep cloning copies all descendants. Shallow cloning (cloneNode(false)) copies only the top-level node — rarely useful.

    Concept 6: The DocumentFragment

    The template's content is a DocumentFragment — a lightweight, detached container. It can hold nodes but is not itself rendered.

    Concept 7: The Two-Step Pattern

    Every template use follows two steps: clone, then insert.

    const clone = template.content.cloneNode(true);
container.appendChild(clone);

    Concept 8: The id Attribute

    Templates typically have an id for JavaScript access. The id is the standard mechanism for finding the template.

    Concept 9: Nested Templates

    Templates can contain other templates. This is useful for recursive structures.

    <template id="tree-node">
    <li>
        <span></span>
        <ul></ul>
    </li>
</template>

    Concept 10: Templates in Shadow DOM

    Templates are commonly used with Shadow DOM to define the shadow root's initial content:

    const template = document.getElementById('my-template');
const shadowRoot = element.attachShadow({ mode: 'open' });
shadowRoot.appendChild(template.content.cloneNode(true));

    Concept 11: Templates and Slots

    Templates can include <slot> elements for content projection:

    <template id="card-template">
    <div class="card">
        <slot name="title"></slot>
        <slot name="body"></slot>
    </div>
</template>

    Concept 12: Declarative Shadow DOM

    The shadowrootmode attribute turns a template into a declarative shadow root:

    <template shadowrootmode="open">
    <p>Shadow content</p>
</template>

    Supported in Chrome 90+, Edge 90+, Safari 16.4+, Firefox 123+.

    Concept 13: shadowrootdelegatesfocus

    Enables focus delegation — when the host is focused, the first focusable element in the shadow root receives focus.

    Concept 14: shadowrootclonable

    Allows the shadow root to be cloned via cloneNode().

    Concept 15: shadowrootserializable

    Allows the shadow root to be serialized via getHTML(). Used for SSR and content extraction.

    Concept 16: The Template Contents Owner Document

    The template's content fragment belongs to a separate owner document — the "template contents owner document." This is why the content is inert and isolated. It is a distinct document context, not the main document.

    Concept 17: The template.innerHTML Empty Result

    template.innerHTML returns an empty string because the content is not in the template element. To get the content's HTML, use:

    template.content.firstElementChild.outerHTML;

    Concept 18: Templates vs. Hidden Elements

    <template> <div hidden>
    Rendered No Yes (then hidden)
    In DOM No Yes
    In accessibility tree No No
    Scripts run No Yes
    Images load No Yes
    CSS matches No Yes
    Content access template.content .children

    Concept 19: Templates vs. String Concatenation

    // Slow: parses HTML string on every use
for (const item of items) {
    container.innerHTML += `<li>${item}</li>`;
}

// Fast: parsed once, cloned cheaply
const fragment = document.createDocumentFragment();
for (const item of items) {
    const clone = template.content.cloneNode(true);
    clone.querySelector('li').textContent = item;
    fragment.appendChild(clone);
}
container.appendChild(fragment);

    Concept 20: Templates and Frameworks

    Most frameworks use templates internally:

    • Lit — HTML tagged template literals.
    • Vue — <template> in Single File Components.
    • Angular — <ng-template>.
    • Svelte — compiles templates to JavaScript.
    • React — uses JSX (not <template>).

    1.  Tokenizer encounters <template>.
    │
    ▼

    │
    ▼

    │   └── Content is parsed into the template's content DocumentFragment.
    │
    ▼
4.  All content between <template> and </template> is
    │   parsed into the template's content fragment.
    │
    ▼

    │   but the content fragment is not.
    │
    ▼
6.  Parsing continues after </template>.

    │
    ▼

    │   of the DocumentFragment.
    │
    ▼

    │   └── Not yet in the DOM.
    │
    ▼
4.  JavaScript modifies the clone (set text, attributes, etc.).
    │
    ▼
5.  container.appendChild(clone) inserts the clone's children
    │   into the container.
    │
    ▼
6.  The clone is now part of the DOM and rendered.

    Step-by-Step: The Inert Content

    1.  Template content is parsed.
    │
    ▼

    │   └── <script> elements are parsed but not run.
    │
    ▼
3.  Images are NOT loaded.
    │   └── <img> elements are parsed but no network request.
    │
    ▼
4.  Styles are NOT applied.
    │   └── <style> elements are parsed but not applied.
    │
    ▼
5.  Iframes are NOT loaded.
    │   └── <iframe> elements are parsed but no network request.
    │
    ▼
6.  Everything remains inert until cloned and inserted.

    │
    ▼

    │
    ▼
3.  Tree constructor creates a shadow root on the parent element.
    │
    ▼
4.  Content is parsed directly into the shadow root.
    │
    ▼

    │
    ▼
6.  The shadow root is now attached to the parent element.
    │
    ▼
7.  Custom element upgrade attaches to the existing shadow root.

    │
    ▼

    ▼

    ▼

    │
    ▼

    │
    ▼

    The HTMLTemplateElement Interface

    interface HTMLTemplateElement extends HTMLElement {
    readonly content: DocumentFragment;
    shadowRootMode: string;
    shadowRootDelegatesFocus: boolean;
    shadowRootClonable: boolean;
    shadowRootSerializable: boolean;
}

    The "Template Contents Owner Document"

    The template's content fragment belongs to a separate owner document — the "template contents owner document." This is a distinct document context, not the main document.

    ┌─────────────────────────────────────────────┐
│  MAIN DOCUMENT                               │
│  └── The page's document                     │
│      └── <template> element                  │
│                                              │
│  TEMPLATE CONTENTS OWNER DOCUMENT            │
│  └── A separate document                     │
│      └── The template's content fragment     │
│          └── Isolated from the main document │
└─────────────────────────────────────────────┘

    This is why the content is inert — it belongs to a different document context.

    The content Property

    The content property is read-only. It returns the DocumentFragment. Its children can be manipulated, but the fragment reference itself cannot be reassigned.

    template.content = otherFragment; // ❌ Error: read-only
template.content.appendChild(node); // ✅ Works

    The Parsing Mode Switch

    When the tree constructor encounters <template>:

    1. It creates an HTMLTemplateElement.
    2. It inserts the template element into the current node.
    3. It switches to a template insertion mode and pushes a marker onto the stack of open elements.
    4. It parses the content into the template's content fragment.
    5. When </template> is encountered, the template is popped and parsing continues.

    The shadowrootmode Processing

    When the parser sees <template shadowrootmode="open">:

    1. It checks if the parent element is a valid shadow host.
    2. It attaches a shadow root to the parent element.
    3. It parses the content directly into the shadow root.
    4. It removes the template element from the DOM.

    This is the only way to create a shadow root from HTML.

    The Clone Algorithm

    template.content.cloneNode(true):

    1. Creates a new DocumentFragment.
    2. Deep-clones each child node.
    3. The clone's owner document is the current document — not the template's owner document.
    4. Returns the new fragment.

    The outerHTML on Templates

    template.outerHTML returns the template element without its content:

    template.outerHTML; // "<template id="my-template"></template>"

    This is a common surprise. To see the content, use template.content.firstElementChild.outerHTML.

    The innerHTML on Templates

    template.innerHTML returns an empty string because the content is not in the template element. Setting template.innerHTML also has no effect — it does not populate the content.

    The DocumentFragment Optimization

    DocumentFragment is optimized for batch DOM operations:

    Appending a fragment:
  └── All children are moved to the target in one operation.
  └── One DOM mutation.
  └── One style recalculation.
  └── One layout.

    The Named Content Document for Templates

    Templates use a separate document context — this ensures that scripts, styles, and resources inside the template are not activated when the template is parsed. They activate only when the clone is inserted into the main document.

    Example 3: Recursive Template (Tree Rendering)

    <ul id="tree"></ul>

<template id="tree-template">
    <li class="node">
        <span class="label"></span>
        <ul class="children"></ul>
    </li>
</template>

<script>
    const template = document.getElementById('tree-template');

    function renderNode(node) {
        const clone = template.content.cloneNode(true);
        clone.querySelector('.label').textContent = node.label;

        if (node.children?.length) {
            const childrenList = clone.querySelector('.children');
            const fragment = document.createDocumentFragment();
            for (const child of node.children) {
                fragment.appendChild(renderNode(child));
            }
            childrenList.appendChild(fragment);
        }

        return clone;
    }

    const tree = {
        label: 'Root',
        children: [
            { label: 'Child 1' },
            { label: 'Child 2', children: [{ label: 'Grandchild' }] }
        ]
    };

    document.getElementById('tree').appendChild(renderNode(tree));
</script>

    Code Breakdown:

    • The template contains a recursive .children list.
    • renderNode clones the template and recursively renders children.
    • The result is a nested tree structure.

    11. Best Practices

    1. Use templates instead of string concatenation. Why: parsed once, cloned cheaply.
    2. Use template.content.cloneNode(true). Why: the content property is the actual content.
    3. Batch clones with a DocumentFragment. Why: one DOM operation for many clones.
    4. Customize the clone before insertion. Why: avoids unnecessary DOM mutations.
    5. Attach event listeners to the clone before insertion. Why: avoids re-querying after insertion.
    6. Use id for template identification. Why: standard way to find templates.
    7. Keep templates focused. Why: small templates are easier to maintain.
    8. Use templates with Shadow DOM. Why: encapsulates styles and structure.
    9. Use templates with slots. Why: enables content projection.
    10. Use shadowrootmode for declarative shadow DOM. Why: server-renderable.
    11. Remember that template.children is empty. Why: content is in template.content.
    12. Remember that template.innerHTML is empty. Why: content is not in the template.
    13. Do not put scripts in templates expecting them to run. Why: they do not run until cloned and inserted.
    14. Do not put external resources in templates expecting them to load. Why: they do not load until cloned and inserted.
    15. Cache template references. Why: getElementById is not free.
    16. Test templates in all target browsers. Why: shadowrootmode support varies.
    17. Use shadowrootclonable when cloning is needed. Why: it enables shadow root cloning.
    18. Use shadowrootserializable for SSR. Why: it enables shadow root serialization.
    19. Use shadowrootdelegatesfocus for form controls. Why: better UX.
    20. Clean up clones when no longer needed. Why: prevents memory leaks.
    21. Use DocumentFragment for cloning batching. Why: performance.
    22. Prefer templates over hidden divs. Why: hidden divs are rendered (then hidden).
    23. Prefer templates over <script type="text/template">. Why: script hacks are obsolete.
    24. Audit template usage after framework upgrades. Why: framework output may change.
    25. Document template patterns. Why: consistency across the team.

    12. Common Mistakes

    ❌ Mistake: Using template.innerHTML

    template.innerHTML; // "" (empty!)

    Why it's wrong: The content is not in the template element — it is in template.content.

    ✅ Correct:

    template.content.querySelector('p').textContent;
// or
template.content.firstElementChild.outerHTML;

    ❌ Mistake: Using template.children

    template.children.length; // 0

    Why it's wrong: The template element has no children — the content is in template.content.

    ✅ Correct:

    template.content.children.length;

    ❌ Mistake: Appending the Template Directly

    container.appendChild(template);

    Why it's wrong: Appends the template element itself, not its content.

    ✅ Correct:

    container.appendChild(template.content.cloneNode(true));

    ❌ Mistake: Forgetting to Clone

    container.appendChild(template.content);

    Why it's wrong: Moves the content out of the template — subsequent uses find nothing.

    ✅ Correct:

    container.appendChild(template.content.cloneNode(true));

    ❌ Mistake: String Concatenation Instead of Templates

    for (const item of items) {
    container.innerHTML += `<li>${item}</li>`;
}

    Why it's wrong: Re-parses HTML on every iteration — slow and error-prone.

    ✅ Correct:

    for (const item of items) {
    const clone = template.content.cloneNode(true);
    clone.querySelector('li').textContent = item;
    fragment.appendChild(clone);
}
container.appendChild(fragment);

    ❌ Mistake: No DocumentFragment Batching

    for (const item of items) {
    container.appendChild(template.content.cloneNode(true));
}

    Why it's wrong: Each append is a separate DOM mutation.

    ✅ Correct:

    const fragment = document.createDocumentFragment();
for (const item of items) {
    fragment.appendChild(template.content.cloneNode(true));
}
container.appendChild(fragment);

    ❌ Mistake: Scripts Inside Templates

    <template>
    <script>console.log('Hello');</script>
</template>

    Why it's wrong: Scripts in templates do not run until cloned and inserted. This may surprise.

    ✅ Correct: Understand that scripts run on insertion, not on parse.

    ❌ Mistake: Images Inside Templates

    <template>
    <img src="large-image.jpg">
</template>

    Why it's wrong: Images in templates do not load until cloned and inserted. This is actually a feature — it defers loading.

    ✅ Correct: This is the desired behavior.

    ❌ Mistake: Assuming shadowrootmode Is Universally Supported

    <template shadowrootmode="open">
    <p>Shadow content</p>
</template>

    Why it's wrong: shadowrootmode requires Chrome 90+, Edge 90+, Safari 16.4+, Firefox 123+.

    ✅ Correct: Test in target browsers; provide a polyfill if needed.

    ❌ Mistake: Not Caching Template References

    for (const item of items) {
    const template = document.getElementById('item-template');
    // ...
}

    Why it's wrong: getElementById is called on every iteration.

    ✅ Correct:

    const template = document.getElementById('item-template');
for (const item of items) {
    // ...
}

    ❌ Mistake: Using cloneNode(false) on the Content

    const clone = template.content.cloneNode(false); // shallow

    Why it's wrong: Shallow cloning copies only the fragment — not its children. The clone is empty.

    ✅ Correct:

    const clone = template.content.cloneNode(true); // deep

    13. Performance Considerations

    • Templates are parsed once — cheap to clone.
    • Cloning is fast — copies the parsed tree, not the HTML string.
    • DocumentFragment batching — one DOM mutation for many clones.
    • Inert content — no scripts, no network requests until cloned.
    • innerHTML is slower — re-parses the HTML string on every use.
    • Template cloning is faster than string concatenation for repeated markup.
    • cloneNode(true) deep clones — shallow clones are cheaper but rarely useful.
    • DocumentFragment avoids reflows — the fragment is not rendered until appended.

    Performance Tips

    1. Parse once, clone many.
    2. Batch with DocumentFragment.
    3. Customize before insertion.
    4. Cache template references.
    5. Use templates instead of string concatenation.
    6. Avoid modifying the template content directly.
    7. Use shallow clones only when the fragment itself is needed.
    8. Test with large numbers of clones.

    14. Security Considerations

    Inert Content Is Safe

    Template content is inert — scripts do not run, images do not load. This makes templates safe to hold untrusted markup until it is cloned.

    Cloning Does Not Sanitize

    Cloning a template does not sanitize its content. If the template contains malicious markup, the clone will too.

    Defense: Sanitize content before inserting it into a template.

    innerHTML on Template Content

    template.content.innerHTML = userInput; // XSS risk

    Setting template.content.innerHTML parses HTML. This is an XSS risk if the input is untrusted.

    Defense: Use textContent or sanitize with DOMPurify.

    Template Injection

    If a template's content is generated from user input without escaping, attackers can inject markup.

    Defense: Escape user input; use textContent for text content.

    Declarative Shadow DOM and CSP

    Declarative Shadow DOM is subject to CSP. Ensure policies cover shadow roots.

    shadowrootclonable and shadowrootserializable

    These attributes allow cloning and serializing shadow roots — verify they do not expose sensitive content.

    Template Element and XSS

    The template element is not an XSS vector by itself. But if the template's content is populated from user input via innerHTML, XSS is possible.

    Defense: Validate and sanitize any content used to populate templates.

    15. Debugging Tips

    • Chrome DevTools → Elements — templates appear in the DOM, but their content does not.
    • Chrome DevTools → Elements → Properties — inspect template.content.
    • $0.content — the selected template's content.
    • $0.content.children — the template's actual children.
    • $0.innerHTML — returns empty (surprise).
    • $0.outerHTML — returns the template element without content.
    • Chrome DevTools → Console — inspect templates directly.
    • document.querySelectorAll('template') — list all templates.
    • template.content.cloneNode(true) — test cloning in console.
    • Chrome DevTools → Layers — verify declarative shadow roots.
    • element.shadowRoot — access a shadow root created by shadowrootmode.
    • getHTML() — serialize a shadow root with shadowrootserializable.
    • document.importNode(template.content, true) — import into another document.
    • Inspect template.content.ownerDocument — the separate document context.

    16. When to Use

    • Repeating markup — lists, cards, rows, items.
    • Web Components — define shadow DOM structure.
    • Custom Elements — instantiate component markup.
    • Client-side templating — replace string concatenation.

    17. When Not to Use

    • Do not use templates for single-use markup. Just write it directly.
    • Do not use templates for hidden content. Use <div hidden>.
    • Do not use templates for string concatenation. Templates are for DOM cloning.
    • Do not put scripts in templates expecting them to run. They run on insertion.
    • Do not use template.innerHTML. Use template.content.
    • Do not use templates without cloning. Always clone before insertion.
    • Do not assume shadowrootmode is universally supported. Test target browsers.
    • Do not use templates to sanitize content. They do not sanitize.
