    Custom Elements

    1. Overview

    Definition

    Custom Elements is a browser API that lets developers define their own HTML elements — complete with a tag name, a JavaScript class, lifecycle callbacks, and (optionally) a shadow root. A custom element is a first-class HTML element: it participates in parsing, styling, DOM APIs, form submission, and accessibility just like a built-in element.

    class UserCard extends HTMLElement {
    constructor() {
        super();
        const shadow = this.attachShadow({ mode: 'open' });
        shadow.innerHTML = `
            <style>
                .card { border: 1px solid #ccc; padding: 1rem; }
            </style>
            <div class="card">
                <h2>${this.getAttribute('name')}</h2>
                <p>${this.getAttribute('email')}</p>
            </div>
        `;
    }
}

customElements.define('user-card', UserCard);

    <user-card name="Alice" email="alice@example.com"></user-card>

    The browser parses <user-card> like any other element. But behind the tag, UserCard is a JavaScript class with a constructor, lifecycle callbacks, and its own encapsulated shadow tree. Custom Elements are the definition mechanism of Web Components — they bind templates, slots, and shadow DOM into a reusable, declarative tag.

    Custom Elements are not a framework. They are a platform primitive — the ability to extend HTML with new elements natively, without JavaScript libraries, build tools, or compilers.

    Purpose

    Custom Elements serve several essential purposes:

    • New HTML elements — define tags that did not exist.
    • Reusable components — encapsulate behavior and presentation.
    • Declarative API — consumers use HTML, not JavaScript configuration.
    • Encapsulation — combine with Shadow DOM for style and structure isolation.
    • Lifecycle callbacks — react to connection, disconnection, and attribute changes.
    • Form participation — act as form controls via ElementInternals.
    • Accessibility — participate in the accessibility tree naturally.
    • Framework interoperability — work alongside React, Vue, Angular, Svelte.

    Custom Elements are the tag layer of Web Components. Templates define the markup; slots project content; Shadow DOM encapsulates; custom elements define the tag.

    Where It Fits

    Web Components
│
├── Templates              ← reusable markup
├── Slots                  ← content projection
├── Shadow DOM             ← style and structure encapsulation
├── Custom Elements        ← reusable component definitions (THIS CHAPTER)
└── Declarative Shadow DOM ← server-rendered shadow roots

    Custom Elements sit at the top of the Web Components stack — they bind the other primitives to a tag.

    2. Why It Exists

    The Problem

    HTML has a fixed set of elements. Developers can use <div>, <span>, <button>, and the rest of the standard vocabulary, but they cannot invent new elements. The browser does not know what a <user-card> or <data-chart> is. It treats them as unknown elements — semantically meaningless, indistinguishable from a <div> in the accessibility tree.

    Before Custom Elements, developers used several workarounds:

    • class attributes with framework components — React.Component, Vue.component, etc. Framework-specific, not native.
    • Directives — Angular's ng-*, Vue's v-*. Not native elements.
    • Web Components polyfills — attempted to emulate custom elements but with performance and compatibility costs.
    • No encapsulation — every component shared the global namespace.
    • No lifecycle — no standard way to react to connection, disconnection, or attribute changes.

    The platform needed a way to extend HTML with new elements that behaved natively — parsed by the HTML parser, styled by CSS, manipulated by DOM APIs, and exposed to accessibility tools.

    Previous Limitations

    Limitation Consequence
    Fixed HTML vocabulary No new elements
    Framework-specific components Not portable across frameworks
    No encapsulation Global namespace collisions
    No lifecycle callbacks No standard way to react to DOM changes
    No native upgrade Components initialized inconsistently
    No form participation Custom controls could not submit
    No accessibility integration Custom elements were invisible to assistive technology

    Why It Was Introduced

    The Custom Elements specification was proposed as part of the Web Components initiative in 2011 by Google. It was designed to bring extensibility to HTML — the ability to define new elements natively.

    The specification went through two versions:

    • Custom Elements v0 (2013) — an early version shipped in Chrome, with a different API (document.registerElement()).
    • Custom Elements v1 (2016) — the standardized version with the modern API (customElements.define()).

    The v1 API became the standard and shipped in Chrome 54 (2016), Firefox 63 (2018), Safari 10.1 (2017), and Edge 79 (2020).

    The specification defines:

    • The customElements registry — a global registry of custom element definitions.
    • The customElements.define() method — registers a custom element.
    • The HTMLElement base class — custom elements extend it.
    • Lifecycle callbacks — connectedCallback, disconnectedCallback, attributeChangedCallback, adoptedCallback.
    • The element upgrade process — how the browser upgrades unknown elements to custom elements.
    • Autonomous vs. customized built-in elements — two flavors of custom elements.

    Custom Elements are inspired by similar mechanisms in other platforms:

    • XBL (XUL) — Mozilla's XML Binding Language.
    • Flex/Flash — custom components.
    • HTML's own extensibility — the dream of <my-widget> since the 1990s.

    In 2026, Custom Elements are baseline and universally supported. They power every major Web Component library — Lit, FAST, Stencil, Polymer — and are used by Google, Adobe, Microsoft, Salesforce, and thousands of production applications.

    3. Syntax / Basic Usage

    The Minimal Custom Element

    class HelloWorld extends HTMLElement {
    connectedCallback() {
        this.textContent = 'Hello, world!';
    }
}

customElements.define('hello-world', HelloWorld);

    <hello-world></hello-world>

    Code Breakdown

    • class HelloWorld extends HTMLElement — the custom element class.
    • connectedCallback() — runs when the element is inserted into the DOM.
    • this.textContent = 'Hello, world!' — sets the element's text.
    • customElements.define('hello-world', HelloWorld) — registers the custom element.

    The Two Flavors

    // Autonomous custom element: extends HTMLElement
class MyButton extends HTMLElement { }
customElements.define('my-button', MyButton);

// Customized built-in element: extends a specific built-in element
class FancyButton extends HTMLButtonElement { }
customElements.define('fancy-button', FancyButton, { extends: 'button' });

    Code Breakdown

    Flavor Extends Tag usage
    Autonomous HTMLElement <my-button>
    Customized built-in HTMLButtonElement <button is="fancy-button">

    Note: Safari does not support customized built-in elements as of 2026. Autonomous elements are the recommended approach.

    The Naming Rules

    Custom element names must:

    • Start with a lowercase letter.
    • Contain a hyphen (-).
    • Be unique across the page.
    • Not conflict with reserved names.
    // ✅ Valid names
'my-element'
'user-card'
'x-component'
'data-chart'

// ❌ Invalid names
'myElement'         // no hyphen
'MY-ELEMENT'        // uppercase
'annotation-xml'    // reserved
'color-profile'     // reserved
'font-face'         // reserved

    The hyphen requirement exists to prevent collisions with future HTML elements.

    The customElements Registry

    // The global registry
console.log(customElements); // CustomElementRegistry

// Define a custom element
customElements.define('my-element', MyElement);

// Check if a name is defined
console.log(customElements.get('my-element')); // MyElement
console.log(customElements.get('nonexistent')); // undefined

// Get all definitions (not a standard API; use window.customElements)
customElements.whenDefined('my-element').then(() => {
    console.log('my-element is ready');
});

    The whenDefined() Method

    customElements.whenDefined('my-element').then(() => {
    // The element is defined
});

    Returns a Promise that resolves when the custom element is defined. Useful for coordinating initialization.

    The upgrade() Method

    customElements.upgrade(element);

    Forces the upgrade of a custom element. Used when elements are created in a different document or need manual upgrading.

    constructor() {
        super();

    connectedCallback() {

    A Complete Example with Shadow DOM

    <template id="user-card-template">
    <style>
        .card {
            border: 1px solid #ccc;
            border-radius: 8px;
            padding: 1rem;
            font-family: system-ui, sans-serif;
        }
        .name { font-weight: bold; font-size: 1.25rem; }

    </style>
    <div class="card">
        <div class="name"><slot name="name"></slot></div>
        <div class="email"><slot name="email"></slot></div>
    </div>
</template>

<script>

        constructor() {
            super();
            const shadow = this.attachShadow({ mode: 'open' });
            const template = document.getElementById('user-card-template');
            shadow.appendChild(template.content.cloneNode(true));
        }
    }
    customElements.define('user-card', UserCard);
</script>

<user-card>
    <span slot="name">Alice</span>
    <span slot="email">alice@example.com</span>
</user-card>

    Code Breakdown

    • The class extends HTMLElement.
    • The constructor calls super() and attachShadow().
    • The template is cloned into the shadow root.
    • The element is registered with customElements.define().

    Reactive Attributes

    class UserCard extends HTMLElement {
    static get observedAttributes() {
        return ['name', 'email'];
    }

    attributeChangedCallback(name, oldValue, newValue) {
        if (oldValue === newValue) return;

        if (name === 'name') {
            this.shadowRoot.querySelector('.name').textContent = newValue;
        }
        if (name === 'email') {
            this.shadowRoot.querySelector('.email').textContent = newValue;
        }
    }
}

    Code Breakdown

    • observedAttributes — a static getter returning the attributes to observe.
    • attributeChangedCallback — called when an observed attribute changes.
    • Updates the shadow DOM in response to attribute changes.

    Form-Associated Custom Elements

    class MyInput extends HTMLElement {
    static formAssociated = true;

    constructor() {
        super();
        this._internals = this.attachInternals();
        const shadow = this.attachShadow({ mode: 'open' });
        shadow.innerHTML = `<input type="text">`;

        const input = shadow.querySelector('input');
        input.addEventListener('input', () => {
            this._internals.setFormValue(input.value);
        });
    }

    get value() {
        return this._internals.value;
    }

    set value(v) {
        this.shadowRoot.querySelector('input').value = v;
        this._internals.setFormValue(v);
    }
}

customElements.define('my-input', MyInput);

    Code Breakdown

    • static formAssociated = true — declares the element as form-associated.
    • attachInternals() — returns an ElementInternals object.
    • setFormValue() — sets the value submitted with the form.
    • The element participates in form submission.

    The ElementInternals API

    this._internals = this.attachInternals();

this._internals.setFormValue(value);
this._internals.setValidity(flags, message, anchor);
this._internals.reportValidity();
this._internals.checkValidity();
this._internals.form;          // the associated form
this._internals.labels;        // the associated labels
this._internals.willValidate;  // whether the element will validate
this._internals.validity;      // the validity state

    Code Breakdown

    • setFormValue — sets the value submitted with the form.
    • setValidity — sets the validity state.
    • reportValidity — shows the validation message.
    • form — the associated form.
    • labels — the labels associated with the element.
    • validity — the current validity state.

    4. Mental Model

    The "Tag Definition" Mental Model

    A custom element is a tag definition — a tag name bound to a JavaScript class:

    ┌─────────────────────────────────────────────┐
│  TAG NAME: "user-card"                       │
│  CLASS: UserCard                             │
│                                              │
│  When the browser sees <user-card>:          │
│  └── Instantiate UserCard                    │
│  └── Run constructor                         │
│  └── Run connectedCallback                   │
│  └── Render the shadow tree                  │
└─────────────────────────────────────────────┘

    The browser treats <user-card> exactly like <div> or <button>. It is a first-class element.

    The "Upgrade" Mental Model

    The browser may encounter a custom element before it is defined:

    ┌─────────────────────────────────────────────┐
│  1. HTML PARSED                              │
│     └── <user-card> is an unknown element     │
│                                              │
│  2. SCRIPT LOADS                             │
│     └── customElements.define() is called    │
│                                              │
│  3. UPGRADE                                  │
│     └── The browser "upgrades" all existing  │
│         <user-card> elements                 │
│     └── Constructor runs                    │
│     └── connectedCallback runs              │
│                                              │
│  4. FUTURE ELEMENTS                          │
│     └── New <user-card> elements are         │
│         upgraded immediately                 │
└─────────────────────────────────────────────┘

    This is why custom elements work regardless of script load order — the browser upgrades unknown elements when the definition arrives.

    The "Two Flavors" Mental Model

    ┌─────────────────────────────────────────────┐
│  AUTONOMOUS CUSTOM ELEMENTS                  │
│  └── Extend HTMLElement                      │
│  └── Use <my-element>                        │
│  └── Fully custom behavior                   │
│  └── Supported everywhere                    │
├─────────────────────────────────────────────┤
│  CUSTOMIZED BUILT-IN ELEMENTS                │
│  └── Extend HTMLButtonElement, etc.          │
│  └── Use <button is="my-button">             │
│  └── Inherit built-in behavior               │
│  └── Not supported in Safari                 │
└─────────────────────────────────────────────┘

    Autonomous elements are the recommended approach.

    The "Lifecycle" Mental Model

    Custom elements have five lifecycle events:

    ┌─────────────────────────────────────────────┐
│  1. constructor()                            │
│     └── Element is created                   │
│     └── Do: attachShadow, setup state         │
│     └── Don't: inspect attributes, children  │
├─────────────────────────────────────────────┤
│  2. connectedCallback()                      │
│     └── Element is added to the DOM          │
│     └── Do: fetch data, attach listeners      │
├─────────────────────────────────────────────┤
│  3. disconnectedCallback()                   │
│     └── Element is removed from the DOM      │
│     └── Do: cleanup, detach listeners         │
├─────────────────────────────────────────────┤
│  4. attributeChangedCallback()                │
│     └── Observed attribute changes           │
│     └── Do: react to the change              │
├─────────────────────────────────────────────┤
│  5. adoptedCallback()                         │
│     └── Element moves to a new document       │
│     └── Rare; used for cross-document moves   │
└─────────────────────────────────────────────┘

    The "Declarative API" Mental Model

    Custom elements let consumers use native HTML:

    ┌─────────────────────────────────────────────┐
│  FRAMEWORK COMPONENT (React)                 │
│  <UserCard name="Alice" email="..." />        │
│  └── JSX — needs a compiler                  │
│  └── Framework-specific                       │
├─────────────────────────────────────────────┤
│  CUSTOM ELEMENT                              │
│  <user-card name="Alice" email="...">         │
│     <span slot="name">Alice</span>            │
│  </user-card>                                 │
│  └── Native HTML                              │
│  └── No compiler needed                       │
│  └── Works with any framework                 │
└─────────────────────────────────────────────┘

    Custom elements are framework-agnostic — they work everywhere HTML works.

    The "Registry" Mental Model

    The customElements registry is a global map of tag names to classes:

    ┌─────────────────────────────────────────────┐
│  customElements REGISTRY                     │
│  └── 'user-card' → UserCard class            │
│  └── 'data-chart' → DataChart class          │
│  └── 'my-button' → MyButton class            │
│                                              │
│  Once a name is defined, it cannot be        │
│  redefined.                                  │
└─────────────────────────────────────────────┘

    Once you call customElements.define('user-card', ...), the name is bound forever. You cannot redefine it.

    5. Core Concepts

    Concept 1: The customElements Registry

    The global registry of custom element definitions. Accessed via window.customElements.

    Concept 2: customElements.define()

    Registers a custom element. Takes a tag name and a class.

    Concept 3: The HTMLElement Base Class

    Custom elements extend HTMLElement (or a built-in element for customized built-ins).

    Concept 4: Autonomous Custom Elements

    Extend HTMLElement. Use <my-element>.

    Concept 5: Customized Built-in Elements

    Extend a specific built-in element. Use <button is="my-button">. Not supported in Safari.

    Concept 6: The Naming Rules

    Custom element names must start with a lowercase letter, contain a hyphen, and not conflict with reserved names.

    Concept 7: The Five Lifecycle Callbacks

    • constructor — element created.
    • connectedCallback — element added to the DOM.
    • disconnectedCallback — element removed from the DOM.
    • attributeChangedCallback — observed attribute changed.
    • adoptedCallback — element moved to a new document.

    Concept 8: The observedAttributes Static Getter

    Returns an array of attribute names to observe. attributeChangedCallback fires for these attributes.

    Concept 9: The Upgrade Process

    The browser upgrades unknown elements to custom elements when the definition arrives.

    Concept 10: customElements.whenDefined()

    Returns a Promise that resolves when a custom element is defined.

    Concept 11: customElements.upgrade()

    Forces the upgrade of a custom element.

    Concept 12: Shadow DOM Integration

    Custom elements commonly use attachShadow() to create an encapsulated shadow tree.

    Concept 13: Template Integration

    Custom elements commonly clone a <template> into their shadow root.

    Concept 14: Slot Integration

    Custom elements can include <slot> elements for content projection.

    Concept 15: Form-Associated Custom Elements

    Custom elements with static formAssociated = true participate in form submission via ElementInternals.

    Concept 16: The attachInternals() Method

    Returns an ElementInternals object for form participation, ARIA, and accessibility.

    Concept 17: The ElementInternals API

    Provides methods and properties for form participation and accessibility:

    • setFormValue(value) — sets the value.
    • setValidity(flags, message, anchor) — sets validity.
    • form — the associated form.
    • labels — the labels.
    • validity — the validity state.

    Concept 18: Accessibility with Custom Elements

    Custom elements participate in the accessibility tree. Use role, aria-*, and ElementInternals for semantics.

    Concept 19: The constructor Restrictions

    • Must call super() first.
    • Must not inspect attributes or children.
    • Must not attach child nodes (except shadow root).
    • Must not change the host's own attributes.

    Concept 20: The is Attribute

    Customized built-in elements use the is attribute:

    <button is="my-button">Click</button>

    Concept 21: The Custom Element Registry Names

    Once defined, a name cannot be redefined. Attempting to redefine throws an error.

    Concept 22: The customElements.getName() Method

    Returns the tag name for a constructor. Added in 2023.

    Concept 23: The ElementInternals ARIA Methods

    ElementInternals also provides ARIA methods for accessibility:

    this._internals.role = 'button';
this._internals.ariaLabel = 'Click me';

    Concept 24: Custom Elements vs. Framework Components

    Custom Elements Framework Components
    Standard HTML/DOM Framework-specific
    Parsing Native Compiler required
    Interop Works with any framework Framework-locked
    Accessibility Native Framework-dependent
    Encapsulation Shadow DOM Framework-dependent
    Lifecycle Standard callbacks Framework-specific

    Concept 25: The Custom Element Lifecycle Order

    1.  constructor
2.  attributeChangedCallback (for initial attributes)
3.  connectedCallback
4.  attributeChangedCallback (for subsequent changes)
5.  disconnectedCallback
6.  adoptedCallback (if moved to a new document)

    ▼

    │
    ▼

    ▼

    ▼

    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼
4.  Form submission triggers setFormValue().
    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼
4.  Subsequent attribute changes fire attributeChangedCallback.
    │
    ▼
5.  Element updates its shadow tree in response.

    7. Internal Architecture / Under the Hood

    The Custom Element Registry

    The customElements registry is a global map of tag names to classes:

    ┌─────────────────────────────────────────────┐
│  customElements REGISTRY                     │
│  └── Map<string, CustomElementConstructor>   │
│      ├── 'user-card' → UserCard              │
│      ├── 'data-chart' → DataChart            │
│      └── 'my-button' → MyButton              │
└─────────────────────────────────────────────┘

    Once a name is defined, it cannot be redefined. Attempting to redefine throws a NotSupportedError.

    The Element Upgrade Algorithm

    When an element is created:

    1. Browser checks if the tag name is in the registry.
    2. If yes:
    3. Change the element's prototype to the custom class.
    4. Run constructor.
    5. Run attributeChangedCallback for initial attributes.
    6. If connected, run connectedCallback.
    7. If no:
    8. The element remains an unknown HTMLElement.
    9. It will be upgraded later when defined.

    The Prototype Chain

    Custom elements have a prototype chain:

    Object.prototype
  └── EventTarget.prototype
      └── Node.prototype
          └── Element.prototype
              └── HTMLElement.prototype
                  └── MyElement.prototype
                      └── myElement (instance)

    The Form-Associated Lifecycle

    Form-associated custom elements have additional callbacks:

    • formAssociatedCallback(form) — called when the element is associated with a form.
    • formDisabledCallback(disabled) — called when the element is disabled.
    • formResetCallback() — called when the form is reset.
    • formStateRestoreCallback(state, mode) — called when the form state is restored.

    The ElementInternals API

    ┌─────────────────────────────────────────────┐
│  ElementInternals                            │
│  ├── setFormValue(value, state)              │
│  ├── setValidity(flags, message, anchor)     │
│  ├── form → HTMLFormElement                  │
│  ├── labels → NodeList                       │
│  ├── validity → ValidityState                │
│  ├── willValidate → boolean                  │
│  ├── checkValidity() → boolean               │
│  ├── reportValidity() → boolean              │
│  ├── role → string                           │
│  └── ariaLabel → string                      │
└─────────────────────────────────────────────┘

    The Custom Element Name Validation

    The browser validates names during define():

    • Must start with a lowercase letter.
    • Must contain a hyphen.
    • Must not be in the reserved list.
    • Must not already be defined.

    The Reserved Names

    The following names are reserved and cannot be used:

    • annotation-xml
    • color-profile
    • font-face
    • font-face-src
    • font-face-uri
    • font-face-format
    • font-face-name
    • missing-glyph

    The Custom Element Lifecycle Order

    1.  constructor
2.  attributeChangedCallback (initial attributes)
3.  connectedCallback
4.  attributeChangedCallback (subsequent changes)
5.  formAssociatedCallback (for form-associated elements)
6.  disconnectedCallback
7.  adoptedCallback (if moved to a new document)

    The ::part() and ::slotted() Integration

    Custom elements expose internal elements via part and receive content via slot:

    <my-button>
    <template shadowrootmode="open">
        <button part="button"><slot></slot></button>
    </template>
</my-button>

    class UserCard extends HTMLElement {
    static get observedAttributes() {
        return ['name', 'email'];
    }

    constructor() {
        super();
        const shadow = this.attachShadow({ mode: 'open' });
        shadow.innerHTML = `
            <style>

                .email { color: #666; }

    class MyInput extends HTMLElement {
    static formAssociated = true;

    constructor() {
        super();
        this._internals = this.attachInternals();

    Example 7: Custom Element with Accessibility

    class MyToggle extends HTMLElement {
    constructor() {
        super();
        this._internals = this.attachInternals();
        this._internals.role = 'switch';
        this._internals.ariaChecked = 'false';

        const shadow = this.attachShadow({ mode: 'open' });
        shadow.innerHTML = `
            <style>
                .track {
                    width: 40px;
                    height: 20px;
                    background: #ccc;
                    border-radius: 10px;
                    cursor: pointer;
                    position: relative;
                    transition: background 0.2s;
                }
                .track[aria-checked="true"] {
                    background: #3498db;
                }
                .thumb {
                    width: 16px;
                    height: 16px;
                    background: white;
                    border-radius: 50%;
                    position: absolute;
                    top: 2px;
                    left: 2px;
                    transition: left 0.2s;
                }
                .track[aria-checked="true"] .thumb {
                    left: 22px;
                }
            </style>
            <div class="track" role="switch" aria-checked="false" tabindex="0">
                <div class="thumb"></div>
            </div>
        `;

        const track = shadow.querySelector('.track');
        track.addEventListener('click', () => this.toggle());
        track.addEventListener('keydown', (e) => {
            if (e.key === 'Enter' || e.key === ' ') {
                e.preventDefault();

            }
        });
    }

        this._internals.ariaChecked = String(!current);
        this.shadowRoot.querySelector('.track').setAttribute('aria-checked', String(!current));
    }
}

    • role = 'switch' declares the semantic role.
    • ariaChecked reflects the toggle state.
    • Keyboard support is added manually.

    Example 8: Custom Element with Data Fetching

    class DataChart extends HTMLElement {
    static get observedAttributes() {
        return ['src'];
    }

    constructor() {
        super();
        this.attachShadow({ mode: 'open' });
        this.shadowRoot.innerHTML = `
            <style>
                .chart {
                    width: 100%;
                    height: 200px;
                    border: 1px solid #ccc;
                }
            </style>
            <div class="chart">Loading...</div>
        `;
    }

    async connectedCallback() {
        await this.loadData();
    }

    async attributeChangedCallback(name, oldValue, newValue) {
        if (name === 'src' && oldValue !== newValue) {
            await this.loadData();
        }
    }

    async loadData() {
        const src = this.getAttribute('src');
        if (!src) return;

        try {
            const response = await fetch(src);
            const data = await response.json();
            this.render(data);
        } catch (error) {
            this.shadowRoot.querySelector('.chart').textContent = 'Error loading data';
        }
    }

    render(data) {
        // Render the chart
        this.shadowRoot.querySelector('.chart').textContent = JSON.stringify(data);
    }
}

customElements.define('data-chart', DataChart);

    Code Breakdown:

    • observedAttributes includes src.
    • connectedCallback loads data.
    • attributeChangedCallback reloads when src changes.
    • Data is fetched asynchronously.

    11. Best Practices

    1. Use autonomous custom elements. Why: they work in all browsers, including Safari.
    2. Name elements with a hyphen. Why: required by the specification.
    3. Use lowercase names. Why: required by the specification.
    4. Call super() first in the constructor. Why: required by the specification.
    5. Do not inspect attributes or children in the constructor. Why: they may not be available yet.
    6. Use connectedCallback for DOM-dependent initialization. Why: attributes and children are available.
    7. Use disconnectedCallback for cleanup. Why: prevents memory leaks.
    8. Use observedAttributes for reactive attributes. Why: standard way to react to changes.
    9. Attach event listeners in connectedCallback. Why: element may be disconnected and reconnected.
    10. Remove event listeners in disconnectedCallback. Why: prevents memory leaks.
    11. Use attachShadow() in the constructor. Why: shadow root should exist before connectedCallback.
    12. Use templates for shadow tree content. Why: declarative, parse-once.
    13. Use ElementInternals for form participation. Why: standard way to participate in forms.
    14. Use ElementInternals for ARIA. Why: standard way to set ARIA on custom elements.
    15. Use CSS custom properties for theming. Why: they cross the shadow boundary.
    16. Expose parts via part for external styling. Why: controlled customization.
    17. Test with assistive technology. Why: verify the accessibility tree.
    18. Handle the upgrade case. Why: elements may exist before the definition loads.
    19. Use customElements.whenDefined() for coordination. Why: ensures the element is ready.
    20. Avoid redefining custom elements. Why: names can only be defined once.
    21. Test on all target browsers. Why: customized built-in elements are not supported in Safari.
    22. Document the public API. Why: attributes, slots, parts, and events.
    23. Use semantic HTML inside the shadow tree. Why: accessibility and default styles.
    24. Consider lazy loading. Why: only load component scripts when needed.
    25. Audit components after framework upgrades. Why: integration may change.

    12. Common Mistakes

    ❌ Mistake: Missing the Hyphen in the Name

    customElements.define('myelement', MyElement); // ❌ Error

    Why it's wrong: Custom element names must contain a hyphen.

    ✅ Correct:

    customElements.define('my-element', MyElement);

    ❌ Mistake: Inspecting Attributes in the Constructor

    class MyElement extends HTMLElement {
    constructor() {
        super();
        console.log(this.getAttribute('name')); // ❌ May be null
    }
}

    Why it's wrong: Attributes may not be available in the constructor.

    ✅ Correct:

    class MyElement extends HTMLElement {
    connectedCallback() {
        console.log(this.getAttribute('name')); // ✅ Available
    }
}

    ❌ Mistake: Not Calling super() First

    class MyElement extends HTMLElement {
    constructor() {
        this.attachShadow({ mode: 'open' }); // ❌ Error
        super();
    }
}

    Why it's wrong: super() must be called before this.

    ✅ Correct:

    class MyElement extends HTMLElement {
    constructor() {
        super();
        this.attachShadow({ mode: 'open' });
    }
}

    ❌ Mistake: Redefining a Custom Element

    customElements.define('my-element', MyElement);
customElements.define('my-element', AnotherElement); // ❌ Error

    Why it's wrong: Names can only be defined once.

    ✅ Correct: Use a different name or check before defining.

    ❌ Mistake: Attaching Event Listeners Without Cleanup

    class MyElement extends HTMLElement {
    connectedCallback() {
        window.addEventListener('resize', this.handleResize);
    }
    // No cleanup
}

    Why it's wrong: Memory leak if the element is removed.

    ✅ Correct:

    class MyElement extends HTMLElement {
    connectedCallback() {
        window.addEventListener('resize', this.handleResize);
    }
    disconnectedCallback() {
        window.removeEventListener('resize', this.handleResize);
    }
    handleResize = () => { /* ... */ }
}

    ❌ Mistake: Using Customized Built-in Elements in Safari

    customElements.define('fancy-button', FancyButton, { extends: 'button' });

    <button is="fancy-button">Click</button>

    Why it's wrong: Safari does not support customized built-in elements.

    ✅ Correct: Use autonomous custom elements.

    ❌ Mistake: Not Handling Missing Attributes

    class UserCard extends HTMLElement {
    constructor() {
        super();
        this.attachShadow({ mode: 'open' });
        this.shadowRoot.innerHTML = `<h2>${this.getAttribute('name')}</h2>`;
        // "null" if attribute is missing
    }
}

    Why it's wrong: getAttribute returns null if the attribute is missing.

    ✅ Correct:

    this.shadowRoot.innerHTML = `<h2>${this.getAttribute('name') ?? ''}</h2>`;

    ❌ Mistake: No Shadow DOM

    class MyElement extends HTMLElement {
    connectedCallback() {
        this.innerHTML = '<p>Hello</p>'; // Overwrites consumer content
    }
}

    Why it's wrong: Overwrites consumer content; no encapsulation.

    ✅ Correct: Use shadow DOM and slots.

    ❌ Mistake: Not Registering the Element

    class MyElement extends HTMLElement {
    // ...
}
// Missing: customElements.define('my-element', MyElement);

    Why it's wrong: The element is not registered.

    ✅ Correct:

    customElements.define('my-element', MyElement);

    ❌ Mistake: Accessing Shadow DOM Before It Exists

    class MyElement extends HTMLElement {
    connectedCallback() {
        this.shadowRoot.querySelector('.foo'); // null if no shadow root
    }
}

    Why it's wrong: shadowRoot is null if attachShadow was not called.

    ✅ Correct: Call attachShadow in the constructor.

    ❌ Mistake: Using innerHTML with User Input

    this.shadowRoot.innerHTML = `<p>${userInput}</p>`;

    Why it's wrong: XSS vulnerability.

    ✅ Correct: Use textContent for user input.

    13. Performance Considerations

    • Custom elements add minimal overhead — the browser handles upgrade natively.
    • Shadow DOM styles are scoped — style matching is faster.
    • Templates are parsed once — cloning is cheap.
    • Lifecycle callbacks are cheap — avoid heavy work in connectedCallback.
    • Attribute observation is efficient — only observed attributes trigger callbacks.
    • Form-associated custom elements add minimal overhead.
    • Custom element definitions are loaded once.
    • Too many custom element instances — each has its own shadow root.

    Performance Tips

    1. Use templates for shadow tree content.
    2. Minimize work in connectedCallback.
    3. Use requestAnimationFrame for visual updates.
    4. Debounce attribute change reactions.
    5. Cache shadow root references.
    6. Lazy-load custom element definitions.
    7. Avoid re-rendering the entire shadow tree.
    8. Use CSS containment.

    14. Security Considerations

    XSS in Custom Elements

    Custom elements are subject to the same XSS risks as any DOM code. Use textContent for user input; sanitize HTML with DOMPurify.

    Attribute Injection

    Attributes are parsed as strings. Do not pass untrusted content through attributes expecting it to be safe.

    Shadow DOM Is Not a Security Boundary

    Shadow DOM provides encapsulation, not security. Scripts inside the shadow tree run in the document context.

    Form Participation and CSRF

    Form-associated custom elements submit values with the form. Ensure CSRF protection is applied.

    Custom Element Names and DOM Clobbering

    Custom element names should not conflict with global identifiers. Use unique, specific names.

    ElementInternals and Accessibility

    Use ElementInternals for ARIA to ensure the element is exposed correctly to assistive technology.

    Deprecation and Versioning

    Once a custom element is defined, it cannot be redefined. Plan the API carefully.

    • Third-party widgets — embeddable components.
    • Micro-frontends — isolated sub-applications.
    • Progressive enhancement — enhance native elements.
    • Web applications — modular, encapsulated UI.

    17. When Not to Use

    • Do not use custom elements for one-off markup. Use plain HTML.
    • Do not use custom elements without a hyphen in the name. Invalid.
    • Do not inspect attributes in the constructor. Use connectedCallback.
    • Do not forget to call super() first. Required.
    • Do not redefine custom elements. Names can only be defined once.
    • Do not rely on customized built-in elements. Not supported in Safari.
    • Do not use shadow DOM as a security boundary. It is not one.
    • Do not put heavy work in connectedCallback. It blocks the main thread.

    19. Did You Know?

    • Custom Elements v1 shipped in 2016 — the modern API (customElements.define()).
    • Custom Elements v0 had a different API — document.registerElement().
    • Custom element names must contain a hyphen — to prevent collisions with future HTML elements.
    • The hyphen rule dates back to the original specification — it ensures forward compatibility.
    • Safari was the last major browser to ship Custom Elements v1 — in Safari 10.1 (2017).
    • Safari does not support customized built-in elements — as of 2026.
    • Form-associated custom elements shipped in 2020 — attachInternals(), setFormValue().
    • ElementInternals can set ARIA roles and properties — for custom element accessibility.
    • The upgrade process handles elements created before the definition — the browser upgrades them.
    • customElements.whenDefined() returns a Promise — for coordinating initialization.
    • customElements.upgrade() forces an upgrade — used for elements in other documents.
    • Custom elements are the definition mechanism of Web Components — they bind everything else to a tag.
    • Lit, FAST, Stencil, and Polymer all use custom elements.
    • React, Vue, and Angular all support custom elements — with some caveats.
    • The is attribute is used for customized built-in elements.
    • The constructor must call super() first — a JavaScript requirement.
    • The constructor must not inspect attributes — they may not be available.
    • connectedCallback may be called multiple times — if the element is reconnected.
    • disconnectedCallback is where you clean up — remove listeners, cancel fetches.
    • Attribute names are case-insensitive in HTML — but the observed names must match.
    • The observed attributes list is static — declared once on the class.
    • Custom elements are baseline and universally supported — Chrome 54+, Firefox 63+, Safari 10.1+, Edge 79+.
    • The best custom element is the one that feels like a native element — no leaks, no surprises.
    • Custom elements are the native way to extend HTML — the platform's answer to framework components.

    20. Summary

    • Custom Elements is the browser API for defining new HTML elements.
    • A custom element is a JavaScript class extending HTMLElement.
    • Register with customElements.define('my-element', MyElement).
    • Names must contain a hyphen and start with a lowercase letter.
    • Two flavors: autonomous (<my-element>) and customized built-in (<button is="my-button">).
    • Safari does not support customized built-in elements.
    • Five lifecycle callbacks: constructor, connectedCallback, disconnectedCallback, attributeChangedCallback, adoptedCallback.
    • observedAttributes declares which attributes trigger attributeChangedCallback.
    • The browser upgrades unknown elements when the definition loads.
    • Custom elements combine with templates, slots, and Shadow DOM.
    • Form-associated custom elements use ElementInternals to participate in forms.
    • ElementInternals also provides ARIA methods for accessibility.
    • CSS custom properties cross the shadow boundary for theming.
    • part and ::part() expose internals for external styling.
    • Custom elements are framework-agnostic — they work everywhere HTML works.
    • Custom elements are baseline and universally supported.
    • Use autonomous elements — Safari does not support customized built-ins.

    • Do not inspect attributes in the constructor — use connectedCallback.
