    Declarative Shadow DOM

    1. Overview

    Definition

    Declarative Shadow DOM is the ability to define a shadow root directly in HTML — without JavaScript — by placing a <template> element with the shadowrootmode attribute as a child of the host element. The browser parses the template's content into a shadow root on the parent during HTML parsing, producing a fully-formed shadow tree before any script runs.

    <my-card>
    <template shadowrootmode="open">
        <style>
            .card {
                border: 1px solid #ccc;
                border-radius: 8px;
                padding: 1rem;
            }
        </style>
        <div class="card">
            <h2>Hello</h2>
            <p>This is inside a shadow root.</p>
        </div>
    </template>
</my-card>

    Before Declarative Shadow DOM, creating a shadow root required JavaScript:

    class MyCard extends HTMLElement {
    constructor() {
        super();
        this.attachShadow({ mode: 'open' }).innerHTML = '...';
    }
}

    With Declarative Shadow DOM, the shadow root exists immediately after parsing — no script, no flash of unstyled content (FOUC), no hydration delay. It is server-renderable, streaming-friendly, and progressive-enhancement-compatible.

    Declarative Shadow DOM is the server-side rendering (SSR) story for Web Components — the missing piece that makes Web Components viable for content sites, e-commerce, and any page where JavaScript cannot be assumed.

    Purpose

    Declarative Shadow DOM serves several essential purposes:

    • Server-side rendering (SSR) — shadow trees can be rendered on the server.
    • No FOUC — styles apply before the first paint.
    • Faster first paint — the shadow root is present immediately.
    • Progressive enhancement — components work without JavaScript.
    • Streaming-friendly — content can be streamed progressively.
    • SEO — shadow content is present in the initial HTML.
    • Accessibility — the accessibility tree is built correctly on load.
    • Hydration — custom elements upgrade into existing shadow roots.
    • Framework support — Lit SSR, Next.js, Astro, Remix, and others.

    Declarative Shadow DOM is the rendering primitive that makes Web Components production-ready for server-driven applications.

    Where It Fits

    Web Components
│
├── Templates              ← reusable markup
├── Slots                  ← content projection
├── Shadow DOM             ← style and structure encapsulation
├── Custom Elements        ← reusable component definitions
└── Declarative Shadow DOM ← server-rendered shadow roots (THIS CHAPTER)

    Declarative Shadow DOM is the bridge between server-side rendering and client-side encapsulation. It lets the shadow tree exist in the HTML — and the custom element upgrade into it later.

    2. Why It Exists

    The Problem

    Shadow DOM has one major limitation in a server-rendered world: it can only be created by JavaScript.

    Before Declarative Shadow DOM, a Web Component's shadow root existed only after:

    1. The HTML was parsed.
    2. The JavaScript loaded.
    3. The custom element was defined.
    4. The element was upgraded.
    5. attachShadow() was called.
    6. The shadow tree was populated.

    This produced a cascade of problems:

    • Flash of unstyled content (FOUC) — content rendered before the shadow root existed.
    • Slow first paint — first paint waited for JavaScript.
    • SEO concerns — shadow content was invisible to crawlers without JS execution.
    • No SSR — server-rendered HTML could not include shadow roots.
    • Progressive enhancement failure — components did not work without JavaScript.
    • Hydration mismatch — client-created shadow roots were not in the initial HTML.

    For static sites, blogs, e-commerce, and any content-driven application, this was a fundamental blocker for adopting Web Components.

    Previous Limitations

    Limitation Consequence
    Shadow DOM required JavaScript No SSR
    FOUC on component load Visual jank
    First paint delayed Poor Core Web Vitals
    Shadow content invisible to crawlers SEO concerns
    No progressive enhancement Required JavaScript
    No streaming support Whole document needed
    Hydration mismatch Client-rendered content only

    Why It Was Introduced

    Declarative Shadow DOM was proposed as a solution to the SSR problem. It was designed to let shadow roots be declared in HTML — parsed by the browser during normal HTML parsing — so that:

    • Shadow trees exist immediately.
    • Styles apply before first paint.
    • No JavaScript is required for initial render.
    • Crawlers see the shadow content.
    • Custom elements upgrade into existing shadow roots.

    The specification shipped in stages:

    • Chrome 90 (April 2021) — the shadowroot attribute (later renamed).
    • Chrome 111 (March 2023) — the shadowrootmode attribute (final syntax).
    • Safari 16.4 (March 2023) — support for shadowrootmode.
    • Firefox 123 (February 2024) — support for shadowrootmode.

    Additional attributes were added in 2024:

    • shadowrootdelegatesfocus — focus delegation.
    • shadowrootclonable — shadow root cloning.
    • shadowrootserializable — shadow root serialization.

    In 2026, Declarative Shadow DOM is baseline and supported in all modern browsers. It is the standard mechanism for server-rendering Web Components and is used by Lit SSR, Astro, Next.js, Remix, and every modern framework that supports Web Components.

    • Useful for wrapping form controls.

    The shadowrootclonable Attribute

    <my-element>
    <template shadowrootmode="open" shadowrootclonable>
        <p>Clonable shadow root</p>
    </template>
</my-element>

<script>
    const el = document.querySelector('my-element');

    console.log(clone.shadowRoot); // the cloned shadow root
</script>

    Code Breakdown

    • shadowrootclonable — allows the shadow root to be cloned via cloneNode().
    • Without it, cloneNode() on the host does not clone the shadow root.

    The shadowrootserializable Attribute

    <my-element>
    <template shadowrootmode="open" shadowrootserializable>
        <p>Serializable shadow root</p>
    </template>
</my-element>

<script>
    const el = document.querySelector('my-element');
    console.log(el.getHTML({ serializableShadowRoots: true }));
    // Includes the shadow root HTML
</script>

    Code Breakdown

    • shadowrootserializable — allows the shadow root to be serialized via getHTML().
    • Enables server-side serialization and content extraction.

    The Custom Element Upgrade

    <my-element>
    <template shadowrootmode="open">
        <p>Shadow content</p>
    </template>
</my-element>

<script>
    class MyElement extends HTMLElement {
        connectedCallback() {
            console.log('Shadow root:', this.shadowRoot);
            // The shadow root already exists — no attachShadow needed
        }
    }
    customElements.define('my-element', MyElement);
</script>

    Code Breakdown

    • The custom element does not call attachShadow().
    • The shadow root already exists from the declarative markup.
    • connectedCallback finds it via this.shadowRoot.

    The attachShadow() Error

    class MyElement extends HTMLElement {
    constructor() {
        super();
        this.attachShadow({ mode: 'open' }); // ❌ Error if declarative shadow root exists
    }
}

    Error: NotSupportedError: Shadow root cannot be created on a host which already hosts a shadow tree.

    Code Breakdown

    If the element has a declarative shadow root, calling attachShadow() throws. The component must check whether a shadow root already exists:

    if (!this.shadowRoot) {
    this.attachShadow({ mode: 'open' });
}

    4. Mental Model

    The "SSR for Shadow DOM" Mental Model

    Declarative Shadow DOM is SSR for shadow roots:

    ┌─────────────────────────────────────────────┐
│  CLIENT-ONLY SHADOW DOM (before DSD)         │
│  └── HTML parsed                             │
│  └── JavaScript loads                        │
│  └── Custom element defined                  │
│  └── attachShadow() called                   │
│  └── Shadow tree populated                   │
│  └── FOUC during this gap                    │
├─────────────────────────────────────────────┤
│  DECLARATIVE SHADOW DOM (with DSD)           │
│  └── HTML parsed                             │
│  └── Shadow tree created during parsing      │
│  └── Styles apply immediately                │
│  └── First paint is correct                  │
│  └── Custom element upgrades into it later   │
└─────────────────────────────────────────────┘

    Declarative Shadow DOM eliminates the client-side shadow DOM gap.

    The "Parsed, Not Executed" Mental Model

    Declarative Shadow DOM is parsed, not executed:

    ┌─────────────────────────────────────────────┐
│  <template shadowrootmode="open">            │
│  └── Parsed by the HTML parser               │
│  └── Recognized as a shadow root declaration │
│  └── Content becomes the shadow tree         │
│  └── Template element is removed             │
└─────────────────────────────────────────────┘

    No JavaScript runs. No attachShadow() call. The shadow root is a parsing-time construct.

    The "The Template Is Consumed" Mental Model

    Unlike normal <template> elements, a declarative shadow DOM template is consumed:

    ┌─────────────────────────────────────────────┐
│  NORMAL <template>                           │
│  └── Stays in the DOM                        │
│  └── Content accessible via template.content │
│  └── Used for cloning                        │
├─────────────────────────────────────────────┤
│  <template shadowrootmode="open">            │
│  └── Removed from the DOM                    │
│  └── Content becomes the shadow tree         │
│  └── The template element does not persist   │
└─────────────────────────────────────────────┘

    The declarative shadow DOM template is consumed by the parser. It is not a reusable template.

    The "Progressive Enhancement" Mental Model

    Declarative Shadow DOM enables progressive enhancement:

    ┌─────────────────────────────────────────────┐
│  WITHOUT JAVASCRIPT                          │
│  └── Shadow tree is present                  │
│  └── Styles apply                            │
│  └── Content renders                         │
│  └── Slotted content projects                │
│  └── The page works                          │
├─────────────────────────────────────────────┤
│  WITH JAVASCRIPT                             │
│  └── Custom element upgrades                 │
│  └── Lifecycle callbacks run                 │
│  └── Interactivity is added                  │
│  └── The component is enhanced               │
└─────────────────────────────────────────────┘

    The component works without JavaScript and enhances with it.

    The "Hydration" Mental Model

    Declarative Shadow DOM is the hydration model for Web Components:

    ┌─────────────────────────────────────────────┐
│  1. SERVER RENDERS                           │
│  └── <my-element>                            │
│      <template shadowrootmode="open">        │
│        ...shadow content...                  │
│      </template>                             │
│      ...slotted content...                   │
│  └── Sent as HTML                            │
│                                              │
│  2. BROWSER PARSES                           │
│  └── Shadow root is created                  │
│  └── Content is rendered                     │
│  └── Styles apply                            │
│  └── No JavaScript required                  │
│                                              │
│  3. JAVASCRIPT LOADS                         │
│  └── Custom element is defined               │
│  └── Existing elements upgrade               │
│  └── Event listeners attach                  │
│  └── The component becomes interactive       │
└─────────────────────────────────────────────┘

    There is no "hydration mismatch" because the shadow tree was never client-created.

    The "Streaming" Mental Model

    Declarative Shadow DOM is streaming-friendly:

    ┌─────────────────────────────────────────────┐
│  STREAMED HTML                               │
│                                              │
│  <header>...</header>                        │
│  ─── flushed ───                             │
│  <my-card>                                   │
│    <template shadowrootmode="open">          │
│      ...shadow content...                    │
│    </template>                               │
│    ...slotted content...                     │
│  </my-card>                                  │
│  ─── flushed ───                             │
│  <footer>...</footer>                        │
│  ─── flushed ───                             │
│                                              │
│  Browser renders as chunks arrive.          │
│  Shadow roots exist as soon as parsed.      │
└─────────────────────────────────────────────┘

    No need to wait for the full document — shadow roots render as they stream.

    The "Framework Interop" Mental Model

    Declarative Shadow DOM works with any framework:

    ┌─────────────────────────────────────────────┐
│  SERVER FRAMEWORKS                           │
│  ├── Next.js — RSC + DSD                     │
│  ├── Astro — partial hydration + DSD         │
│  ├── Remix — streaming + DSD                 │
│  ├── SvelteKit — SSR + DSD                   │
│  └── Lit SSR — first-class DSD               │
│                                              │
│  CLIENT FRAMEWORKS                           │

│  ├── Vue — web components + DSD              │
│  └── Angular — web components + DSD          │

    Declarative Shadow DOM is framework-agnostic — it is a platform primitive.

    7. Internal Architecture / Under the Hood

    The Parser's Shadow Root Creation

    When the parser encounters <template shadowrootmode="open">:

    1. It checks if the parent element is a valid shadow host.
    2. It creates a shadow root on the parent.
    3. It switches to a shadow tree parsing mode.
    4. It parses the template's content into the shadow root.
    5. It does not create a <template> element in the tree.
    6. It removes the template from the DOM.

    The shadowrootmode Handling

    The shadowrootmode attribute is a parser directive:

    • It is read during parsing.
    • It determines the mode of the shadow root.
    • It is not reflected to the DOM as a property.

    The Attribute Set

    Attribute Effect
    shadowrootmode "open" or "closed"
    shadowrootdelegatesfocus Focus delegation
    shadowrootclonable Shadow root cloning
    shadowrootserializable Shadow root serialization

    The Parser Algorithm

    The full algorithm:

    1. Parser encounters <template> with shadowrootmode.
    2. Validate the parent element is a shadow host (any element can be a shadow host).
    3. Validate that no shadow root already exists on the parent.
    4. Create a shadow root on the parent with the given mode.
    5. Set the shadow root's flags (delegates focus, clonable, serializable).
    6. Parse the template's content into the shadow root.
    7. Remove the template element from the DOM.

    The attachShadow() Error

    If attachShadow() is called on a host with a declarative shadow root:

    NotSupportedError: Shadow root cannot be created on a host which already hosts a shadow tree.

    The custom element must check:

    if (!this.shadowRoot) {
    this.attachShadow({ mode: 'open' });
}

    The Upgrade Algorithm

    When a custom element is defined:

    1. For each element matching the tag name:
    2. Change the prototype from HTMLElement to the custom class.
    3. Run constructor.
    4. Run attributeChangedCallback for initial attributes.
    5. Run connectedCallback if the element is connected.

    If a declarative shadow root exists:

    • this.shadowRoot returns it.
    • constructor must not call attachShadow().

    The getHTML() Serialization

    The getHTML() method (added in 2024) serializes an element's subtree, including:

    • Light DOM children.
    • Serializable shadow roots (if serializableShadowRoots: true).
    element.getHTML({ serializableShadowRoots: true });

    The Polyfill

    @webcomponents/template-shadowroot polyfills DSD for older browsers:

    <script type="module">
    import { polyfill } from '@webcomponents/template-shadowroot';
    polyfill();
</script>

    The polyfill:

    1. Finds all <template shadowrootmode> elements.
    2. Creates shadow roots on their parents.
    3. Moves the content into the shadow roots.
    4. Removes the templates.

    The Polyfill's Timing

    The polyfill must run before custom elements upgrade — otherwise, the element may not find the shadow root.

    The declarativeShadowRoot Property

    The property shadowRoot on the host returns the declarative shadow root:

    element.shadowRoot; // the shadow root

    The Shadow Root Mode Is Immutable

    Once created, the shadow root mode cannot be changed.

    Example 10: Complete Custom Element with DSD and Hydration

    <my-counter>
    <template shadowrootmode="open">
        <style>
            .counter {
                display: flex;
                align-items: center;
                gap: 1rem;
                font-family: system-ui;
            }
            button {
                padding: 0.5rem 1rem;
                border: 1px solid #ccc;
                border-radius: 4px;
                cursor: pointer;
                font: inherit;
            }
            .value { font-size: 1.5rem; font-weight: bold; }
        </style>
        <div class="counter">
            <button class="decrement">-</button>
            <span class="value">0</span>
            <button class="increment">+</button>
        </div>
    </template>
</my-counter>

<script>
    class MyCounter extends HTMLElement {
        constructor() {
            super();
            // Do NOT call attachShadow — it already exists
        }

        connectedCallback() {
            // Shadow root exists from the declarative markup
            this._value = 0;
            this.shadowRoot.querySelector('.decrement')
                .addEventListener('click', () => this.decrement());
            this.shadowRoot.querySelector('.increment')
                .addEventListener('click', () => this.increment());
        }

        increment() {
            this._value++;
            this.updateValue();
        }

        decrement() {
            this._value--;
            this.updateValue();
        }

        updateValue() {
            this.shadowRoot.querySelector('.value').textContent = this._value;
        }
    }

    customElements.define('my-counter', MyCounter);
</script>

    Code Breakdown:

    • The declarative shadow root provides the initial HTML.
    • The custom element upgrades into it.
    • Event listeners attach in connectedCallback.
    • The component is interactive after JavaScript loads.

    11. Best Practices

    1. Use shadowrootmode="open" by default. Why: closed offers no security benefit.
    2. Do not call attachShadow() in the constructor if a declarative shadow root exists. Why: it throws an error.
    3. Check this.shadowRoot before calling attachShadow(). Why: supports both DSD and client-only rendering.
    4. Use shadowrootdelegatesfocus for form controls. Why: better UX.
    5. Use shadowrootclonable when cloning is needed. Why: enables shadow root cloning.
    6. Use shadowrootserializable for SSR. Why: enables serialization.
    7. Render declarative shadow DOM on the server. Why: no FOUC, faster first paint.
    8. Stream declarative shadow DOM. Why: progressive rendering.
    9. Use the polyfill for older browsers. Why: shadowrootmode support varies.
    10. Load the polyfill before custom elements. Why: it must create shadow roots before upgrade.
    11. Do not rely on closed mode for security. Why: it is not a security boundary.
    12. Test with SSR frameworks. Why: Lit SSR, Astro, Next.js have different behavior.
    13. Test the upgrade path. Why: verify the element finds its shadow root.
    14. Test without JavaScript. Why: progressive enhancement.
    15. Test accessibility. Why: verify the accessibility tree is correct.
    16. Test with screen readers. Why: verify announcements.
    17. Test with SEO tools. Why: verify crawlers see the content.
    18. Avoid inline scripts in DSD content. Why: they run when cloned (rare).
    19. Keep the shadow tree small. Why: it is part of the initial HTML.
    20. Document the component's DSD support. Why: consumers need to know.
    21. Use framework-specific SSR tools. Why: they generate correct DSD.
    22. Audit DSD after framework upgrades. Why: SSR output may change.
    23. Test streaming. Why: verify chunks render correctly.
    24. Test with shadowrootclonable and shadowrootserializable. Why: verify they work as expected.
    25. Consider the total HTML size. Why: DSD increases HTML payload.

    12. Common Mistakes

    ❌ Mistake: Calling attachShadow() in the Constructor

    class MyElement extends HTMLElement {
    constructor() {
        super();
        this.attachShadow({ mode: 'open' }); // ❌ Error if DSD exists
    }
}

    Why it's wrong: Throws NotSupportedError if a declarative shadow root exists.

    ✅ Correct:

    class MyElement extends HTMLElement {
    constructor() {
        super();
        if (!this.shadowRoot) {
            this.attachShadow({ mode: 'open' });
        }
    }
}

    ❌ Mistake: Missing shadowrootmode

    <my-element>
    <template>
        <p>Not a shadow root</p>
    </template>
</my-element>

    Why it's wrong: Without shadowrootmode, the template is a normal template — not a shadow root.

    ✅ Correct:

    <my-element>
    <template shadowrootmode="open">
        <p>Shadow content</p>
    </template>
</my-element>

    ❌ Mistake: Using DSD Without the Polyfill

    <my-element>
    <template shadowrootmode="open">...</template>
</my-element>

    Why it's wrong: Older browsers do not support shadowrootmode.

    ✅ Correct: Include the polyfill.

    ❌ Mistake: Loading the Polyfill After Custom Elements

    <script type="module">
    class MyElement extends HTMLElement { }
    customElements.define('my-element', MyElement);
</script>
<script type="module">
    import { polyfill } from '@webcomponents/template-shadowroot';
    polyfill();
</script>

    Why it's wrong: The custom element upgrades before the shadow root exists.

    ✅ Correct: Load the polyfill first.

    ❌ Mistake: Using closed Mode for Security

    <template shadowrootmode="closed">
    <p>Secret content</p>
</template>

    Why it's wrong: closed is not a security boundary — DevTools can access it.

    ✅ Correct: Use open unless you have a specific reason.

    ❌ Mistake: Not Testing Without JavaScript

    Why it's wrong: DSD is designed for progressive enhancement. If the component requires JavaScript, you lose the benefit.

    ✅ Correct: Test the page with JavaScript disabled.

    ❌ Mistake: Not Testing the Upgrade

    Why it's wrong: The upgrade path may fail silently.

    ✅ Correct: Test with the custom element definition loaded after the HTML.

    ❌ Mistake: Ignoring HTML Size

    Why it's wrong: DSD increases the initial HTML payload significantly.

    ✅ Correct: Measure the HTML size and consider lazy loading.

    ❌ Mistake: Using DSD for Components That Don't Need It

    Why it's wrong: DSD adds complexity. Simple components may not need it.

    ✅ Correct: Use DSD for SSR-critical components.

    ❌ Mistake: Forgetting to Include DSD in the Server Response

    Why it's wrong: The client-only fallback requires JavaScript, defeating the purpose.

    ✅ Correct: Ensure the server renders the DSD.

    14. Security Considerations

    closed Mode Is Not a Security Boundary

    As with client-side shadow DOM, closed mode hides the shadow root but does not prevent access.

    XSS in DSD

    DSD content is parsed HTML. If it contains user input without escaping, XSS is possible.

    Defense: Sanitize user input before including it in DSD.

    CSP and DSD

    DSD is subject to CSP. Inline styles and scripts are still blocked by strict CSP unless nonces or hashes are used.

    SSR and Injection

    If the server generates DSD from user input, escape it.

    Defense: Use a templating engine with auto-escaping.

    DSD and Trusted Types

    Trusted Types may be required for DSD generation if the server uses innerHTML-style APIs.

    Hydration and Security

    Do not put sensitive data in DSD that should only be available to authenticated users.

    shadowrootserializable and Data Leakage

    shadowrootserializable allows shadow root serialization. Ensure the shadow tree does not contain sensitive data.
