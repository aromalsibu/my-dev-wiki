    Chapter: Lazy Loading

    1. Overview

    Definition

    Lazy loading is a technique that defers the loading of non-critical resources until they are actually needed — typically when they are about to enter the user's viewport. Instead of loading every image, video, iframe, and script on page load, the browser waits until the user scrolls near them, reducing initial page weight, saving bandwidth, and improving performance metrics like Largest Contentful Paint (LCP), Time to Interactive (TTI), and Total Blocking Time (TBT).

    HTML supports lazy loading natively for <img> and <iframe> through the loading="lazy" attribute. For other resources (video, audio, background images), lazy loading is typically implemented with the Intersection Observer API in JavaScript.

    Example: 

    <img src="photo.jpg" alt="A scenic view" loading="lazy">
<iframe src="https://example.com/embed" loading="lazy"></iframe>

    Purpose

    Lazy loading serves several essential purposes:

    • Performance – reduces initial page load size and time.
    • Bandwidth savings – only loads what the user actually sees.
    • Battery savings – less data and CPU on mobile devices.
    • Core Web Vitals – improves LCP, CLS, and INP.
    • User experience – faster perceived load time.
    • Server savings – fewer requests to the server.
    • Scalability – pages with thousands of images remain fast.
    • Mobile first – essential for users on slow connections.

    Where It Fits

    Lazy loading is a performance optimization technique that applies to any resource that is:

    • Not immediately visible in the viewport.
    • Expensive to load (large images, videos, iframes).
    • Optional for the initial render (ads, analytics, social embeds).

    It works alongside:

    • Responsive images (srcset, sizes, <picture>).
    • Resource hints (preload, prefetch, preconnect).
    • Caching (HTTP caching, Service Workers).
    • CDNs (global delivery).
    Performance Optimization
│
├── Resource Hints (preload, prefetch, preconnect)
├── Lazy Loading (this chapter)
├── Responsive Images
├── Caching
├── Compression
└── CDN

    2. Why It Exists

    The Problem

    A typical modern web page loads dozens or hundreds of resources:

    • Images – hero, thumbnails, gallery, avatars, icons.
    • Videos – trailers, embedded players.
    • Iframes – ads, embeds, social widgets.
    • Scripts – analytics, chat widgets, third-party libraries.
    • Fonts – custom typefaces.
    • Styles – multiple CSS files.

    Without lazy loading, the browser tries to fetch all of them at once on page load, even if the user never scrolls down. This causes:

    • Slow initial load – the network is saturated with unnecessary requests.
    • High bandwidth usage – especially painful on mobile data.
    • Battery drain – decoding and rendering costs.
    • Poor Core Web Vitals – high LCP, high TBT, high CLS.
    • Wasted server resources – requests for content never seen.
    • Poor user experience – users wait for content they don't need.

    Studies show:

    • A 1-second delay in page load can reduce conversions by 7%.
    • 53% of mobile users abandon pages that take longer than 3 seconds to load.
    • Images account for ~50% of a typical page's weight.

    Lazy loading solves the problem by loading only what the user is about to see.

    Previous Limitations

    Limitation Consequence
    Eager loading of all resources Slow initial load
    High bandwidth usage Wasted data
    Battery drain Shorter mobile battery life
    Poor Core Web Vitals Lower SEO ranking
    Server load Higher costs
    Poor UX on slow connections Users abandon the page
    No native support (pre-HTML5) Required JavaScript libraries

    Why Lazy Loading Was Introduced

    Lazy loading has existed as a JavaScript technique for over a decade. Libraries like LazyLoad, lozad.js, and lazysizes were widely used. But JavaScript-based lazy loading had drawbacks:

    • Required additional JavaScript.
    • Slower (JS must load before images can be lazy-loaded).
    • Accessible only after JS loads.
    • More complex to implement correctly.

    In HTML5, the loading attribute was introduced to provide native lazy loading for <img> and <iframe>. This enables:

    • No JavaScript – native browser support.
    • Faster – the browser can start lazy-loading immediately.
    • More reliable – no dependency on JS libraries.
    • Simpler – one attribute.
    • Better performance – browsers optimize native lazy loading.
    • Progressive enhancement – works even if JS is disabled.

    Native lazy loading was first supported in Chrome 76 (2019), and is now supported in all modern browsers.

<script>

    4. Mental Model

    The "Waiter Serving Food" Analogy

    Think of the browser as a waiter at a restaurant:

    • Eager loading = the waiter brings every dish to the table at once, filling the table with food the customer may not want.
    • Lazy loading = the waiter brings dishes as the customer is ready for them — appetizers first, then mains, then dessert.

    Lazy loading serves content just in time.

    The "Library Book Cart" Analogy

    Imagine a library with a cart of books. Eager loading pushes the entire cart to your table, even if you only want one book. Lazy loading delivers books as you request them — one at a time, just before you need them.

    The "Fog of War" Mental Model

    In strategy games, the map is covered by fog of war — you only see what's near your units. Lazy loading is like fog of war for the web: content near the viewport is loaded; content far away stays unloaded until it's needed.

    The "Conveyor Belt" Mental Model

    Think of the page as a conveyor belt moving past the user. Eager loading puts everything on the belt at once; lazy loading adds items just before they reach the user.

    The "Priorities" Mental Model

    Not all resources are equally important:

    Priority Resource Strategy
    Highest Above-the-fold images loading="eager", fetchpriority="high"
    High Critical CSS/JS Preload
    Medium Below-the-fold images loading="lazy"
    Low Ads, embeds, analytics loading="lazy", defer
    Lowest Footer images, third-party loading="lazy", Intersection Observer

    Lazy loading is about matching resource priority to user needs.

    5. Core Concepts

    Concept 1: The loading Attribute

    The loading attribute is a native HTML attribute for lazy loading <img> and <iframe>:

    <img src="photo.jpg" alt="Photo" loading="lazy">
    Value Behaviour
    lazy Load when near the viewport
    eager Load immediately
    auto Browser decides

    Concept 2: When "Lazy" Loads

    Browsers use heuristics to decide when to load a lazy image:

    • Chrome: loads when the image is within a distance based on connection speed (e.g., 1250px on fast connections, 2500px on slow).
    • Firefox: similar heuristics.
    • Safari: loads when near the viewport.

    The exact distance varies. The goal is to load just before the user sees the image.

    Concept 3: The Intersection Observer API

    The Intersection Observer API observes when an element enters or exits the viewport:

    const observer = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
        if (entry.isIntersecting) {
            // Load the resource
        }
    });
});
observer.observe(element);

    Options:

    • root – the element used as the viewport (default: browser viewport).
    • rootMargin – margin around the root (e.g., 200px to load early).
    • threshold – the percentage of the target visible (e.g., 0.1).

    Concept 4: rootMargin

    The rootMargin option lets you load resources before they enter the viewport:

    const observer = new IntersectionObserver(callback, {
    rootMargin: '200px 0px'
});

    This loads images when they're within 200px of the viewport.

    Concept 5: threshold

    The threshold option defines how much of the element must be visible:

    const observer = new IntersectionObserver(callback, {
    threshold: 0.1
});

    0.1 means 10% of the element must be visible.

    Concept 6: loading="lazy" vs. Intersection Observer

    Aspect loading="lazy" Intersection Observer
    Native ✅ ❌ (JS required)
    Works without JS ✅ ❌
    Customizable ❌ ✅
    Supports images ✅ ✅
    Supports iframes ✅ ✅
    Supports other resources ❌ ✅

    Best practice: Use loading="lazy" for images and iframes. Use Intersection Observer for other resources (backgrounds, videos, custom widgets).

    Concept 7: Lazy Loading Above-the-Fold Images

    Do NOT lazy load above-the-fold images (hero, LCP image). Instead:

    <img src="hero.jpg" alt="Hero" fetchpriority="high">

    Use fetchpriority="high" to prioritise LCP images.

    Concept 8: Lazy Loading and CLS

    Lazy loading can cause layout shift (CLS) if dimensions aren't reserved:

    <img src="photo.jpg" alt="Photo" loading="lazy" width="800" height="600">

    Always set width and height — or use aspect-ratio in CSS.

    Concept 9: Lazy Loading and LCP

    Lazy loading hurts LCP if applied to the LCP element. The LCP image should be loaded eagerly with high priority:

    <img src="hero.jpg" alt="Hero" fetchpriority="high">

    Rule: Lazy load below-the-fold images; eager load above-the-fold images.

    Concept 10: preload="none" for Video

    Videos have a preload attribute (not loading):

    <video controls preload="none" poster="poster.jpg">

    preload="none" defers video loading until the user plays it.

    Concept 11: Lazy Loading with IntersectionObserver for Videos

    const observer = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
        if (entry.isIntersecting) {
            const video = entry.target;
            video.src = video.dataset.src;
            video.load();
            observer.unobserve(video);
        }
    });
});

    Concept 12: Lazy Loading Background Images

    Background images set via CSS background-image are not lazy loaded natively:

    .hero {
    background-image: url('hero.jpg');
}

    Use JavaScript with Intersection Observer to lazy load them.

    Concept 13: The noscript Fallback

    For JavaScript-based lazy loading, always provide a <noscript> fallback:

    <img data-src="photo.jpg" alt="Photo" class="lazy">
<noscript>
    <img src="photo.jpg" alt="Photo">
</noscript>

    Why: Users with JS disabled see the images.

    Concept 14: Native Lazy Loading Is Progressive Enhancement

    loading="lazy" degrades gracefully:

    • Browsers that support it: lazy load.
    • Browsers that don't: load eagerly (like normal).

    This is progressive enhancement — no harm to older browsers.

    Concept 15: Lazy Loading and SEO

    • Googlebot supports loading="lazy".
    • Googlebot scrolls pages to trigger lazy loading.
    • Ensure images are discoverable (in the DOM, with valid src or data-src).
    • Avoid lazy loading critical content.

    Concept 16: Lazy Loading and Accessibility

    • alt text is required regardless of lazy loading.
    • Screen readers may not scroll, so lazy-loaded content might not load.
    • Best practice: Provide a "load more" button for critical content.

    Concept 17: The loading Attribute on <iframe>

    <iframe src="https://example.com/embed" loading="lazy" title="Embedded content"></iframe>

    Use case: Embeds (YouTube, maps, social widgets) that are below the fold.

    Concept 18: Lazy Loading and Ads

    Ads are often the heaviest resources:

    <ins class="adsbygoogle"
     data-ad-client="ca-pub-..."
     data-ad-slot="..."
     loading="lazy"></ins>

    Concept 19: Lazy Loading Third-Party Scripts

    Third-party scripts (analytics, chat widgets) can be loaded lazily:

    <script>
    window.addEventListener('load', () => {
        const script = document.createElement('script');
        script.src = 'https://example.com/chat-widget.js';
        document.body.appendChild(script);
    });
</script>

    Or with Intersection Observer for on-demand loading.

    Concept 20: Lazy Loading Libraries

    Before native support, libraries were used:

    • lazysizes – popular, feature-rich.
    • lozad.js – lightweight, uses Intersection Observer.
    • LazyLoad – vanilla JS.

    Best practice: Use native loading="lazy" when possible; fall back to libraries for advanced needs.

    Concept 21: Lazy Loading and Service Workers

    Service Workers can intercept requests and provide offline or lazy-loaded content:

    // In a service worker
self.addEventListener('fetch', (event) => {
    event.respondWith(
        caches.match(event.request).then(response => response || fetch(event.request))
    );
});

    Concept 22: Content-visibility CSS

    The content-visibility CSS property can skip rendering off-screen content:

    .card {
    content-visibility: auto;
    contain-intrinsic-size: 300px 200px;
}

    Note: content-visibility is different from lazy loading but serves a similar purpose (deferring rendering).

    Concept 23: Lazy Loading and Core Web Vitals

    • LCP – don't lazy load LCP images.
    • CLS – set dimensions.
    • INP – lazy loading reduces main-thread work.

    Concept 24: Lazy Loading and Mobile

    Mobile benefits most from lazy loading:

    • Slower connections.
    • Limited data plans.
    • Battery constraints.

    Concept 25: Testing Lazy Loading

    • Chrome DevTools Network panel – filter by image, scroll, see when images load.
    • Coverage panel – see unused bytes.
    • Lighthouse – audits for lazy loading.
    • WebPageTest – filmstrip view.

    6. How It Works

    Step-by-Step: Browser Lazy Loading with loading="lazy"

    1.  Browser parses the HTML and encounters an image.
    │
    ▼
2.  It reads the `loading` attribute.
    │
    ▼
3.  If `loading="lazy"`:
    │   ├── Browser stores the image as "pending".
    │   ├── It doesn't fetch the image yet.
    │   └── It creates a placeholder box (using width/height).
    │
    ▼
4.  As the user scrolls:
    │   ├── The browser tracks the viewport.
    │   ├── When the image is near the viewport (based on heuristics):
    │   │   ├── It fetches the image.
    │   │   ├── It decodes the image.
    │   │   └── It paints the image.
    │   └── If the image never enters the viewport, it's never loaded.
    │
    ▼
5.  The `load` event fires when the image is loaded.

    Step-by-Step: Intersection Observer Lazy Loading

    1.  JavaScript creates an IntersectionObserver.
    │
    ▼
2.  It observes elements with the `lazy` class.
    │
    ▼
3.  When an element enters the viewport:
    │   ├── The callback fires with the entry.
    │   ├── `entry.isIntersecting` is `true`.
    │   ├── The script swaps `data-src` to `src`.
    │   ├── The browser fetches the image.
    │   └── The observer unobserves the element.
    │
    ▼
4.  Elements not yet intersecting remain unloaded.

    The Browser's Lazy Loading Heuristics

    Chrome (and others) use heuristics:

    • Fast connection (4G): load when within ~1250px.
    • Slow connection (2G): load when within ~2500px.
    • Save-Data enabled: load when within ~8000px? No — actually it may be more conservative.

    The goal is to anticipate the user's scroll and load just in time.

    Intersection Observer Flow

    Observe → Element enters viewport → Callback fires → Load resource → Unobserve

    Lazy Loading and the Browser Cache

    • Lazy loaded images are cached like eager images.
    • On a second visit, they're loaded from cache.
    • loading="lazy" doesn't affect caching.

    Lazy Loading and HTTP/2

    • HTTP/2 multiplexing reduces the benefit of reducing requests.
    • But lazy loading still saves bandwidth and reduces initial load.

    Lazy Loading and Priority Hints

    • fetchpriority="high" – for LCP images.
    • fetchpriority="low" – for below-the-fold images.
    • fetchpriority="auto" – default.

    Native Lazy Loading vs. Eager Loading

    Aspect Lazy Eager
    Load timing Near viewport Immediately
    Bandwidth Reduced Full
    Initial load Faster Slower
    LCP impact Neutral/harmful Positive
    Best for Below the fold Above the fold

    • Lazy loading – defers fetching a resource.

3.  Element not intersecting → nothing.

    ▼
4.  User scrolls.
    │
    ▼
5.  Element enters viewport.
    │
    ▼
6.  Callback fires with entry.
    │

    11. Best Practices

    1. Lazy load below-the-fold images.
    2. Do NOT lazy load above-the-fold images.
    3. Use loading="lazy" for images and iframes.
    4. Use preload="none" for videos.
    5. Use Intersection Observer for other resources.
    6. Always set width and height – prevent CLS.
    7. Provide <noscript> fallbacks – for JS-based lazy loading.
    8. Use fetchpriority="high" for LCP images.
    9. Use rootMargin – load before the viewport.
    10. Test with DevTools – Network and Coverage panels.
    11. Test on slow connections – throttle in DevTools.
    12. Test on mobile – real devices.
    13. Monitor Core Web Vitals – LCP, CLS, INP.
    14. Don't lazy load critical content.
    15. Provide placeholders – for better UX.
    16. Consider blur-up – for visual continuity.
    17. Use content-visibility – for off-screen sections.
    18. Test in multiple browsers – Safari support varies.
    19. Consider feature detection – for older browsers.
    20. Document your lazy loading strategy – in a style guide.

    12. Common Mistakes

    ❌ Mistake: Lazy Loading Above-the-Fold Images

    <img src="hero.jpg" alt="Hero" loading="lazy">

    Why it's wrong: Delays LCP; hurts performance.

    ✅ Correct: 

    <img src="hero.jpg" alt="Hero" fetchpriority="high">

    ❌ Mistake: No width/height

    <img src="photo.jpg" alt="Photo" loading="lazy">

    Why it's wrong: Causes layout shift (CLS).

    ✅ Correct: 

    <img src="photo.jpg" alt="Photo" loading="lazy" width="800" height="600">

    ❌ Mistake: No <noscript> Fallback

    <img data-src="photo.jpg" alt="Photo" class="lazy">

    Why it's wrong: Users with JS disabled see nothing.

    ✅ Correct: 

    <img data-src="photo.jpg" alt="Photo" class="lazy">
<noscript>
    <img src="photo.jpg" alt="Photo">
</noscript>

    ❌ Mistake: Lazy Loading the LCP Image

    <img src="hero.jpg" alt="Hero" loading="lazy">

    Why it's wrong: LCP is the most important metric; lazy loading delays it.

    ✅ Correct: Use fetchpriority="high" and no loading="lazy".

    ❌ Mistake: Not Testing on Slow Connections

    Why it's wrong: Lazy loading is most important on slow connections.

    ✅ Correct: Use DevTools network throttling.

    ❌ Mistake: Using loading="lazy" on <video>

    <video loading="lazy">

    Why it's wrong: <video> doesn't support loading.

    ✅ Correct: 

    <video preload="none">

    ❌ Mistake: Not Unobserving Elements

    const observer = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
        if (entry.isIntersecting) {
            const img = entry.target;
            img.src = img.dataset.src;
            // Missing: observer.unobserve(img);
        }
    });
});

    Why it's wrong: Wastes resources re-checking.

    ✅ Correct: 

    observer.unobserve(entry.target);

    ❌ Mistake: No Placeholder

    <img data-src="photo.jpg" alt="Photo" class="lazy">

    Why it's wrong: Users see a blank space.

    ✅ Correct: Use a placeholder or skeleton.

    ❌ Mistake: No alt on Lazy Images

    <img data-src="photo.jpg" class="lazy">

    Why it's wrong: Accessibility failure.

    ✅ Correct: 

    <img data-src="photo.jpg" alt="A scenic view" class="lazy">

    ❌ Mistake: Lazy Loading Everything

    <img src="logo.png" alt="Logo" loading="lazy">

    Why it's wrong: Above-the-fold content should load eagerly.

    ✅ Correct: 

    <img src="logo.png" alt="Logo">

    ❌ Mistake: Not Testing on Safari

    Why it's wrong: Safari's support varies by version.

    ✅ Correct: Test on Safari 15.4+ (images) and 16.4+ (iframes).

    ❌ Mistake: No Feature Detection

    Why it's wrong: Older browsers won't lazy load.

    ✅ Correct: Feature-detect and fall back.

    ❌ Mistake: Lazy Loading Ads Without Fallback

    Why it's wrong: Ads might not load; revenue lost.

    ✅ Correct: Provide a fallback for ad blockers.

    13. Performance Considerations

    • Initial load – reduced significantly.
    • Bandwidth – saved for off-screen content.
    • Core Web Vitals – improves LCP, CLS, INP.
    • Server load – fewer requests.
    • Battery – less CPU and network.
    • Cache – lazy-loaded images cache normally.
    • HTTP/2 – reduces request overhead but lazy loading still saves bandwidth.
    • Placeholders – add minimal cost.
    • Intersection Observer – efficient; no scroll listeners.

    Performance Tips

    1. Use native lazy loading – faster than JS.
    2. Set dimensions – prevent CLS.
    3. Use fetchpriority – for priorities.
    4. Preload LCP images – for LCP.
    5. Use content-visibility – for off-screen sections.
    6. Minify HTML – reduce file size.
    7. Test with Lighthouse.

    14. Security Considerations

    • XSS – don't use user input in src or data-src without sanitization.
    • CORS – lazy-loaded cross-origin resources need CORS.
    • CSP – restrict resource sources with img-src, frame-src.
    • Placeholder – don't leak sensitive data.
    • Ad blockers – lazy-loaded ads may be blocked.
    • Tracking – lazy loading may affect analytics (content not loaded = no tracking).

    Security Best Practices

    1. Sanitize user input – for src.
    2. Use HTTPS – for all resources.
    3. Set CSP – restrict resource sources.
    4. Validate URLs – for lazy-loaded resources.
    5. Test with ad blockers.
