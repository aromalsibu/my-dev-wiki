    Chapter: Responsive Images

    1. Overview

    Definition

    Responsive images are images that adapt to the user's device, viewport size, screen resolution, and network conditions. Instead of serving a single image to every device, responsive images allow the browser to choose the most appropriate source from a set of candidates — selecting a smaller image for a phone, a larger one for a desktop, a higher-resolution one for a Retina display, and a different crop for a narrow layout.

    HTML provides two mechanisms for responsive images:

    • srcset + sizes on <img> — for resolution switching (same image, different sizes).
    • <picture> + <source> — for art direction and format fallback (different images or formats for different conditions).

    Together, these features solve one of the biggest performance problems of the modern web: serving images that are too large, too small, or incorrectly cropped for the user's context.

    Example: 

    <img src="photo-800.jpg"
     srcset="photo-400.jpg 400w,
             photo-800.jpg 800w,
             photo-1200.jpg 1200w"
     sizes="(max-width: 600px) 100vw, 50vw"
     alt="A scenic mountain view"
     width="800" height="600">

    Purpose

    Responsive images serve several essential purposes:

    • Performance – serve smaller images to smaller devices, reducing bandwidth and load time.
    • Visual quality – serve higher-resolution images to high-DPI displays.
    • Art direction – serve different crops or compositions for different layouts.
    • Format fallback – serve modern formats (AVIF, WebP) with fallbacks for older browsers.
    • User experience – avoid blurry images on Retina displays and oversized images on phones.
    • Bandwidth savings – reduce data usage, especially on mobile.
    • SEO – faster pages rank better; Google uses page speed as a ranking factor.
    • Core Web Vitals – reduce LCP (Largest Contentful Paint) and CLS (Cumulative Layout Shift).

    Where It Fits

    Responsive images are a cross-cutting concern that combines:

    • HTML – srcset, sizes, <picture>, <source>.
    • CSS – media queries, max-width: 100%, object-fit.
    • Server-side – image resizing, format conversion, CDN.
    • Build tools – generating multiple sizes and formats.
    • Performance monitoring – LCP, CLS, and bandwidth metrics.

    They sit at the intersection of media, performance, and responsive design.

    Responsive Images
│
├── Resolution Switching (srcset + sizes)
├── Art Direction (<picture> + media)
├── Format Fallback (<picture> + type)
├── Lazy Loading (loading="lazy")
├── Priority Hints (fetchpriority)
└── CSS (object-fit, aspect-ratio)

    2. Why It Exists

    The Problem

    Before responsive images, developers had two bad options:

    1. Serve one large image to everyone – looks great on desktops and Retina displays but wastes bandwidth on phones and slows page loads.
    2. Serve one small image to everyone – fast on phones but blurry on desktops and Retina displays.

    Neither option was acceptable. A hero image might be 200 KB on a phone but 2 MB on a desktop — a 10× difference. Serving the desktop image to a phone wasted data and slowed the page. Serving the phone image to a desktop looked unprofessional.

    Meanwhile, Retina displays (introduced with the iPhone 4 in 2010) doubled the pixel density. An image that looked sharp on a standard display looked blurry on Retina. Developers needed to serve 2× images — but only to devices that needed them.

    And art direction was impossible: a wide landscape image that worked on desktop might crop poorly on a narrow phone. Developers had to either compromise or use CSS hacks.

    Previous Limitations

    Limitation Consequence
    One image for all devices Wasteful or blurry
    No Retina support Blurry on high-DPI displays
    No art direction Poor crops on different viewports
    No format fallback Couldn't use modern formats
    Manual JavaScript solutions Complex, fragile, often inaccessible
    No browser optimization Browser couldn't choose the best image

    Why Responsive Images Were Introduced

    Responsive images were introduced through the Responsive Images Community Group and the <picture> element specification, which became part of HTML5. The goal was to let developers provide multiple image candidates and let the browser choose the best one based on:

    • Viewport size – how wide is the screen?
    • Device pixel ratio – how dense is the display?
    • Network conditions – how fast is the connection? (optional)
    • Art direction – which crop or composition is appropriate?
    • Format support – which format can the browser display?

    The result was two complementary features:

    1. srcset + sizes — for resolution switching (same image, different sizes).
    2. <picture> + <source> — for art direction and format fallback.

    Responsive images enable:

    • Optimal performance – the browser loads only what it needs.
    • Optimal quality – high-DPI displays get high-resolution images.
    • Optimal composition – different crops for different layouts.
    • Optimal format – modern formats with fallbacks.
    • No JavaScript – the browser handles selection natively.

    3. Syntax / Basic Usage

    Resolution Switching with srcset (Width Descriptors)

    <img src="photo-800.jpg"
     srcset="photo-400.jpg 400w,
             photo-800.jpg 800w,
             photo-1200.jpg 1200w"
     sizes="(max-width: 600px) 100vw, 50vw"
     alt="A scenic mountain view"
     width="800" height="600">
    • srcset – candidate images with their intrinsic widths (400w, 800w, 1200w).
    • sizes – how wide the image will be displayed at various viewports.
    • The browser picks the best candidate based on viewport and DPR.

    Resolution Switching with srcset (Pixel Density Descriptors)

    <img src="photo.jpg"
     srcset="photo.jpg 1x,
             photo@2x.jpg 2x,
             photo@3x.jpg 3x"
     alt="A scenic mountain view">
    • 1x, 2x, 3x – pixel density descriptors.
    • Use when the image is displayed at a fixed size.

    Note: You cannot mix w and x descriptors in the same srcset.

    The sizes Attribute

    <img src="photo-800.jpg"
     srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1200.jpg 1200w"
     sizes="(max-width: 600px) 100vw,
            (max-width: 900px) 50vw,
            33vw"
     alt="A photo">
    • 100vw – 100% of the viewport width.
    • 50vw – 50% of the viewport width.
    • 33vw – 33% of the viewport width.
    • 600px – a fixed width.
    • calc(100vw - 2rem) – a calculated width.

    The first matching media condition is used.

    Art Direction with <picture>

    <picture>
    <source media="(min-width: 1200px)" srcset="hero-wide.jpg">
    <source media="(min-width: 800px)" srcset="hero-medium.jpg">
    <source media="(min-width: 400px)" srcset="hero-small.jpg">
    <img src="hero-fallback.jpg" alt="A panoramic mountain landscape">
</picture>
    • The browser picks the first <source> whose media condition matches.
    • The <img> is the fallback and is required.

    Format Fallback with <picture>

    <picture>
    <source srcset="image.avif" type="image/avif">
    <source srcset="image.webp" type="image/webp">
    <img src="image.jpg" alt="A photo">
</picture>
    • The browser picks the first <source> whose type it supports.
    • The <img> is the fallback for older browsers.

    Combining Art Direction, Resolution, and Format

    <picture>
    <source media="(min-width: 1200px)"
            srcset="hero-wide.avif 1200w, hero-wide@2x.avif 2400w"
            sizes="100vw"
            type="image/avif">
    <source media="(min-width: 1200px)"
            srcset="hero-wide.jpg 1200w, hero-wide@2x.jpg 2400w"
            sizes="100vw"
            type="image/jpeg">
    <source media="(min-width: 800px)"
            srcset="hero-medium.avif 800w, hero-medium@2x.avif 1600w"
            sizes="100vw"
            type="image/avif">
    <img src="hero-small.jpg" alt="A panoramic mountain landscape">
</picture>

    Lazy Loading with Responsive Images

    <img src="photo-800.jpg"
     srcset="photo-400.jpg 400w, photo-800.jpg 800w"
     sizes="(max-width: 600px) 100vw, 50vw"
     alt="A photo"
     loading="lazy"
     width="800" height="600">

    Priority Hints

    <img src="hero-800.jpg"
     srcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1200.jpg 1200w"
     sizes="100vw"
     alt="Hero image"
     fetchpriority="high"
     width="1200" height="600">

    Code Breakdown

    Attribute Purpose
    srcset Candidate images with descriptors
    sizes Display sizes at various viewports
    <picture> Wrapper for art direction and format fallback
    <source> Candidate source with media, srcset, type, sizes
    media Media query for art direction
    type MIME type for format fallback
    loading lazy or eager
    fetchpriority high, low, or auto

    4. Mental Model

    The "Wardrobe" Analogy

    Think of responsive images as a wardrobe. You have the same outfit in different sizes (small, medium, large) and different styles (casual, formal). The browser is like a personal stylist: it looks at the occasion (viewport, device, network) and picks the best outfit (image) from your wardrobe.

    The "Menu" Analogy

    A responsive image is like a restaurant menu with multiple options:

    • srcset – the list of dishes (images) with their portion sizes (400w, 800w).
    • sizes – the table size (how much room you have).
    • <picture> – the menu categories (appetizers, mains, desserts) — different courses for different needs.
    • The browser – the waiter who picks the best dish for your table.

    The "Tailor" Analogy

    Think of the browser as a tailor. You provide a set of measurements (srcset) and the customer's requirements (sizes, media). The tailor picks the garment that fits best. The customer doesn't have to choose — the tailor does it automatically.

    The "Two Problems, Two Solutions" Mental Model

    There are two distinct problems in responsive images:

    1. Resolution switching – "same image, different sizes."
    2. Solution: srcset + sizes.
    3. Art direction – "different image for different contexts."
    4. Solution: <picture> + <source media="...">.

    Format fallback is a third use case, solved with <picture> + <source type="...">.

    The "Browser Knows Best" Mental Model

    The most important insight: the browser chooses the image, not the developer. You provide candidates and hints; the browser combines them with its knowledge of the viewport, DPR, network, and cache to pick the best source. This is why srcset and sizes are hints, not commands.

    The "Resolution Switching vs. Art Direction" Mental Model

    Problem Solution When to Use
    Same image, different sizes srcset + sizes Photos that work at any size
    Different image for different layouts <picture> + media Crops, compositions
    Modern format with fallback <picture> + type AVIF/WebP with JPEG fallback

    5. Core Concepts

    Concept 1: Width Descriptors (w)

    Width descriptors tell the browser the intrinsic width of each candidate:

    srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1200.jpg 1200w"
    • 400w means the image is 400 pixels wide.
    • The browser uses this to calculate which candidate is appropriate.

    Concept 2: Pixel Density Descriptors (x)

    Pixel density descriptors tell the browser the DPR for each candidate:

    srcset="photo.jpg 1x, photo@2x.jpg 2x, photo@3x.jpg 3x"
    • 1x – standard display.
    • 2x – Retina display (2× DPR).
    • 3x – high-end phones (3× DPR).

    Note: Use x descriptors when the image is displayed at a fixed size (e.g., a logo).

    Concept 3: The sizes Attribute

    The sizes attribute tells the browser how wide the image will be displayed:

    sizes="(max-width: 600px) 100vw, 50vw"
    • Media conditions are evaluated in order.
    • The first match wins.
    • The default (no media condition) is the fallback.

    Format: (media-condition) length or just length for the default.

    Concept 4: The Browser's Selection Algorithm

    1. Parse srcset to get candidates with widths.
    2. Parse sizes to get the display width at the current viewport.
    3. Multiply by the DPR to get the required pixel width.
    4. Choose the smallest candidate that is ≥ the required width.
    5. If none is large enough, choose the largest.

    Concept 5: The <picture> Element

    The <picture> element is a wrapper for <source> elements and an <img>:

    <picture>
    <source ...>
    <source ...>
    <img ...>
</picture>
    • The browser evaluates each <source> in order.
    • The first matching <source> is used.
    • The <img> is the fallback.

    Concept 6: The <source> Element

    The <source> element has:

    • media – a media query (for art direction).
    • srcset – candidate images with descriptors.
    • sizes – sizes for the candidates.
    • type – MIME type (for format fallback).

    Concept 7: media for Art Direction

    <source media="(min-width: 1200px)" srcset="hero-wide.jpg">

    The browser uses the first <source> whose media query matches.

    Concept 8: type for Format Fallback

    <source srcset="image.avif" type="image/avif">

    The browser uses the first <source> whose type it supports.

    Note: The browser does not check if the image is valid — it trusts the type attribute.

    Concept 9: Order of <source> Elements

    The order matters:

    1. Format fallback – put modern formats first.
    2. Art direction – put more specific media queries first.
    3. Resolution switching – put larger images first (browser picks).

    Best practice: 

    <picture>
    <source media="(min-width: 1200px)" srcset="wide.avif" type="image/avif">
    <source media="(min-width: 1200px)" srcset="wide.jpg" type="image/jpeg">
    <source media="(min-width: 800px)" srcset="medium.avif" type="image/avif">
    <source media="(min-width: 800px)" srcset="medium.jpg" type="image/jpeg">
    <img src="small.jpg" alt="A photo">
</picture>

    Concept 10: The currentSrc Property

    console.log(img.currentSrc); // The URL actually used

    This tells you which candidate the browser selected.

    Concept 11: Responsive Images and CSS

    img {
    max-width: 100%;
    height: auto;
}

    Why: Ensures images never overflow their container.

    Concept 12: The object-fit Property

    img {
    width: 300px;
    height: 200px;
    object-fit: cover;
}

    Values:

    • fill – stretch (default).
    • contain – fit inside.
    • cover – fill, cropping.
    • none – no scaling.
    • scale-down – smaller of none or contain.

    Concept 13: The aspect-ratio Property

    img {
    aspect-ratio: 16 / 9;
    width: 100%;
    height: auto;
}

    Why: Reserves space before the image loads, preventing layout shift.

    Concept 14: Lazy Loading

    <img src="photo.jpg" alt="A photo" loading="lazy">

    Values:

    • lazy – load when near the viewport.
    • eager – load immediately (default).

    Best practice: Use lazy for below-the-fold images; eager for hero images.

    Concept 15: Fetch Priority

    <img src="hero.jpg" alt="Hero" fetchpriority="high">

    Values:

    • high – prioritise loading.
    • low – deprioritise.
    • auto – default.

    Use case: high for LCP images.

    Concept 16: Preloading Responsive Images

    <link rel="preload"
      as="image"
      href="hero-1200.jpg"
      imagesrcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1200.jpg 1200w"
      imagesizes="100vw">

    Use case: Preload the hero image to improve LCP.

    Concept 17: Server-Side Responsive Images

    Many CDNs and image services (Cloudinary, Imgix, Cloudflare Images) generate responsive variants automatically:

    <img src="https://cdn.example.com/image/upload/w_800/photo.jpg"
     srcset="https://cdn.example.com/image/upload/w_400/photo.jpg 400w,
             https://cdn.example.com/image/upload/w_800/photo.jpg 800w,
             https://cdn.example.com/image/upload/w_1200/photo.jpg 1200w"
     sizes="(max-width: 600px) 100vw, 50vw"
     alt="A photo">

    Concept 18: Build-Time Responsive Images

    Build tools (Webpack, Vite, Eleventy) can generate multiple sizes and formats:

    // Vite example
import heroImage from './hero.jpg?responsive';

    Concept 19: The image-set() CSS Function

    .hero {
    background-image: image-set(
        url('hero-1x.jpg') 1x,
        url('hero-2x.jpg') 2x
    );
}

    Note: Limited browser support for image-set() in CSS.

    Concept 20: Responsive Images and Core Web Vitals

    • LCP – the hero image is often the LCP element; use fetchpriority="high" and preload.
    • CLS – set width/height or aspect-ratio to prevent layout shift.
    • FID/INP – responsive images reduce main-thread work.

    Concept 21: Browser Support

    • srcset + sizes – all modern browsers.
    • <picture> – all modern browsers.
    • AVIF – Chrome, Firefox, Safari (2022+).
    • WebP – all modern browsers.
    • loading="lazy" – all modern browsers.
    • fetchpriority – Chrome, Edge, Firefox (2023+).
    • image-set() – Chrome, Safari; partial Firefox.

    Concept 22: Responsive Images and SEO

    • Google uses mobile-first indexing.
    • Fast pages rank better.
    • alt text is indexed for image search.
    • Structured data (ImageObject) can enhance image search.

    Concept 23: Responsive Images and Accessibility

    • Always provide alt text.
    • Use <picture> for art direction, but keep alt on the <img>.
    • Ensure images are not the only way to convey information.

    Concept 24: Responsive Images and Bandwidth

    • Phones on cellular connections benefit most.
    • Serving 400w instead of 1200w saves ~90% of bytes.
    • Lazy loading below-the-fold images saves even more.

    Concept 25: The "Mobile-First" Responsive Image Strategy

    • Start with the smallest image.
    • Use srcset to provide larger images.
    • Use sizes to tell the browser how the image is displayed.
    • Let the browser choose.

    6. How It Works

    Step-by-Step: Browser Selection Algorithm

    1.  Browser parses the `<img>` element.
    │
    ▼
2.  It reads the `srcset` attribute.
    │   ├── Parses candidates: (URL, descriptor).
    │   └── Descriptors are widths (`400w`) or DPR (`2x`).
    │
    ▼
3.  It reads the `sizes` attribute.
    │   ├── Evaluates media conditions.
    │   └── Determines the display width at the current viewport.
    │
    ▼
4.  It calculates the required pixel width:
    │   └── display width × device pixel ratio.
    │
    ▼
5.  It selects the best candidate:
    │   ├── Smallest candidate ≥ required width.
    │   └── Or largest if none is big enough.
    │
    ▼
6.  It fetches the selected image.
    │
    ▼
7.  It decodes and paints the image.
    │
    ▼
8.  It sets `currentSrc` to the chosen URL.

    Example Selection

    Given: 

    <img src="photo-800.jpg"
     srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1200.jpg 1200w"
     sizes="(max-width: 600px) 100vw, 50vw">

    • Viewport: 800px, DPR: 2
    • sizes: 50vw (since 800px > 600px) = 400px
    • Required: 400 × 2 = 800px
    • Candidates: 400w, 800w, 1200w

    • Choice: 800w

    • Viewport: 400px, DPR: 2

    • sizes: 100vw (since 400px ≤ 600px) = 400px
    • Required: 400 × 2 = 800px
    • Candidates: 400w, 800w, 1200w

    • Choice: 800w

    • Viewport: 400px, DPR: 1

    • sizes: 100vw = 400px
    • Required: 400 × 1 = 400px
    • Candidates: 400w, 800w, 1200w
    • Choice: 400w

    Art Direction Selection

    <picture>
    <source media="(min-width: 1200px)" srcset="wide.jpg">
    <source media="(min-width: 800px)" srcset="medium.jpg">
    <img src="small.jpg" alt="A photo">
</picture>
    • Viewport: 1400px → wide.jpg
    • Viewport: 900px → medium.jpg
    • Viewport: 500px → small.jpg (fallback)

    Format Fallback Selection

    <picture>
    <source srcset="image.avif" type="image/avif">
    <source srcset="image.webp" type="image/webp">
    <img src="image.jpg" alt="A photo">
</picture>
    • Browser supports AVIF → image.avif
    • Browser supports WebP but not AVIF → image.webp
    • Browser supports neither → image.jpg

    The <picture> Algorithm

    1. Iterate <source> elements in order.
    2. For each <source>:
    3. Check type (if present). If unsupported, skip.
    4. Check media (if present). If no match, skip.
    5. If both pass, use the <source>.
    6. If no <source> matches, use the <img>.

    The currentSrc Property

    const img = document.querySelector('img');
console.log(img.currentSrc); // The URL actually used

    Use case: Debugging which image the browser chose.

    The sizes Attribute and CSS

    The sizes attribute should match the actual CSS width of the image:

    img {
    width: 50vw;
}

    <img sizes="50vw" ...>

    If they don't match, the browser may choose a suboptimal image.

    The w Descriptor and Intrinsic Width

    The w descriptor is the actual intrinsic width of the image file:

    <img srcset="photo-400.jpg 400w, photo-800.jpg 800w">
    • photo-400.jpg must actually be 400 pixels wide.
    • photo-800.jpg must actually be 800 pixels wide.

    If the widths are wrong, the browser chooses the wrong image.

    7. Internal Architecture / Under the Hood

    The srcset Parsing Algorithm

    1. Split the value by commas.
    2. For each candidate:
    3. Trim whitespace.
    4. Split by whitespace.
    5. First part is the URL.
    6. Second part (optional) is the descriptor.
    7. If the descriptor ends in w, it's a width.
    8. If it ends in x, it's a pixel density.
    9. If no descriptor, it defaults to 1x.

    The sizes Parsing Algorithm

    1. Split the value by commas.
    2. For each entry:
    3. If it starts with (, it's a media condition followed by a length.
    4. Otherwise, it's a length (the default).
    5. Evaluate media conditions in order.
    6. The first match wins.
    7. If no match, use the default.

    The Selection Algorithm

    1. For each candidate with a w descriptor:
    2. Calculate density = width / displayWidth.
    3. For each candidate with an x descriptor:
    4. Use its density directly.
    5. Pick the candidate with the smallest density ≥ DPR.
    6. If none, pick the largest.

    The <picture> Selection Algorithm

    1. For each <source> in order:
    2. If type is present and unsupported, skip.
    3. If media is present and doesn't match, skip.
    4. Otherwise, use this <source>.
    5. If no <source> matches, use the <img>.

    Browser Caching

    • The browser caches each candidate image separately.
    • If the viewport changes and a different candidate is needed, it's fetched.
    • Cached images are reused.

    The load Event

    Fires when the selected image loads:

    img.addEventListener('load', () => {
    console.log('Loaded:', img.currentSrc);
});

    The error Event

    console.error('Failed:', img.currentSrc);
});

    Accessibility Tree

    • The <img> is exposed with the alt text.
    • currentSrc is not exposed to assistive technologies.

    ▼

    │   ├── Parses candidates.
    │   ├── Evaluates media conditions.
    │   └── Determines required pixel width.
    │
    ▼
5.  Browser selects the best candidate.
    │
    ▼
6.  Browser fetches the image.
    │
    ▼
7.  Browser decodes the image.
    │
    ▼
8.  Browser paints the image.
    │
    ▼
9.  `load` event fires.
    │
    ▼
10. `currentSrc` is set.
    │
    ▼
11. If viewport changes, the browser may re-evaluate and load a different candidate.

    Responsive Re-evaluation

    When the viewport changes (e.g., resizing, rotating), the browser may:

    • Re-evaluate sizes.
    • Choose a different candidate.
    • Fetch it if not cached.

    11. Best Practices

    1. Always provide width and height – prevents layout shift.
    2. Use srcset and sizes – for resolution switching.
    3. Use <picture> – for art direction and format fallback.
    4. Use modern formats – AVIF, WebP, with fallbacks.
    5. Use loading="lazy" – for below-the-fold images.
    6. Use fetchpriority="high" – for LCP images.
    7. Preload the hero image – with imagesrcset and imagesizes.
    8. Use object-fit – for consistent sizing.
    9. Use aspect-ratio – for reserving space.
    10. Match sizes to CSS – ensure the browser chooses correctly.
    11. Use x descriptors – for fixed-size images (logos).
    12. Use w descriptors – for flexible images (photos).
    13. Don't mix w and x – in the same srcset.
    14. Order <source> correctly – specific media queries first.
    15. Test on real devices – not just emulators.
    16. Test on slow networks – ensure lazy loading works.
    17. Monitor Core Web Vitals – LCP and CLS.
    18. Use a CDN – for global delivery.
    19. Use build tools – to generate responsive variants.
    20. Document your strategy – in a style guide.

    12. Common Mistakes

    ❌ Mistake: No srcset

    <img src="large.jpg" alt="A photo">

    Why it's wrong: Same image for all devices.

    ✅ Correct: 

    <img src="photo-800.jpg"
     srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1200.jpg 1200w"
     sizes="(max-width: 600px) 100vw, 50vw"
     alt="A photo"
     width="800" height="600">

    ❌ Mistake: Wrong sizes Value

    <img srcset="photo-400.jpg 400w, photo-800.jpg 800w" sizes="100vw">

    Why it's wrong: If the image is displayed at 50vw, sizes="100vw" causes the browser to choose an image that's too large.

    ✅ Correct: Match sizes to the actual CSS width.

    ❌ Mistake: Incorrect Width Descriptors

    <img srcset="photo-800.jpg 400w, photo-1200.jpg 800w">

    Why it's wrong: The w descriptor must be the actual intrinsic width.

    ✅ Correct: 

    <img srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1200.jpg 1200w">

    ❌ Mistake: Mixing w and x

    <img srcset="photo-400.jpg 400w, photo@2x.jpg 2x">

    Why it's wrong: You cannot mix width and density descriptors in the same srcset.

    ✅ Correct: Use one or the other.

    ❌ Mistake: No <img> in <picture>

    <picture>
    <source srcset="image.avif" type="image/avif">
</picture>

    Why it's wrong: The <img> is required as a fallback.

    ✅ Correct: 

    <picture>
    <source srcset="image.avif" type="image/avif">
    <img src="image.jpg" alt="A photo">
</picture>

    ❌ Mistake: Wrong <source> Order

    <picture>
    <source srcset="image.jpg" type="image/jpeg">
    <source srcset="image.avif" type="image/avif">
    <img src="fallback.jpg" alt="A photo">
</picture>

    Why it's wrong: The browser always picks JPEG (first supported), never AVIF.

    ✅ Correct: Put AVIF first.

    ❌ Mistake: No alt on <img> Inside <picture>

    <picture>
    <source srcset="image.avif" type="image/avif">
    <img src="image.jpg">
</picture>

    Why it's wrong: No accessible description.

    ✅ Correct: 

    <picture>
    <source srcset="image.avif" type="image/avif">
    <img src="image.jpg" alt="A photo">
</picture>

    ❌ Mistake: Lazy Loading the Hero Image

    <img src="hero.jpg" alt="Hero" loading="lazy">

    Why it's wrong: Delays LCP; the hero should load immediately.

    ✅ Correct: 

    <img src="hero.jpg" alt="Hero" fetchpriority="high">

    ❌ Mistake: No Dimensions

    <img src="photo.jpg" alt="A photo" srcset="..." sizes="...">

    Why it's wrong: Causes layout shift (CLS).

    ✅ Correct: Add width and height.

    ❌ Mistake: Using srcset Without sizes

    <img srcset="photo-400.jpg 400w, photo-800.jpg 800w" alt="A photo">

    Why it's wrong: Without sizes, the browser assumes 100vw.

    ✅ Correct: Add sizes.

    ❌ Mistake: Not Testing on Real Devices

    Why it's wrong: Emulators may not accurately reflect DPR and network.

    ✅ Correct: Test on real phones, tablets, and desktops.

    ❌ Mistake: Serving Oversized Images

    <img src="photo-4000.jpg" alt="A photo" width="400" height="300">

    Why it's wrong: Wastes bandwidth.

    ✅ Correct: Serve the right size.

    ❌ Mistake: No Format Fallback

    <img src="image.avif" alt="A photo">

    Why it's wrong: Older browsers can't display AVIF.

    ✅ Correct: 

    <picture>
    <source srcset="image.avif" type="image/avif">
    <source srcset="image.webp" type="image/webp">
    <img src="image.jpg" alt="A photo">
</picture>

    • Decode – use decoding="async" for non-critical images.
    • Lazy loading – defers off-screen images.
    • CDN – global delivery, automatic resizing.
    • Build tools – generate variants at build time.
    • Image compression – reduce file size.

    16. When to Use

    • For any image that appears at different sizes – hero, gallery, cards.
    • For Retina displays – use x descriptors.
    • For art direction – use <picture>.
    • For format fallback – use <picture>.

    19. Did You Know?

    • Responsive images were introduced through the Responsive Images Community Group and the <picture> element specification.

    • The srcset attribute was first proposed by Mat Marquis in 2012.

    • The w descriptor stands for width — the intrinsic width of the image.

    • The x descriptor stands for pixel density — the DPR of the target display.

    • You cannot mix w and x descriptors in the same srcset.

    • The sizes attribute is only used with w descriptors.

    • The browser chooses the image, not the developer — srcset and sizes are hints.

    • <picture> is not a container for multiple images — it's a wrapper for <source> elements and a fallback <img>.

    • The <img> is required inside <picture>.

    • The order of <source> elements matters — the first matching one wins.

    • Format fallback uses the type attribute.

    • Art direction uses the media attribute.

    • AVIF offers better compression than WebP and JPEG.

    • WebP offers better compression than JPEG and PNG.

    • loading="lazy" defers off-screen images.

    • fetchpriority="high" prioritises LCP images.

    • Preloading the hero image improves LCP.

    • aspect-ratio reserves space and prevents CLS.

    • object-fit: cover crops images to fill their box.

    • image-set() is a CSS function for responsive background images.

    • CDNs like Cloudinary, Imgix, and Cloudflare Images generate responsive variants automatically.

    • Build tools like Eleventy Image, Vite, and Webpack generate variants at build time.

    • Google uses mobile-first indexing — responsive images are essential for SEO.

    • Core Web Vitals (LCP, CLS, INP) are affected by image loading.

    • The currentSrc property tells you which image the browser chose.

    • The naturalWidth and naturalHeight properties give the intrinsic size.

    • Best practices include using srcset, sizes, <picture>, modern formats, lazy loading, and preloading.

    • Common mistakes include no srcset, wrong sizes, mixing w and x, and wrong <source> order.

    • Following best practices for responsive images leads to faster, sharper, and more efficient web pages.

    20. Summary

    • Responsive images adapt to the user's device, viewport, and screen resolution.
    • Two mechanisms: srcset + sizes (resolution switching) and <picture> + <source> (art direction and format fallback).
    • srcset provides candidate images with w (width) or x (density) descriptors.
    • sizes tells the browser how wide the image will be displayed.
    • <picture> wraps <source> elements and a required fallback <img>.
    • media enables art direction (different images for different viewports).
    • type enables format fallback (AVIF → WebP → JPEG).
    • loading="lazy" defers off-screen images.
    • fetchpriority="high" prioritises LCP images.
    • Preload the hero image with imagesrcset and imagesizes.
    • object-fit and aspect-ratio control sizing and prevent CLS.
    • Best practices: use srcset, sizes, <picture>, modern formats, lazy loading, preloading, and test on real devices.
    • Common mistakes include no srcset, wrong sizes, mixing w and x, and wrong <source> order.
