    Chapter: Responsive Tables

    1. Overview

    Definition

    Responsive tables are HTML tables that adapt their layout to different screen sizes and devices — from wide desktop monitors to narrow mobile phones. A responsive table preserves readability, usability, and accessibility regardless of the viewport width, without requiring horizontal zooming, panning, or pinch‑to‑zoom gestures.

    Tables are one of the hardest HTML structures to make responsive. Unlike text, images, or cards, tables have two dimensions — rows and columns — and both must remain understandable when the available width shrinks. Different strategies have emerged:

    • Horizontal scroll – wrap the table in a scrollable container.
    • Stacked layout – convert rows into cards on small screens.
    • Priority columns – hide less important columns on mobile.
    • Flip/rotate – rotate the table 90° on small screens.
    • Collapsible rows – show only key columns and expand for details.
    • Virtualized/grid libraries – for very large data sets.

    There is no single "best" approach — the right strategy depends on the data, the users, and the context. But every responsive table must respect the WCAG 1.4.10 (Reflow) requirement: content must be usable at 320 CSS pixels wide without horizontal scrolling.

    Purpose

    Responsive tables serve several essential purposes:

    • Mobile usability – most web traffic is now mobile; tables must work on small screens.
    • Readability – text should not be microscopic or require zooming.
    • Accessibility – WCAG 1.4.10 requires reflow at 320px.
    • Retention – users abandon sites with broken mobile layouts.
    • SEO – Google uses mobile‑first indexing.
    • Conversion – usable tables improve task completion.
    • Universal design – benefits all users, not just those on phones.

    Where It Fits

    Responsive tables are a cross-cutting concern that combines:

    • Semantic HTML – proper table structure.
    • CSS – media queries, flexbox, grid, overflow.
    • JavaScript – for advanced patterns (collapsible rows, column toggles).
    • Accessibility – preserving header–cell associations in all layouts.
    • Performance – avoiding layout thrash and large DOM.

    They sit at the intersection of layout and data presentation.

    Responsive Table Strategies
│
├── Horizontal Scroll (simplest)
├── Stacked Layout (most common)
├── Priority Columns (hide/show)
├── Flip / Rotate (unusual)
├── Collapsible Rows (advanced)
└── Virtualized Grid (large data)

    2. Why It Exists

    The Problem

    Tables were designed for desktop screens with plenty of horizontal space. A table with 8 columns might fit comfortably on a 1440px monitor but become unusable on a 375px phone. Without responsive handling:

    • Columns are squeezed to unreadable widths.
    • Text wraps awkwardly, breaking numbers and dates.
    • Users must pinch‑zoom and pan horizontally.
    • Header–cell relationships are lost.
    • Touch targets become too small.
    • Accessibility is broken (WCAG 1.4.10 violation).

    This is not a niche problem — over 60% of web traffic comes from mobile devices, and tables appear everywhere: financial reports, product comparisons, schedules, directories, dashboards, and admin panels.

    Previous Limitations

    Limitation Consequence
    Fixed-width tables Overflow on small screens.
    Horizontal scrolling Poor UX on mobile.
    min-width columns Squeezed to unreadable widths.
    Hidden columns without indication Lost data.
    display: none on columns Accessibility issues.
    CSS flips without semantics Reading order broken.
    No mobile strategy Users abandon the site.

    Why Responsive Tables Were Introduced

    Responsive tables emerged as part of the broader Responsive Web Design movement, popularized by Ethan Marcotte in 2010. As mobile usage exploded, developers needed strategies to make tables work on small screens without sacrificing data or accessibility.

    Key milestones:

    • 2010 – Responsive Web Design article by Ethan Marcotte.
    • 2011–2013 – Early responsive table patterns (scroll, stack).
    • 2014 – HTML5 finalized; semantic tables reinforced.
    • 2018 – WCAG 2.1 introduced 1.4.10 (Reflow) requiring 320px usability.
    • 2020s – Mobile‑first indexing makes responsive tables essential for SEO.

    Today, responsive tables are a core requirement of professional web development.

    3. Syntax / Basic Usage

    Strategy 1: Horizontal Scroll (Simplest)

    Wrap the table in a container with overflow-x: auto.

    <div class="table-wrapper">
    <table>
        <thead>
            <tr>
                <th scope="col">Name</th>
                <th scope="col">Email</th>
                <th scope="col">Phone</th>
                <th scope="col">Department</th>
                <th scope="col">Location</th>
            </tr>
        </thead>
        <tbody>
            <tr>
                <td>Alice</td>
                <td>alice@example.com</td>
                <td>(555) 123-4567</td>
                <td>Engineering</td>
                <td>New York</td>
            </tr>
        </tbody>
    </table>

    .table-wrapper {
    overflow-x: auto;
    -webkit-overflow-scrolling: touch;
}

table {
    min-width: 600px; /* Optional: prevents columns from squishing */
    border-collapse: collapse;
}

    Pros: Simple, preserves all data, keeps semantics. Cons: Horizontal scrolling on small screens is not ideal for touch.

    Strategy 2: Stacked Layout (Most Common)

    On small screens, convert each row into a card, with each cell displaying its header via data-label.

    <table class="responsive-stack">

        <tr>
            <th scope="col">Name</th>
            <th scope="col">Email</th>
            <th scope="col">Department</th>
        </tr>

        <tr>

            <td data-label="Department">Engineering</td>
        </tr>
        <tr>
            <td data-label="Name">Bob</td>
            <td data-label="Email">bob@example.com</td>
            <td data-label="Department">Design</td>
        </tr>
    </tbody>
</table>

    @media (max-width: 600px) {
    .responsive-stack thead {
        display: none;
    }
    .responsive-stack,
    .responsive-stack tbody,
    .responsive-stack tr,
    .responsive-stack td {
        display: block;
        width: 100%;

        border-radius: 8px;

        padding: 0.5rem;
        border: none;

        text-align: right;

        text-align: left;

        border-bottom: none;
    }
}

    Pros: No horizontal scroll, all data visible, works well on narrow screens. Cons: Requires data-label attributes; header–cell association relies on CSS (screen readers still see the original table structure — which is good).

    Pros: Simple, focuses on key data. Cons: Hides data; may be inaccessible if not handled carefully (see Best Practices).

    Strategy 4: Flip / Rotate

    Rotate the table 90° on small screens.

    @media (max-width: 600px) {
    .flip-table {
        display: block;
        overflow-x: auto;
    }
    .flip-table thead {
        display: block;
        float: left;
    }
    .flip-table tbody {
        display: block;
        width: auto;
        position: relative;
        overflow-x: auto;
        white-space: nowrap;
    }
    .flip-table tr {
        display: inline-block;
    }
    .flip-table th,
    .flip-table td {
        display: block;
        text-align: left;
    }
}

    Pros: Preserves all data. Cons: Unusual; hard to read; rarely used.

    Strategy 5: Collapsible Rows

    Show only key columns; expand for details.

    <table class="collapsible-rows">
    <thead>
        <tr>
            <th scope="col">Name</th>

            <th scope="col"></th>

            </td>

                <strong>Email:</strong> alice@example.com<br>
                <strong>Phone:</strong> (555) 123-4567
            </td>
        </tr>
    </tbody>
</table>

    Pros: Focuses on key info; expands on demand. Cons: Requires JavaScript; more complex.

    4. Mental Model

    The "Swiss Army Knife" Analogy

    Responsive tables are like a Swiss Army knife — you choose the right tool for the situation. Horizontal scroll is the blade (simple), stacking is the scissors (most useful), priority columns are the tweezers (specialized), and collapsible rows are the corkscrew (advanced).

    The "Newspaper Layout" Analogy

    A newspaper adapts its layout to the page size. On a broadsheet, it uses many columns; on a tabloid, fewer; on a phone screen, a single column. Responsive tables do the same — they reflow to fit the available space.

    The "Water Filling a Container" Analogy

    Content should flow like water into whatever container it's given. A responsive table doesn't fight the viewport — it adapts, filling the space efficiently without overflow.

    The "Two Views of the Same Data" Analogy

    A table on desktop is one view; a stacked card on mobile is another. Both show the same data, but in different forms. The challenge is preserving meaning across both views.

    The "Reflow vs. Scroll" Mental Model

    There are two fundamental approaches:

    • Reflow – the table changes layout (stack, priority, flip).
    • Scroll – the table stays the same, but the container scrolls.

    WCAG 1.4.10 requires reflow for most content, but tables with two dimensions are an exception if scrolling doesn't require two‑dimensional scrolling.

    5. Core Concepts

    Concept 1: WCAG 1.4.10 (Reflow)

    WCAG 2.1 Success Criterion 1.4.10 requires:

    Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions, for: - Vertical scrolling content at a width equivalent to 320 CSS pixels. - Horizontal scrolling content at a height equivalent to 256 CSS pixels.

    Exception: Content that requires two‑dimensional layout (like maps, data tables with 2D relationships) is exempt. However, best practice is still to make tables usable at 320px.

    Concept 2: The data-label Pattern

    The data-label attribute holds the column header text, which is displayed via ::before in the stacked layout:

    <td data-label="Email">alice@example.com</td>

    td::before {
    content: attr(data-label);
}

    Why: It preserves the header–cell association visually when the <thead> is hidden.

    Concept 3: Preserving Accessibility

    When you hide <thead> with display: none, screen readers lose the header association. Solutions:

    1. Use sr-only class instead of display: none:
    .sr-only {
    position: absolute;
    width: 1px;
    height: 1px;
    padding: 0;
    margin: -1px;
    overflow: hidden;
    clip: rect(0, 0, 0, 0);
    white-space: nowrap;
    border: 0;
}
    1. Use role="presentation" on <thead> – not recommended.
    2. Keep the <thead> in the DOM and use CSS to visually hide it – the best approach.

    Concept 4: Horizontal Scroll with -webkit-overflow-scrolling

    .table-wrapper {
    overflow-x: auto;
    -webkit-overflow-scrolling: touch; /* Momentum scrolling on iOS */
}

    Note: -webkit-overflow-scrolling is deprecated in newer iOS versions but still useful for older ones.

    Concept 5: Scroll Hints

    When a table scrolls horizontally, users need a visual hint. Common approaches:

    • Fade/shadow on the edge:
    .table-wrapper {
    background: linear-gradient(to right, white 30%, rgba(255,255,255,0)),
                linear-gradient(to right, rgba(255,255,255,0), white 70%) 100% 0;
    background-repeat: no-repeat;
    background-size: 40px 100%, 40px 100%;
    background-attachment: local, scroll;
}
    • "Scroll →" text or icon.
    • Scrollbar styling.

    Concept 6: Sticky First Column

    For wide tables, make the first column sticky:

    .table-wrapper th:first-child,
.table-wrapper td:first-child {
    position: sticky;
    left: 0;
    background: white;
    z-index: 1;
}

    Use case: Employee directories, product lists.

    Concept 7: Sticky Header

    For long tables, make the header sticky:

    .table-wrapper thead th {
    position: sticky;
    top: 0;
    background: white;
    z-index: 2;
}

    Use case: Long lists, financial reports.

    Concept 8: min-width and table-layout: fixed

    table {
    min-width: 600px; /* Prevents squishing */
    table-layout: fixed; /* Predictable column widths */
}

    Why: min-width ensures columns don't collapse to unreadable widths.

    Concept 9: Responsive Font Sizes

    @media (max-width: 600px) {
    table {
        font-size: 0.875rem; /* Smaller on mobile */
    }
}

    Note: Don't go too small — 14px minimum for readability.

    Concept 10: Touch-Friendly Targets

    If table cells contain interactive elements (buttons, links), ensure they're at least 44×44 CSS pixels for touch.

    td button,
td a {
    min-width: 44px;
    min-height: 44px;
    padding: 0.5rem;
}

    Concept 11: Virtualized Tables

    For tables with thousands of rows, use virtualization — only render visible rows. Libraries:

    • TanStack Table (React, Vue, Svelte, vanilla).
    • AG Grid (commercial).
    • Handsontable (commercial).
    • Grid.js (open source).
    • React Virtualized / react-window.

    Note: Virtualized tables lose native table semantics — use ARIA roles (role="grid", role="row", etc.) carefully.

    Concept 12: CSS Grid vs. Table Layout

    Some developers use CSS Grid for tabular data instead of <table>. This is strongly discouraged because:

    • Screen readers see a flat list, not a table.
    • Header–cell associations are lost.
    • Sorting and navigation are harder.

    Exception: For application grids (spreadsheet‑like, editable), role="grid" with ARIA is appropriate.

    Concept 13: Responsive Stack with display: block

    The stacked pattern uses display: block on table elements, which removes table semantics. However, because the <table> element is still in the DOM, screen readers still interpret it as a table. The display: block only affects visual layout.

    Important: Don't use role="presentation" — the semantics must be preserved for screen readers.

    Concept 14: ::before Content and Accessibility

    The ::before pseudo-element content is not read by screen readers in most cases (it's considered decorative). This is good — we don't want duplicate headers announced. The screen reader reads the original <thead> and <th>.

    Concept 15: Progressive Enhancement

    A responsive table should work without JavaScript (for scroll/stack) and be enhanced with JavaScript (for collapsible rows, column toggles). This ensures the table works for all users.

    Concept 16: Mobile-First CSS

    Start with the stacked layout for small screens, then enhance for larger screens:

    /* Mobile-first: stacked */
table, thead, tbody, tr, td {
    display: block;
}

/* Desktop: table */
@media (min-width: 601px) {
    table { display: table; }
    thead { display: table-header-group; }
    tbody { display: table-row-group; }
    tr { display: table-row; }
    td, th { display: table-cell; }
}

    Why: Mobile-first ensures the baseline is simple and performant.

    Step-by-Step: Browser Rendering a Responsive Table

    1.  Browser parses the HTML and builds the DOM.
    │
    ▼
2.  Browser applies CSS.
    │
    ▼
3.  Media queries evaluate based on viewport width.
    │   ├── Desktop (>600px) → table layout.
    │   └── Mobile (≤600px) → stacked layout.
    │

    │   ├── thead { display: none } (or sr-only).

    The Accessibility Tree in Stacked Layout

    Even when the visual layout is stacked, the accessibility tree still exposes:

    • table role.
    • rowgroup, row, columnheader, rowheader, cell.

    This is because the DOM is unchanged — only CSS changes the visual presentation. Screen readers read the DOM, not the visual layout.

    The display: block Effect

    Setting display: block on table elements removes the table layout algorithm, but the semantics remain. This is a key insight: visual layout and semantics are independent.

    The data-label Attribute

    The data-label attribute is a custom data attribute (data-*), which is valid HTML5 and accessible via attr() in CSS.

    <td data-label="Email">alice@example.com</td>

    td::before {
    content: attr(data-label);
}

    Media Query Breakpoints

    Common breakpoints for tables:

    Breakpoint Device
    320px Small phone
    480px Phone
    600px Large phone / small tablet
    768px Tablet
    1024px Desktop

    Best practice: Use the breakpoint where your table breaks — not arbitrary device widths.

    7. Internal Architecture / Under the Hood

    The CSS Table Model

    CSS defines the table layout algorithm with display values:

    Element Default display
    <table> table
    <thead> table-header-group
    <tbody> table-row-group
    <tfoot> table-footer-group
    <tr> table-row
    <th>, <td> table-cell
    <caption> table-caption
    <colgroup> table-column-group
    <col> table-column

    When you set display: block, the element no longer participates in the table layout algorithm — it becomes a regular block.

    The DOM vs. the Visual Layout

    The DOM is the source of truth for accessibility. CSS changes visual layout but not the DOM. This is why:

    • Screen readers still see a table even when visually stacked.
    • The ::before content is not read (it's decorative).
    • Header–cell associations are preserved.

    The Accessibility Tree

    The browser's accessibility engine builds the tree from the DOM, not the visual layout. So:

    • <table> → role: table.
    • <th scope="col"> → role: columnheader.
    • <td> → role: cell.

    Even if the visual layout is stacked, the accessibility tree remains a table.

    overflow-x: auto and Scrolling

    When overflow-x: auto is set on a container:

    • The browser creates a scroll container.
    • Content wider than the container can be scrolled horizontally.
    • On touch devices, -webkit-overflow-scrolling: touch enables momentum scrolling (older iOS).

    position: sticky in Tables

    position: sticky works on <th> inside <thead> for sticky headers:

    thead th {
    position: sticky;
    top: 0;
    z-index: 1;
}

    And on the first column for sticky columns:

    th:first-child, td:first-child {
    position: sticky;
    left: 0;
    z-index: 2;
}

    Note: Sticky headers and sticky columns can conflict with overflow-x: auto — test carefully.

    table-layout: fixed

    With table-layout: fixed:

    • Column widths are determined by the first row (or <col> widths).
    • Rendering is faster.
    • Column widths are predictable.
    table {
    table-layout: fixed;
    width: 100%;
}

    Media Query Evaluation

    Media queries evaluate based on:

    • Viewport width (max-width, min-width).
    • Device pixel ratio (resolution).
    • Orientation (orientation).
    • Preferences (prefers-reduced-motion, prefers-color-scheme).

    11. Best Practices

    1. Use semantic <table> – never replace with div + ARIA for data tables.

    2. Preserve header–cell associations – use <th>, scope, headers.

    3. Start mobile-first – base styles for small screens, enhance for large.

    4. Use data-label for stacked layouts – shows the header in each cell.

    5. Use sr-only instead of display: none for <thead> – preserves accessibility.

    6. Don't rely on ::before for accessibility – the DOM provides the headers.

    7. Provide scroll hints – for horizontal scroll tables.

    8. Use -webkit-overflow-scrolling: touch – for momentum scrolling on iOS.

    9. Use min-width on the table – prevents column squishing.

    10. Use table-layout: fixed – for predictable column widths.

    11. Use sticky headers – for long tables.

    12. Use sticky first column – for wide tables.

    13. Test with WCAG 1.4.10 (Reflow) – ensure usability at 320px.

    14. Test with screen readers – ensure header associations are preserved.

    15. Test keyboard navigation – ensure all interactive elements are reachable.

    16. Use touch-friendly targets – minimum 44×44 CSS pixels.

    17. Test on real devices – emulators don't catch everything.

    18. Avoid hiding data without a way to reveal it – provide a toggle.

    19. Use prefers-reduced-motion – for users who prefer no animation.

    20. Use prefers-color-scheme – for dark mode support.

    21. Validate HTML – ensure correct structure.

    22. Use aria-sort – for sortable tables.

    23. Use aria-rowcount and aria-colcount – for virtualized tables.

    24. Document your conventions – in a style guide.

    25. Test on slow connections – ensure the table loads quickly.

    12. Common Mistakes

    ❌ Mistake: Using display: none on <thead>

    thead {
    display: none;
}

    Why it's wrong: Screen readers lose the header association.

    ✅ Correct: Use sr-only class:

    .sr-only {
    position: absolute;
    width: 1px;
    height: 1px;
    padding: 0;
    margin: -1px;
    overflow: hidden;
    clip: rect(0, 0, 0, 0);
    white-space: nowrap;
    border: 0;
}

    ❌ Mistake: Hiding Columns Without a Way to Show Them

    @media (max-width: 600px) {
    .col-3, .col-4 {
        display: none;
    }
}

    Why it's wrong: Data is lost for mobile users.

    ✅ Correct: Provide a toggle to show hidden columns.

    ❌ Mistake: Using CSS Grid for Data Tables

    <div class="grid">
    <div>Name</div>
    <div>Age</div>
</div>

    Why it's wrong: Screen readers see a flat list, not a table.

    ✅ Correct: Use <table> with proper semantics.

    ❌ Mistake: Breaking Header–Cell Associations with CSS

    td {
    order: 2;
}

    Why it's wrong: Visual order no longer matches DOM order.

    ✅ Correct: Keep DOM order matching visual order.

    ❌ Mistake: No data-label on Stacked Cells

    <td>alice@example.com</td>

    Why it's wrong: Users can't tell what the value represents.

    ✅ Correct: 

    <td data-label="Email">alice@example.com</td>

    ❌ Mistake: Squishing Columns Without min-width

    table {
    width: 100%;
}

    Why it's wrong: Columns collapse to unreadable widths.

    ✅ Correct: 

    table {
    width: 100%;
    min-width: 600px;
}

    ❌ Mistake: Not Testing at 320px

    Why it's wrong: WCAG 1.4.10 requires usability at 320px.

    ✅ Correct: Test at 320px width and ensure the table is usable.

    ❌ Mistake: Using overflow: hidden on the Wrapper

    .table-wrapper {
    overflow: hidden;
}

    Why it's wrong: Content is clipped and inaccessible.

    ✅ Correct: 

    .table-wrapper {
    overflow-x: auto;
}

    ❌ Mistake: Not Providing Scroll Hints

    Why it's wrong: Users don't know the table scrolls.

    ✅ Correct: Add a scroll hint (fade, text, or icon).

    ❌ Mistake: Forgetting to Test with Screen Readers

    Why it's wrong: You won't know if the table is accessible.

    ✅ Correct: Test with NVDA, JAWS, or VoiceOver.

    ❌ Mistake: Using position: fixed for Sticky Headers

    thead th {
    position: fixed;
}

    Why it's wrong: position: fixed removes the header from the table flow.

    ✅ Correct: 

    thead th {
    position: sticky;
    top: 0;
}

    ❌ Mistake: Not Handling prefers-reduced-motion

    .table-wrapper {
    scroll-behavior: smooth;
}

    Why it's wrong: Users who prefer reduced motion may experience discomfort.

    ✅ Correct: 

    @media (prefers-reduced-motion: no-preference) {
    .table-wrapper {
        scroll-behavior: smooth;
    }
}

    13. Performance Considerations

    • Table layout algorithm – table-layout: fixed is faster than auto.
    • Sticky positioning – position: sticky has a small performance cost.
    • Virtualization – for large tables, virtualize rows to reduce DOM size.
    • Media queries – negligible performance impact.
    • overflow-x: auto – creates a scroll container; minimal cost.
    • Stacked layout – display: block on many elements can be slower than native table layout, but the impact is minimal.
    • ::before content – negligible cost.
    • Repaints – resizing the viewport triggers repaints; test on low-end devices.

    Performance Tips

    1. Use table-layout: fixed – faster rendering.
    2. Virtualize large tables – for hundreds/thousands of rows.
    3. Avoid complex sticky headers – test performance.
    4. Minimize DOM size – fewer cells = faster rendering.
    5. Use content-visibility: auto – for off-screen tables (with caution).
    6. Minify CSS and HTML – reduce file size.
    7. Use will-change sparingly – only for animated tables.

    14. Security Considerations

    • XSS – if table content contains user-generated data, sanitize it before rendering.
    • innerHTML – avoid using innerHTML with user input; use textContent or a sanitizer.
    • Injection – never insert user input directly into table attributes.
    • Data leakage – tables often contain sensitive data; ensure access controls are in place.
    • No direct security implications – responsive table techniques themselves are not security risks.

    Security Best Practices

    1. Sanitize user input – before inserting into tables.
    2. Use textContent – instead of innerHTML for text.
    3. Validate structure – ensure the table structure is well-formed.
    4. Use CSP – to restrict inline scripts and styles.
    5. Protect sensitive data – with server-side access controls.

    15. Debugging Tips

    • DevTools Device Toolbar – test different viewport sizes.
    • DevTools Elements panel – inspect the table structure and computed styles.
    • Computed styles – check display, overflow-x, table-layout.
    • Console – use document.querySelectorAll('table') to count tables.
    • Accessibility Inspector – check the accessibility tree at different sizes.
    • Screen reader testing – test at both desktop and mobile sizes.
    • Keyboard testing – navigate the table with Tab and arrow keys.
    • Validator – check for invalid nesting and attributes.
    • Lighthouse – audit for accessibility and performance.
    • axe DevTools – accessibility testing extension.
    • Test at 320px – WCAG 1.4.10 requirement.
    • Test on real devices – emulators don't catch everything.

    16. When to Use

    • For all data tables – responsive tables are the default.
    • For mobile-first sites – tables must work on small screens.
    • For e-commerce – product comparisons, orders.
    • For financial apps – reports, transactions.
    • For admin panels – user lists, logs.
    • For dashboards – metrics, KPIs.
    • For any table that appears on mobile.

    17. When Not to Use

    • For non-tabular data – use lists, cards, or paragraphs.
    • For layout – use CSS Grid or Flexbox.
    • For very large data sets – use a virtualized grid or a data grid library.
    • For application grids – use ARIA grid patterns with full keyboard support.
    • For print-only tables – use print styles instead.

    19. Did You Know?

    • Over 60% of web traffic comes from mobile devices — responsive tables are essential.

    • WCAG 2.1 Success Criterion 1.4.10 (Reflow) requires content to be usable at 320 CSS pixels wide without horizontal scrolling.

    • Data tables with two-dimensional relationships are exempt from 1.4.10, but best practice is still to make them usable at 320px.

    • The data-label pattern was popularized by Aaron Gustafson and others around 2012.

    • sr-only class (also called visually-hidden) hides content visually but keeps it accessible to screen readers.

    • Screen readers read the DOM, not the visual layout — so stacked tables still work as tables for screen reader users.

    • display: block on table elements removes the table layout algorithm but preserves the semantics.

    • table-layout: fixed is the fastest table layout algorithm.

    • Sticky headers use position: sticky on <thead> th.

    • Sticky first columns use position: sticky; left: 0 on the first cell of each row.

    • -webkit-overflow-scrolling: touch enables momentum scrolling on older iOS devices.

    • scrollbar-gutter: stable prevents layout shift when the scrollbar appears.

    • prefers-reduced-motion respects users who prefer no animation.

    • prefers-color-scheme supports dark mode.

    • Virtualized tables render only visible rows, improving performance for large data sets.

    • ARIA role="grid" is for interactive application grids, not static data tables.

    • aria-sort indicates the current sort order of a column.

    • aria-rowcount and aria-colcount are used for virtualized tables.

    • Mobile-first CSS starts with the smallest screen and enhances for larger screens.

    • The ::before pseudo-element is not read by screen readers — it's decorative.

    • Touch targets should be at least 44×44 CSS pixels.

    • Google uses mobile-first indexing — mobile usability affects SEO.

    • Responsive tables benefit all users, not just those on phones.

    • The best responsive strategy depends on the data — there's no one-size-fits-all solution.

    • Testing at 320px width is a core part of WCAG 1.4.10 compliance.

    • Real device testing catches issues that emulators miss.

    • Accessibility and responsiveness go hand in hand — both are about adapting to the user's context.

    • Responsive tables are a fundamental skill for modern web developers.

    20. Summary

    • Responsive tables adapt their layout to different screen sizes and devices.
    • The main strategies are: horizontal scroll, stacked layout, priority columns, flip/rotate, collapsible rows, and virtualized grids.
    • Horizontal scroll is the simplest; wrap the table in overflow-x: auto.
    • Stacked layout converts rows into cards on mobile, using data-label and ::before.
    • Priority columns hide less important columns on small screens (with a way to reveal them).
    • WCAG 1.4.10 (Reflow) requires usability at 320 CSS pixels wide.
    • Preserve accessibility — use sr-only instead of display: none for <thead>, and keep the DOM structure intact.
    • Best practices: mobile-first CSS, data-label, scroll hints, min-width, table-layout: fixed, sticky headers, touch-friendly targets, prefers-reduced-motion, prefers-color-scheme, and thorough testing.
    • Common mistakes include using display: none on <thead>, hiding columns without a toggle, using CSS Grid for data tables, and not testing at 320px.
    • Test with screen readers — stacked tables still work as tables because the DOM is unchanged.
    • Performance: use table-layout: fixed, virtualize large tables, and minimize DOM size.
    • Security: sanitize user input, use textContent, and protect sensitive data.
    • Responsive tables are essential for modern web development — they benefit all users and meet accessibility requirements.
