    Chapter: Relative URLs

    1. Overview

    Definition

    A relative URL is a URL that specifies the location of a resource relative to the current document's URL (or another base URL), rather than providing the full absolute address. Instead of specifying the protocol, domain, and path (e.g., https://example.com/about/team.html), a relative URL provides only the difference between the current location and the target — such as team.html, ../about/, or /contact.

    Relative URLs are resolved by the browser against a base URL — typically the URL of the current document, or an explicit <base> element if one is present. The result is a complete, absolute URL that the browser uses to make the request.

    Relative URLs are essential for creating portable, maintainable websites that can be moved between domains, subdirectories, and environments (development, staging, production) without rewriting every link.

    Purpose

    Relative URLs serve several essential purposes:

    • Portability – links work regardless of the domain or subdirectory.
    • Maintainability – changing the domain or moving the site requires no link updates.
    • Brevity – shorter, cleaner markup.
    • Consistency – ensures all internal links use the same base.
    • Environment flexibility – the same code works in development, staging, and production.
    • Bandwidth savings – shorter URLs mean smaller HTML files.

    Where It Fits

    Relative URLs are used in any HTML attribute that accepts a URL:

    • <a href="..."> – links.
    • <img src="..."> – images.
    • <link href="..."> – stylesheets, icons.
    • <script src="..."> – scripts.
    • <form action="..."> – form submission.
    • <iframe src="..."> – embedded frames.
    • <video src="...">, <audio src="...">, <source src="..."> – media.
    • <area href="..."> – image map areas.
    • CSS url(...) – background images, fonts.
    <!-- Relative URL -->
<a href="about.html">About</a>
<img src="images/logo.png" alt="Logo">

<!-- Absolute URL -->
<a href="https://example.com/about.html">About</a>
<img src="https://example.com/images/logo.png" alt="Logo">

    2. Why It Exists

    The Problem

    Imagine you have a website with hundreds of pages, each containing dozens of links. If every link used an absolute URL (e.g., https://example.com/about.html), then:

    • Moving the site to a new domain (https://newdomain.com) would require updating every single link.
    • Moving the site to a subdirectory (https://example.com/v2/) would require updating every link.
    • Running the site locally for development (http://localhost:3000/) would require yet another set of links.

    This is impractical for any non-trivial website.

    Previous Limitations

    Limitation Consequence
    Hardcoded absolute URLs Site can't be moved without rewriting links.
    Environment-specific URLs Different code for dev, staging, production.
    Verbose markup Long URLs clutter the HTML.
    Error-prone Manual URL updates are easy to get wrong.
    No portability Site is locked to a specific domain.

    Why Relative URLs Were Introduced

    Relative URLs were introduced as part of the original URL specification (RFC 1630, 1994) to solve the portability problem. They allow authors to specify only the part of the URL that differs from the current document's URL. The browser resolves the relative URL against the base URL to produce an absolute URL.

    This enables:

    • Portability – the site can be moved to a new domain or subdirectory without changes.
    • Environment flexibility – the same code works in development, staging, and production.
    • Brevity – shorter, cleaner markup.
    • Maintainability – links are easier to read and update.
    • Consistency – all internal links share the same base.

    Relative URLs are a fundamental part of how the web works. Without them, the web would be far less flexible and far more brittle.

    3. Syntax / Basic Usage

    The Three Types of Relative URLs

    Type Syntax Example Resolved Against
    Document-relative path/to/file about.html Current document's directory
    Root-relative /path/to/file /about.html Site root (domain)
    Protocol-relative //domain/path //example.com/page Current protocol (deprecated)

    Document-Relative URLs

    Document-relative URLs are resolved against the directory of the current document.

    <!-- Current URL: https://example.com/blog/post.html -->

<a href="about.html">About</a>
<!-- Resolves to: https://example.com/blog/about.html -->

<a href="images/logo.png">Logo</a>
<!-- Resolves to: https://example.com/blog/images/logo.png -->

<a href="../index.html">Home</a>
<!-- Resolves to: https://example.com/index.html -->

<a href="../../contact.html">Contact</a>
<!-- Resolves to: https://example.com/contact.html -->

    Path syntax: - file.html – same directory. - subdir/file.html – subdirectory. - ../file.html – parent directory. - ../../file.html – grandparent directory.

    Root-Relative URLs

    Root-relative URLs start with / and are resolved against the site root (the domain).

    <!-- Current URL: https://example.com/blog/post.html -->

<a href="/about.html">About</a>
<!-- Resolves to: https://example.com/about.html -->

<a href="/images/logo.png">Logo</a>
<!-- Resolves to: https://example.com/images/logo.png -->

<a href="/blog/">Blog</a>
<!-- Resolves to: https://example.com/blog/ -->

    Root-relative URLs are independent of the current document's location. They always resolve from the domain root.

    Protocol-Relative URLs (Deprecated)

    Protocol-relative URLs start with // and use the current page's protocol.

    <!-- Current URL: https://example.com/page.html -->

<a href="//cdn.example.com/script.js">Script</a>
<!-- Resolves to: https://cdn.example.com/script.js -->

<!-- Current URL: http://example.com/page.html -->
<a href="//cdn.example.com/script.js">Script</a>
<!-- Resolves to: http://cdn.example.com/script.js -->

    Note: Protocol-relative URLs are deprecated because they don't work with file:// URLs and can cause security issues. Use explicit https:// instead.

    Absolute URLs (for Comparison)

    Absolute URLs include the full protocol and domain.

    <a href="https://example.com/about.html">About</a>

    Complete Comparison Table

    Current URL Relative URL Resolved URL
    https://example.com/blog/post.html about.html https://example.com/blog/about.html
    https://example.com/blog/post.html ../about.html https://example.com/about.html
    https://example.com/blog/post.html /about.html https://example.com/about.html
    https://example.com/blog/post.html images/logo.png https://example.com/blog/images/logo.png
    https://example.com/blog/post.html //cdn.com/x.js https://cdn.com/x.js
    https://example.com/blog/post.html https://other.com https://other.com

    Code Breakdown

    Part What It Does Why It Matters
    about.html Document-relative path. Resolves against the current directory.
    ../about.html Parent directory. Navigates up one level.
    /about.html Root-relative path. Resolves against the domain root.
    //cdn.com/x.js Protocol-relative URL. Uses the current protocol (deprecated).
    https://... Absolute URL. Full address; no resolution needed.

    4. Mental Model

    The "GPS Coordinates vs. Directions" Analogy

    Think of an absolute URL as GPS coordinates — they pinpoint an exact location on Earth, regardless of where you are. A relative URL is like directions — "go two blocks north, then turn left." The directions only make sense if you know your starting point (the base URL). But they're shorter, easier to give, and work from anywhere as long as you know where you are.

    The "Address Book" Analogy

    An absolute URL is a full mailing address — "123 Main Street, Anytown, USA." A relative URL is like saying "the house next door" or "two doors down" — it only makes sense relative to where you are. If you move to a new city, the full address changes, but "the house next door" still works.

    The "File System" Analogy

    If you're familiar with a file system, relative URLs work exactly like relative paths in a terminal:

    • cd .. goes to the parent directory.
    • cd images goes to the images subdirectory.
    • / is the root of the file system.

    Relative URLs use the same logic on the web.

    The "Treasure Map" Analogy

    An absolute URL is a treasure map with exact coordinates. A relative URL is a treasure map that says "from the old oak tree, walk 100 paces north." The latter is shorter, easier to remember, and works as long as you can find the oak tree (the base URL).

    5. Core Concepts

    Concept 1: The Base URL

    The base URL is the URL against which all relative URLs are resolved. By default, it is the URL of the current document. For example:

    • If the current URL is https://example.com/blog/post.html, the base URL is https://example.com/blog/post.html.
    • A relative URL about.html resolves to https://example.com/blog/about.html.

    Concept 2: The <base> Element

    The <base> element allows you to override the base URL for all relative URLs in the document:

    <head>
    <base href="https://example.com/">
</head>
<body>
    <a href="about.html">About</a>
    <!-- Resolves to: https://example.com/about.html -->
</body>

    Note: The <base> element affects all relative URLs in the document, including images, stylesheets, and scripts. Use it with caution — it can break existing links if not set correctly. There can be only one <base> element per document, and it must be in the <head>.

    You can also set the target attribute on <base> to specify the default target for all links:

    <base href="https://example.com/" target="_blank">

    Concept 3: The Document's Directory

    For document-relative URLs, the base is the directory containing the current document, not the document itself.

    • Current URL: https://example.com/blog/post.html
    • Document's directory: https://example.com/blog/
    • Relative URL about.html → https://example.com/blog/about.html

    Concept 4: Path Segments

    A URL path is made up of segments separated by /:

    https://example.com/blog/2026/09/post.html
                    └───┴────┴───┘
                     path segments

    Relative URLs navigate these segments:

    Relative URL Effect
    post.html Replace the last segment.
    ../ Remove the last segment.
    ../../ Remove the last two segments.
    images/ Add a segment.
    / Reset to the root.

    Concept 5: Trailing Slash

    A trailing slash matters:

    • https://example.com/blog – the resource is a file or directory named "blog".
    • https://example.com/blog/ – the resource is a directory; the browser will look for index.html inside it.

    Best practice: Use a trailing slash for directories to avoid an extra redirect.

    Concept 6: Query Strings and Fragments

    Relative URLs can include query strings and fragments:

    <a href="search.html?q=html">Search for HTML</a>
<a href="post.html#section-2">Jump to Section 2</a>
<a href="?page=2">Next Page</a>  <!-- Same page, new query -->
<a href="#top">Back to Top</a>   <!-- Same page, fragment -->

    Concept 7: Resolution Rules

    The browser uses the URL resolution algorithm (defined in the URL Living Standard) to resolve relative URLs. The algorithm:

    1. Parses the base URL into its components (scheme, host, path, query, fragment).
    2. Applies the relative URL's path to the base path.
    3. Handles . (current directory) and .. (parent directory) segments.
    4. Merges query strings and fragments if present.
    5. Produces the final absolute URL.

    Examples:

    Base URL Relative URL Resolved URL
    https://example.com/a/b/c.html d.html https://example.com/a/b/d.html
    https://example.com/a/b/c.html ../d.html https://example.com/a/d.html
    https://example.com/a/b/c.html ../../d.html https://example.com/d.html
    https://example.com/a/b/c.html /d.html https://example.com/d.html
    https://example.com/a/b/c.html ?q=1 https://example.com/a/b/c.html?q=1
    https://example.com/a/b/c.html #top https://example.com/a/b/c.html#top
    https://example.com/a/b/c.html //other.com/x https://other.com/x

    Concept 8: Document-Relative vs. Root-Relative

    Aspect Document-Relative Root-Relative
    Starts with A path segment (about.html) /
    Base Current document's directory Domain root
    Portability Works when moved with the document Works anywhere on the site
    Use case Links between related pages Site-wide resources (CSS, images)

    Best practice: Use root-relative URLs for site-wide resources (CSS, images, scripts) and document-relative URLs for links between related pages in the same directory.

    Concept 9: Environment Portability

    One of the biggest benefits of relative URLs is environment portability:

    • Development: http://localhost:3000/
    • Staging: https://staging.example.com/
    • Production: https://example.com/

    With relative URLs, the same HTML works in all environments. With absolute URLs, you'd need different code for each environment.

    Concept 10: SEO Considerations

    • Relative URLs are fine for SEO – search engines resolve them against the base URL.
    • Canonical URLs should be absolute – to avoid ambiguity.
    • Sitemaps should use absolute URLs – as required by the sitemap protocol.
    • Internal links – relative URLs are preferred for internal linking.
    • hreflang – should use absolute URLs.

    Concept 11: The <base> Element and JavaScript

    The <base> element affects:

    • HTML attributes – href, src, action, etc.
    • CSS url() – relative URLs in stylesheets (resolved against the stylesheet's URL, not the base).
    • JavaScript – the document.baseURI property returns the base URL.
    console.log(document.baseURI); // The base URL

    Concept 12: Security Considerations

    • Base URL injection – if an attacker can inject a <base> element, they can redirect all relative URLs on the page. This is rare but possible in some CMSs.
    • Protocol-relative URLs – deprecated for security reasons; use explicit https://.
    • Open redirects – relative URLs can be manipulated if the base URL is user-controlled.
    • XSS – never use user input directly in href or src without sanitization.

    6. How It Works

    Step-by-Step: Browser Resolving a Relative URL

    1.  Author writes a relative URL in an attribute.
    │   └── Example: <a href="../about.html">About</a>
    │
    ▼
2.  Browser determines the base URL:
    │   ├── If a <base> element is present, use its href.
    │   └── Otherwise, use the current document's URL.
    │
    ▼
3.  Browser parses the base URL into components:
    │   ├── Scheme: https
    │   ├── Host: example.com
    │   ├── Path: /blog/2026/post.html
    │   ├── Query: (none)
    │   └── Fragment: (none)
    │
    ▼
4.  Browser applies the relative URL to the base path:
    │   ├── Split the base path into segments: ["blog", "2026", "post.html"]
    │   ├── Process the relative URL:
    │   │   ├── ".." → remove the last segment: ["blog", "2026"]
    │   │   ├── "about.html" → replace the last segment: ["blog", "about.html"]
    │   │   └── Result: /blog/about.html
    │   └── If the relative URL starts with "/", reset to root.
    │
    ▼
5.  Browser assembles the resolved URL:
    │   └── https://example.com/blog/about.html
    │
    ▼
6.  Browser uses the resolved URL for navigation, resource loading, etc.

    The URL Resolution Algorithm (Simplified)

    Given a base URL B and a relative URL R:

    1. If R is absolute (has a scheme), return R.
    2. If R starts with //, use B's scheme and R's host and path.
    3. If R starts with /, use B's scheme and host, and R's path.
    4. If R is empty, return B without the fragment.
    5. If R starts with ?, use B's path and R's query.
    6. If R starts with #, use B's path and query, and R's fragment.
    7. Otherwise, merge R with B's path:
    8. Remove the last segment of B's path.
    9. Append R.
    10. Process . and .. segments.

    The URL API

    JavaScript provides the URL API for working with URLs:

    const base = new URL('https://example.com/blog/post.html');
const resolved = new URL('../about.html', base);
console.log(resolved.href); // "https://example.com/about.html"

    The second argument to the URL constructor is the base URL. This makes it easy to resolve relative URLs programmatically.

    The document.baseURI Property

    The document.baseURI property returns the base URL of the document:

    console.log(document.baseURI); // "https://example.com/blog/post.html"

    If a <base> element is present, document.baseURI returns its href.

    7. Internal Architecture / Under the Hood

    The URL Living Standard

    The URL specification (maintained by WHATWG) defines the algorithm for parsing and resolving URLs. It is implemented in the browser's URL parser (e.g., Chrome's url library, Firefox's nsStandardURL).

    The HTMLAnchorElement.href Property

    When you read the href property of an <a> element, the browser returns the resolved absolute URL, not the raw attribute value:

    const link = document.querySelector('a');
console.log(link.href);              // "https://example.com/blog/about.html" (resolved)
console.log(link.getAttribute('href')); // "../about.html" (raw)

    The <base> Element Implementation

    The browser processes the first <base> element in the <head> and stores its href as the document's base URL. This base URL is used for all subsequent URL resolutions. The <base> element also affects:

    • document.baseURI
    • The resolution of relative URLs in HTML attributes.
    • The default target for links (if target is set on <base>).

    CSS and Relative URLs

    In CSS, relative URLs (e.g., url(../images/bg.png)) are resolved against the stylesheet's URL, not the document's base URL. This is an important distinction:

    • HTML relative URLs → resolved against the document's base URL.
    • CSS relative URLs → resolved against the stylesheet's URL.

    JavaScript and the URL Constructor

    The URL constructor uses the same URL resolution algorithm as the browser:

    new URL('../about.html', 'https://example.com/blog/post.html');
// → URL { href: "https://example.com/about.html" }

    This is the recommended way to resolve relative URLs in JavaScript.

    SEO and Crawlers

    Search engines resolve relative URLs against the base URL (or the canonical URL if present). They prefer absolute URLs in some contexts (canonical, sitemaps, hreflang) to avoid ambiguity.

    8. Lifecycle / Workflow

    The Lifecycle of a Relative URL

    1.  Author writes a relative URL in an HTML attribute.
    │   └── Example: <img src="images/logo.png" alt="Logo">
    │
    ▼
2.  File is deployed.
    │
    ▼
3.  Browser parses the document and encounters the relative URL.
    │
    ▼
4.  Browser determines the base URL:
    │   ├── If a <base> element is present → use its href.
    │   └── Otherwise → use the current document's URL.
    │
    ▼
5.  Browser resolves the relative URL against the base URL.
    │   └── Example: https://example.com/images/logo.png
    │
    ▼
6.  Browser makes the request (or uses cache) for the resolved URL.
    │
    ▼
7.  The resource is loaded and rendered.
    │
    ▼
8.  If the page is moved to a new domain or subdirectory:
    │   └── The relative URL still works (as long as the structure is preserved).
    │
    ▼
9.  If the <base> element changes:
    │   └── All relative URLs on the page resolve against the new base.

    Dynamic Modification

    // Changing the base URL dynamically
const base = document.querySelector('base');
base.href = 'https://newdomain.com/';
// All relative URLs will now resolve against the new base.

    Note: Changing the <base> element dynamically affects all subsequent URL resolutions, but already-resolved resources are not re-fetched.

    const base = new URL('https://example.com/blog/post.html');

console.log(new URL('about.html', base).href);
// → "https://example.com/blog/about.html"

console.log(new URL('../about.html', base).href);
// → "https://example.com/about.html"

console.log(new URL('/contact.html', base).href);
// → "https://example.com/contact.html"

console.log(new URL('?q=1', base).href);
// → "https://example.com/blog/post.html?q=1"

console.log(new URL('#top', base).href);
// → "https://example.com/blog/post.html#top"

    Example 8: Portability Across Environments

    Development: http://localhost:3000/blog/post.html
    Staging: https://staging.example.com/blog/post.html
    Production: https://example.com/blog/post.html

    Same HTML: 

    <a href="../about.html">About</a>
<img src="/images/logo.png" alt="Logo">
<link rel="stylesheet" href="/styles/main.css">

    Resolved URLs:

    Environment ../about.html /images/logo.png
    Development http://localhost:3000/about.html http://localhost:3000/images/logo.png
    Staging https://staging.example.com/about.html https://staging.example.com/images/logo.png
    Production https://example.com/about.html https://example.com/images/logo.png

    Example 9: A Complete Page with Relative URLs

    <!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>My Blog</title>
    <link rel="stylesheet" href="/styles/main.css">
    <link rel="icon" href="/favicon.ico">
</head>
<body>
    <header>
        <a href="/">
            <img src="/images/logo.png" alt="My Blog">
        </a>
        <nav aria-label="Main navigation">
            <ul>
                <li><a href="/">Home</a></li>
                <li><a href="/about.html">About</a></li>
                <li><a href="/blog/">Blog</a></li>
                <li><a href="/contact.html">Contact</a></li>
            </ul>
        </nav>
    </header>

    <main>
        <article>
            <h1>Blog Post Title</h1>
            <img src="/images/post-image.jpg" alt="Post image">
            <p>Content...</p>
            <a href="/blog/post-2.html">Next Post →</a>
        </article>
    </main>

    <footer>
        <p>&copy; 2026 My Blog</p>
    </footer>

    <script src="/scripts/main.js" defer></script>
</body>
</html>

    Key observations: - Root-relative URLs (/styles/main.css, /images/logo.png) for site-wide resources. - Root-relative URLs for navigation (/, /about.html, /blog/). - Document-relative URLs for related content (post-2.html within /blog/).

    Example 10: The <base> Element in a SPA

    <!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>SPA</title>
    <base href="/app/">
    <link rel="stylesheet" href="styles.css">
    <!-- Resolves to: /app/styles.css -->
</head>
<body>
    <a href="dashboard">Dashboard</a>
    <!-- Resolves to: /app/dashboard -->
    <img src="logo.png" alt="Logo">
    <!-- Resolves to: /app/logo.png -->
    <script src="app.js" defer></script>
    <!-- Resolves to: /app/app.js -->
</body>
</html>

    Why: In a Single Page Application, the <base> element ensures that all relative URLs resolve from the app's root, regardless of the current route.

    10. Common Use Cases

    Use Case Recommended URL Type
    Site-wide resources (CSS, images, scripts) Root-relative (/styles/main.css)
    Navigation menus Root-relative (/about.html)
    Links within the same directory Document-relative (post-2.html)
    Links to parent directories Document-relative (../about.html)
    Links to subdirectories Document-relative (subdir/page.html)
    Single Page Applications Root-relative or <base> element
    Multi-environment deployments Root-relative or document-relative
    External links Absolute (https://example.com)
    Canonical URLs Absolute (https://example.com/page)
    Sitemaps Absolute (https://example.com/page)
    hreflang links Absolute
    Email and phone links mailto: and tel:

    11. Best Practices

    1. Use root-relative URLs for site-wide resources – CSS, images, scripts, favicons.

    2. Use document-relative URLs for related content – links between pages in the same directory.

    3. Avoid hardcoded absolute URLs for internal links – they break portability.

    4. Use absolute URLs for external links – to be explicit.

    5. Use absolute URLs for canonical, sitemaps, and hreflang – as required by specifications.

    6. Be consistent – choose a convention and stick to it.

    7. Avoid protocol-relative URLs – they're deprecated; use explicit https://.

    8. Use the <base> element with caution – it affects all relative URLs in the document.

    9. Test in different environments – ensure links work in development, staging, and production.

    10. Test with a subdirectory – ensure root-relative URLs work when the site is in a subdirectory.

    11. Use trailing slashes for directories – to avoid extra redirects.

    12. Keep the directory structure shallow – to simplify relative URLs.

    13. Use the URL API in JavaScript – for programmatic URL resolution.

    14. Validate your URLs – check for broken links with tools like linkchecker or Screaming Frog.

    15. Consider a build step – for hash-based asset filenames, use a build tool to rewrite URLs.

    16. Use a CDN for external resources – with absolute URLs.

    17. Document your URL conventions – in a style guide or README.

    18. Don't use file:// for development – use a local server to avoid relative URL issues.

    19. Test with a base element – if you use one, ensure all relative URLs still work.

    20. Monitor for 404 errors – relative URL mistakes often result in 404s.

    12. Common Mistakes

    ❌ Mistake: Using Absolute URLs for Internal Links

    <a href="https://example.com/about.html">About</a>
    Why it's wrong: Breaks portability. If you move the site to a new domain or subdirectory, the link breaks.

    ✅ Correct: 

    <a href="/about.html">About</a>  <!-- Root-relative -->
<!-- or -->
<a href="../about.html">About</a>  <!-- Document-relative -->

    ❌ Mistake: Forgetting the Leading Slash for Root-Relative

    <!-- Current URL: https://example.com/blog/post.html -->
<a href="about.html">About</a>
<!-- Resolves to: https://example.com/blog/about.html (wrong!) -->
    Why it's wrong: Without the leading slash, the URL is document-relative and resolves against the current directory, not the root.

    ✅ Correct: 

    <a href="/about.html">About</a>
<!-- Resolves to: https://example.com/about.html -->

    ❌ Mistake: Using Too Many ../

    <!-- Current URL: https://example.com/a/b/c/page.html -->
<a href="../../../d.html">D</a>
<!-- Resolves to: https://example.com/d.html -->
    Why it's wrong: Using many ../ is fragile. If the file is moved, the link breaks.

    ✅ Correct: Use root-relative URLs for site-wide navigation: 

    <a href="/d.html">D</a>

    ❌ Mistake: Forgetting the Trailing Slash for Directories

    <a href="/blog">Blog</a>
    Why it's wrong: The server may treat /blog as a file, causing a redirect to /blog/. The redirect adds latency.

    ✅ Correct: 

    <a href="/blog/">Blog</a>

    ❌ Mistake: Using Protocol-Relative URLs

    <script src="//cdn.example.com/script.js"></script>
    Why it's wrong: Protocol-relative URLs are deprecated and don't work with file:// URLs. They can also cause security issues.

    ✅ Correct: 

    <script src="https://cdn.example.com/script.js"></script>

    ❌ Mistake: Using <base> Without Understanding Its Effects

    <head>
    <base href="https://example.com/app/">
</head>
<body>
    <a href="about.html">About</a>
    <!-- Resolves to: https://example.com/app/about.html -->
    <img src="logo.png" alt="Logo">
    <!-- Resolves to: https://example.com/app/logo.png -->
</body>
    Why it's wrong: The <base> element affects all relative URLs, including images, scripts, and stylesheets. If you're not expecting this, it can break your page.

    ✅ Correct: Use <base> only when you understand its effects and have a clear need (e.g., SPAs).

    ❌ Mistake: Hardcoding Environment-Specific URLs

    <link rel="stylesheet" href="http://localhost:3000/styles/main.css">
    Why it's wrong: Breaks in production.

    ✅ Correct: 

    <link rel="stylesheet" href="/styles/main.css">

    ❌ Mistake: Using Relative URLs for External Resources

    <link rel="stylesheet" href="https://fonts.googleapis.com/css?family=Roboto">
    Why it's wrong: Not a mistake — external resources must use absolute URLs. But if you accidentally use a relative URL for an external resource, it will resolve against your domain.

    ✅ Correct: External resources should always use absolute URLs.

    ❌ Mistake: Not Testing in a Subdirectory

    <!-- Site is at https://example.com/v2/ -->
<a href="/about.html">About</a>
<!-- Resolves to: https://example.com/about.html (wrong! should be /v2/about.html) -->
    Why it's wrong: Root-relative URLs resolve against the domain root, not the subdirectory. If the site is in a subdirectory, root-relative URLs will point to the wrong location.

    ✅ Correct: Use document-relative URLs or configure the server appropriately.

    ❌ Mistake: Forgetting to Update Links After Moving Files

    <!-- File moved from /blog/post.html to /blog/2026/post.html -->
<a href="post-2.html">Next</a>
<!-- Now resolves to /blog/2026/post-2.html instead of /blog/post-2.html -->
    Why it's wrong: Document-relative URLs break when files are moved.

    ✅ Correct: Use root-relative URLs for stability, or update links after moving files.

    13. Performance Considerations

    • Shorter URLs – relative URLs are shorter, reducing HTML size and bandwidth.
    • Caching – relative URLs don't affect caching; the resolved absolute URL is what's cached.
    • Redirects – missing trailing slashes can cause redirects, adding latency. Use correct URLs.
    • CDN – for external resources, use absolute URLs to the CDN.
    • Preload/prefetch – use resolved absolute URLs for preload/prefetch hints.
    • DNS prefetch – use absolute URLs for external domains.
    • HTTP/2 – relative URLs don't affect HTTP/2 multiplexing.
    • Build tools – can rewrite relative URLs for asset hashing and CDN distribution.

    Performance Tips

    1. Use root-relative URLs for assets – ensures consistent resolution.
    2. Include trailing slashes – avoids redirects.
    3. Use a CDN – with absolute URLs for static assets.
    4. Preload critical resources – with resolved absolute URLs.
    5. Minify HTML – removes whitespace, reducing size.

    14. Security Considerations

    • Base URL injection – if an attacker can inject a <base> element, they can redirect all relative URLs. Sanitize user input in the <head>.
    • Protocol-relative URLs – deprecated; can cause mixed content issues. Use https:// explicitly.
    • Open redirects – relative URLs can be manipulated if the base URL is user-controlled. Validate redirects.
    • XSS – never use user input in href or src without sanitization.
    • Path traversal – ../ can be used to navigate outside the intended directory. Validate paths on the server.
    • HTTPS – always use HTTPS for external resources.

    Security Best Practices

    1. Sanitize user input – especially in <base>, href, and src.
    2. Use explicit https:// – avoid protocol-relative URLs.
    3. Validate redirects – don't allow arbitrary URLs.
    4. Set Content-Security-Policy – to restrict resource loading.
    5. Use rel="noopener noreferrer" – for external links.
    6. Avoid javascript: URLs – in href.
    7. Monitor for mixed content – ensure all resources are HTTPS.

    15. Debugging Tips

    • DevTools Elements panel – inspect an element to see the raw href/src attribute.
    • DevTools Console – use element.href to see the resolved URL.
    • element.getAttribute('href') – returns the raw attribute value.
    • new URL(relative, base) – resolve URLs programmatically.
    • Network panel – see the actual URLs requested by the browser.
    • Broken link checkers – use tools like linkchecker, Screaming Frog, or W3C Link Checker.
    • Lighthouse – audits for broken links and SEO issues.
    • document.baseURI – check the document's base URL.
    • Server logs – look for 404 errors caused by broken relative URLs.
    • Test in multiple environments – development, staging, production.
    • Test in a subdirectory – ensure root-relative URLs work correctly.

    16. When to Use

    • For internal links – navigation, related content, resources.
    • For site-wide assets – CSS, images, scripts (root-relative).
    • For links between related pages – document-relative.
    • For multi-environment deployments – for portability.
    • For SPAs – with the <base> element.
    • For any URL where the full absolute URL isn't necessary.

    17. When Not to Use

    • For external links – use absolute URLs.
    • For canonical URLs – use absolute URLs.
    • For sitemaps – use absolute URLs.
    • For hreflang links – use absolute URLs.
    • For Open Graph images – use absolute URLs.
    • For email links – use mailto:.
    • For phone links – use tel:.
    • For javascript: URLs – never use.
    • For data: URLs – these are self-contained and don't need resolution.

    • Base URL – the URL against which relative URLs are resolved.
    • <base> element – overrides the base URL.
    • document.baseURI – the document's base URL.

    19. Did You Know?

    • The first URL specification (RFC 1630) was published in 1994 by Tim Berners-Lee and others. It defined the concept of relative URLs.

    • Relative URLs are resolved by the browser, not the server. The server only sees the resolved absolute URL in the HTTP request.

    • The <base> element can have a target attribute that sets the default target for all links on the page: 

      <base href="/app/" target="_blank">

    • Only one <base> element is allowed per document, and it must be in the <head>.

    • In CSS, relative URLs are resolved against the stylesheet's URL, not the document's base URL. This is a common source of confusion.

    • The URL API in JavaScript uses the same resolution algorithm as the browser, making it the recommended way to resolve URLs programmatically.

    • Protocol-relative URLs (//example.com) were popular in the early 2010s but are now deprecated because they don't work with file:// URLs and can cause mixed content issues.

    • Root-relative URLs resolve against the domain root, not the current directory. This makes them stable regardless of the current page's location.

    • Document-relative URLs resolve against the current document's directory. They are portable when the site is moved as a whole, but break if files are moved individually.

    • The trailing slash in a URL matters. /blog and /blog/ can resolve to different resources.

    • Path traversal (../) can be used to navigate up the directory tree. Browsers limit how far up you can go (you can't go above the root).

    • Query strings (?key=value) are preserved when resolving relative URLs, unless the relative URL includes its own query string.

    • Fragments (#id) are preserved when resolving relative URLs, unless the relative URL includes its own fragment.

    • <base> injection is a known attack vector. If an attacker can inject a <base> element into a page, they can redirect all relative URLs to a malicious domain.

    • Search engines resolve relative URLs against the base URL (or canonical URL) when crawling.

    • Sitemaps must use absolute URLs, as required by the sitemap protocol.

    • Canonical URLs should be absolute to avoid ambiguity.

    • hreflang links should use absolute URLs for language targeting.

    • Open Graph images should use absolute URLs, as social media platforms may not resolve relative URLs correctly.

    • Build tools like Webpack, Vite, and Parcel can rewrite relative URLs for asset hashing and CDN distribution.

    • The document.baseURI property returns the base URL of the document, which is useful for resolving relative URLs in JavaScript.

    • Relative URLs are essential for portability — they allow the same code to work in development, staging, and production environments.

    • Best practice: use root-relative URLs for site-wide resources and document-relative URLs for related content.

    20. Summary

    • A relative URL specifies the location of a resource relative to the current document's URL (or a base URL).
    • There are three types: document-relative (about.html), root-relative (/about.html), and protocol-relative (//example.com — deprecated).
    • Relative URLs are resolved against a base URL, which is the current document's URL unless a <base> element is present.
    • Document-relative URLs resolve against the current directory and can navigate up with ../.
    • Root-relative URLs resolve against the domain root and are stable regardless of the current page.
    • Best practices: use root-relative URLs for site-wide resources, document-relative URLs for related content, avoid protocol-relative URLs, and use absolute URLs for external resources, canonical, sitemaps, and hreflang.
    • Common mistakes include using absolute URLs for internal links, forgetting the leading slash for root-relative URLs, using too many ../, and using <base> without understanding its effects.
    • Relative URLs are essential for portability, maintainability, and environment flexibility.
    • They are a fundamental part of how the web works and are supported by all browsers and tools.
