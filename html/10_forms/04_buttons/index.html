    Chapter: Buttons

    1. Overview

    Definition

    A button is an interactive HTML element that users click, tap, or activate via keyboard to trigger an action. HTML provides two ways to create buttons:

    • <button> element — a container element that can hold text, icons, and other inline content. It is the preferred way to create buttons in modern HTML.
    • <input> element with type="submit", type="reset", or type="button" — a void element whose label is set via the value attribute.

    Buttons are the primary mechanism for submitting forms, resetting forms, and triggering JavaScript actions. They are among the most interactive elements on the web.

    Example: 

    <!-- Preferred: <button> element -->
<button type="submit">Submit</button>

<!-- Alternative: <input> element -->
<input type="submit" value="Submit">

    Purpose

    Buttons serve several essential purposes:

    • Form submission – submit form data to a server.
    • Form reset – clear form fields to their default values.
    • Generic actions – trigger JavaScript (open a dialog, toggle a menu, etc.).
    • Navigation-like actions – though links (<a>) are preferred for navigation.
    • Accessibility – native buttons are keyboard-accessible and screen-reader-friendly.
    • Consistency – browsers provide default button styling and behavior.
    • Progressive enhancement – submit buttons work even without JavaScript.

    Where It Fits

    Buttons are interactive content and phrasing content (for <button>) or flow content (depending on context). They can appear anywhere interactive content is accepted — inside <form>, <div>, <p>, <li>, <td>, and more.

    <form action="/submit" method="POST">
    <label for="name">Name:</label>
    <input type="text" id="name" name="name">

    <button type="submit">Save</button>
    <button type="reset">Clear</button>
</form>

    2. Why It Exists

    The Problem

    Before buttons, form submission relied on <input type="submit"> — a specialized input whose label was set via the value attribute. This worked, but had several limitations:

    • No rich content – the label was plain text only; no icons, no HTML.
    • Styling limitations – <input> elements are harder to style consistently.
    • value attribute collision – the value attribute served double duty as both the label and the submitted value.
    • No type="button" alternative – generic buttons were also <input> elements with the same limitations.

    Developers wanted buttons that could contain icons, spans, and other markup; that were easier to style; and that had a cleaner separation between label and value.

    Previous Limitations

    Limitation Consequence
    <input type="submit"> only No rich content in buttons.
    value as label Label and submitted value were coupled.
    Harder to style Inconsistent styling across browsers.
    No generic button <input type="button"> was limited.
    Accessibility issues Some custom buttons were not keyboard-accessible.

    Why the <button> Element Was Introduced

    The <button> element was introduced in HTML 4.0 (1997) to provide a richer, more flexible alternative to <input type="submit">. It enables:

    • Rich content – text, icons, spans, images.
    • Clear separation – label is the content; submitted value is the value attribute.
    • Easier styling – <button> is a container, easier to style consistently.
    • Three types – submit, reset, button.
    • Accessibility – native keyboard support and screen reader announcements.

    The <button> element is now the preferred way to create buttons in HTML.

    4. Mental Model

    The "Button" Analogy

    Think of a <button> as a physical button on a machine. Pressing it triggers an action — starting, stopping, resetting, saving. The label on the button tells you what it does. A disabled button is like a button that's been locked — it looks like a button but doesn't respond.

    The "Sign vs. Action" Analogy

    A link (<a>) is a sign pointing to another location. A button is an action you perform. Links navigate; buttons act. This distinction is important for both semantics and accessibility.

    The "Three Types" Mental Model

    • submit — sends the form.
    • reset — clears the form.
    • button — does nothing on its own; needs JavaScript.

    The "Native vs. Custom" Mental Model

    Before <button>, buttons were built from <div>s with JavaScript. These custom buttons were often inaccessible (no keyboard support, no screen reader role). Native <button> elements are keyboard-accessible by default, have the correct role, and are announced correctly.

    The "Label vs. Value" Mental Model

    For <button>:

    • Label = the button's content (text, icon).
    • Value = the value attribute (submitted with the form).

    For <input type="submit">:

    • Label = the value attribute.
    • Value = also the value attribute (for submit, nothing is submitted unless name is set).

    The <button> element separates these concerns cleanly.

    5. Core Concepts

    Concept 1: The Three Button Types

    Type Purpose Default Action
    submit Submits the form Form submission
    reset Resets the form Form reset
    button Generic None (JavaScript needed)

    Important: Inside a <form>, a <button> without a type defaults to type="submit". Outside a form, it defaults to type="button".

    <!-- Inside a form: defaults to submit -->
<form>
    <button>Click</button>  <!-- Submits the form! -->
</form>

    Best practice: Always specify type explicitly.

    Concept 2: <button> vs <input type="submit">

    Aspect <button> <input type="submit">
    Content Rich (text, icons, HTML) Plain text only
    Label Content value attribute
    Submitted value value attribute value attribute
    Styling Easier Harder
    Default type submit (in form) submit
    Self-closing No (has closing tag) Yes (void)
    Pseudo-elements ::before, ::after work ::before, ::after limited

    Rule: Prefer <button> for new code.

    Concept 3: The type Attribute

    Always specify type. Without it, the browser default may surprise you.

    <!-- Bad: defaults to submit inside a form -->
<button>Click</button>

<!-- Good: explicit type -->
<button type="button">Click</button>

    Concept 4: The value Attribute

    For <button>, the value attribute is submitted with the form when the button is clicked. Combined with name, it lets the server know which button was clicked.

    <button type="submit" name="action" value="save">Save</button>
<button type="submit" name="action" value="delete">Delete</button>

    Server receives action=save or action=delete.

    Concept 5: The disabled Attribute

    A disabled button:

    • Is not clickable.
    • Is not focusable.
    • Is not submitted with the form.
    • Is announced as "dimmed" or "unavailable" by screen readers.
    <button type="submit" disabled>Submit</button>

    Note: Don't use disabled for form validation — it prevents the user from fixing the error. Instead, use aria-disabled="true" and validate on submit.

    Concept 6: The form Attribute

    A button outside a <form> can be associated with it using the form attribute:

    <form id="myForm">
    <input type="text" name="name">
</form>

<button type="submit" form="myForm">Submit</button>

    Concept 7: Override Attributes

    Buttons inside a form can override the form's attributes:

    Button Attribute Overrides
    formaction action
    formmethod method
    formenctype enctype
    formnovalidate Validation
    formtarget target 
    <form action="/save" method="POST">
    <button type="submit">Save</button>
    <button type="submit" formaction="/publish">Publish</button>
</form>

    Concept 8: Keyboard Accessibility

    Native buttons are keyboard-accessible:

    • Tab – moves focus to the button.
    • Enter – activates the button.
    • Space – activates the button.

    Important: Enter and Space both work for native buttons. Custom buttons built with <div> often only support Enter.

    Concept 9: Screen Reader Announcements

    Screen readers announce buttons as:

    • "Submit, button" (for <button>Submit</button>).
    • "Save, button" (for <button>Save</button>).

    Disabled buttons are announced as "dimmed" or "unavailable".

    Concept 10: Buttons vs. Links

    Aspect <button> <a>
    Purpose Action Navigation
    Role button link
    Keyboard Enter + Space Enter
    Right-click Context menu (limited) Open in new tab, copy link
    href No Yes
    Use case Submit, toggle, open Navigate

    Rule: Use <a> for navigation; use <button> for actions.

    Concept 11: Styling Buttons

    Buttons can be styled with CSS:

    button {
    padding: 0.5rem 1rem;
    background: #3498db;
    color: white;
    border: none;
    border-radius: 4px;
    cursor: pointer;
    font-size: 1rem;
}

button:hover {
    background: #2980b9;
}

button:focus {
    outline: 2px solid #2c3e50;
    outline-offset: 2px;
}

button:disabled {
    background: #bdc3c7;
    cursor: not-allowed;
}

    Concept 12: Button Icons

    Icons can be added as SVG or images:

    <button type="submit">
    <svg aria-hidden="true" width="16" height="16"><!-- icon --></svg>
    Save
</button>

    Accessibility tip: Mark icons as aria-hidden="true" and provide visible text.

    Concept 13: Icon-Only Buttons

    Icon-only buttons need an accessible name:

    <button type="button" aria-label="Close">✕</button>

    Without aria-label, the button's accessible name is just "✕" (or nothing), which is unclear.

    Concept 14: Toggle Buttons

    Toggle buttons use aria-pressed to indicate state:

    <button type="button" aria-pressed="false" id="toggleBtn">Bold</button>

<script>
    const btn = document.getElementById('toggleBtn');
    btn.addEventListener('click', () => {
        const pressed = btn.getAttribute('aria-pressed') === 'true';
        btn.setAttribute('aria-pressed', !pressed);
    });
</script>

    Concept 15: Buttons and Progressive Enhancement

    A submit button works even without JavaScript — it submits the form natively. A <button type="button"> requires JavaScript to do anything.

    Best practice: Use <button type="submit"> for form submission; enhance with JavaScript only when needed.

    Concept 16: The popovertarget Attribute (Modern)

    Buttons can control popovers natively:

    <button popovertarget="myPopover">Open Menu</button>
<div id="myPopover" popover>Menu content</div>

    Concept 17: The commandfor Attribute (Newer)

    Modern browsers support declarative commands:

    <button commandfor="myDialog" command="show-modal">Open Dialog</button>
<dialog id="myDialog">...</dialog>

    Note: Browser support varies; check compatibility.

    Concept 18: Accessibility — The First Rule of ARIA

    If a <button> element fits, use it — don't use <div role="button">.

    <!-- Bad -->
<div role="button" tabindex="0" onclick="doSomething()">Click</div>

<!-- Good -->
<button type="button" onclick="doSomething()">Click</button>

    Concept 19: Buttons in Forms

    • A form can have multiple submit buttons with different name/value pairs.
    • A form can have multiple reset buttons (rare).
    • A form can have generic buttons that trigger JavaScript.
    • A form's first submit button is the default when pressing Enter.
    <form>
    <input type="text" name="q">
    <button type="submit" name="action" value="search">Search</button>
    <button type="submit" name="action" value="lucky">I'm Feeling Lucky</button>
</form>

    Concept 20: The autofocus Attribute

    A button can autofocus on page load:

    <button type="submit" autofocus>Submit</button>

    Note: Use sparingly — autofocus can be disorienting.

    Concept 21: Button Reset Behavior

    A <button type="reset"> resets all controls in the form to their default values (specified via value, checked, selected attributes).

    <form>
    <input type="text" name="name" value="Default">
    <input type="checkbox" name="agree" checked>
    <button type="reset">Reset</button>
</form>

    Concept 22: Accessibility and Focus

    • Buttons are focusable by default.
    • The focus indicator should be visible.
    • Don't remove the focus outline without providing an alternative.
    • Custom buttons must be focusable (tabindex="0").

    Concept 23: Button Role

    The <button> element has an implicit button role. The accessible name comes from:

    1. aria-labelledby
    2. aria-label
    3. The button's content (text)
    4. title (fallback)

    Concept 24: Button State

    Buttons have states:

    • Default – normal.
    • Hover – mouse over.
    • Focus – keyboard-focused.
    • Active – being pressed.
    • Disabled – not interactive.

    CSS pseudo-classes:

    • :hover
    • :focus
    • :focus-visible
    • :active
    • :disabled

    Concept 25: Buttons and Touch

    On touch devices, buttons should be at least 44×44 CSS pixels for accessibility (WCAG 2.5.5).

    button {
    min-width: 44px;
    min-height: 44px;
    padding: 0.5rem 1rem;
}

    6. How It Works

    Step-by-Step: Browser Processing a Button

    1.  The tokenizer encounters a `<button>` tag.
    │
    ▼
2.  It creates a DOM node for the button.
    │
    ▼
3.  It reads the `type` attribute (default: "submit" inside a form).
    │
    ▼
4.  It processes the button's content (text, icons, etc.).
    │
    ▼
5.  When the closing tag is encountered, the button is closed.
    │
    ▼
6.  The accessibility tree node is created:
    │   └── role: button, name: button text.
    │
    ▼
7.  Default styles are applied.
    │
    ▼
8.  The page is rendered.
    │
    ▼
9.  User clicks or presses Enter/Space:
    │   ├── submit → form submission
    │   ├── reset → form reset
    │   └── button → click event only

    Button Activation

    • Mouse: click.
    • Keyboard: Enter or Space when focused.
    • Screen reader: virtual cursor + Enter/Space.
    • Touch: tap.

    Form Submission Flow

    1.  User clicks a submit button.
    │
    ▼
2.  Browser checks validation:
    │   ├── Invalid → show errors, prevent submission.
    │   └── Valid → proceed.
    │
    ▼
3.  Browser collects form data.
    │
    ▼
4.  Browser submits to the action URL using method.
    │
    ▼
5.  Server responds.

    The click Event

    All buttons fire a click event:

    button.addEventListener('click', (e) => {
    console.log('Button clicked');
});

    For submit buttons, the click event fires before the submit event.

    The submit Event

    The form's submit event fires when a submit button is clicked:

    form.addEventListener('submit', (e) => {
    e.preventDefault(); // Prevent default submission
    // Custom submission logic
});

    Accessibility Tree

    In the accessibility tree:

    • <button> → role: button.
    • <input type="submit"> → role: button.
    • The accessible name is the button's text or value.
    • State includes disabled if present.

    Default User Agent Styles

    button {
    display: inline-block;
    padding: 1px 6px;
    border: 2px outset buttonborder;
    background-color: buttonface;
    color: buttontext;
    cursor: default;
    font-family: inherit;
    font-size: inherit;
}

button:disabled {
    color: graytext;
}

    Browsers apply OS-specific styling. Override with CSS for consistency.

    7. Internal Architecture / Under the Hood

    The HTMLButtonElement Interface

    In the DOM, <button> is represented by HTMLButtonElement:

    Property Description
    type Button type: submit, reset, button
    value Submitted value
    name Field name
    disabled Whether disabled
    form The associated form
    formAction Override for action
    formMethod Override for method
    formEnctype Override for enctype
    formNoValidate Override for novalidate
    formTarget Override for target
    labels Associated labels
    validity Validity state
    willValidate Whether validated
    checkValidity() Returns validity
    setCustomValidity() Sets custom error 
    const btn = document.querySelector('button');
console.log(btn.type);     // "submit"
console.log(btn.value);    // ""
console.log(btn.disabled); // false

    The HTMLInputElement Interface (for <input type="submit">)

    Similar properties, but with value serving double duty as the label.

    The Button Role

    The <button> element has an implicit button role in the accessibility tree. This is why you don't need to add role="button".

    Accessibility Mapping

    Element Role Accessible Name
    <button>Save</button> button "Save"
    <button aria-label="Close">✕</button> button "Close"
    <input type="submit" value="Save"> button "Save"
    <button disabled>Save</button> button (disabled) "Save" (dimmed)

    Default User Agent Styles

    Browsers apply OS-specific button styling. This is why buttons look different on macOS, Windows, and Linux.

    To make buttons consistent, reset their styles:

    button {
    all: unset;
    /* Then apply your own styles */
    padding: 0.5rem 1rem;
    background: #3498db;
    color: white;
    border-radius: 4px;
    cursor: pointer;
}

    Caution: all: unset also removes the focus indicator and other important defaults. Use with care.

    The click Event

    All buttons fire a click event. Submit and reset buttons also trigger their default actions after the click event, unless prevented.

    The disabled Property

    A disabled button:

    • Has disabled attribute.
    • Does not fire click events.
    • Is skipped in tab order.
    • Is announced as unavailable by screen readers.
    • Is not submitted with the form.

    11. Best Practices

    1. Use <button> over <input type="submit"> – richer content, easier styling.

    2. Always specify type – avoid accidental submissions.

    3. Use type="button" for non-submit actions – inside a form, the default is submit.

    4. Use <a> for navigation – buttons are for actions.

    5. Provide accessible names – text or aria-label for icon buttons.

    6. Don't disable submit buttons for validation – let users fix errors.

    7. Use aria-pressed for toggle buttons – indicates state.

    8. Use aria-expanded for expand/collapse buttons – indicates state.

    9. Use name and value for multiple submit buttons – to distinguish them.

    10. Use formnovalidate for draft saves – skip validation when needed.

    11. Ensure touch targets are at least 44×44px.

    12. Provide visible focus indicators – don't remove outlines.

    13. Test keyboard navigation – Tab, Enter, Space.

    14. Test with screen readers – ensure the button is announced.

    15. Style buttons consistently – reset browser defaults.

    16. Use cursor: pointer – to indicate interactivity.

    17. Provide loading states – disable and show a spinner.

    18. Avoid autofocus – unless truly needed.

    19. Group related buttons – with role="group" or role="toolbar".

    20. Document button conventions – in a style guide.

    12. Common Mistakes

    ❌ Mistake: Using <div> as a Button

    <div class="button" onclick="submit()">Submit</div>

    Why it's wrong: No keyboard support, no role, no accessibility.

    ✅ Correct: 

    <button type="submit">Submit</button>

    ❌ Mistake: Forgetting type

    <form>
    <button>Click</button>  <!-- Submits the form! -->
</form>

    Why it's wrong: Inside a form, <button> defaults to type="submit".

    ✅ Correct: 

    <form>
    <button type="button">Click</button>
</form>

    ❌ Mistake: Using <a> for Actions

    <a href="#" onclick="doSomething()">Click</a>

    Why it's wrong: <a> is for navigation; the # also jumps to the top.

    ✅ Correct: 

    <button type="button" onclick="doSomething()">Click</button>

    ❌ Mistake: Icon-Only Button Without aria-label

    <button type="button">✕</button>

    Why it's wrong: Screen reader announces "✕" or nothing.

    ✅ Correct: 

    <button type="button" aria-label="Close">✕</button>

    ❌ Mistake: Disabling Submit for Validation

    <button type="submit" disabled>Submit</button>

    Why it's wrong: Users can't submit even after fixing errors.

    ✅ Correct: Validate on submit, show errors, and let users fix them.

    ❌ Mistake: Removing Focus Outline

    button:focus {
    outline: none;
}

    Why it's wrong: Keyboard users can't see which button is focused.

    ✅ Correct: 

    button:focus-visible {
    outline: 2px solid #2c3e50;
    outline-offset: 2px;
}

    ❌ Mistake: Multiple Submit Buttons Without name/value

    <button type="submit">Save</button>
<button type="submit">Delete</button>

    Why it's wrong: The server can't tell which button was clicked.

    ✅ Correct: 

    <button type="submit" name="action" value="save">Save</button>
<button type="submit" name="action" value="delete">Delete</button>

    ❌ Mistake: Using disabled for Loading Without Announcing

    <button type="submit" disabled>Loading...</button>

    Why it's wrong: Screen readers don't know why the button is disabled.

    ✅ Correct: 

    <button type="submit" aria-disabled="true" aria-busy="true">
    <span aria-hidden="true">⏳</span>
    <span class="sr-only">Loading</span>
</button>

    ❌ Mistake: Button Without Accessible Name

    <button type="button"></button>

    Why it's wrong: No accessible name; screen readers announce "button".

    ✅ Correct: 

    <button type="button" aria-label="Close">✕</button>

    ❌ Mistake: Using role="button" on <button>

    <button role="button">Submit</button>

    Why it's wrong: Redundant — <button> already has the button role.

    ✅ Correct: 

    <button>Submit</button>

    ❌ Mistake: Button Inside a Link

    <a href="/page">
    <button>Click</button>
</a>

    Why it's wrong: Interactive content inside a link is invalid.

    ✅ Correct: Use either a link or a button, not both.

    ❌ Mistake: type="button" Outside a Form for Submission

    <button type="button" onclick="document.forms[0].submit()">Submit</button>

    Why it's wrong: Unnecessary JavaScript — use type="submit".

    ✅ Correct: 

    <button type="submit">Submit</button>

    13. Performance Considerations

    • Buttons are lightweight – one DOM node each.
    • Native buttons – faster than custom <div> buttons.
    • No performance cost for disabled state.
    • Event listeners – one per button is fine; event delegation for many.
    • Loading states – disable the button on submit to prevent double submission.
    • pointer-events: none – can be used to disable clicks during loading.

    Performance Tips

    1. Use event delegation – one listener on a parent for many buttons.
    2. Debounce rapid clicks – prevent double submission.
    3. Disable buttons during async operations.
    4. Minimize inline styles – use CSS classes.
    5. Use CSS for hover/focus states – no JavaScript needed.
    6. Minify HTML/CSS – reduce file size.

    14. Security Considerations

    • CSRF protection – use tokens for form submissions.
    • Double submission – disable the button during submission.
    • XSS – never insert user input into button text or attributes without escaping.
    • innerHTML – avoid using innerHTML with user input.
    • Rate limiting – prevent brute force attacks.
    • HTTPS – mandatory for sensitive form submissions.
    • Server‑side validation – always validate on the server, even if the button is disabled client‑side.
    • formaction override – validate on the server; don't trust the client.

    Security Best Practices

    1. Use HTTPS – for all form submissions.
    2. CSRF tokens – include in all state-changing forms.
    3. Server-side validation – never trust client input.
    4. Disable buttons during submission – prevent double submission.
    5. Sanitize user input – before displaying in button text.
    6. Use CSP – to restrict inline scripts and styles.
    7. Rate limiting – for sensitive actions.

    15. Debugging Tips

    • DevTools Elements panel – inspect the button.
    • Computed styles – check the applied styles.

    16. When to Use

    • For form submission – type="submit".
    • For form reset – type="reset".
    • For actions – type="button".
    • For dialogs – open/close.
    • For toggles – with aria-pressed.
    • For expand/collapse – with aria-expanded.
    • For icon actions – with aria-label.
    • For loading states – disable + spinner.
    • For confirmations – type="button" + confirm().

    17. When Not to Use

    • For navigation – use <a>.
    • For links – use <a>.
    • For non-interactive content – use <span> or <div>.
    • As a wrapper for other interactive content – invalid nesting.
    • Without an accessible name – always provide one.
    • Without a type – always specify.

    19. Did You Know?

    • The <button> element was introduced in HTML 4.0 (1997) as a richer alternative to <input type="submit">.

    • Inside a <form>, a <button> without a type defaults to type="submit".

    • Outside a form, a <button> without a type defaults to type="button" (in most browsers).

    • <button> can contain rich content — icons, spans, images — while <input type="submit"> cannot.

    • Keyboard activation: <button> responds to both Enter and Space. <a> responds only to Enter.

    • aria-pressed makes a button a toggle button — it indicates an on/off state.

    • aria-expanded indicates whether a controlled element is expanded or collapsed.

    • Icon-only buttons need an aria-label to be accessible.

    • formnovalidate on a submit button skips client-side validation for that submission.

    • formaction overrides the form's action for a specific button.

    • Multiple submit buttons with different name/value let the server know which was clicked.

    • Disabled buttons are not focusable and not submitted.

    • role="button" is unnecessary on <button> — it already has the role.

    • <div role="button"> requires tabindex="0" and keyboard event handlers.

    • The First Rule of ARIA: use native <button> instead of <div role="button">.

    • Touch target size: WCAG 2.5.5 requires at least 44×44 CSS pixels.

    • Focus indicators are essential for keyboard users. Don't remove them.

    • cursor: pointer is not the default for buttons in all browsers — add it.

    • Buttons can have autofocus — but use sparingly.

    • popovertarget allows a button to control a popover natively (modern browsers).

    • commandfor and command allow declarative commands (newer feature).

    • Loading states should disable the button and announce "busy" to screen readers.

    • Double submission can be prevented by disabling the button during async operations.

    • CSRF tokens are essential for state-changing form submissions.

    • <button> in a link is invalid — do not nest interactive elements.

    • <a> styled as a button is fine for navigation — it's semantically correct.

    • Best practices include always specifying type, providing accessible names, and testing with screen readers.

    • Common mistakes include forgetting type, using <div> as a button, and removing focus outlines.

    • Following best practices for buttons leads to more accessible, maintainable, and usable forms.

    20. Summary

    • A button is an interactive element that triggers an action when clicked, tapped, or activated via keyboard.
    • HTML provides two ways to create buttons: <button> (preferred) and <input type="submit/reset/button">.
    • The type attribute determines the button's behavior: submit, reset, or button.
    • Always specify type — inside a form, the default is submit.
    • Use <button> for rich content and easier styling.
    • Use <a> for navigation; use <button> for actions.
    • Icon-only buttons need an aria-label.
    • Toggle buttons use aria-pressed.
    • Expand/collapse buttons use aria-expanded.
    • Multiple submit buttons use name and value to distinguish them.
    • Override attributes (formaction, formmethod, etc.) allow per-button behavior.
    • Disabled buttons are not focusable and not submitted — use sparingly for validation.
    • Best practices: always specify type, provide accessible names, ensure touch targets are 44×44px, provide focus indicators, and test with screen readers.
    • Common mistakes include using <div> as a button, forgetting type, and removing focus outlines.
    • Buttons are essential for form submission, form reset, dialog control, toggles, and JavaScript-driven actions.
    • They are one of the most important interactive elements on the web.
