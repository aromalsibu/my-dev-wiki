    Chapter: Validation

    1. Overview

    Definition

    Form validation is the process of checking whether the data a user has entered into a form meets the expected requirements before it is accepted or submitted. HTML provides a native, declarative validation system — often called constraint validation — that allows developers to specify rules using attributes on form controls, without writing any JavaScript. When a form is submitted, the browser automatically checks all constraints and, if any fail, prevents submission and displays an error message.

    The native validation system is complemented by:

    • JavaScript validation – for custom rules and better UX.
    • Server-side validation – the only truly reliable validation (must always be present).
    • ARIA – to announce errors to assistive technologies.

    Example: 

    <form action="/submit" method="POST">
    <label for="email">Email:</label>
    <input type="email" id="email" name="email" required>
    <button type="submit">Submit</button>
</form>

    If the user enters an invalid email or leaves the field empty, the browser shows an error and blocks submission.

    Purpose

    Form validation serves several essential purposes:

    • Data quality – ensures data is correct, complete, and in the expected format.
    • User feedback – gives users immediate feedback on errors.
    • Server protection – reduces the load of invalid submissions reaching the server.
    • Security – the first line of defence against malformed or malicious input (but never the only one).
    • Accessibility – error messages must be accessible to all users.
    • Compliance – many industries require validated data (finance, healthcare, government).
    • UX – prevents frustration of submitting invalid data and waiting for server responses.

    Where It Fits

    Validation is a cross-cutting concern that touches every form control. It combines:

    • HTML attributes – required, pattern, min, max, minlength, maxlength, type, step.
    • CSS – :valid, :invalid, :required, :optional pseudo-classes.
    • JavaScript – the Constraint Validation API.
    • ARIA – aria-invalid, aria-describedby, role="alert".
    • Server-side code – always required.
    Validation Layers
│
├── Client-side (HTML attributes)
├── Client-side (JavaScript)
├── Accessibility (ARIA)
└── Server-side (language-specific)

    2. Why It Exists

    The Problem

    Without validation, users can submit anything — empty required fields, malformed email addresses, out-of-range numbers, mismatched passwords, invalid credit cards. The server receives garbage data, which it must handle:

    • Data corruption – invalid data enters the database.
    • Security vulnerabilities – malformed input can exploit server bugs.
    • Poor UX – users wait for a server round-trip to learn about an error.
    • Wasted resources – the server processes invalid submissions.
    • Frustration – users repeat the form after a delayed error.

    Before HTML5, validation required JavaScript for even basic rules. This was:

    • Inconsistent – every site implemented its own.
    • Inaccessible – custom error messages were often not announced.
    • Fragile – JavaScript could be disabled.
    • Verbose – boilerplate code for every form.

    Previous Limitations

    Limitation Consequence
    No native validation JavaScript required for every rule.
    Inconsistent UI Each site had its own error display.
    Inaccessible Errors not announced to screen readers.
    Easily bypassed JavaScript could be disabled.
    Verbose code Boilerplate for every form.
    No mobile optimization Mobile keyboards not aligned with input types.

    Why Native Validation Was Introduced

    HTML5 introduced constraint validation to provide a native, declarative, accessible validation system. It enables:

    • Declarative rules – required, pattern, min, max, type.
    • Native UI – browsers show error messages automatically.
    • Accessibility – errors are announced by screen readers.
    • Mobile optimization – correct keyboards for each type.
    • CSS integration – :valid, :invalid pseudo-classes.
    • JavaScript API – the Constraint Validation API for custom rules.

    The native validation system doesn't replace server-side validation — it's an enhancement for UX. But it's a huge improvement over custom JavaScript-only validation.

    4. Mental Model

    The "Bouncer" Analogy

    Think of validation as a bouncer at a club. The bouncer checks IDs (required), ensures people are old enough (min), and verifies they're on the guest list (pattern). Only those who pass can enter (submit). The bouncer works automatically — you don't need to ask them to check.

    The "Checklist" Analogy

    Validation is like a checklist before takeoff. Each item must be checked: required (fuel), format (correct coordinates), range (altitude within limits). If any item fails, the flight is delayed. The checklist is applied automatically every time.

    The "Contract" Analogy

    Validation is a contract between the form and the user. The form states its requirements (constraints), and the user agrees to meet them. If the user breaks the contract (invalid input), the form refuses to submit.

    The "Concentric Circles" Mental Model

    Validation happens in concentric circles:

    1. HTML attributes – the innermost, easiest.
    2. JavaScript – additional custom rules.
    3. ARIA – accessibility announcements.
    4. Server-side – the outermost, ultimate authority.

    Each circle catches what the previous one misses.

    The "Never Trust the Client" Mental Model

    The most important mental model: never trust the client. Client-side validation (HTML or JavaScript) is for user experience — it gives instant feedback. But it can be bypassed (disable JS, use curl, modify HTML). Server-side validation is the only true validation — it must always be present.

    5. Core Concepts

    Concept 1: Constraint Validation

    The HTML5 constraint validation system applies constraints to form controls. Each control either satisfies or violates its constraints. If any control is invalid, the form cannot be submitted.

    <input type="email" required>

    Constraints: - Must not be empty (required). - Must match email format (type="email").

    Concept 2: The validity Property

    Each form control has a validity property — a ValidityState object with boolean flags:

    Property Meaning
    valid All constraints pass.
    valueMissing required and empty.
    typeMismatch Doesn't match type (email, url, number).
    patternMismatch Doesn't match pattern.
    tooLong Exceeds maxlength.
    tooShort Below minlength.
    rangeUnderflow Below min.
    rangeOverflow Above max.
    stepMismatch Doesn't match step.
    badInput Browser can't parse.
    customError Custom error set. 
    const input = document.querySelector('input');
if (input.validity.valueMissing) {
    console.log('Field is required');
}

    Concept 3: The checkValidity() Method

    Returns true if the control is valid, false otherwise. Fires an invalid event if invalid.

    input.checkValidity(); // true/false
form.checkValidity();  // true if all controls valid

    Concept 4: The reportValidity() Method

    Like checkValidity(), but also shows the browser's error message if invalid.

    input.reportValidity();
form.reportValidity();

    Concept 5: The setCustomValidity() Method

    Sets a custom error message. The control is considered invalid until setCustomValidity('') is called.

    if (password.value !== confirm.value) {
    confirm.setCustomValidity('Passwords do not match');
} else {
    confirm.setCustomValidity('');
}

    Concept 6: The invalid Event

    Fires on each invalid control when validity is checked.

    input.addEventListener('invalid', () => {
    console.log('Invalid input');
});

    Note: The invalid event does not bubble, so you must attach listeners to each control.

    Concept 7: The novalidate Attribute

    The novalidate attribute on <form> disables native validation. Useful for custom validation.

    <form novalidate>
    ...
</form>

    Concept 8: The formnovalidate Attribute

    The formnovalidate attribute on a submit button disables validation for that submission.

    <button type="submit" formnovalidate>Save Draft</button>

    Concept 9: CSS Validation Pseudo-Classes

    Pseudo-Class Matches
    :valid Controls that pass validation.
    :invalid Controls that fail validation.
    :required Controls with required.
    :optional Controls without required.
    :in-range Values within min/max.
    :out-of-range Values outside min/max.
    :read-only Controls with readonly.
    :read-write Controls without readonly.
    :placeholder-shown Controls showing placeholder.
    :default Default-selected controls.
    :indeterminate Checkboxes/radios in indeterminate state.

    Caution: :invalid applies on page load for empty required fields. Use :user-invalid (newer) or JavaScript to avoid premature styling.

    Concept 10: The :user-invalid Pseudo-Class

    A newer pseudo-class that only matches after the user interacts:

    input:user-invalid {
    border-color: red;
}

    Browser support: Modern browsers (2023+).

    Concept 11: Accessible Error Messages

    Screen readers must be able to announce errors. Techniques:

    • aria-invalid="true" on the control.
    • aria-describedby referencing the error message.
    • role="alert" on the error container.
    • aria-live="polite" for dynamic errors.
    <label for="email">Email:</label>
<input type="email" id="email" name="email" aria-describedby="email-error" aria-invalid="true">
<span id="email-error" role="alert">Please enter a valid email.</span>

    Concept 12: Browser Validation Messages

    Browsers show their own error messages. These vary by browser and locale. To customize:

    • Use setCustomValidity().
    • Use JavaScript validation with custom messages.
    • Use CSS for visual cues.

    Concept 13: Client vs. Server Validation

    Aspect Client-Side Server-Side
    Speed Instant Delayed
    Security Bypassable Reliable
    UX Good feedback Poor feedback
    Cost Free (HTML) Server resources
    Use case UX enhancement True validation

    Rule: Always validate on both sides. Client for UX, server for security.

    Concept 14: Regular Expressions in pattern

    The pattern attribute uses JavaScript regex syntax (without slashes):

    <input pattern="[0-9]{5}">           <!-- 5 digits -->
<input pattern="[A-Za-z]{3,}">        <!-- 3+ letters -->
<input pattern="\d{3}-\d{3}-\d{4}">   <!-- phone format -->

    Note: The pattern is anchored — it must match the entire value.

    Concept 15: The title Attribute with pattern

    Always pair pattern with title:

    <input pattern="[0-9]{5}" title="Five-digit ZIP code">

    The browser shows the title in the validation message.

    Concept 16: The inputmode Attribute

    While not a validation attribute, inputmode complements validation:

    <input type="text" inputmode="numeric" pattern="[0-9]*">

    Shows a numeric keyboard on mobile.

    Concept 17: The autocomplete Attribute

    Autofill helps users avoid validation errors by providing correctly formatted data.

    <input type="email" autocomplete="email" required>

    Concept 18: The type Attribute as Validation

    The type attribute provides built-in validation:

    • email – must be a valid email.
    • url – must be a valid URL.
    • number – must be numeric.
    • date – must be a valid date.
    • time – must be a valid time.
    • color – must be a hex color.

    Concept 19: Validation and Accessibility

    • Labels – every control must have a label.
    • Error messages – associated via aria-describedby.
    • aria-invalid – set to true on invalid controls.
    • role="alert" – announces errors immediately.
    • Focus – move focus to the first invalid field.
    • Color – don't rely on color alone.
    • Text – always provide text descriptions.

    Concept 20: The form.checkValidity() Method

    Returns true if all controls are valid:

    if (form.checkValidity()) {
    form.submit();
} else {
    // Show errors
}

    Concept 21: Focus Management

    When validation fails, focus should move to the first invalid control:

    form.addEventListener('submit', (e) => {
    const invalid = form.querySelector(':invalid');
    if (invalid) {
        e.preventDefault();
        invalid.focus();
    }
});

    Concept 22: Validation and Progressive Enhancement

    Native validation works without JavaScript. Enhance with:

    • Custom error messages.
    • Real-time validation.
    • Complex rules.

    Best practice: Ensure the form works with JavaScript disabled.

    Concept 23: The willValidate Property

    input.willValidate is true if the control is subject to validation, false otherwise (e.g., disabled, readonly, or not a form control).

    Concept 24: Validation and Disabled Controls

    Disabled controls are not validated and not submitted.

    <input type="email" required disabled>

    Note: Readonly controls are validated (if required, they must have a value).

    Concept 25: Validation and Hidden Inputs

    Hidden inputs (type="hidden") are not validated.

    Concept 26: The minlength and maxlength Attributes

    minlength/maxlength apply to text inputs and textareas:

    <input type="text" minlength="3" maxlength="20">
<textarea minlength="10" maxlength="500"></textarea>

    Note: These count Unicode code points.

    Concept 27: Validation and step

    The step attribute applies to number, range, date, time, datetime-local, month, week:

    <input type="number" min="0" max="100" step="5">
<input type="time" step="900"> <!-- 15-minute increments -->

    Concept 28: Validation and multiple

    For email and file:

    <input type="email" multiple>        <!-- comma-separated -->
<input type="file" multiple>          <!-- multiple files -->

    Concept 29: Validation and accept

    For file inputs:

    <input type="file" accept="image/*">

    Note: This is a hint, not a validation rule. Users can still select other files.

    Concept 30: The reportValidity() vs checkValidity()

    Method Returns Shows Error
    checkValidity() Boolean No
    reportValidity() Boolean Yes

    Concept 31: Form-Level Validation

    form.checkValidity() checks all controls. form.reportValidity() shows the first error.

    Concept 32: The submit Event and Validation

    Native validation runs before the submit event fires. If validation fails, the event doesn't fire.

    form.addEventListener('submit', (e) => {
    // Only runs if validation passes
    e.preventDefault();
    // Custom submission logic
});

    Concept 33: The invalid Event

    Fires on each invalid control when validity is checked:

    input.addEventListener('invalid', (e) => {
    e.preventDefault(); // Suppress default message
    // Show custom message
});

    Note: The default message is shown unless preventDefault() is called.

    Concept 34: Custom Validation

    input.addEventListener('input', () => {
    if (input.value.length < 3) {
        input.setCustomValidity('Must be at least 3 characters');
    } else {
        input.setCustomValidity('');
    }
});

    Concept 35: Server-Side Validation

    Always validate on the server:

    • Whitelist allowed values.
    • Sanitize input.
    • Escape output.
    • Validate length, format, range.
    • Use parameterized queries for SQL.

    6. How It Works

    Step-by-Step: Native Validation Flow

    1.  User fills out the form and clicks submit.
    │
    ▼
2.  Browser runs constraint validation:
    │   ├── For each control, check all constraints.
    │   ├── If any fail, the control is invalid.
    │   └── Focus moves to the first invalid control.
    │
    ▼
3.  If any control is invalid:
    │   ├── The `invalid` event fires on each.
    │   ├── The browser shows its error message.
    │   ├── The form submission is prevented.
    │   └── The `submit` event does NOT fire.
    │
    ▼
4.  If all controls are valid:
    │   ├── The `submit` event fires.
    │   ├── The form is submitted.
    │   └── The server processes the data.

    Validation Order

    Constraints are checked in this order:

    1. required – is the field filled?
    2. type – does it match the type?
    3. min/max – is it within range?
    4. minlength/maxlength – is the length correct?
    5. pattern – does it match?
    6. step – is it on a step boundary?
    7. customError – was setCustomValidity called?

    The ValidityState Object

    const input = document.querySelector('input');
console.log(input.validity);
// ValidityState {
//   valid: true,
//   valueMissing: false,
//   typeMismatch: false,
//   patternMismatch: false,
//   tooLong: false,
//   tooShort: false,
//   rangeUnderflow: false,
//   rangeOverflow: false,
//   stepMismatch: false,
//   badInput: false,
//   customError: false
// }

    Browser Default Messages

    Browsers show messages like:

    • "Please fill out this field."
    • "Please enter an email address."
    • "Please enter a URL."
    • "Value must be less than or equal to 100."

    These are localized by the browser.

    Accessibility Tree

    The accessibility tree exposes:

    • The control's validity state (aria-invalid).
    • The error message via aria-describedby.
    • The required state.

    Screen readers announce: "Email, required, invalid entry, please enter an email address."

    Custom Validation Flow

    form.addEventListener('submit', (e) => {
    e.preventDefault();
    // Custom validation
    if (!customRule()) {
        showError();
        return;
    }
    // Proceed with submission
    form.submit();
});

    7. Internal Architecture / Under the Hood

    The Constraint Validation API

    Defined in the HTML specification:

    • HTMLInputElement, HTMLSelectElement, HTMLTextAreaElement, HTMLButtonElement implement ValidityState.
    • Each has validity, validationMessage, willValidate, checkValidity(), reportValidity(), setCustomValidity().

    The ValidityState Interface

    interface ValidityState {
    readonly attribute boolean valueMissing;
    readonly attribute boolean typeMismatch;
    readonly attribute boolean patternMismatch;
    readonly attribute boolean tooLong;
    readonly attribute boolean tooShort;
    readonly attribute boolean rangeUnderflow;
    readonly attribute boolean rangeOverflow;
    readonly attribute boolean stepMismatch;
    readonly attribute boolean badInput;
    readonly attribute boolean customError;
    readonly attribute boolean valid;
}

    The Validation Algorithm

    When a control's value changes or validation is triggered:

    1. Compute valueMissing (if required and empty).
    2. Compute typeMismatch (if type-specific validation fails).
    3. Compute patternMismatch (if pattern is set and doesn't match).
    4. Compute tooLong/tooShort (if maxlength/minlength).
    5. Compute rangeUnderflow/rangeOverflow (if min/max).
    6. Compute stepMismatch (if step and value not on boundary).
    7. Compute badInput (if the browser can't parse the value).
    8. Compute customError (if setCustomValidity set a message).
    9. Set valid to true only if all others are false.

    The invalid Event

    Fired on invalid controls when checkValidity() or submission triggers validation. Does not bubble; can be captured with capture phase.

    The form.checkValidity() Algorithm

    1. Iterate all controls.
    2. Call checkValidity() on each.
    3. Return true if all pass.

    Browser Error Messages

    Browsers generate messages from the constraint that failed. Localized strings are stored in the browser's locale files.

    Custom Validity

    setCustomValidity(msg) sets the customError flag and stores the message. The control becomes invalid until cleared.

    Accessibility Mapping

    • :invalid → aria-invalid="true" in the accessibility tree.
    • required → aria-required="true".
    • validationMessage → exposed as the control's "description" or "error".

    Server-Side Validation

    Server-side validation is language-specific:

    • Node.js: Joi, Yup, express-validator.
    • Python: Pydantic, WTForms, Marshmallow.
    • Ruby: ActiveModel::Validations.
    • PHP: Respect\Validation, Symfony Validator.
    • Java: Bean Validation (JSR 380).

    11. Best Practices

    1. Always validate on the server – client-side is UX only.
    2. Use native HTML validation – it's accessible and free.
    3. Provide title with pattern – tells users the expected format.
    4. Use type for semantic validation – email, url, number, etc.
    5. Use minlength/maxlength for text fields.
    6. Use min/max/step for numeric fields.
    7. Provide accessible error messages – aria-describedby, role="alert".
    8. Set aria-invalid="true" on invalid controls.
    9. Move focus to the first invalid field.
    10. Show errors next to the field – not just at the top.
    11. Use :user-invalid – not :invalid alone (avoids styling empty fields on load).
    12. Don't rely on color alone – use text and icons.
    13. Provide a summary of errors – for long forms.
    14. Test with screen readers – errors must be announced.
    15. Test with keyboard only – errors must be reachable.
    16. Use novalidate for custom validation – to suppress browser messages.
    17. Use setCustomValidity('') to clear – never leave a custom error set.
    18. Sanitize and escape on the server – prevent XSS and injection.
    19. Use prepared statements – prevent SQL injection.
    20. Document validation conventions – in a style guide.

    12. Common Mistakes

    ❌ Mistake: Only Client-Side Validation

    if (email.validity.valid) {
    form.submit();
}

    Why it's wrong: Client-side validation can be bypassed.

    ✅ Correct: Always validate on the server as well.

    ❌ Mistake: No title with pattern

    <input pattern="[0-9]{5}">

    Why it's wrong: Users don't know the expected format.

    ✅ Correct: 

    <input pattern="[0-9]{5}" title="Five-digit ZIP code">

    ❌ Mistake: Relying on Color Alone for Errors

    input:invalid {
    border-color: red;
}

    Why it's wrong: Color-blind users can't distinguish.

    ✅ Correct: Also provide text and icons.

    ❌ Mistake: Not Announcing Errors to Screen Readers

    <input type="email" required>
<span>Invalid email</span>

    Why it's wrong: Screen readers don't know the error is associated.

    ✅ Correct: 

    <input type="email" required aria-describedby="email-error" aria-invalid="true">
<span id="email-error" role="alert">Invalid email</span>

    ❌ Mistake: No :user-invalid for Styling

    input:invalid {
    border-color: red;
}

    Why it's wrong: Empty required fields are styled red on page load.

    ✅ Correct: 

    input:user-invalid {
    border-color: red;
}

    ❌ Mistake: setCustomValidity Never Cleared

    if (password.value !== confirm.value) {
    confirm.setCustomValidity('Passwords do not match');
}
// Missing else branch

    Why it's wrong: The control remains invalid forever.

    ✅ Correct: 

    if (password.value !== confirm.value) {
    confirm.setCustomValidity('Passwords do not match');
} else {
    confirm.setCustomValidity('');
}

    ❌ Mistake: Server Validation Only

    app.post('/signup', (req, res) => {
    // validate
});

    Why it's wrong: Users wait for a server round-trip to learn about errors.

    ✅ Correct: Validate on both client and server.

    ❌ Mistake: Trusting Client Validation for Security

    <input type="email" required>
<!-- Server assumes the email is valid -->

    Why it's wrong: Attackers can bypass client validation.

    ✅ Correct: Always validate on the server.

    ❌ Mistake: Not Focusing the First Invalid Field

    if (!form.checkValidity()) {
    e.preventDefault();
    // No focus management
}

    Why it's wrong: Users may not know which field is invalid.

    ✅ Correct: 

    if (!form.checkValidity()) {
    e.preventDefault();
    const invalid = form.querySelector(':invalid');
    if (invalid) invalid.focus();
}

    ❌ Mistake: Using :invalid on Page Load

    input:invalid {
    border-color: red;
}

    Why it's wrong: All empty required fields are red on load.

    ✅ Correct: Use :user-invalid or :not(:placeholder-shown).

    ❌ Mistake: No Client Validation at All

    <form action="/submit" method="POST">
    <input type="text" name="email">
</form>

    Why it's wrong: Users wait for server feedback.

    ✅ Correct: 

    <form action="/submit" method="POST">
    <input type="email" name="email" required>
</form>

    ❌ Mistake: Not Testing Accessibility

    <input type="email" required>

    Why it's wrong: You don't know if the error is announced.

    ✅ Correct: Test with screen readers.

    ❌ Mistake: pattern Without Anchoring

    <input pattern="[0-9]{5}">

    Why it's wrong: The pattern is automatically anchored — it must match the entire value. This is actually correct — but developers sometimes expect partial matches.

    ✅ Correct: Understand that pattern matches the full value.

    ❌ Mistake: Overly Strict Patterns

    <input pattern="^(?=.*[A-Z])(?=.*[a-z])(?=.*\d)(?=.*[@$!%*?&])[A-Za-z\d@$!%*?&]{8,}$">

    Why it's wrong: Overly complex patterns frustrate users and often miss the point.

    ✅ Correct: Use simpler patterns; validate the rest on the server.

    13. Performance Considerations

    • Native validation – fast, no JavaScript.
    • Real-time validation – debounce to avoid excessive checks.
    • Async validation – debounce and cancel pending requests.
    • Server-side validation – the bottleneck; optimize queries.
    • Error rendering – minimize DOM updates.
    • :user-invalid – more performant than adding/removing classes.

    Performance Tips

    1. Debounce input validation – 300ms is common.
    2. Cancel pending requests – use AbortController.
    3. Validate on blur – not on every keystroke.
    4. Minimize DOM updates – batch changes.
    5. Use native validation – no JavaScript needed.
    6. Cache validation results – for repeated values.

    14. Security Considerations

    • Client-side validation is not security – always validate on the server.
    • Sanitize input – remove/escape dangerous characters.
    • Escape output – prevent XSS.
    • Use parameterized queries – prevent SQL injection.
    • Whitelist validation – allow only known-good values.
    • Rate limiting – prevent brute-force and DoS.
    • CSRF tokens – prevent cross-site request forgery.
    • HTTPS – encrypt form submissions.
    • Don't expose sensitive data in errors – e.g., "user does not exist" vs. "invalid credentials".
    • Log validation failures – for security monitoring.

    Security Best Practices

    1. Server-side validation – always.
    2. Whitelist – not blacklist.
    3. Sanitize – before storage or display.
    4. Escape – when outputting.
    5. Parameterize – for database queries.
    6. Rate-limit – per IP and per account.
    7. CSRF tokens – for state-changing forms.

    9. Log – validation failures.

    20. Summary

    • Form validation ensures data is correct, complete, and in the expected format before submission.
    • HTML provides native constraint validation via attributes: required, pattern, min, max, minlength, maxlength, type, step.
    • The Constraint Validation API (checkValidity(), reportValidity(), setCustomValidity(), validity) provides programmatic access.
    • CSS pseudo-classes (:valid, :invalid, :required, :optional, :in-range, :out-of-range, :user-invalid) style validation states.
    • Accessible error messages require aria-describedby, aria-invalid="true", and role="alert".
    • Client-side validation is for UX; server-side validation is for security.
    • Best practices: validate on both sides, provide accessible errors, focus on the first invalid field, use :user-invalid, and test with screen readers.
    • Common mistakes include only client-side validation, no title with pattern, and forgetting to clear setCustomValidity.
    • Security: sanitize, escape, parameterize, rate-limit, and use CSRF tokens.
    • Validation is essential for data quality, user experience, and security.
    • It is one of the most important aspects of modern web forms.
