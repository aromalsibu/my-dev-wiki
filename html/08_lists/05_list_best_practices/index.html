    Chapter: List Best Practices

    1. Overview

    Definition

    List best practices are a set of guidelines, patterns, and conventions for choosing, structuring, and styling HTML lists (<ul>, <ol>, <dl>) in a way that maximises semantics, accessibility, maintainability, and performance. They synthesise the individual rules covered in the chapters on ordered, unordered, description, and nested lists into a cohesive decision-making framework.

    List best practices answer questions like:

    • Which list type should I use?
    • When should I nest lists?
    • How do I style lists without breaking semantics?
    • How do I make lists accessible?
    • How do I avoid common pitfalls?

    They are not rigid rules — they are heuristics that help you write list markup that works for users, search engines, and future maintainers.

    Purpose

    List best practices serve several essential purposes:

    • Consistency – a shared vocabulary for list decisions across teams and projects.
    • Accessibility – ensure lists are usable by screen reader users and keyboard users.
    • Semantic correctness – choose the right list type for the content.
    • Maintainability – write list markup that is easy to read, extend, and refactor.
    • Performance – avoid unnecessary nesting and DOM bloat.
    • SEO – help search engines understand the structure and surface rich results.
    • Interoperability – ensure lists work across browsers, devices, and assistive technologies.

    Where It Fits

    List best practices are a meta-layer over the technical knowledge of <ul>, <ol>, <dl>, and <li>. They guide your decision-making at every step: choosing a list type, nesting lists, adding attributes, and styling them. They apply to every project, every page, and every component.

    2. Why It Exists

    The Problem

    Lists are deceptively simple. A <ul> with a few <li> elements seems trivial. But in practice, lists are used in dozens of contexts — navigation menus, feature lists, FAQs, glossaries, product specs, site maps, documentation, card grids — and each context has its own requirements and pitfalls.

    Without best practices, developers make inconsistent choices:

    • Using <ul> for ordered steps.
    • Using <div> for lists (losing semantics).
    • Over-nesting lists for layout purposes.
    • Removing list markers without preserving semantics.
    • Forgetting to nest lists inside <li>.
    • Using <dl> for general lists.
    • Ignoring accessibility.

    These choices accumulate into inconsistent, inaccessible, and hard-to-maintain codebases.

    Previous Limitations

    Problem Consequence
    Inconsistent list types Confusing for users and machines.
    Div-based "lists" Lost semantics; inaccessible.
    Over-nesting Bloated DOM; hard to maintain.
    list-style: none without role="list" Screen readers lose list semantics in Safari/VoiceOver.
    No aria-label on nav lists Ambiguous navigation.
    Deep nesting Poor performance and readability.
    Ignoring dl Missing semantic opportunities.

    Why Best Practices Were Established

    List best practices emerged from:

    • WCAG – accessibility guidelines for lists.
    • ARIA Authoring Practices – guidance on roles and states.
    • Browser vendor documentation – MDN, Web.dev, etc.
    • Community experience – lessons learned from real-world projects.
    • Style guides – Google, Airbnb, and others publish HTML style guides.

    Following these practices leads to better outcomes for users, developers, and businesses.

    3. Syntax / Basic Usage (Core Principles in Action)

    Principle 1: Choose the Right List Type

    Content List Type
    Ordered steps, rankings, sequences <ol>
    Grouped items (order doesn't matter) <ul>
    Term–description pairs <dl>

    Bad: 

    <!-- Ordered content in an unordered list -->
<ul>
    <li>First, preheat the oven.</li>
    <li>Then, mix the ingredients.</li>
    <li>Finally, bake for 25 minutes.</li>
</ul>

    Good: 

    <ol>
    <li>Preheat the oven.</li>
    <li>Mix the ingredients.</li>
    <li>Bake for 25 minutes.</li>
</ol>

    Principle 2: Use <li> as the Only Child of <ul> and <ol>

    Bad: 

    <ul>
    <p>Some text</p>
    <li>Item 1</li>
</ul>

    Good: 

    <ul>
    <li>Some text</li>
    <li>Item 1</li>
</ul>

    Principle 3: Nest Lists Inside <li>

    Bad: 

    <ul>
    <li>Item 1</li>
    <ul>
        <li>Sub-item</li>
    </ul>
    <li>Item 2</li>
</ul>

    Good: 

    <ul>
    <li>Item 1
        <ul>
            <li>Sub-item</li>
        </ul>
    </li>
    <li>Item 2</li>
</ul>

    Principle 4: Use <nav> for Navigation Lists

    Bad: 

    <ul>
    <li><a href="/">Home</a></li>
    <li><a href="/about">About</a></li>
</ul>

    Good: 

    <nav aria-label="Main navigation">
    <ul>
        <li><a href="/">Home</a></li>
        <li><a href="/about">About</a></li>
    </ul>
</nav>

    Principle 5: Preserve Semantics When Removing Markers

    Bad: 

    ul {
    list-style: none;
    padding: 0;
}
    (Safari/VoiceOver may remove list semantics.)

    Good: 

    <ul role="list">
    <li>Item 1</li>
    <li>Item 2</li>
</ul>

    ul {
    list-style: none;
    padding: 0;
}

    Or: 

    ul {
    list-style: none;
    padding: 0;
}
ul li {
    display: list-item;
}

    Principle 6: Use <dl> for Term–Description Pairs

    Bad: 

    <ul>
    <li><strong>HTML</strong> — HyperText Markup Language</li>
    <li><strong>CSS</strong> — Cascading Style Sheets</li>
</ul>

    Good: 

    <dl>
    <dt>HTML</dt>
    <dd>HyperText Markup Language</dd>
    <dt>CSS</dt>
    <dd>Cascading Style Sheets</dd>
</dl>

    Principle 7: Keep Nesting Shallow

    Bad: 

    <ul>
    <li>Level 1
        <ul>
            <li>Level 2
                <ul>
                    <li>Level 3
                        <ul>
                            <li>Level 4
                                <ul>
                                    <li>Level 5</li>
                                </ul>
                            </li>
                        </ul>
                    </li>
                </ul>
            </li>
        </ul>
    </li>
</ul>

    Good: 3–4 levels maximum, or use a different structure (e.g., <details>, separate pages).

    Principle 8: Don't Use Lists for Layout

    Bad: 

    <ul style="display: flex;">
    <li>Column 1</li>
    <li>Column 2</li>
</ul>

    Good: 

    <div style="display: flex;">
    <div>Column 1</div>
    <div>Column 2</div>
</div>

    Exception: Navigation menus and card grids often use <ul> with display: flex/grid because the items are semantically a list.

    4. Mental Model

    The "Toolbox" Analogy

    Think of list types as tools in a toolbox:

    • <ol> – a numbered checklist for sequences.
    • <ul> – a bullet list for grouped items.
    • <dl> – a dictionary for term–description pairs.

    Using the right tool for the job is the essence of list best practices. Using a screwdriver as a hammer works, but it's inefficient and can damage the tool.

    The "Contract with Machines" Analogy

    Choosing the right list type is like signing a contract with machines. You promise to use <ol> for ordered content and <ul> for unordered content. In return, machines promise to interpret your content correctly. Breaking the contract (e.g., using <ul> for steps) confuses machines and users alike.

    The "Code Review Checklist" Analogy

    List best practices are like a code review checklist. Before you ship list markup, you mentally review it:

    • Is the list type correct?
    • Is nesting done correctly?
    • Is the list accessible?
    • Is the styling appropriate?
    • Is the structure semantic?

    If you can answer "yes" to all, you've followed best practices.

    The "Building Blocks" Analogy

    Lists are building blocks for larger structures — navigation menus, card grids, FAQs, glossaries. Best practices ensure the blocks are stacked correctly so the larger structure is stable.

    5. Core Concepts

    Concept 1: Semantic Choice — <ol> vs <ul> vs <dl>

    The first and most important decision is choosing the right list type:

    Question Answer List Type
    Does order matter? Yes <ol>
    Does order matter? No <ul>
    Is it a term–description pair? Yes <dl>

    Common mistakes: - Using <ul> for instructions (should be <ol>). - Using <ol> for features (should be <ul>). - Using <ul> for glossaries (should be <dl>).

    Rule: The semantics of the list type should match the semantics of the content.

    Concept 2: <li> as the Only Child

    The <ul> and <ol> elements accept only <li> children. Any other content must be wrapped in <li>.

    <!-- Valid -->
<ul>
    <li>Item 1</li>
    <li>Item 2</li>
</ul>

<!-- Invalid -->
<ul>
    <p>Paragraph</p>
    <li>Item 1</li>
</ul>

    Concept 3: Nesting Inside <li>

    Nested lists must be inside the <li> element they belong to, not between <li> elements.

    <!-- Valid -->
<li>Item
    <ul>
        <li>Sub-item</li>
    </ul>
</li>

<!-- Invalid -->
<li>Item</li>
<ul>
    <li>Sub-item</li>
</ul>

    Concept 4: Preserving Semantics with list-style: none

    In Safari and VoiceOver, list-style: none removes the list semantics — screen readers no longer announce the list. The fix is to add role="list" to the <ul> or <ol>.

    <ul role="list">
    <li>Item 1</li>
    <li>Item 2</li>
</ul>

    Why: Safari's accessibility engine has a long-standing bug where list-style: none removes the list role. Adding role="list" restores it.

    Concept 5: Navigation Lists Need <nav> and Labels

    A navigation menu should be wrapped in <nav> with an aria-label (especially if there are multiple navs on the page).

    <nav aria-label="Main navigation">
    <ul>
        <li><a href="/">Home</a></li>
    </ul>
</nav>

<nav aria-label="Footer navigation">
    <ul>
        <li><a href="/privacy">Privacy</a></li>
    </ul>
</nav>

    Concept 6: aria-current="page" for Current Items

    In navigation menus, mark the current page with aria-current="page".

    <nav aria-label="Main navigation">
    <ul>
        <li><a href="/" aria-current="page">Home</a></li>
        <li><a href="/about">About</a></li>
    </ul>
</nav>

    Concept 7: Styling Without Breaking Semantics

    Lists can be styled extensively with CSS without breaking semantics:

    ul {
    list-style: none;
    padding: 0;
    margin: 0;
}
ul li {
    display: inline-block;
    margin-right: 1rem;
}

    But if you remove the markers, consider the accessibility implications (see Concept 4).

    Concept 8: Lists for Card Grids

    Card grids are often built with <ul> and <li> because the items are semantically a list.

    <ul class="card-grid">
    <li class="card">
        <h3>Card 1</h3>
        <p>Description</p>
    </li>
    <li class="card">
        <h3>Card 2</h3>
        <p>Description</p>
    </li>
</ul>

    .card-grid {
    list-style: none;
    padding: 0;
    display: grid;
    grid-template-columns: repeat(auto-fit, minmax(250px, 1fr));
    gap: 1rem;
}

    Concept 9: Lists for Site Maps

    Site maps are naturally hierarchical and should use nested <ul>.

    <nav aria-label="Site map">
    <ul>
        <li><a href="/">Home</a>
            <ul>
                <li><a href="/about">About</a></li>
            </ul>
        </li>
        <li><a href="/products">Products</a></li>
    </ul>
</nav>

    Concept 10: Lists for Glossaries and FAQs

    Glossaries and FAQs are term–description pairs and should use <dl>.

    <dl>
    <dt>HTML</dt>
    <dd>HyperText Markup Language</dd>
</dl>

    Concept 11: Lists for Documentation

    Documentation often uses all three list types:

    • <ol> for step-by-step procedures.
    • <ul> for feature lists, options, and parameters.
    • <dl> for parameter descriptions and glossaries.

    Concept 12: Performance — Keep Lists Shallow

    Deep nesting increases DOM size and rendering complexity. Keep nesting to 3–4 levels maximum.

    Concept 13: Accessibility — Test with Screen Readers

    Test lists with NVDA, JAWS, VoiceOver, or TalkBack to ensure they're announced correctly. Pay attention to:

    • Whether the list is announced.
    • Whether the item count is announced.
    • Whether nested lists are announced.
    • Whether the current item (aria-current) is announced.

    Concept 14: SEO — Use Lists for Structured Content

    Search engines use lists to understand grouped and sequenced content. Combine lists with structured data for rich results:

    • FAQPage – <dl> with questions and answers.
    • HowTo – <ol> with steps.
    • ItemList – <ul> or <ol> with items.

    Concept 15: Validation — Ensure Correct Structure

    Validate your HTML to catch list structure errors:

    • Only <li> as children of <ul>/<ol>.
    • Nested lists inside <li>.
    • Correct <dt>/<dd> structure in <dl>.

    7. Internal Architecture / Under the Hood

    How List Type Affects the Accessibility Tree

    Element Accessibility Role
    <ul> list
    <ol> list
    <li> listitem
    <dl> list (or definitionlist)
    <dt> term (or listitem)
    <dd> definition (or listitem)

    The list-style: none bug in Safari/VoiceOver removes the list role. Adding role="list" restores it.

    How list-style: none Affects Semantics

    ul {
    list-style: none;
}

    In Safari/VoiceOver, this removes the list role from the <ul>. The fix:

    <ul role="list">

    ul {
    list-style: none;
}

    This forces the list role to be preserved.

    How <nav> Affects the Accessibility Tree

    <nav> creates a navigation landmark in the accessibility tree. Screen reader users can jump to it. Multiple navs should have unique aria-labels.

    How aria-current Works

    aria-current="page" tells assistive technologies that the link represents the current page. Screen readers may announce "current page" or "current".

    How SEO Uses Lists

    Search engines use lists to understand structure:

    • Ordered lists – sequence, rankings, steps.
    • Unordered lists – grouped items, features.
    • Description lists – term–description pairs, FAQs, metadata.

    Structured data (JSON-LD) can be combined with lists for rich results.

    How Validation Catches Errors

    The W3C validator checks:

    • Only <li> as children of <ul>/<ol>.
    • Nested lists inside <li>.
    • <dt>/<dd> structure in <dl>.
    • Correct attributes.

    11. Best Practices (The Full List)

    Choosing the Right List Type

    1. Use <ol> for ordered content – steps, rankings, sequences.
    2. Use <ul> for unordered content – features, categories, navigation.
    3. Use <dl> for term–description pairs – glossaries, FAQs, metadata.
    4. Use <menu> for toolbars – semantic alternative to <ul>.

    Structure

    1. Use <li> as the only child of <ul>/<ol>.
    2. Nest lists inside <li> – not between items.
    3. Keep nesting shallow – 3–4 levels maximum.
    4. Use semantic elements – <ul>, <ol>, <dl> — not <div>.
    5. Use <dl> with <dt> and <dd> as siblings.
    6. Use <div> wrappers in <dl> for styling (HTML5 only).

    Accessibility

    1. Use <nav> for navigation lists.
    2. Add aria-label to multiple navs.
    3. Use aria-current="page" for the current item.
    4. Add role="list" if using list-style: none (Safari/VoiceOver bug).
    5. Test with screen readers.
    6. Ensure keyboard accessibility — all links focusable.
    7. Keep list items concise — long items are hard to scan.
    8. Use descriptive link text — "About Us" not "Click here".

    Styling

    1. Use CSS list-style-type — not the obsolete type attribute.
    2. Use ::marker for custom marker styling.
    3. Use CSS counters for custom numbering (e.g., 1.1, 1.1.1).
    4. Use padding-inline-start for logical indentation.
    5. Don't use lists for layout — use CSS Grid or Flexbox.
    6. Exception: Navigation menus and card grids are semantically lists.

    Navigation

    1. Wrap navigation in <nav>.
    2. Use <ul> for navigation menus.
    3. Use <ol> for breadcrumbs (order matters).
    4. Use aria-label on <nav> when there are multiple navs.
    5. Use aria-current="page" for the current page.
    6. Provide a mobile-friendly menu — e.g., hamburger menu.

    SEO

    1. Use <ol> for "HowTo" content — with structured data.
    2. Use <dl> for FAQ content — with structured data.
    3. Use <ul> for "ItemList" content — with structured data.
    4. Keep list items descriptive — search engines use the text.
    5. Use structured data for rich results.

    Validation

    1. Validate your HTML — W3C validator.
    2. Check for invalid nesting.
    3. Check for missing role="list" if using list-style: none.
    4. Check for aria-label on multiple navs.
    5. Check for aria-current on navigation.

    Performance

    1. Keep lists shallow — avoid deep nesting.
    2. Use <details> for collapsible lists — native and efficient.
    3. Virtualize very large lists — for hundreds of items.
    4. Minify HTML — reduce file size.
    5. Avoid inline styles — use CSS classes.

    Maintenance

    1. Use meaningful class names — not .red or .big.
    2. Comment complex list structures — for maintainability.
    3. Document your list conventions — in a style guide.
    4. Review lists regularly — as the site evolves.
    5. Stay updated — follow HTML Living Standard changes.

    12. Common Mistakes

    ❌ Mistake: Using <ul> for Ordered Content

    <h2>How to Make Tea</h2>
<ul>
    <li>Boil water.</li>
    <li>Add tea leaves.</li>
    <li>Steep for 3 minutes.</li>
</ul>
    Why it's wrong: The steps have a specific order; use <ol>.

    ✅ Correct: 

    <ol>
    <li>Boil water.</li>
    <li>Add tea leaves.</li>
    <li>Steep for 3 minutes.</li>
</ol>

    ❌ Mistake: Using <ul> for Glossaries

    <ul>
    <li><strong>HTML</strong> — HyperText Markup Language</li>
    <li><strong>CSS</strong> — Cascading Style Sheets</li>
</ul>
    Why it's wrong: Term–description pairs should use <dl>.

    ✅ Correct: 

    <dl>
    <dt>HTML</dt>
    <dd>HyperText Markup Language</dd>
    <dt>CSS</dt>
    <dd>Cascading Style Sheets</dd>
</dl>

    ❌ Mistake: Using <div> Instead of <ul>

    <div class="features">
    <div>Fast</div>
    <div>Responsive</div>
    <div>Accessible</div>
</div>
    Why it's wrong: Loses list semantics; screen readers won't announce the list.

    ✅ Correct: 

    <ul class="features">
    <li>Fast</li>
    <li>Responsive</li>
    <li>Accessible</li>
</ul>

    ❌ Mistake: Placing Content Directly Inside <ul>

    <ul>
    <p>Some text</p>
    <li>Item 1</li>
</ul>
    Why it's wrong: Only <li> is a valid child of <ul>.

    ✅ Correct: 

    <ul>
    <li>Some text</li>
    <li>Item 1</li>
</ul>

    ❌ Mistake: Nesting a List Between <li> Elements

    <ul>
    <li>Item 1</li>
    <ul>
        <li>Sub-item</li>
    </ul>
</ul>
    Why it's wrong: Nested lists must be inside an <li>.

    ✅ Correct: 

    <ul>
    <li>Item 1
        <ul>
            <li>Sub-item</li>
        </ul>
    </li>
</ul>

    ❌ Mistake: Removing Markers Without Preserving Semantics

    <ul style="list-style: none;">
    <li>Item 1</li>
    <li>Item 2</li>
</ul>
    Why it's wrong: Safari/VoiceOver may remove the list semantics.

    ✅ Correct: 

    <ul role="list" style="list-style: none;">
    <li>Item 1</li>
    <li>Item 2</li>
</ul>

    ❌ Mistake: Using <ul> for Layout

    <ul style="display: flex;">
    <li>Column 1</li>
    <li>Column 2</li>
</ul>
    Why it's wrong: Lists are for related items, not layout. Use <div>.

    ✅ Correct: 

    <div style="display: flex;">
    <div>Column 1</div>
    <div>Column 2</div>
</div>

    Exception: If the items are semantically a list (e.g., a card grid), use <ul>.

    ❌ Mistake: Navigation Menu Without <nav>

    <ul>
    <li><a href="/">Home</a></li>
    <li><a href="/about">About</a></li>
</ul>
    Why it's wrong: Screen readers can't jump to the navigation.

    ✅ Correct: 

    <nav aria-label="Main navigation">
    <ul>
        <li><a href="/">Home</a></li>
        <li><a href="/about">About</a></li>
    </ul>
</nav>

    ❌ Mistake: Multiple Navs Without Labels

    <nav>
    <ul>...</ul>
</nav>
<nav>
    <ul>...</ul>
</nav>
    Why it's wrong: Screen reader users can't distinguish between the navs.

    ✅ Correct: 

    <nav aria-label="Main navigation">
    <ul>...</ul>
</nav>
<nav aria-label="Footer navigation">
    <ul>...</ul>
</nav>

    ❌ Mistake: Not Using aria-current for the Current Page

    <nav aria-label="Main navigation">
    <ul>
        <li><a href="/">Home</a></li>
        <li><a href="/about">About</a></li>
    </ul>
</nav>
    Why it's wrong: The current page is not indicated.

    ✅ Correct: 

    <nav aria-label="Main navigation">
    <ul>
        <li><a href="/" aria-current="page">Home</a></li>
        <li><a href="/about">About</a></li>
    </ul>
</nav>

    ❌ Mistake: Deep Nesting

    <ul>
    <li>Level 1
        <ul>
            <li>Level 2
                <ul>
                    <li>Level 3
                        <ul>
                            <li>Level 4
                                <ul>
                                    <li>Level 5</li>
                                </ul>
                            </li>
                        </ul>
                    </li>
                </ul>
            </li>
        </ul>
    </li>
</ul>
    Why it's wrong: Deep nesting is hard to read, navigate, and maintain.

    ✅ Correct: Keep nesting to 3–4 levels; use <details> or separate pages for deeper hierarchies.

    ❌ Mistake: Using the Obsolete type Attribute

    <ul type="square">
    Why it's wrong: The type attribute is obsolete in HTML5.

    ✅ Correct: 

    <ul class="square">

    .square { list-style-type: square; }

    ❌ Mistake: Hardcoding Bullets or Numbers

    <ul>
    <li>• Item 1</li>
    <li>• Item 2</li>
</ul>
    Why it's wrong: The browser adds bullets automatically.

    ✅ Correct: 

    <ul>
    <li>Item 1</li>
    <li>Item 2</li>
</ul>

    ❌ Mistake: Using <dl> for General Lists

    <dl>
    <dt>Item 1</dt>
    <dd>Item 2</dd>
</dl>
    Why it's wrong: <dl> is for term–description pairs, not general lists.

    ✅ Correct: Use <ul> for general lists.

    13. Performance Considerations

    • DOM size – each list adds DOM nodes. Deep nesting increases DOM size.
    • Rendering – deeply nested lists increase layout complexity.
    • CSS selectors – ul ul ul selectors can be slow for very deep nesting.
    • Marker rendering – each level requires a marker. Minimal cost.
    • Large lists – lists with thousands of items can impact rendering; consider virtualization.
    • <details> – using <details> for collapsible lists can improve initial render performance.
    • display: grid or display: flex – efficient for card grids and menus.

    Performance Tips

    1. Keep lists shallow – avoid deep nesting.
    2. Use <details> for collapsible content.
    3. Virtualize very large lists.
    4. Minify HTML.
    5. Avoid inline styles.
    6. Use CSS classes.
    7. Use content-visibility: auto for large lists (with caution).

    14. Security Considerations

    • XSS – if list items contain user-generated content, sanitize it before rendering.
    • innerHTML – avoid using innerHTML with user input; use textContent or a sanitizer.
    • Injection – never insert user input directly into <li>, <dt>, or <dd> without escaping.
    • Navigation links – validate URLs to prevent open redirects and XSS.
    • No direct security implications – list elements themselves are not security risks.

    Security Best Practices

    1. Sanitize user input – before inserting into list items.
    2. Use textContent – instead of innerHTML for text.
    3. Validate URLs – for navigation links.
    4. Use rel="noopener noreferrer" – for external links.
    5. Use CSP – to restrict inline scripts and styles.

    15. Debugging Tips

    • DevTools Elements panel – inspect the list structure.
    • Collapse/expand nodes – to see the hierarchy.
    • Computed styles – check list-style-type, padding-inline-start.
    • Accessibility Inspector – check the list and listitem roles.
    • Console – use document.querySelectorAll('ul') to count lists.
    • getComputedStyle(ul).listStyleType – check the marker style.
    • Validator – check for invalid nesting and attributes.
    • Screen reader testing – ensure the list is announced correctly.
    • Test with CSS disabled – ensure the list still makes sense.
    • Lighthouse – audits for accessibility and SEO.

    16. When to Use

    • For grouped content – features, categories, tags.
    • For ordered content – steps, rankings, sequences.
    • For term–description pairs – glossaries, FAQs, metadata.
    • For navigation – menus, breadcrumbs, site maps.
    • For card grids – when items are semantically a list.
    • For documentation – parameters, options, procedures.
    • For structured data – FAQ, HowTo, ItemList.

    17. When Not to Use

    • For layout – use CSS Grid or Flexbox.
    • For single items – use <p> or <div>.
    • For arbitrary grouping – use <div> if there's no semantic list.
    • For tabular data – use <table>.
    • For content that isn't a list – don't force it.

    • The Safari/VoiceOver list-style: none bug has been a known issue for years. Adding role="list" is the recommended workaround.

    • Screen readers announce lists as "list of N items" and each item as "item N of M". This helps users understand the structure.

    • Search engines use lists to understand grouped and sequenced content. Combining lists with structured data can trigger rich results.

    • Breadcrumb navigation should use <ol> because the order of pages matters (from general to specific).

    • Navigation menus should use <ul> wrapped in <nav> with aria-label.

    • The aria-current="page" attribute tells assistive technologies which link represents the current page.

    • CSS counters can create custom numbering schemes like "1.1", "1.1.1", "1.1.1.1" for nested lists.

    • The ::marker pseudo-element can style markers with color, font, and content.

    • Card grids are often built with <ul> because the cards are semantically a list.

    • The <details> element can be used inside <li> to create collapsible nested lists without JavaScript.

    • Deep nesting (10+ levels) is hard to read and navigate. Most content needs only 3–4 levels.

    • display: grid on a <ul> is a common technique for card layouts.

    • display: flex on a <ul> is a common technique for horizontal navigation menus.

    • The padding-inline-start property is used for logical indentation (respects RTL).

    • Structured data (JSON-LD, Microdata) can be combined with lists for rich results.

    • WCAG 1.3.1 (Info and Relationships) requires that lists be marked up semantically.

    • WCAG 2.4.6 (Headings and Labels) applies to list headings and labels.

    • WCAG 4.1.2 (Name, Role, Value) requires that lists have appropriate roles.

    • The ARIA Authoring Practices recommends using native HTML lists wherever possible.

    • The HTML Living Standard defines the content models for lists: <li> is the only valid child of <ul> and <ol>.

    • Lists are read depth-first by screen readers, which is the natural reading order for hierarchical content.

    • Nested lists are a key part of document outlines, site maps, navigation menus, and taxonomies.

    • List semantics are preserved even when lists are styled as grids or flex containers.

    • List items can contain any flow content, including headings, paragraphs, images, and other lists.

    • Description lists (<dl>) are used in FAQ rich results by Google.

    • Ordered lists (<ol>) are used in HowTo rich results by Google.

    • Unordered lists (<ul>) are used in ItemList rich results by Google.

    • role="list" is the recommended fix for the Safari/VoiceOver list-style: none bug.

    • Testing with screen readers is essential for ensuring list accessibility.

    • Consistency in list usage across a site improves usability and maintainability.

    • Documentation of list conventions helps teams maintain consistency.

    • List best practices are not rigid rules — they are heuristics that guide good decisions.

    • Following list best practices leads to more accessible, maintainable, and semantic HTML.

    20. Summary

    • List best practices are guidelines for choosing, structuring, and styling HTML lists.
    • Choose the right list type: <ol> for ordered content, <ul> for unordered content, <dl> for term–description pairs.
    • Use <li> as the only child of <ul> and <ol>.
    • Nest lists inside <li> — not between items.
    • Keep nesting shallow — 3–4 levels maximum.
    • Preserve semantics with role="list" when using list-style: none.
    • Use <nav> for navigation lists with aria-label and aria-current.

    • Don't use lists for layout — use CSS Grid or Flexbox (except when items are semantically a list, like card grids).
    • Validate and test — with the W3C validator and screen readers.
    • Common mistakes: using <ul> for ordered content, using <div> instead of <ul>, placing content directly inside <ul>, nesting lists between <li> elements, and removing markers without preserving semantics.
    • List best practices lead to more accessible, maintainable, and semantic HTML — benefiting users, developers, and search engines alike.
