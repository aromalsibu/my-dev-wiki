    Semantic HTML

    1. Overview

    Definition

    Semantic HTML is the practice of using HTML elements that describe the meaning and purpose of their content — not just its appearance. A <nav> element means "this is navigation." A <button> means "this is an interactive control." A <article> means "this is a self-contained piece of content."

    <!-- Semantic -->
<nav aria-label="Main">
    <ul>
        <li><a href="/">Home</a></li>
        <li><a href="/about">About</a></li>
    </ul>
</nav>

<!-- Non-semantic (div soup) -->
<div class="nav">
    <div class="nav-item"><a href="/">Home</a></div>
    <div class="nav-item"><a href="/about">About</a></div>
</div>

    The two examples may look identical visually. But the first tells the browser, the search engine, and the screen reader exactly what the content is. The second tells them nothing.

    Purpose

    Semantic HTML serves several essential purposes:

    • Accessibility — screen readers use element roles and landmarks to navigate. <nav> becomes a jump target; <button> becomes an operable control.
    • SEO — search engines weight semantic structure. A <main> with an <h1> communicates hierarchy; a <div> soup does not.
    • Maintainability — semantic markup is self-documenting. A new developer can understand the structure without reading CSS classes.
    • Machine readability — AI systems, browser extensions, reader modes, and translation tools all rely on semantics to interpret content.
    • Keyboard navigation — native elements carry built-in keyboard behavior. <button> responds to Enter and Space; a <div onclick> does not.
    • Default browser behavior — native elements work with browser features: form validation, autofill, password managers, reader mode, find-in-page, and printing.
    • Robustness — semantic HTML degrades gracefully. When CSS or JavaScript fails, the content remains usable.

    Where It Fits

    Semantic HTML is the foundation layer of accessibility. Everything else — ARIA, focus management, keyboard navigation, screen reader compatibility — is built on top of it.

    Accessibility Stack
│
├── Semantic HTML        ← foundation (native elements, landmarks, headings)
├── ARIA                 ← supplement (roles, states, properties)
├── CSS                  ← contrast, focus styles, layout
├── JavaScript           ← focus management, dynamic content
└── Testing              ← screen readers, automated tools

    If the foundation is wrong, no amount of ARIA or JavaScript can fix it reliably.

    2. Why It Exists

    The Problem

    HTML has always had semantic elements. But in the mid-2000s, developers stopped using them. They used <div> for everything, styling it with CSS classes to look like navigation, headers, articles, and footers. This produced what became known as "div soup" — markup that renders correctly but conveys nothing about meaning.

    <!-- Div soup: looks right, means nothing -->
<div class="header">
    <div class="nav">
        <div class="nav-link"><a href="/">Home</a></div>
    </div>
</div>
<div class="content">
    <div class="post">
        <div class="post-title">How SVG Works</div>
        <div class="post-body">...</div>
    </div>
</div>
<div class="footer">...</div>

    To a screen reader, this is a flat list of text. To a search engine, it is unstructured content. To a reader mode, it is an undifferentiated block.

    Previous Limitations

    Limitation Consequence
    No landmarks Screen reader users cannot jump to navigation or main content
    No heading hierarchy No way to navigate by headings
    No native controls Keyboard access requires manual JavaScript
    No form semantics Autofill and validation do not work
    No SEO signals Search engines cannot weight structure
    No reader mode Reader modes cannot extract the article

    Why It Was Introduced

    HTML5 (2008–2014) introduced a set of sectioning and semantic elements to solve the div-soup problem:

    • <header>, <footer>, <nav>, <main>, <article>, <section>, <aside>, <figure>, <figcaption>, <time>, <mark>, <details>, <summary>.

    These elements had existed conceptually since HTML 4 (<div id="header">), but HTML5 formalized them as first-class elements with defined roles, landmarks, and accessibility mappings.

    The goal: give meaning to structure so that browsers, assistive technology, search engines, and future tools can understand the page without parsing CSS classes.

    3. Syntax / Basic Usage

    The Semantic Document Skeleton

    <!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Semantic HTML Demo — Dev Notes</title>
</head>
<body>
    <a href="#main-content" class="skip-link">Skip to main content</a>

    <header>
        <h1>Dev Notes</h1>
        <nav aria-label="Main">
            <ul>
                <li><a href="/">Home</a></li>
                <li><a href="/blog">Blog</a></li>
                <li><a href="/about">About</a></li>
            </ul>
        </nav>
    </header>

    <main id="main-content">
        <article>
            <header>
                <h2>How SVG Embedding Works</h2>
                <p>
                    Published <time datetime="2026-01-15">January 15, 2026</time>
                    by <span rel="author">Jane Developer</span>
                </p>
            </header>
            <section>
                <h3>Inline SVG</h3>
                <p>...</p>
            </section>
            <section>
                <h3>Image SVG</h3>
                <p>...</p>
            </section>
            <footer>
                <p>Filed under: <a href="/tags/svg">SVG</a></p>
            </footer>
        </article>

        <aside aria-label="Related posts">
            <h2>Related</h2>
            <ul>
                <li><a href="/css-cascade">The CSS Cascade</a></li>
            </ul>
        </aside>
    </main>

    <footer>
        <p>&copy; 2026 Dev Notes</p>
    </footer>
</body>
</html>

    Code Breakdown

    Element Meaning Accessibility Role
    <header> Introductory content banner (when top-level)
    <nav> Navigation links navigation landmark
    <main> Primary content main landmark
    <article> Self-contained content article role
    <section> Thematic grouping region (when labelled)
    <aside> Complementary content complementary landmark
    <footer> Closing content contentinfo (when top-level)
    <h1>–<h6> Heading hierarchy heading role with level
    <time> Date/time Semantic date
    <figure>/<figcaption> Figure with caption figure role

    The Heading Hierarchy

    <h1>Page Title</h1>

<h2>Section A</h2>
<h3>Subsection A.1</h3>
<h3>Subsection A.2</h3>

<h2>Section B</h2>
<h3>Subsection B.1</h3>

    Rules:

    • One <h1> per page (recommended, not required).
    • Never skip levels (<h1> → <h3> is a failure).
    • Headings must reflect content structure, not visual size.
    • Use CSS to style headings differently — do not choose an <h4> because it "looks right."

    Native Interactive Elements

    <!-- Buttons: keyboard-operable, announced as "button" -->
<button type="button">Save</button>

<!-- Links: navigate to a URL, announced as "link" -->
<a href="/about">About</a>

<!-- Inputs: associated with labels, participate in forms -->
<label for="email">Email</label>
<input id="email" type="email" required>

<!-- Details/summary: native disclosure widget -->
<details>
    <summary>Show more</summary>
    <p>Hidden content</p>
</details>

    Code Breakdown

    • <button> — Enter/Space activates; announced as button. Never use <div onclick> for a button.
    • <a href> — navigates; announced as link. Never use <a> without href as a button.
    • <input> + <label> — autofill, validation, password managers, and screen reader association all work automatically.
    • <details>/<summary> — native disclosure widget; no JavaScript required.

    4. Mental Model

    The "Meaning vs Appearance" Mental Model

    Every HTML element answers two questions:

    <div>          → What does it look like? (nothing)
<span>         → What does it look like? (nothing)
<nav>          → What is it? (navigation)
<button>       → What is it? (control)
<article>      → What is it? (content)

    Semantic HTML answers "what is it?", not "what does it look like?". Styling is CSS's job.

    The "Screen Reader Roadmap" Mental Model

    A screen reader user navigates by structure, not by visuals. Semantic HTML provides the roadmap:

    ┌─────────────────────────────────────────────┐
│  <header>           ← landmark: banner       │
│    <nav>            ← landmark: navigation   │
│  <main>             ← landmark: main         │
│    <h1>             ← heading level 1        │
│    <article>        ← content block          │
│      <h2>           ← heading level 2        │
│      <section>      ← region                 │
│        <h3>         ← heading level 3        │
│  <aside>            ← landmark: complementary│
│  <footer>           ← landmark: contentinfo  │
└─────────────────────────────────────────────┘

    Keyboard shortcuts in NVDA/JAWS: - H — next heading - K — next link - B — next button - F — next form field - D — next landmark - 1–6 — heading levels

    Without semantics, none of these work.

    The "Layered Meaning" Mental Model

    Semantic HTML provides meaning at multiple levels:

    Layer 1: Document structure   → <html>, <head>, <body>
Layer 2: Landmarks            → <header>, <nav>, <main>, <aside>, <footer>
Layer 3: Content grouping     → <article>, <section>, <figure>
Layer 4: Headings             → <h1>–<h6>
Layer 5: Text meaning         → <em>, <strong>, <mark>, <time>, <abbr>
Layer 6: Interaction          → <button>, <a>, <input>, <select>, <textarea>

    Each layer adds a dimension of meaning. The more layers present, the richer the accessibility tree.

    The "ARIA as Duct Tape" Mental Model

    ARIA is duct tape for when HTML fails. It patches gaps:

    <!-- Native HTML: no duct tape needed -->
<button>Save</button>

<!-- ARIA duct tape: adds role but not behavior -->
<div role="button" tabindex="0" onclick="save()" onkeydown="...">
    Save
</div>

    The second example requires manual keyboard handling, manual focus styles, manual disabled states. Native HTML gives all of this for free.

    Rule 1 of ARIA: if a native HTML element provides the semantics and behavior you need, use it. Use ARIA only when native HTML cannot express the semantics.

    5. Core Concepts

    Concept 1: Landmarks

    Landmarks are page regions that screen readers can jump to directly. Modern HTML provides them via native elements:

    Element Implicit Landmark Role Count Per Page
    <header> (top-level) banner 1
    <nav> navigation Multiple
    <main> main 1
    <aside> complementary Multiple
    <footer> (top-level) contentinfo 1
    <section> (with aria-label) region Multiple
    <form> (with aria-label) form Multiple

    Rule: one <main> per page; one <header> and <footer> at the top level (nested headers/footers inside <article> and <section> do not create landmarks).

    Concept 2: The Heading Hierarchy

    Headings create a navigable outline. Screen readers announce level (h1, h2) and allow jumping between them. Skip heading levels = broken structure.

    <!-- Correct -->
<h1>Page title</h1>
<h2>Section</h2>
<h3>Subsection</h3>

<!-- Wrong: skipped level -->
<h1>Page title</h1>
<h3>Section</h3>

    Never use headings for styling. Use CSS classes for that.

    Concept 3: <article> vs <section> vs <div>

    Element Use When
    <article> Content that could stand alone (blog post, product card, comment)
    <section> A thematic grouping with a heading
    <div> A generic container for styling; no semantic meaning

    Test for <article>: would this content make sense in an RSS feed on its own? If yes, it is an <article>.

    Test for <section>: does it have a heading? If not, use <div>.

    Concept 4: <header> and <footer>

    These are context-dependent:

    • At the top level of <body> — they become banner and contentinfo landmarks.
    • Inside <article> or <section> — they are just semantic grouping; no landmark.
    <body>
    <header>...</header>    <!-- banner landmark -->
    <main>
        <article>
            <header>...</header>  <!-- NOT a landmark; article header -->
            <footer>...</footer>  <!-- NOT a landmark; article footer -->
        </article>
    </main>
    <footer>...</footer>    <!-- contentinfo landmark -->
</body>

    Concept 5: Native Interactive Elements

    The single most impactful accessibility decision: use <button> for buttons, <a> for links, and <input>/<select>/<textarea> for forms.

    Need Element Why
    Trigger an action <button> Keyboard-operable, announced as button
    Navigate to a URL <a href> Announced as link, right-click, middle-click
    Text input <input type="text"> Autofill, validation, form association
    Toggle <input type="checkbox"> Announced as checkbox, Space toggles
    Select from list <select> Native dropdown, keyboard-navigable
    Disclosure <details>/<summary> Native expand/collapse

    Concept 6: Text-Level Semantics

    Inline elements carry meaning:

    Element Meaning
    <em> Stress emphasis (changes meaning)
    <strong> Importance (seriousness)
    <mark> Highlighted/relevant
    <abbr> Abbreviation; use title for expansion
    <time> Date/time; use datetime for machine-readable format
    <code> Code fragment
    <kbd> User input
    <samp> Sample output
    <var> Variable
    <cite> Title of a work
    <blockquote> Extended quotation
    <q> Short inline quotation

    Concept 7: Landmark Labelling

    When a landmark type appears multiple times, label it with aria-label:

    <nav aria-label="Main">
    <ul>...</ul>
</nav>

<nav aria-label="Footer">
    <ul>...</ul>
</nav>

    Screen readers announce "Main navigation" and "Footer navigation."

    Concept 8: The <main> Element

    <main> wraps the primary content of the page. There should be only one <main> per page, and it should not include repeated content (headers, navigation, footers).

    <header>...</header>
<main>
    <h1>Page title</h1>
    <p>Content...</p>
</main>
<footer>...</footer>

    Concept 9: <figure> and <figcaption>

    <figure>
    <img src="chart.png" alt="Bar chart of Q1 revenue">
    <figcaption>Figure 1: Q1 2026 revenue by region.</figcaption>
</figure>

    <figcaption> is announced as the figure's caption. The <figure> is announced as a figure. Screen readers can associate them.

    Concept 10: <time> with datetime

    <time datetime="2026-01-15T08:00:00Z">January 15, 2026</time>

    The datetime attribute provides a machine-readable date. Search engines, AI systems, and calendar tools can parse it.

    Concept 11: <details> and <summary> for Disclosure

    <details>
    <summary>Shipping information</summary>
    <p>Free shipping on orders over $75.</p>
</details>

    Native disclosure widget. No JavaScript needed. Keyboard-accessible, announced correctly.

    Concept 12: Semantic HTML and Reader Mode

    Reader modes in Safari, Firefox, and Chrome extract the "main article" from the page. They rely on semantic elements. A page built with <article>, <h1>, and <p> is reader-mode friendly. A <div> soup is not.

    Concept 13: Semantic HTML and Find-in-Page

    Browsers' find-in-page works on text nodes. But structured content — headings, list items, table cells — is easier to navigate. Some browsers support "find in heading" extensions that rely on semantics.

    Concept 14: Semantic HTML and SEO

    Search engines use semantic structure to weight content:

    • <h1> is the page's primary topic.
    • <main> contains the primary content.
    • <article> signals standalone content.
    • <time> provides freshness signals.
    • <nav> and <footer> are deprioritized.

    A <div> with class="heading-1" has no such weight.

    Concept 15: Semantic HTML and AI Systems

    AI answer engines (AI Overviews, ChatGPT, Perplexity) parse HTML structure to extract content. Clean semantic markup — headings, paragraphs, lists, tables — improves extraction and citation accuracy. Div soup produces weaker signals.

    Concept 16: Semantic HTML and CSS

    Semantic markup and CSS are orthogonal. Semantic HTML describes what something is; CSS decides how it looks.

    <!-- Bad: chooses element based on appearance -->
<h4>Latest News</h4>

<!-- Good: chooses element based on meaning, styles with CSS -->
<h2 class="visually-small">Latest News</h2>

    Concept 17: Browser Default Behaviors

    Native elements come with browser behaviors that div-based equivalents do not have:

    • <button> responds to keyboard, prevents form submission by default (with type="button"), and integrates with assistive technology.
    • <input> participates in forms, autofill, password managers, and validation.
    • <details> toggles open/closed without JavaScript.
    • <a href> supports right-click, middle-click, and browser URL preview.

    Concept 18: Semantic HTML and Internationalization

    Semantic HTML supports language and direction:

    <html lang="en">
<p lang="fr">Bonjour</p>
<p dir="rtl" lang="ar">مرحبا</p>

    Screen readers switch voices based on lang. Layout direction is determined by dir.

    Concept 19: The <search> Element

    The <search> element (new in HTML) wraps search functionality:

    <search>
    <form action="/search">
        <label for="q">Search</label>
        <input id="q" type="search" name="q">
        <button type="submit">Go</button>
    </form>
</search>

    Browser support is still expanding, but it provides a semantic landmark for search.

    Concept 20: <dialog> for Modals

    <dialog id="confirm">
    <form method="dialog">
        <h2>Confirm deletion</h2>
        <p>This cannot be undone.</p>
        <button value="cancel">Cancel</button>
        <button value="confirm">Delete</button>
    </form>
</dialog>

<button onclick="document.getElementById('confirm').showModal()">
    Delete
</button>

    The native <dialog> element provides focus trapping, Escape handling, and modal semantics — all without JavaScript frameworks.

    6. How It Works

    Step-by-Step: Semantic Element to Accessibility Tree

    1.  HTML is parsed.
    │
    ▼
2.  Each element gets:
    │   ├── Role (from element name)
    │   ├── Name (from content or aria-label)
    │   ├── State (from attributes like disabled, checked)
    │   └── Level (for headings)
    │
    ▼
3.  Accessibility tree is built.
    │
    ▼
4.  Landmarks are registered:
    │   banner, navigation, main, complementary, contentinfo
    │
    ▼
5.  Headings form a navigable tree.
    │
    ▼
6.  Screen reader exposes:
    │   ├── Landmark navigation (D key)
    │   ├── Heading navigation (H key, 1-6 keys)
    │   ├── Link navigation (K key)
    │   └── Form field navigation (F key)

    Step-by-Step: Keyboard Navigation in a Form

    1.  User tabs into form.
    │
    ▼
2.  Focus moves to <input> (native, focusable).
    │
    ▼
3.  Screen reader announces:
    │   "Email address, edit, required"
    │   (from <label> and required attribute)
    │
    ▼
4.  User types.
    │
    ▼
5.  Browser validates email format on blur.
    │
    ▼
6.  User tabs to <button type="submit">.
    │
    ▼
7.  Pressing Enter submits the form (native behavior).

    Step-by-Step: Landmark Navigation

    Screen reader shortcut: D → next landmark

1.  banner       (header)
2.  navigation   (nav)
3.  main         (main)
4.  complementary (aside)
5.  contentinfo  (footer)

    Without semantic elements, these landmarks do not exist.

    7. Internal Architecture / Under the Hood

    Element-to-Role Mapping

    The HTML Accessibility API Mappings specification defines how each element maps to an ARIA role:

    Element ARIA Role
    <article> article
    <aside> complementary
    <button> button
    <footer> (top-level) contentinfo
    <header> (top-level) banner
    <h1>–<h6> heading (level 1–6)
    <main> main
    <nav> navigation
    <ol>, <ul> list
    <li> listitem
    <table> table
    <form> (labelled) form
    <section> (labelled) region

    The Landmark Calculation Algorithm

    Not every <header> is a banner. The rule:

    • A <header> is banner only if it is not a descendant of <article>, <aside>, <main>, <nav>, or <section>.
    • A <footer> is contentinfo only if it is not a descendant of those elements.
    • A <section> is region only if it has an accessible name (via aria-label or aria-labelledby).

    Native Behavior vs ARIA

    Native elements provide both semantics and behavior. ARIA provides only semantics:

    <button>              → role + keyboard + focus + disabled + click
<div role="button">   → role only (needs JS for keyboard, focus, disabled)

<input type="email">  → role + validation + autofill + keyboard
<div role="textbox">  → role only (needs JS for everything)

    This is why Rule 1 of ARIA exists.

    The Accessibility Tree vs the DOM

    The DOM is the browser's internal representation. The accessibility tree is a parallel tree optimized for assistive technology:

    • aria-hidden="true" removes elements from the accessibility tree but not the DOM.
    • display: none removes from both.
    • role="presentation" removes semantics but keeps the element.
    • CSS-generated content (::before) may not appear in the accessibility tree.

                <option value="daily">Daily</option>
                <option value="weekly" selected>Weekly</option>
                <option value="monthly">Monthly</option>
            </select>
        </div>

        <button type="submit">Subscribe</button>
    </fieldset>
</form>

    Code Breakdown:

    • <fieldset> + <legend> — groups related controls with a name.
    • <label for="..."> — programmatically associates labels with inputs.
    • autocomplete="email" — enables browser autofill.
    • aria-describedby — links hint text to input.
    • <select> — native dropdown, keyboard-navigable.

    Example 4: Accessible Data Table

    <table>
    <caption>Q1 2026 Revenue by Region</caption>
    <thead>
        <tr>
            <th scope="col">Region</th>
            <th scope="col">Revenue</th>
            <th scope="col">Growth</th>
        </tr>
    </thead>
    <tbody>
        <tr>
            <th scope="row">North America</th>
            <td>$2.1M</td>
            <td>+18%</td>
        </tr>
        <tr>
            <th scope="row">Europe</th>
            <td>$1.4M</td>
            <td>+12%</td>
        </tr>
    </tbody>
</table>

    Code Breakdown:

    • <caption> — accessible table name.
    • <thead> / <tbody> — structural grouping.
    • scope="col" — identifies column headers.
    • scope="row" — identifies row headers.
    • Screen readers announce "Region: Europe, Revenue: $1.4M, Growth: +12%" when navigating cells.

    Example 5: Native Dialog

    <dialog id="confirm-delete">
    <form method="dialog">
        <h2>Confirm deletion</h2>
        <p>This action cannot be undone.</p>
        <button value="cancel">Cancel</button>
        <button value="confirm">Delete</button>
    </form>
</dialog>

<button onclick="document.getElementById('confirm-delete').showModal()">
    Delete account
</button>

    Code Breakdown:

    • <dialog> — native modal; traps focus automatically.
    • showModal() — opens as a modal with backdrop.
    • method="dialog" — form submission closes the dialog; button value is returned.
    • Escape key closes the dialog natively.

    11. Best Practices

    1. Choose elements by meaning, not appearance. Why: semantics describe what content is, CSS describes how it looks.
    2. Use <button> for actions, <a> for navigation. Why: native keyboard behavior and correct announcements.
    3. Never use <a> without href as a button. Why: it has no keyboard behavior and is not announced as a link.
    4. Never use <div> or <span> for interactive controls without ARIA and keyboard handlers. Why: they are invisible to assistive technology by default.
    5. Maintain a logical heading hierarchy. Why: screen readers navigate by headings.
    6. Never skip heading levels. Why: it breaks the document outline.
    7. Use only one <main> per page. Why: it is the primary content landmark.
    8. Label repeated landmarks with aria-label. Why: multiple navs need distinct names.
    9. Use <article> for self-contained content. Why: it enables syndication and content extraction.
    10. Use <section> only when it has a heading. Why: unlabelled sections are just <div>s.
    11. Use <figure> and <figcaption> for images with captions. Why: screen readers announce the caption association.
    12. Use <time> with datetime for dates. Why: machine-readable; used by search and AI systems.
    13. Use <label> for every form control. Why: programmatic association is required for accessibility.
    14. Use <fieldset> and <legend> for grouped controls. Why: they provide context.
    15. Use <details> and <summary> for disclosure. Why: native, keyboard-accessible, no JavaScript needed.
    16. Use <dialog> for modals. Why: native focus trapping and Escape handling.
    17. Prefer native HTML over ARIA. Why: native elements have behavior; ARIA only has semantics.
    18. Add lang to <html> and inline language changes. Why: screen readers switch voices.
    19. Test with a screen reader. Why: semantics only matter if they translate to announcements.
    20. Test with keyboard only. Why: native behavior is the accessibility baseline.

    12. Common Mistakes

    ❌ Mistake: Using <div> for Buttons

    <div class="btn" onclick="save()">Save</div>

    Why it's wrong: Not focusable, not keyboard-operable, not announced as a button.

    ✅ Correct:

    <button type="button" onclick="save()">Save</button>

    ❌ Mistake: Using <a> Without href as a Button

    <a onclick="save()">Save</a>

    Why it's wrong: No href means no keyboard focus, no role, no correct announcement.

    ✅ Correct:

    <button type="button" onclick="save()">Save</button>

    ❌ Mistake: Multiple <h1> Elements

    <h1>Page Title</h1>
<article>
    <h1>Article Title</h1>
</article>

    Why it's wrong: Multiple top-level headings confuse the document outline.

    ✅ Correct:

    <h1>Page Title</h1>
<article>
    <h2>Article Title</h2>
</article>

    ❌ Mistake: Skipping Heading Levels

    <h1>Page Title</h1>
<h4>Section</h4>

    Why it's wrong: Breaks the outline; screen reader users lose hierarchy.

    ✅ Correct:

    <h1>Page Title</h1>
<h2>Section</h2>

    ❌ Mistake: Using Headings for Styling

    <h4>Latest News</h4>  <!-- chosen because it "looks right" -->

    Why it's wrong: Heading level is semantic, not visual.

    ✅ Correct:

    <h2 class="small-heading">Latest News</h2>

    ❌ Mistake: Multiple <main> Elements

    <main>Home content</main>
<main>Sidebar content</main>

    Why it's wrong: Only one <main> landmark per page.

    ✅ Correct:

    <main>
    <section>Home content</section>
    <aside>Sidebar content</aside>
</main>

    ❌ Mistake: <section> Without a Heading

    <section>
    <p>Some content</p>
</section>

    Why it's wrong: An unlabelled <section> has no accessible name; it is not a landmark.

    ✅ Correct:

    <section>
    <h2>Section Title</h2>
    <p>Some content</p>
</section>

    ❌ Mistake: Using <div> for Paragraphs

    <div class="paragraph">Some text.</div>

    Why it's wrong: Loses paragraph semantics; reader modes and screen readers treat it as a generic container.

    ✅ Correct:

    <p>Some text.</p>

    ❌ Mistake: No lang Attribute

    <html>

    Why it's wrong: Screen readers cannot select the correct voice.

    ✅ Correct:

    <html lang="en">

    ❌ Mistake: Unlabelled Multiple Navs

    <nav>...</nav>
<nav>...</nav>

    Why it's wrong: Screen readers announce both as "navigation"; the user cannot distinguish them.

    ✅ Correct:

    <nav aria-label="Main">...</nav>
<nav aria-label="Account">...</nav>

    13. Performance Considerations

    • Semantic elements have no runtime cost — they are parsed the same as <div>.
    • Native elements are faster than ARIA-heavy alternatives — the browser handles keyboard and focus natively.
    • Reader mode extraction works better with semantic content.
    • Search engine parsing is more efficient with clear structure.
    • No JavaScript required for <details>, <dialog>, <button>, and form controls.

    Performance Tips

    1. Prefer native elements over JavaScript-heavy custom widgets.
    2. Use <details> for accordions instead of JavaScript.
    3. Use <dialog> for modals instead of third-party libraries.
    4. Use semantic landmarks so reader mode extracts the article directly.

    14. Security Considerations

    Semantic HTML Does Not Introduce Security Issues

    Semantic elements are parsed by the HTML parser — no new attack surface. They do not execute scripts.

    ARIA and DOM Injection

    Dynamically setting aria-label from untrusted input could expose data. Escape or validate any ARIA values generated from user input.

    Form Semantics and Autofill

    autocomplete attributes on form fields can expose sensitive values if misconfigured (e.g., autocomplete="cc-number" on an unrelated field). Use correct autocomplete values.

    <dialog> and Focus

    The <dialog> element traps focus when opened modally. Ensure that closing it returns focus to the trigger.

    15. Debugging Tips

    • Chrome DevTools → Elements → Accessibility pane — inspect any element's role, name, and state.
    • Chrome DevTools → Elements → Accessibility tree — see the full accessibility tree.
    • Firefox DevTools → Accessibility — visualizes landmarks and heading hierarchy.
    • axe DevTools extension — flags missing headings, unlabelled landmarks, and div-button patterns.
    • Lighthouse — audits for semantic structure and missing alt text.
    • Screen reader (NVDA, VoiceOver) — verify landmarks and heading navigation work.
    • Keyboard-only walkthrough — Tab through the page; verify focus reaches all controls.
    • HTML validator — validator.w3.org — catches invalid nesting.
    • View source — confirm semantic elements are present in static HTML, not injected by JavaScript after load.

    16. When to Use

    • Always. Semantic HTML is the default. Every page benefits from it.
    • Every interactive control — buttons, links, inputs.
    • Every content block — articles, sections, figures.
    • Every form — labels, fieldsets, legends.
    • Every image — alt text or aria-hidden.
    • Every page — landmarks and heading hierarchy.

    17. When Not to Use

    • Never skip semantics for the sake of custom styling. Style with CSS; keep the semantics.
    • Do not use <article> for everything. Not every block is self-contained.
    • Do not add <section> just for styling. Use <div> if there is no heading and no thematic grouping.
    • Do not use headings for visual sizing.
    • Do not use ARIA to paper over bad HTML. Fix the HTML.

    19. Did You Know?

    • HTML5 introduced 8 new semantic elements in 2008: <article>, <aside>, <figure>, <figcaption>, <footer>, <header>, <nav>, <section>.
    • The <main> element is only one per page — using more than one is invalid.
    • A <header> is only a banner landmark when it is not nested inside <article>, <aside>, <main>, <nav>, or <section>.
    • A <section> needs an accessible name to become a region landmark. Without one, it is just a container.
    • Screen reader users navigate by landmarks (D), headings (H), links (K), and form fields (F).
    • The <dialog> element provides native focus trapping — no JavaScript library needed.
    • The <details> element is a native disclosure widget — no JavaScript needed for expand/collapse.
    • The <search> element is new in HTML and provides a semantic landmark for search.
    • Rule 1 of ARIA is "don't use ARIA if native HTML can do it."
    • Pages with ARIA average 59.1 detectable errors — versus 42 on pages without ARIA (WebAIM Million 2026).
    • Reader modes in Safari, Firefox, and Chrome rely on semantic elements to extract articles.
    • AI answer engines parse semantic structure to extract and cite content accurately.
    • The <time> element's datetime attribute provides a machine-readable date — used by search engines and AI systems.
    • Search engines weight <h1> and <main> more heavily than div-based equivalents.

    20. Summary

    • Semantic HTML uses elements that describe meaning, not appearance.
    • It is the foundation of accessibility — everything else builds on it.
    • Landmarks (header, nav, main, aside, footer) let screen reader users jump between regions.
    • Heading hierarchy (h1–h6) creates a navigable outline.
    • Native interactive elements (button, a, input, select, details, dialog) provide keyboard behavior and correct announcements for free.
    • Rule 1 of ARIA: use native HTML whenever it suffices.
    • Semantic HTML benefits everyone — accessibility, SEO, AI, maintainability, robustness.
    • Common mistakes: <div> buttons, skipped heading levels, multiple <h1>, unlabelled navs, missing lang.
    • Test with keyboard only, screen reader, and automated tools.
    • Choose elements by meaning — style with CSS.
    • Semantic HTML is the default — every page benefits from it.
