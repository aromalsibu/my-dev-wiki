    ARIA

    1. Overview

    Definition

    ARIA (Accessible Rich Internet Applications) is a W3C specification that adds semantic roles, states, and properties to HTML elements — enabling assistive technologies like screen readers to interpret dynamic web content and custom user interface controls.

    <!-- Native HTML: no ARIA needed -->
<button>Save</button>

<!-- ARIA: adds semantics to a div, but not behavior -->
<div role="button" tabindex="0" aria-pressed="false">Save</div>

    The two examples may look identical. But the first is a real button — focusable, keyboard-operable, announced correctly. The second is a <div> with ARIA duct tape — it tells the screen reader it is a button, but without JavaScript it does not behave like one.

    ARIA is a specification, not a library or a framework. It defines attributes you can add to HTML elements. It does not add functionality. It only changes how assistive technologies perceive an element.

    Purpose

    ARIA serves three specific areas that native HTML does not fully cover:

    • Structural landmarks — indicating the main structural areas of a page (though HTML5 now covers most of this natively).
    • Custom widget roles — defining the roles and properties of UI elements that HTML does not natively express (tabs, sliders, comboboxes, trees, grids).
    • Dynamic content announcement — providing a method for communicating alerts, page changes, and dynamically updated information to assistive technology.

    ARIA exists to bridge gaps between what HTML can express and what modern web applications need to express.

    Where It Fits

    Accessibility Stack
│
├── Semantic HTML        ← foundation (native elements, landmarks, headings)
├── ARIA                 ← supplement (roles, states, properties)
├── CSS                  ← contrast, focus styles, layout
├── JavaScript           ← focus management, dynamic state updates
└── Testing              ← screen readers, automated tools

    ARIA is not a replacement for semantic HTML. It complements it. When native HTML elements carry the correct semantics — <button>, <nav>, <header>, <input> — those elements provide the most reliably accessible experience. ARIA is for situations where native elements cannot express the required widget behavior, or where dynamic content changes need to be communicated.

    2. Why It Exists

    The Problem

    In the mid-2000s, web applications became dynamic. AJAX, JavaScript-rendered interfaces, and custom widgets — tabs, sliders, date pickers, autocomplete comboboxes — proliferated. But HTML had no way to express these complex widgets semantically.

    A screen reader sees a <div> with a click handler and announces nothing useful. It sees a <span> that opens a dropdown and has no idea it is a control. It sees a list of <li> elements styled as tabs and cannot distinguish the active tab from the inactive ones.

    ARIA was created to solve this: give developers a vocabulary to describe custom widgets to assistive technology.

    Previous Limitations

    Limitation Consequence
    No widget roles Custom controls announced as generic text
    No state communication "Expanded/collapsed," "selected," "checked" unknown
    No live region support Dynamic content changes not announced
    No relationship attributes Labels, descriptions, and controls not connected
    No landmark roles No way to skip between page regions

    Why It Was Introduced

    ARIA was proposed by Richard Schwerdtfeger at IBM in 2006 and became a W3C Recommendation in 2014. The first version (ARIA 1.0) defined the core vocabulary. ARIA 1.1 added new roles and properties. ARIA 1.2 is the current version, adding refinements for comboboxes, feeds, and other widgets.

    The goal: make dynamic web applications perceivable to assistive technology without requiring screen readers to reverse-engineer custom widgets from DOM structure.

    3. Syntax / Basic Usage

    The Three Types of ARIA Declarations

    ARIA defines three categories of attributes:

    Category What It Declares Examples
    Roles What an element is role="button", role="tablist", role="slider"
    States Dynamic condition aria-expanded, aria-selected, aria-checked
    Properties Supplemental description aria-label, aria-describedby, aria-controls

    The Minimal ARIA Example

    <!-- A custom toggle button (ARIA adds semantics, JS adds behavior) -->
<button
    type="button"
    aria-pressed="false"
    onclick="this.setAttribute('aria-pressed',
             this.getAttribute('aria-pressed') === 'false' ? 'true' : 'false')">
    Mute
</button>

    Code Breakdown

    • aria-pressed="false" — declares the toggle state. Screen readers announce "not pressed."
    • The JavaScript updates aria-pressed on click. Without this update, the attribute is a lie — the screen reader announces a state that does not match reality.
    • This is a native <button> with ARIA state — the best of both worlds. Behavior comes from HTML; state communication comes from ARIA.

    Fully Commented Production Example

    <!-- Tabs widget: ARIA declares roles, states, and relationships -->
<div class="tabs">
    <!-- Tab list: declares the container as a tab list -->
    <div role="tablist" aria-label="Settings">
        <!-- Tab: declares role, state, and controls relationship -->
        <button role="tab"
                id="tab-general"
                aria-selected="true"
                aria-controls="panel-general"
                tabindex="0">
            General
        </button>
        <button role="tab"
                id="tab-security"
                aria-selected="false"
                aria-controls="panel-security"
                tabindex="-1">
            Security
        </button>
    </div>

    <!-- Tab panel: declares role and labelledby relationship -->
    <div role="tabpanel"
         id="panel-general"
         aria-labelledby="tab-general"
         tabindex="0">
        <h2>General settings</h2>
        <p>...</p>
    </div>

    <div role="tabpanel"
         id="panel-security"
         aria-labelledby="tab-security"
         tabindex="0"
         hidden>
        <h2>Security settings</h2>
        <p>...</p>
    </div>
</div>

    Code Breakdown

    Attribute Purpose
    role="tablist" Declares the container as a tab list
    role="tab" Declares each control as a tab
    aria-selected Indicates which tab is active
    aria-controls Links the tab to its panel
    role="tabpanel" Declares each content area as a tab panel
    aria-labelledby Links the panel back to its tab
    tabindex Manages keyboard focus within the tab list (roving tabindex pattern)

    4. Mental Model

    The "Duct Tape" Mental Model

    ARIA is duct tape for HTML. It patches gaps where native HTML cannot express what a widget is.

    <!-- Native HTML: no duct tape needed -->
<button>Save</button>

<!-- ARIA duct tape: adds role but not behavior -->
<div role="button" tabindex="0" onclick="save()" onkeydown="...">
    Save
</div>

    The second example requires manual keyboard handling, manual focus styles, manual disabled states. Native HTML gives all of this for free. The best ARIA is no ARIA — because native HTML already provides both semantics and behavior.

    The "Three Layers" Mental Model

    ARIA operates at three layers:

    ┌─────────────────────────────────────────────┐
│  ROLE       → what is it?                    │
│  role="tab"                                  │
├─────────────────────────────────────────────┤
│  STATE      → what condition is it in?       │
│  aria-selected="true"                        │
├─────────────────────────────────────────────┤
│  PROPERTY   → what else describes it?        │
│  aria-controls="panel-1"                     │
│  aria-label="Settings"                       │
└─────────────────────────────────────────────┘

    A complete ARIA widget needs all three layers. A role without state is incomplete. A state without a relationship property leaves the user lost.

    The "Five Rules" Mental Model

    The W3C defines five rules of ARIA use:

    Rule 1: Don't use ARIA if native HTML can do it.
Rule 2: Don't change native semantics unless absolutely necessary.
Rule 3: All interactive ARIA controls must be keyboard operable.
Rule 4: Never use role="presentation" or aria-hidden="true" on focusable elements.
Rule 5: All interactive elements must have an accessible name.

    These rules are not suggestions — they are the foundation of correct ARIA implementation. Violating them produces the errors that make ARIA harmful.

    The "ARIA Paradox" Mental Model

    The 2026 WebAIM Million report found that pages using ARIA averaged 59.1 detectable accessibility errors, compared to 42 on pages without ARIA.

    This is the ARIA paradox: more ARIA does not mean more accessibility. It often means more errors.

    Why?

    • Developers add ARIA to fix a scan result, then close the ticket without adding the JavaScript behavior the ARIA requires.
    • aria-expanded="false" is added to a dropdown but never updated when the dropdown opens. The screen reader announces it as permanently closed — worse than no ARIA at all.
    • ARIA roles are added to elements that already have native roles, causing conflicting announcements.
    • aria-hidden="true" is added to interactive elements, making them invisible to screen readers.

    5. Core Concepts

    Concept 1: ARIA Does Not Add Behavior

    The single most important fact about ARIA: it changes only how assistive technologies perceive an element. It does not add functionality or keyboard behavior.

    <!-- A div with role="button" tells a screen reader it's a button -->
<!-- But without JavaScript, it won't respond to Enter or Space -->
<div role="button">Save</div>

    A native <button> is focusable, keyboard-operable, and announced correctly — all by default. A <div role="button"> requires tabindex="0", onkeydown handlers for Enter and Space, and focus styles. And even then, it may not behave identically across browsers and screen readers.

    Concept 2: The Five Rules of ARIA

    Rule Meaning
    Rule 1 Prefer native HTML elements that already have the required semantics and behavior
    Rule 2 Do not override native element semantics unless absolutely necessary
    Rule 3 All interactive ARIA controls must be keyboard operable
    Rule 4 Never use role="presentation" or aria-hidden="true" on focusable elements
    Rule 5 All interactive elements must have an accessible name

    Rule 1 is the most important: if native HTML can do it, use native HTML.

    Concept 3: Roles

    Roles declare what an element is. There are six categories of roles:

    Category Examples Purpose
    Landmark banner, navigation, main, complementary, contentinfo Page structure (HTML5 covers most)
    Widget button, checkbox, tab, slider, combobox Interactive controls
    Document structure article, heading, list, table Content organization (HTML5 covers most)
    Window dialog, alertdialog Modal windows
    Live region alert, status, log Dynamic content
    Abstract widget, input, select Never use directly

    Never use abstract roles. They are for the specification's internal taxonomy, not for developers.

    Concept 4: States

    States describe the current condition of a widget. They change at runtime.

    State Applies To Meaning
    aria-expanded Combobox, menu, disclosure Open or closed
    aria-selected Tab, option, grid cell Selected or not
    aria-checked Checkbox, radio, switch Checked, unchecked, mixed
    aria-pressed Toggle button Pressed or not
    aria-disabled Any widget Disabled
    aria-hidden Any element Hidden from assistive technology
    aria-busy Live region Content is updating
    aria-current Link, step Current item in a set

    States must be updated dynamically. A static aria-expanded="false" that never changes is worse than no attribute at all.

    Concept 5: Properties

    Properties provide supplemental descriptive information that does not change frequently.

    Property Purpose
    aria-label Direct string label
    aria-labelledby Reference to another element for label
    aria-describedby Reference to longer description
    aria-controls Relationship to controlled element
    aria-owns Relationship to owned elements
    aria-live Politeness level for live region
    aria-atomic Whether to announce entire region
    aria-relevant What changes to announce
    aria-haspopup Whether element opens a popup
    aria-valuenow, aria-valuemin, aria-valuemax Slider/range values

    Concept 6: The Accessible Name Computation

    The accessible name is what a screen reader announces. The computation follows this priority:

    1. aria-labelledby    → references other elements
2. aria-label         → direct string
3. Native label       → <label>, alt, <caption>
4. Text content       → for buttons, links
5. title attribute    → last resort

    If aria-labelledby is present, it overrides aria-label and all other sources.

    Concept 7: Live Regions

    Live regions announce dynamic content changes to screen readers without moving focus.

    Attribute Politeness Use Case
    aria-live="polite" Waits for user idle Status updates, chat messages
    aria-live="assertive" Interrupts immediately Alerts, errors
    role="alert" Implicit assertive Error messages, urgent warnings
    role="status" Implicit polite General status updates
    role="log" Implicit polite Chat logs, activity feeds 
    <div role="alert" id="error-message"></div>

<script>
    document.getElementById('error-message').textContent =
        'Please enter a valid email address.';
    // Screen reader announces immediately
</script>

    Concept 8: aria-hidden — Use With Caution

    aria-hidden="true" removes an element from the accessibility tree. It is useful for:

    • Decorative icons inside buttons that already have aria-label.
    • Off-screen content that should not be announced.

    It is dangerous when applied to interactive elements. aria-hidden="true" on a focusable button makes it invisible to screen readers but still reachable by keyboard — a keyboard trap. This is the most common and severe ARIA implementation error and automated testing catches only 30–40% of such cases.

    Concept 9: aria-label vs aria-labelledby

    <!-- aria-label: direct string -->
<button aria-label="Close dialog">✕</button>

<!-- aria-labelledby: references visible text -->
<h2 id="dialog-title">Confirm deletion</h2>
<div role="dialog" aria-labelledby="dialog-title">
    ...
</div>

    Prefer aria-labelledby when visible text exists — it keeps the label and visible text synchronized. Use aria-label only when no visible label exists.

    Concept 10: Redundant Roles

    Adding a role that an element already has natively is redundant and potentially harmful.

    <!-- Redundant: button already has role="button" -->
<button role="button">OK</button>

<!-- Redundant: nav already has role="navigation" -->
<nav role="navigation">...</nav>

<!-- Redundant: main already has role="main" -->
<main role="main">...</main>

    These are unnecessary. The native roles already provide the correct semantics. Adding a redundant role can cause conflicting announcements in some screen readers.

    Concept 11: ARIA and Keyboard Navigation

    Rule 3: all interactive ARIA controls must be keyboard operable. ARIA declares semantics, but it does not add keyboard functionality.

    If you build a custom widget with ARIA roles, you must also implement:

    • tabindex management (roving tabindex for composite widgets).
    • Keyboard event handlers for Enter, Space, Arrow keys, Home, End, Escape.
    • Focus management when the widget opens, closes, or updates.

    Concept 12: Focus Management in SPAs

    Focus management is the most common source of accessibility regressions in single-page applications. When a route changes, focus must be moved deliberately.

    // After route change, move focus to the main heading
function onRouteChange() {
    const heading = document.querySelector('main h1');
    heading.setAttribute('tabindex', '-1');
    heading.focus();
}

    Concept 13: aria-current

    Indicates the current item within a set — useful for navigation.

    <nav aria-label="Main">
    <ul>
        <li><a href="/" aria-current="page">Home</a></li>
        <li><a href="/about">About</a></li>
    </ul>
</nav>

    Screen readers announce "Home, current page."

    Concept 14: aria-describedby for Hints and Errors

    <label for="password">Password</label>
<input id="password" type="password"
       aria-describedby="password-hint password-error">
<span id="password-hint">Must be at least 8 characters.</span>
<span id="password-error" role="alert"></span>

    Screen readers announce the hint after the label, and the error when populated.

    Concept 15: Testing with Real Assistive Technology

    Browser simulators do not reliably reflect actual screen reader behavior. Testing with real screen readers (NVDA, JAWS, VoiceOver, TalkBack) is essential.

    Automated tools catch only 30–50% of accessibility issues. Manual testing with assistive technology catches the rest.

    Concept 16: ARIA and Framework Components

    UI frameworks (React, Vue, Angular) often generate ARIA-heavy markup. This can be helpful — or harmful. Always verify:

    • Are roles correct for the widget type?
    • Are states updated dynamically?
    • Is keyboard behavior implemented?
    • Is the accessible name correct?

    Many frameworks ship components with incorrect ARIA. Do not assume framework ARIA is correct.

    Concept 17: ARIA and LLM-Generated Code

    LLM-generated code often over-relies on ARIA where native semantic HTML would be more appropriate. The ARIA Authoring Practices Guide (APG) is a useful reference, but its patterns are not gospel. Favor semantic HTML first; use ARIA only where required.

    Concept 18: The role Attribute and Fallback

    If a browser or assistive technology does not support a role, it falls back to the default role of the element.

    <div role="slider">  <!-- If slider role unsupported, falls back to generic -->

    This is why native elements are more reliable — they have well-established default roles.

    Concept 19: ARIA Version

    ARIA 1.2 is the current version. It added refinements for comboboxes, feeds, and other widgets. ARIA 1.3 is in development.

    Concept 20: The ARIA Authoring Practices Guide (APG)

    The W3C maintains the ARIA Authoring Practices Guide (APG) — a collection of design patterns and examples for building accessible widgets. It includes keyboard interaction patterns, ARIA usage, and example implementations.

    The APG is a valuable reference, but it is not the specification. Some patterns are complex and may not be necessary for every project.

    6. How It Works

    Step-by-Step: ARIA in the Accessibility Tree

    1.  HTML is parsed.
    │
    ▼
2.  Native roles are assigned from element names.
    │
    ▼
3.  ARIA attributes are read:
    │   ├── role → overrides native role (if valid)
    │   ├── aria-* → sets states and properties
    │   └── aria-hidden → removes from tree
    │
    ▼
4.  Accessibility tree is built:
    │   ├── Role (from element or ARIA)
    │   ├── Name (from aria-labelledby, aria-label, etc.)
    │   ├── State (from aria-expanded, aria-selected, etc.)
    │   └── Properties (from aria-controls, aria-describedby, etc.)
    │
    ▼
5.  Screen reader reads the tree.

    Step-by-Step: Live Region Announcement

    1.  Live region exists in the DOM.
    │
    ▼
2.  Content changes (via JavaScript).
    │
    ▼
3.  Browser detects change in live region.
    │
    ▼
4.  Accessibility API fires an event.
    │
    ▼
5.  Screen reader announces the new content.

    Step-by-Step: Toggle Button State Update

    1.  User clicks the toggle button.
    │
    ▼
2.  JavaScript updates aria-pressed:
    │   btn.setAttribute('aria-pressed',
    │       btn.getAttribute('aria-pressed') === 'false' ? 'true' : 'false');
    │
    ▼
3.  Browser detects ARIA state change.
    │
    ▼
4.  Accessibility API fires state change event.
    │
    ▼
5.  Screen reader announces "pressed" or "not pressed."

    7. Internal Architecture / Under the Hood

    The Accessibility Tree and ARIA

    The accessibility tree is a parallel representation of the DOM, optimized for assistive technology. ARIA modifies this tree:

    • role changes the node's role in the tree.
    • aria-* attributes add states and properties.
    • aria-hidden="true" removes the node and its subtree.
    • role="presentation" removes the node's semantics but keeps its children.

    Role Precedence

    When both a native role and an ARIA role are present:

    1. ARIA role overrides the native role.
    2. If the ARIA role is invalid, the native role is used.
    3. If the ARIA role is abstract, behavior is undefined.

    This is why redundant roles are harmful — they can conflict with native semantics.

    State and Property Processing

    States and properties are read by the browser and exposed via the platform accessibility API:

    • Windows: IAccessible2, UIA
    • macOS: NSAccessibility
    • Linux: ATK/AT-SPI

    Screen readers query these APIs to build their announcements.

    ARIA and the DOM

    ARIA attributes do not affect DOM structure, CSS rendering, or JavaScript behavior. They are metadata only — read by the accessibility API, invisible to the user.

    The aria-labelledby Algorithm

    1. Find all elements referenced by ID in aria-labelledby.
    2. Concatenate their text content.
    3. Use the result as the accessible name.

    If multiple IDs are referenced, the names are concatenated in order.

    9. Practical Examples

    Example 1: Toggle Button

    <button type="button"
        aria-pressed="false"
        onclick="this.setAttribute('aria-pressed',
                 this.getAttribute('aria-pressed') === 'false' ? 'true' : 'false')">
    Mute
</button>

    Code Breakdown:

    • Native <button> — keyboard-operable, focusable.
    • aria-pressed — declares the toggle state.
    • JavaScript updates the state on click.
    • Screen reader announces "Mute, toggle button, not pressed" → "Mute, toggle button, pressed."

    Example 2: Accessible Tabs

    <div role="tablist" aria-label="Account settings">
    <button role="tab" id="tab-profile" aria-selected="true"
            aria-controls="panel-profile" tabindex="0">
        Profile
    </button>
    <button role="tab" id="tab-billing" aria-selected="false"
            aria-controls="panel-billing" tabindex="-1">
        Billing
    </button>
</div>

<div role="tabpanel" id="panel-profile"
     aria-labelledby="tab-profile" tabindex="0">
    <h2>Profile settings</h2>
    <p>...</p>
</div>

<div role="tabpanel" id="panel-billing"
     aria-labelledby="tab-billing" tabindex="0" hidden>
    <h2>Billing settings</h2>
    <p>...</p>
</div>

    Code Breakdown:

    • role="tablist" — declares the tab container.
    • role="tab" — declares each tab.
    • aria-selected — indicates the active tab.
    • aria-controls — links tab to panel.
    • role="tabpanel" and aria-labelledby — links panel back to tab.
    • tabindex — roving tabindex: only the active tab is in the tab order.

    Example 3: Live Region for Form Errors

    <form>
    <label for="email">Email address</label>
    <input id="email" type="email" required
           aria-describedby="email-error">
    <span id="email-error" role="alert"></span>

    <button type="submit">Subscribe</button>
</form>

<script>
    document.querySelector('form').addEventListener('submit', (e) => {
        const email = document.getElementById('email');
        const error = document.getElementById('email-error');
        if (!email.validity.valid) {
            e.preventDefault();
            error.textContent = 'Please enter a valid email address.';
        }
    });
</script>

    Code Breakdown:

    • role="alert" — implicitly aria-live="assertive" and aria-atomic="true".
    • When textContent is set, the screen reader announces immediately.
    • aria-describedby links the error to the input.

    Example 4: Accessible Modal

    <div role="dialog"
     aria-modal="true"
     aria-labelledby="dialog-title"
     id="confirm-dialog">
    <h2 id="dialog-title">Confirm deletion</h2>
    <p>This action cannot be undone.</p>
    <button onclick="closeDialog()">Cancel</button>
    <button onclick="confirmDelete()">Delete</button>
</div>

    Code Breakdown:

    • role="dialog" — declares the modal.
    • aria-modal="true" — tells assistive technology the rest of the page is inert.
    • aria-labelledby — links to the dialog title.

    Example 5: Live Region for Status Updates

    <div role="status" aria-live="polite" id="status-message"></div>

<script>
    function updateStatus(message) {
        document.getElementById('status-message').textContent = message;
    }
    updateStatus('Settings saved successfully.');
</script>

    Code Breakdown:

    • role="status" — implicitly aria-live="polite".
    • aria-live="polite" — waits for the user to be idle before announcing.
    • Screen reader announces "Settings saved successfully" without interrupting.

    Use Case ARIA Approach

    Tabs role="tablist", role="tab", role="tabpanel", aria-selected, aria-controls
    Accordion aria-expanded, aria-controls
    Modal dialog role="dialog", aria-modal="true", aria-labelledby

    11. Best Practices

    1. Use native HTML first. Why: native elements have behavior; ARIA only has semantics.
    2. Use ARIA only when native HTML cannot express the required semantics. Why: pages with ARIA average more errors than pages without.
    3. Never override native semantics with redundant roles. Why: it confuses assistive technology.
    4. Ensure all interactive ARIA controls are keyboard operable. Why: ARIA does not add keyboard behavior.
    5. Update ARIA states dynamically. Why: a static aria-expanded="false" is worse than no attribute.
    6. Never use aria-hidden="true" on focusable elements. Why: it creates a keyboard trap.
    7. Provide accessible names for all interactive elements. Why: screen readers need a name to announce.
    8. Prefer aria-labelledby over aria-label when visible text exists. Why: keeps label and visible text synchronized.
    9. Use role="alert" for urgent messages. Why: it interrupts immediately.
    10. Use role="status" for non-urgent updates. Why: it waits for user idle.
    11. Test with real screen readers (NVDA, JAWS, VoiceOver). Why: browser simulators do not reflect actual behavior.
    12. Test with keyboard only. Why: ARIA widgets must be keyboard-operable.
    13. Use the APG as a reference, not gospel. Why: its patterns are complex and may not suit every project.
    14. Do not use abstract roles. Why: they are for the specification's internal taxonomy.
    15. Verify framework-generated ARIA. Why: frameworks often ship incorrect ARIA.
    16. Use aria-current for navigation. Why: it identifies the current item in a set.
    17. Use aria-describedby for hints and errors. Why: it links supplemental information to inputs.
    18. Manage focus in SPAs and modals. Why: focus management is the most common regression source.
    19. Keep ARIA simple. Why: complex ARIA is more likely to be wrong.
    20. Audit ARIA regularly. Why: ARIA decays as content and behavior change.

    12. Common Mistakes

    ❌ Mistake: aria-hidden="true" on Focusable Elements

    <button aria-hidden="true">Save</button>

    Why it's wrong: The button is invisible to screen readers but still reachable by keyboard — a keyboard trap.

    ✅ Correct:

    <button>Save</button>

    ❌ Mistake: Static aria-expanded

    <button aria-expanded="false">Menu</button>
<!-- Never updated when menu opens -->

    Why it's wrong: The screen reader announces the menu as permanently closed — worse than no ARIA at all.

    ✅ Correct:

    <button aria-expanded="false" id="menu-btn">Menu</button>
<script>
    btn.addEventListener('click', () => {
        const expanded = btn.getAttribute('aria-expanded') === 'true';
        btn.setAttribute('aria-expanded', !expanded);
    });
</script>

    ❌ Mistake: Redundant Roles

    <button role="button">OK</button>
<nav role="navigation">...</nav>

    Why it's wrong: The native roles already provide the correct semantics.

    ✅ Correct:

    <button>OK</button>
<nav>...</nav>

    ❌ Mistake: aria-label on Non-Interactive Elements

    <p aria-label="Important paragraph">Some text.</p>

    Why it's wrong: aria-label on static text is often ignored by screen readers and can cause confusion.

    ✅ Correct: Use visible text or aria-describedby if needed.

    ❌ Mistake: Missing Accessible Name on Icon Button

    <button>
    <svg>...</svg>
</button>

    Why it's wrong: The button has no accessible name; screen readers announce nothing useful.

    ✅ Correct:

    <button aria-label="Close dialog">
    <svg aria-hidden="true">...</svg>
</button>

    ❌ Mistake: Using role="button" Without Keyboard Handler

    <div role="button" onclick="save()">Save</div>

    Why it's wrong: ARIA declares semantics but does not add keyboard behavior.

    ✅ Correct: Use <button> or add tabindex="0" and keyboard handlers.

    ❌ Mistake: Misspelled ARIA Attribute

    <button arialabel="Close">X</button>

    Why it's wrong: arialabel is not a valid attribute; the button has no accessible name.

    ✅ Correct:

    <button aria-label="Close">X</button>

    13. Performance Considerations

    • ARIA attributes have no rendering cost — they are metadata only.
    • Live regions have minimal overhead — content updates trigger accessibility events.
    • Complex ARIA widgets may add JavaScript overhead for state management.
    • Focus management is cheap — a single .focus() call.
    • Automated testing catches some ARIA errors but adds CI time.

    Performance Tips

    1. Prefer native HTML over ARIA-heavy custom widgets.
    2. Keep live regions minimal.
    3. Update ARIA states only when they change.
    4. Use roving tabindex for composite widgets rather than managing tabindex on every child.

    14. Security Considerations

    ARIA and DOM Injection

    Dynamically setting aria-label from untrusted input could expose data. Escape or validate any ARIA values generated from user input.

    aria-hidden and Content Leakage

    aria-hidden="true" removes elements from the accessibility tree but not the DOM. Sensitive content hidden this way is still in the DOM and accessible via DevTools.

    Live Region Abuse

    Rapidly updating live regions can overwhelm screen reader users. Use aria-live="polite" for non-urgent updates and avoid spamming.

    Framework ARIA and Supply Chain

    Framework components with incorrect ARIA can introduce accessibility vulnerabilities. Audit third-party components.

    15. Debugging Tips

    • Chrome DevTools → Elements → Accessibility pane — inspect any element's role, name, and state.
    • Chrome DevTools → Elements → Accessibility tree — see the full accessibility tree with ARIA applied.
    • Firefox DevTools → Accessibility — visualizes ARIA roles and landmarks.
    • axe DevTools extension — flags ARIA errors and misuse.
    • Lighthouse — audits for ARIA issues.
    • Screen reader testing — NVDA (Windows), VoiceOver (macOS/iOS), TalkBack (Android).
    • getComputedAccessibleNode() — experimental API for checking accessible name and role.
    • element.ariaExpanded — DOM property for reading ARIA state.
    • document.querySelectorAll('[role]') — list all roles on the page.
    • document.querySelectorAll('[aria-hidden="true"]') — find hidden elements.

    16. When to Use

    • When native HTML cannot express the widget semantics — tabs, sliders, comboboxes, trees, grids.
    • When dynamic content needs to be announced — live regions, alerts, status updates.
    • When relationships need to be communicated — aria-controls, aria-describedby, aria-labelledby.
    • When states need to be communicated — aria-expanded, aria-selected, aria-pressed.
    • When native HTML has gaps — but only after verifying native HTML cannot do it.

    17. When Not to Use

    • When native HTML can do it. Use <button>, <nav>, <input>, <dialog>, <details>.
    • When ARIA would be redundant. Do not add role="button" to <button>.
    • When you cannot implement the required behavior. A role without keyboard behavior is worse than no ARIA.
    • When you cannot test with real assistive technology. Untested ARIA is risky ARIA.

    20. Summary

    • ARIA adds semantic roles, states, and properties to HTML elements for assistive technology.
    • It does not add behavior — it only changes how assistive technologies perceive an element.

    • The five rules of ARIA govern correct implementation: native first, no redundant roles, keyboard operable, no aria-hidden on focusable elements, accessible names.
