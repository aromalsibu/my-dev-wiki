    Testing Accessibility

    1. Overview

    Definition

    Accessibility testing is the systematic process of evaluating a web page, application, or digital product against established accessibility standards — primarily WCAG 2.2 Level AA — using a combination of automated tools, manual inspection, and assistive technology testing. Its purpose is to identify barriers that prevent people with disabilities from perceiving, operating, understanding, and interacting with digital content.

    <!-- What automated tools catch -->
<img src="chart.png">                     <!-- missing alt -->
<button style="color:#aaa;background:#fff">  <!-- contrast 2.3:1 -->

<!-- What only manual testing catches -->
<a href="/article">Read more</a>          <!-- vague link text -->
<div tabindex="0">Custom widget</div>     <!-- no role, no keyboard handler -->

    The first example produces automated violations. The second produces zero automated violations but is completely inaccessible to screen reader and keyboard users. This is the central truth of accessibility testing: automation finds the obvious; humans find the important.

    Purpose

    Accessibility testing serves several essential purposes:

    • Barrier identification — discovers what prevents users with disabilities from completing tasks.
    • Legal compliance — demonstrates conformance with WCAG 2.2 AA, the standard referenced by the ADA, Section 508, and the European Accessibility Act.
    • Regression prevention — catches accessibility breaks before they reach production.
    • User experience — improves the experience for all users, not just those with disabilities.
    • Risk reduction — identifies issues before lawsuits, fines, or enforcement actions.
    • Continuous improvement — establishes a baseline and measures progress over time.

    Accessibility testing is not a one-time audit. It is a continuous practice integrated into design, development, and release cycles.

    Where It Fits

    Accessibility Testing
│
├── Automated testing      ← axe-core, Lighthouse, WAVE (30–40% of issues)
├── Manual testing         ← keyboard navigation, focus, reading order (~42%)
├── Assistive technology   ← NVDA, JAWS, VoiceOver, TalkBack
├── Mobile testing         ← VoiceOver iOS, TalkBack Android
├── CI/CD integration      ← axe-core in Playwright/Cypress
└── Real user testing      ← users with disabilities

    Testing spans the entire development lifecycle — from design review to post-release monitoring.

    2. Why It Exists

    The Problem

    The 2026 WebAIM Million report found that 95.9% of the top one million home pages have automatically detectable WCAG failures, averaging 56.1 errors per page — a 10.1% increase from 2025, reversing years of gradual improvement. And since automated tools catch only 30–40% of real accessibility issues, the true failure rate is significantly higher.

    Without systematic testing, these barriers remain invisible to the teams that build them. Developers use mice, see the screen, and navigate visually. They never encounter the barriers that screen reader users, keyboard-only users, and low-vision users face daily.

    Previous Limitations

    Limitation Consequence
    No testing at all Accessibility treated as an afterthought
    Automated-only testing 60–70% of issues missed entirely
    No screen reader testing Announcement quality and reading order never verified
    No keyboard-only testing Focus traps and tab order issues ship undetected
    No mobile testing Touch target, gesture, and VoiceOver issues missed
    Testing only before launch Regressions introduced by every subsequent change
    No CI integration Issues caught too late, remediation expensive

    Why It Was Introduced

    Accessibility testing evolved alongside accessibility standards. WCAG 1.0 (1999) introduced testable checkpoints. WCAG 2.0 (2008) made them technology-agnostic and testable. WCAG 2.2 (2023) added new criteria that require new testing methods.

    The testing tooling evolved in parallel:

    • 2010s — WAVE and basic automated scanners.
    • 2015 — Deque released axe-core, the first engine with zero false positives on automated checks.
    • 2018 — Lighthouse integrated axe-core for accessibility audits.
    • 2020s — CI/CD integration became standard; accessibility testing shifted left into development.
    • 2025–2026 — The European Accessibility Act made testing a legal requirement for EU-facing digital products. France's DGCCRF began inspections in December 2025. The Dutch ACM moved toward active enforcement in mid-2026. In June 2026, a French court ordered Carrefour to make its site and app accessible within six months, with €500 per day penalties for delay.

    Accessibility testing exists because you cannot fix what you cannot see. Testing makes barriers visible before they reach users, regulators, and courts.

    Layer 1: Automated Testing with axe-core

    // Playwright + axe-core integration
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('homepage has no accessibility violations', async ({ page }) => {
    await page.goto('https://example.com');

    const results = await new AxeBuilder({ page })
        .withTags(['wcag2a', 'wcag2aa', 'wcag22aa'])
        .analyze();

    expect(results.violations).toEqual([]);
});

    Code Breakdown

    • @axe-core/playwright — integrates axe-core into Playwright tests.
    • .withTags(['wcag2a', 'wcag2aa', 'wcag22aa']) — restricts to WCAG 2.2 A and AA criteria.
    • .analyze() — runs the scan and returns violations, incomplete items, and passes.
    • expect(results.violations).toEqual([]) — fails the test if any violations exist.

### Setup

- [ ] Open the page in Chrome or Firefox

### Test Steps

   - [ ] Focus order follows visual order
   - [ ] Focus indicator is visible on every element

   - [ ] Reverse order is correct

4. **Escape** — press `Escape`

   - [ ] Dropdowns dismiss

   - [ ] Tabs navigate
   - [ ] Menus navigate
   - [ ] Radio groups navigate

- [ ] No keyboard traps (can always Tab out)
- [ ] Focus not obscured by sticky headers
- [ ] Skip link works

    4. Mental Model

    The "Iceberg" Mental Model

    Automated testing sees only the tip of the iceberg:

                        ▲
                   ╱ ╲          ← Automated catches this
                  ╱   ╲            (30–40% of issues)
                 ╱─────╲
                ╱       ╲
               ╱         ╲      ← Manual testing required
              ╱           ╲        (60–70% of issues)
             ╱             ╲
            ╱───────────────╲
           ╱                 ╲
          ╱                   ╲
         ╱─────────────────────╲

    The visible tip: missing alt text, insufficient contrast, missing form labels. The submerged mass: reading order, focus management, error announcement, keyboard traps, announcement quality, cognitive load.

    The "Four Testing Layers" Mental Model

    Layer 1: LINT (at keystroke)
  └── ESLint a11y plugins, TypeScript types
  └── Catches: missing alt in JSX, invalid ARIA

Layer 2: AUTOMATED (CI/CD)
  └── axe-core, Pa11y, Lighthouse
  └── Catches: contrast, labels, ARIA validity

Layer 3: MANUAL (pre-merge)
  └── Keyboard, focus, reading order, zoom
  └── Catches: tab order, focus traps, reading order

Layer 4: ASSISTIVE TECH (pre-release)
  └── NVDA, JAWS, VoiceOver, TalkBack
  └── Catches: announcement quality, interaction flow

    Each layer catches what the layer above cannot. Skipping a layer leaves gaps.

    The "Tool Selection" Mental Model

    Need Tool Why
    CI/CD pipeline axe-core, Pa11y Free, accurate, scriptable
    Developer education WAVE Visual overlay, intuitive
    Quick health check Lighthouse Built into Chrome, fast
    Guided manual review axe DevTools IGT Semi-automated checks for incomplete items
    Screen reader testing NVDA Free, widely used
    Enterprise coverage JAWS Market leader
    Mobile testing VoiceOver, TalkBack Built into devices

    The "Cost of Late Discovery" Mental Model

    Design phase:      $1 to fix
Development:       $10 to fix
QA:                $100 to fix
Production:        $1,000 to fix
Litigation:        $100,000+ to fix

    Accessibility issues found in design cost almost nothing to fix. Issues found in production cost 1,000× more. Testing must happen early and continuously.

    5. Core Concepts

    Concept 1: Automated Tools Catch 30–40%

    The 2026 consensus: automated engines catch roughly 30–40% of WCAG AA failures. Deque claims ~57% with axe-core plus Intelligent Guided Tests. But ~42% of WCAG 2.2 AA criteria cannot be automated at all, and a further ~45% require human judgement to interpret.

    Implication: Automated testing alone can never achieve compliance. It is the floor, not the ceiling.

    Concept 2: axe-core — The Industry Standard

    axe-core is the open-source engine that powers Lighthouse, axe DevTools, and most CI integrations. It has zero false positives on automated checks. It runs on WCAG 2.0/2.1/2.2 A and AA criteria.

    Concept 3: Lighthouse — Fast Health Check, Not Compliance Signal

    Lighthouse uses axe-core under the hood but only ships a subset of its rules — around 50–60 audits as of early 2026. It is useful for a quick "is this page in the ballpark" check but is not a compliance signal.

    Concept 4: WAVE — Visual Feedback for Education

    WAVE (WebAIM) places icons directly on the rendered page, showing issues in context. It has a higher false-positive rate than axe-core and is not appropriate for CI, but it is excellent for developer education and stakeholder walkthroughs.

    Concept 5: Lint as the Floor

    ESLint accessibility plugins (eslint-plugin-jsx-a11y, eslint-plugin-vue-a11y) catch issues at keystroke — missing alt in JSX, invalid ARIA attributes, click handlers on non-interactive elements. Lint is the floor, not the ceiling.

    Concept 6: The Irreducible Manual 42%

    Roughly 42% of WCAG 2.2 AA criteria cannot be automated. These include: keyboard operability, focus order, focus visibility, reading order, error recovery, redundant entry, and accessible authentication.

    Concept 7: Keyboard Navigation Testing

    The keyboard pass is the single highest-value manual test:

    • Tab / Shift+Tab — forward and backward through all interactive elements.
    • Enter / Space — activate buttons and links.
    • Arrow keys — within widgets (menus, tabs, listbox, autocomplete).
    • Escape — close modals, dropdowns, dismiss popovers.

    Verify: coverage (every mouse action has a keyboard equivalent), order (tab follows visual layout), visible indicator (every focusable element has visible focus), and not obscured (sticky headers do not hide focused elements).

    Concept 8: Screen Reader Market Share (2026)

    Based on the WebAIM Screen Reader User Survey #10 (2024, still the most recent data):

    Screen reader Desktop primary Mobile primary
    JAWS 40.5% —
    NVDA 37.7% —
    VoiceOver 9.7% ~70.6%
    TalkBack — ~34.7%

    Testing priority: NVDA + Chrome (free, 21.3% of users), JAWS + Chrome (24.7%, #1 combination), VoiceOver + Safari (mobile dominance).

    Concept 9: Testing Matrix

    Priority Screen reader Browser OS
    1 JAWS Chrome Windows
    2 NVDA Chrome Windows
    3 VoiceOver Safari macOS
    4 VoiceOver Safari iOS
    5 TalkBack Chrome Android

    Concept 10: Mobile Accessibility Testing

    Mobile testing is not optional: 91.3% of screen reader users also use a mobile device. Mobile-specific checks: touch target size (44×44pt iOS, 48×48dp Android), gestures, dynamic type, and reduced motion.

    Concept 11: The Testing Workflow

    Design → Lint → Automated → Manual → AT → Mobile → Release
  │        │        │          │       │       │        │
  │        │        │          │       │       │        └── Monitor
  │        │        │          │       │       └── VoiceOver/TalkBack
  │        │        │          │       └── NVDA/JAWS/VoiceOver
  │        │        │          └── Keyboard, focus, zoom, contrast
  │        │        └── axe-core in CI/CD
  │        └── ESLint a11y plugins
  └── Color contrast, touch targets, semantic structure

    Concept 12: CI/CD Integration

    Automated accessibility checks should run in CI/CD on every pull request. Use @axe-core/playwright, jest-axe, or pa11y to gate merges. This prevents regressions from reaching production.

    Concept 13: Real User Testing

    The most valuable testing is with real users with disabilities. Automated tools, manual checklists, and screen reader testing all catch issues — but real users reveal usability problems that no checklist anticipates.

    Concept 14: Testing Is Continuous

    Accessibility decays. Every new feature, every CMS update, every design change can introduce barriers. Testing must be continuous, not a one-time audit.

    Concept 15: The European Accessibility Act Enforcement (2026)

    Since June 2025, the EAA requires accessible e-commerce, banking, transport, and digital products in the EU. Enforcement accelerated in 2026:

    • Netherlands: Dutch ACM moving toward active enforcement mid-2026.
    • France: Carrefour ordered by court in June 2026 to fix its site within six months, with €500/day penalties.
    • Italy: Implementing Decree with transitional arrangements until 2030.

    Testing is no longer optional — it is a legal requirement.

    Concept 16: WCAG 2.2 Testing Checklist

    55 criteria (31 A + 24 AA) must be verified. The checklist should be a workflow, not a scorecard: scan first, fix templates, automate what can be automated, manually verify the rest.

    Concept 17: axe DevTools Intelligent Guided Tests

    axe DevTools browser extension offers Intelligent Guided Tests (IGT) — semi-automated checks for incomplete items like color-meaning use, link-purpose, and focus-order. Deque demonstrates ~80% issue coverage when combining the engine with guided manual review.

    Concept 18: Testing the New WCAG 2.2 Criteria

    WCAG 2.2 added criteria that require new testing methods:

    • 2.4.11 Focus Not Obscured — keyboard sweep to verify focus is not hidden by sticky elements.
    • 2.5.7 Dragging Movements — verify non-drag alternative exists.
    • 2.5.8 Target Size — verify 24×24 CSS pixel minimum.
    • 3.3.7 Redundant Entry — verify no duplicate data requests.
    • 3.3.8 Accessible Authentication — verify no cognitive function tests.

    Concept 19: Testing Zoom and Reflow

    WCAG 1.4.4 (Resize Text) and 1.4.10 (Reflow) require testing at 200% zoom and 320 CSS pixel viewport. Automated tools do not test zoom and reflow — manual inspection is required.

    Concept 20: Accessibility Statements

    The EAA requires organizations to publish accessibility statements describing compliance status, known issues, and contact information. Testing provides the data for these statements.

    7. Internal Architecture / Under the Hood

    How axe-core Works

    axe-core injects into the page and walks the DOM. For each node, it:

    1. Determines the element's role and accessible name.
    2. Checks against rule definitions (e.g., image-alt, color-contrast).
    3. Returns violations, incomplete items, passes, and inapplicable rules.

    The engine is rules-based, not AI-based. It can only check what is programmatically determinable.

    Why Automated Tools Have Limits

    Automated tools cannot determine:

    • Whether alt text is meaningful or just present.
    • Whether link text is descriptive in context.
    • Whether reading order is logical.
    • Whether focus order makes sense.
    • Whether error messages are helpful.
    • Whether content is understandable.

    These require human judgement.

    The Accessibility Tree and Testing

    Screen readers read the accessibility tree, not the DOM. Testing tools inspect the DOM and the accessibility tree. Chrome DevTools → Elements → Accessibility pane shows the computed accessible name, role, and state for any element.

    Lighthouse vs axe-core

    Lighthouse uses axe-core but:

    • Ships only ~50–60 of axe-core's ~100+ rules.
    • Weights results by user impact.
    • Reports a score (0–100), which can be misleading.

    Use Lighthouse for a quick check. Use axe-core directly for compliance.

    CI/CD Integration Architecture

    Developer push → CI pipeline
                    │
                    ├── Install Playwright + axe-core
                    ├── Start dev server
                    ├── Run tests against all routes
                    ├── Collect violations
                    └── Fail build if violations > 0

    Example 1: Playwright + axe-core CI Test

    import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

const routes = ['/', '/about', '/products', '/contact'];

    test(`${route} has no accessibility violations`, async ({ page }) => {

            .withTags(['wcag2a', 'wcag2aa', 'wcag22aa'])
            .analyze();

        expect(results.violations).toEqual([]);
    });
}

    Code Breakdown:

    • Iterates over all routes.

    • expect(results.violations).toEqual([]) — fails the test if any violations exist.
    • This runs in CI on every pull request.

    11. Best Practices

    1. Start testing in design, not development. Why: issues caught in design cost 1,000× less to fix.
    2. Integrate axe-core into CI/CD. Why: prevents regressions from reaching production.
    3. Use ESLint a11y plugins. Why: catches issues at keystroke, before CI.
    4. Test with keyboard only. Why: keyboard accessibility is the foundation of all accessibility.
    5. Test with at least one screen reader. Why: automated tools cannot verify announcement quality.
    6. Test with NVDA and VoiceOver at minimum. Why: NVDA is free; VoiceOver covers Apple platforms.
    7. Test on mobile. Why: 91.3% of screen reader users also use mobile.
    8. Test zoom to 200%. Why: WCAG 1.4.4 requires it; automated tools do not test zoom.
    9. Test reflow at 320 CSS pixels. Why: WCAG 1.4.10 requires it.
    10. Use axe-core directly, not just Lighthouse. Why: Lighthouse ships only a subset of axe rules.
    11. Combine automated and manual testing. Why: automated catches 30–40%; manual catches the rest.
    12. Document testing protocols. Why: consistency across team members.
    13. Test after every significant UI change. Why: accessibility regressions are common.
    14. Use real content, not lorem ipsum. Why: meaningful content reveals real issues.
    15. Involve users with disabilities. Why: they find issues no checklist anticipates.
    16. Audit quarterly. Why: accessibility decays as content and code change.
    17. Publish an accessibility statement. Why: EAA requires it; testing provides the data.
    18. Track violations over time. Why: measure progress and identify regression patterns.
    19. Train the team. Why: accessibility is everyone's responsibility.
    20. Use the WCAG 2.2 checklist as a workflow, not a scorecard. Why: it is a process, not a grade.

    12. Common Mistakes

    ❌ Mistake: Automated-Only Testing

    // CI passes, but no screen reader testing

    Why it's wrong: Automated tools catch only 30–40% of issues. The site may be unusable with a screen reader despite passing CI.

    ✅ Correct: Combine automated, manual, and screen reader testing.

    ❌ Mistake: No Keyboard Testing

    <div class="btn" onclick="save()">Save</div>

    Why it's wrong: Automated tools do not catch keyboard inoperability. The button works with a mouse but not a keyboard.

    ✅ Correct: Test keyboard navigation on every release.

    ❌ Mistake: Testing Only at the End

    <!-- Accessibility audit scheduled two weeks before launch -->

    Why it's wrong: Issues found late are expensive to fix and may delay launch.

    ✅ Correct: Test continuously from design through release.

    ❌ Mistake: Relying on Lighthouse Score

    <!-- Lighthouse score 100, but no manual testing -->

    Why it's wrong: Lighthouse uses a subset of axe-core rules and weights them by impact. A perfect score does not mean compliance.

    ✅ Correct: Use Lighthouse for a quick check; use axe-core and manual testing for compliance.

    ❌ Mistake: Testing Only on Desktop

    <!-- Desktop testing only -->

    Why it's wrong: 91.3% of screen reader users also use mobile. Mobile has unique concerns: touch targets, gestures, VoiceOver/TalkBack.

    ✅ Correct: Test on iOS and Android with VoiceOver and TalkBack.

    ❌ Mistake: No CI Integration

    <!-- Accessibility tested manually once per quarter -->

    Why it's wrong: Regressions reach production between audits.

    ✅ Correct: Integrate axe-core into CI/CD.

    ❌ Mistake: Ignoring WCAG 2.2 New Criteria

    <!-- Testing only WCAG 2.1 criteria -->

    Why it's wrong: WCAG 2.2 added criteria that many existing sites fail: Focus Not Obscured, Focus Appearance, Dragging Movements, Target Size, Redundant Entry, Accessible Authentication.

    ✅ Correct: Test against WCAG 2.2 AA.

    ❌ Mistake: No Accessibility Statement

    Why it's wrong: The EAA requires it for relevant services.

    ✅ Correct: Publish and maintain an accessibility statement.

    13. Performance Considerations

    • axe-core adds minimal overhead — typically under 100ms per page.
    • Lighthouse audits take 10–30 seconds per page — run in CI, not on every commit.
    • Screen reader testing is manual — no performance impact on the page.
    • CI integration adds seconds to pipeline — but prevents regressions.
    • Large DOM may slow automated scanning — but this is rare.

    Performance Tips

    1. Run axe-core on key templates, not every page.
    2. Use Lighthouse CI on pull requests, not every push.
    3. Cache npm dependencies for CI.
    4. Run automated tests in parallel with other CI jobs.

    14. Security Considerations

    Accessibility Overlays Are Not a Fix

    Third-party overlay widgets claim to make sites accessible automatically. They do not. They cannot fix missing semantics, keyboard traps, or poor contrast. Overlays have been sued for failing to provide actual accessibility.

    Testing Tools and Data

    Automated testing tools run in the browser. Do not test on production with sensitive data unless the tool is vetted. Use staging environments.

    Screen Reader Testing and Authentication

    Screen reader testing often requires logging in. Ensure test accounts are set up with appropriate security.

    CI/CD Access

    Accessibility testing tools in CI/CD may need network access to staging environments. Secure credentials and limit scope.

    15. Debugging Tips

    • Chrome DevTools → Elements → Accessibility pane — inspect accessible name, role, and state.
    • axe DevTools extension — run scans directly in the browser.
    • WAVE extension — visual overlay of issues.
    • Lighthouse — built into Chrome DevTools.
    • document.activeElement — check which element has focus.
    • element.labels — verify label association.
    • form.checkValidity() — check form validation state.
    • NVDA — NVDA+T for title, H for headings, D for landmarks.
    • VoiceOver — VO+U for rotor.
    • prefers-reduced-motion — test in DevTools → Rendering.
    • Zoom to 200% — test in browser zoom.
    • Mobile emulation — Chrome DevTools device toolbar.

    16. When to Use

    • Every project — accessibility testing is a baseline requirement.
    • Every release — test before shipping.
    • Every new component — test in isolation.
    • Every form — labels, errors, keyboard.
    • Every interactive widget — modals, dropdowns, tabs.
    • Every EU-facing product — EAA compliance since June 2025.
    • Every government service — Section 508, ADA Title II.

    17. When Not to Use

    • Do not rely on automated testing alone. It catches only 30–40%.
    • Do not use overlays as a substitute. They do not work.
    • Do not skip manual keyboard testing. Automated tools cannot verify tab order.
    • Do not skip screen reader testing. Automated tools cannot verify announcement quality.
    • Do not test only at the end. Test continuously.

    • Accessibility testing is the systematic evaluation of digital products against WCAG 2.2 AA using automated tools, manual inspection, and assistive technology.

    • Automated tools catch only 30–40% of issues; ~42% of criteria cannot be automated at all.

    • Lighthouse is a quick check, not a compliance signal — it ships only a subset of axe-core rules.
    • Keyboard testing is the highest-value manual test — coverage, order, visibility, no traps.
    • Screen reader testing is mandatory — test with NVDA, JAWS, and VoiceOver.
    • Mobile testing is not optional — 91.3% of screen reader users also use mobile.
    • WCAG 2.2 added 9 new criteria requiring new testing methods.
    • The EAA is enforced — fines and court orders began in 2026.
    • Integrate axe-core into CI/CD to prevent regressions.
    • Test continuously — from design through release and beyond.
    • Use real users with disabilities — they find what no tool can.
    • Accessibility testing is both a legal obligation and a competitive advantage.
