    Accessible Forms

    1. Overview

    Definition

    Accessible forms are HTML forms designed and built so that every user — regardless of disability, assistive technology, or input method — can perceive the form's purpose, understand what is required, enter data accurately, recover from errors, and submit successfully.

    <form action="/subscribe" method="post">
    <fieldset>
        <legend>Newsletter preferences</legend>

        <label for="email">Email address</label>
        <input id="email" type="email" name="email" required
               autocomplete="email"
               aria-describedby="email-hint">
        <span id="email-hint">We'll never share your email.</span>

        <button type="submit">Subscribe</button>
    </fieldset>
</form>

    A form can be visually perfect and still be entirely unusable by a screen reader user, a keyboard-only user, or a voice control user. Accessibility is not about appearance — it is about whether the form's structure, labels, states, errors, and feedback are programmatically available to assistive technology.

    Forms are where accessibility failures become conversion failures. An inaccessible form costs money. Every barrier — a missing label, an unannounced error, an unreachable button — is a lost submission.

    Purpose

    Accessible forms serve several essential purposes:

    • Label association — every input is programmatically linked to its label so screen readers announce the purpose.
    • Keyboard operability — every field and button is reachable via Tab and operable via standard keys.
    • Error communication — errors are announced, associated with their fields, and never color-only.
    • Instruction delivery — hints, formats, and constraints are available to screen readers before the user types.
    • State communication — required, disabled, invalid, and filled states are announced.
    • Autofill support — autocomplete attributes enable browser and password manager automation.
    • Grouping semantics — related controls are grouped with <fieldset> and <legend>.
    • Legal compliance — WCAG 2.2, ADA Title II, Section 508, and the European Accessibility Act all require accessible forms.

    A form is the most common place where a user with a disability will abandon a task. Making it accessible is both a legal obligation and a conversion optimization.

    Where It Fits

    Accessibility Stack
│
├── Semantic HTML        ← <label>, <input>, <fieldset>, <button>
├── ARIA                 ← aria-describedby, aria-invalid, role="alert"
├── Keyboard Navigation  ← Tab order, Enter/Space activation
├── Focus Management     ← focus moves to first invalid field on error
├── Screen Reader        ← announces labels, states, errors
└── Testing              ← keyboard-only + screen reader walkthrough

    Forms sit at the intersection of every accessibility concern: semantics, labels, keyboard, focus, announcements, and error recovery. They are the ultimate integration test for accessibility.

    2. Why It Exists

    The Problem

    A visual user sees a form: the label sits above the input, an asterisk marks the required field, an error message appears in red below the field, and a "Next" button sits at the bottom. All of this is apparent in a glance.

    A screen reader user hears none of this automatically. Without programmatic association, the screen reader announces "edit" with no label. Without required, it does not say the field is required. Without aria-describedby, it does not announce the hint. Without aria-invalid, it does not announce the error. Without proper focus management, it does not even move to the error.

    The visual form is a design; the accessible form is a programmatic contract. Without the contract, the form is a series of anonymous input boxes.

    Previous Limitations

    Limitation Consequence
    Placeholder as only label Screen reader announces "edit" with no context
    No required attribute User does not know the field is mandatory until submission
    Color-only error indication Color-blind users cannot perceive the error
    Unassociated error messages Screen reader does not announce the error
    No fieldset/legend Radio groups and checkboxes announced without group context
    Positive tabindex Tab order disrupted
    outline: none on focus Keyboard users cannot see focus
    No autocomplete Browser autofill does not work
    Custom dropdown from <div> Keyboard-inoperable; screen reader cannot identify it

    Why It Was Introduced

    WCAG 1.0 (1999) required form labels. WCAG 2.0 (2008) formalized criteria for labels, error identification, and error suggestion. WCAG 2.1 (2018) added criteria for redundant entry and accessible authentication. WCAG 2.2 (2023) added four new criteria that directly affect forms:

    • 3.3.7 Redundant Entry (Level A) — do not ask the user for the same information twice in the same process.
    • 3.3.8 Accessible Authentication (Minimum) (Level AA) — do not require cognitive function tests (puzzles, memorization) for authentication.
    • 3.3.9 Accessible Authentication (Enhanced) (Level AAA) — no cognitive test even with alternative assistance.
    • 3.2.6 Consistent Help (Level A) — help mechanisms must appear in the same relative location across pages.

    These additions reflect a shift: accessibility is not just about screen readers. It is about cognitive load, memory, and authentication too.

    The Minimal Accessible Form

    Code Breakdown

    Element / Attribute Purpose
    <fieldset> + <legend> Groups related controls; screen reader announces the group name
    <label for> Associated label; the first thing announced when focus lands
    autocomplete Enables autofill and password managers
    aria-describedby Links hint and error text to the input
    role="alert" Announces error text as soon as it is populated
    type="radio" + <label for> Each radio has its own label
    role="radiogroup" Explicit grouping for radios (though <fieldset> handles this natively)
    novalidate Disables browser validation so you can implement accessible custom messages

    The Accessible Name and Description Pipeline

    <label for="email">Email address</label>
<input id="email"
       aria-describedby="email-hint email-error">
<span id="email-hint">We'll never share your email.</span>
<span id="email-error" role="alert"></span>

    When focus lands on the input, the screen reader announces:

    "Email address, edit, required, We'll never share your email."
    • Name comes from <label>.
    • Role comes from <input type="email"> (mapped to textbox).
    • State comes from required.
    • Description comes from aria-describedby (concatenated in order).

    When the error span is populated, role="alert" fires an immediate announcement.

    4. Mental Model

    The "Contract" Mental Model

    A visual form is a design. An accessible form is a contract between your markup and assistive technology:

    Your markup promises:          The screen reader says:
─────────────────────────────────────────────────────
<label for="email">       →    "Email address"
<input required>          →    "required"
aria-describedby="hint"   →    "We'll never share your email"
aria-invalid="true"       →    "invalid entry"
role="alert"              →    "*announces error immediately*"

    Every visual cue the sighted user sees must have a programmatic counterpart the screen reader can announce. If the visual cue exists without the counterpart, the contract is broken.

    The "Five Layers of Form Accessibility" Mental Model

    Layer 1: Labels        →  Every control has an accessible name.
Layer 2: Grouping      →  Related controls are grouped (fieldset/legend).
Layer 3: State         →  Required, disabled, invalid announced.
Layer 4: Instructions  →  Hints and constraints announced before typing.
Layer 5: Errors        →  Errors announced, associated, and recoverable.

    A form that passes layers 1 and 2 but fails layer 5 leaves users stranded after an error. All five layers are required.

    The "Focus Order = Reading Order" Mental Model

    Tab order should follow the visual reading order:

    ┌─────────────────────────────────────────────┐
│  Full name       [____________]              │
│  Email           [____________]              │
│  Password        [____________]              │
│  Contact: ( ) Email ( ) Phone ( ) SMS        │
│                                              │
│  [Create account]                            │
└─────────────────────────────────────────────┘

    The tab order follows the DOM order. If your CSS reorders the fields visually (flex-direction: row-reverse, order: -1), the tab order no longer matches — and screen reader users are lost.

    The "Error Recovery Loop" Mental Model

    User submits form
    │
    ▼
Validation fails
    │
    ▼
Identify all invalid fields
    │
    ▼
Mark each with aria-invalid="true"
    │
    ▼
Populate error messages (role="alert")
    │
    ▼
Move focus to FIRST invalid field
    │
    ▼
Screen reader announces the error
    │
    ▼
User fixes the field
    │
    ▼
Clear aria-invalid and error
    │
    ▼
Loop until submission succeeds

    Every step in the loop is a place where accessibility can break. The error recovery loop is the most complex and failure-prone part of form accessibility.

    The "Never Color Alone" Mental Model

    Color is never the sole indicator of anything:

    ❌ Wrong:        Red border indicates error.
                 Red asterisk indicates required.

✅ Correct:      Red border + error icon + error text + aria-invalid.
                 Red asterisk + "required" text + required attribute.

    Color-blind users, screen reader users, and users in bright sunlight all need non-color indicators.

    5. Core Concepts

    Concept 1: WCAG 2.2 Form Criteria

    The most relevant success criteria for forms:

    Criterion Level Requirement
    1.3.1 Info and Relationships A Structure is programmatically determinable
    1.3.5 Identify Input Purpose AA autocomplete matches the purpose
    2.1.1 Keyboard A All functionality keyboard-operable
    2.4.3 Focus Order A Focus order is logical
    2.4.6 Headings and Labels AA Labels and headings describe purpose
    2.4.7 Focus Visible AA Focus indicator visible
    3.2.2 On Input A Input does not cause unexpected context change
    3.3.1 Error Identification A Errors are identified in text
    3.3.2 Labels or Instructions A Labels or instructions provided
    3.3.3 Error Suggestion AA Suggested correction provided
    3.3.4 Error Prevention AA Reversible for legal/financial data
    3.3.7 Redundant Entry A Do not ask for the same info twice
    3.3.8 Accessible Authentication (Minimum) AA No cognitive function test
    3.2.6 Consistent Help A Help mechanisms in consistent location

    Concept 2: Label Association

    Every form control must have a programmatically associated label. There are two ways:

    <!-- Method 1: for/id (preferred) -->
<label for="email">Email address</label>
<input id="email" type="email">

<!-- Method 2: wrapping (also valid) -->
<label>
    Email address
    <input type="email">
</label>

    Never use placeholder as the only label. Placeholders disappear when the user types and have poor contrast. They are not announced as labels by most screen readers.

    Concept 3: fieldset and legend

    Group related controls with <fieldset> and <legend>:

    <fieldset>
    <legend>Shipping address</legend>
    <label for="street">Street</label>
    <input id="street" autocomplete="street-address">
    <label for="city">City</label>
    <input id="city" autocomplete="address-level2">
</fieldset>

    The screen reader announces the legend when entering the group, then each field within.

    Concept 4: Required Fields

    Required fields must be indicated both visually and programmatically:

    <label for="email">
    Email address
    <span aria-hidden="true">*</span>
    <span class="visually-hidden">(required)</span>
</label>
<input id="email" type="email" required>
    • required on the input — programmatic indication.
    • Visible asterisk — visual indication.
    • aria-hidden="true" — prevents the asterisk from being announced.
    • .visually-hidden text — provides a non-symbolic indicator for screen readers.
    • A legend at the top of the form should explain what * means.

    Concept 5: Error Identification

    Every error must be:

    1. Identified in text (not color alone).
    2. Associated with the field that caused it.
    3. Announced when it occurs or when the user returns to the field.
    <input id="email" type="email" required
       aria-describedby="email-error"
       aria-invalid="true">
<span id="email-error" role="alert">
    Please enter a valid email address, e.g. name@example.com.
</span>

    Concept 6: aria-invalid

    aria-invalid="true" tells the screen reader the field has an invalid entry. Without it, the error is visually apparent but not programmatically announced.

    Concept 7: role="alert" vs aria-live

    role="alert" is implicitly aria-live="assertive" and aria-atomic="true". Use it for error messages and urgent updates. For non-urgent updates, use role="status" or aria-live="polite".

    Concept 8: autocomplete Attribute

    The autocomplete attribute enables browser autofill and password managers:

    Value Purpose
    name Full name
    email Email address
    tel Phone number
    street-address Street address
    postal-code Postal code
    cc-number Credit card number
    current-password Existing password
    new-password New password
    one-time-code OTP / 2FA code

    For WCAG 2.2 criterion 1.3.5 (AA), autocomplete must match the input's actual purpose.

    Concept 9: inputmode Attribute

    inputmode controls the on-screen keyboard type on mobile:

    <input type="text" inputmode="numeric" pattern="[0-9]*">

    Values: text, decimal, numeric, tel, email, url, search, none.

    Concept 10: enterkeyhint Attribute

    <input type="text" enterkeyhint="next">
<input type="email" enterkeyhint="done">
<input type="search" enterkeyhint="search">

    Values: enter, done, go, next, previous, search, send.

    Concept 11: Grouping Radios and Checkboxes

    Radio buttons that belong to the same question must share a name attribute:

    <fieldset>
    <legend>Contact preference</legend>

    <input type="radio" id="contact-email" name="contact" value="email" checked>
    <label for="contact-email">Email</label>

    <input type="radio" id="contact-phone" name="contact" value="phone">
    <label for="contact-phone">Phone</label>
</fieldset>

    Screen readers announce "Contact preference, group" then each option.

    Concept 12: Redundant Entry (WCAG 3.3.7)

    Do not ask for the same information twice in the same process:

    <!-- Wrong: ask for email in step 1 and step 3 -->
<label for="email1">Email (step 1)</label>
<label for="email2">Email (step 3)</label>

<!-- Correct: pre-fill from step 1, allow edit -->
<label for="email">Email</label>
<input id="email" type="email" value="pre-filled@example.com">

    Exception: re-entering a password for verification is allowed. Mark the second entry as "Confirm password."

    Concept 13: Accessible Authentication (WCAG 3.3.8)

    Do not require a cognitive function test for authentication:

    • No puzzles (CAPTCHA, image selection).
    • No memorization (transcription of a code).
    • No reliance on remembering complex passwords.

    Acceptable alternatives: password managers, email links, biometrics, WebAuthn / passkeys, magic links, OTP autofill via autocomplete="one-time-code".

    Concept 14: Consistent Help (WCAG 3.2.6)

    If the page provides help mechanisms (contact info, chat, FAQ link), they must appear in the same relative order across pages. This helps users with cognitive disabilities find help predictably.

    Concept 15: Error Prevention (WCAG 3.3.4)

    For legal, financial, or data-deletion submissions, the form must be reversible, checked, or confirmed:

    • Reversible: submission can be undone.
    • Checked: input is validated for errors before submission.
    • Confirmed: user reviews and confirms before final submission.

    A "confirm before delete" modal is the classic pattern.

    Concept 16: Focus Order in Forms

    Tab order follows DOM order. If CSS reorders fields visually, the tab order breaks. Never use tabindex values greater than 0 to control form order — use DOM order.

    Concept 17: Focus on First Invalid Field

    After form validation fails, focus must move to the first invalid field:

    const firstInvalid = form.querySelector(':invalid');
firstInvalid?.focus();

    This ensures the error is announced and the user can correct it immediately.

    Concept 18: novalidate for Custom Messages

    Browsers have built-in validation, but their messages are inconsistent across browsers and may not be accessible. Use novalidate and implement custom accessible error messages.

    Concept 19: Password Managers and Accessibility

    Password managers are accessibility tools. Users with cognitive disabilities, motor impairments, or memory conditions depend on them. Do not block paste, autofill, or password manager interaction.

    Concept 20: Mobile Form Accessibility

    Mobile forms have specific accessibility concerns:

    • inputmode selects the correct on-screen keyboard.
    • enterkeyhint tells the user what Enter will do.
    • Touch targets must be at least 24×24 CSS pixels (WCAG 2.5.8).
    • autocomplete="one-time-code" enables OTP autofill.

    7. Internal Architecture / Under the Hood

    The Label Association Algorithm

    When a screen reader queries the name of an input, the browser follows this priority:

    1. aria-labelledby — reference to other element(s)
    2. aria-label — direct string
    3. <label for="..."> — associated label
    4. <label> wrapping — ancestor label
    5. title attribute — last resort
    6. Placeholder (in some cases) — not reliable

    If no label is found, the screen reader announces a generic role with no name.

    The Fieldset/Legend Algorithm

    When focus enters a control inside a <fieldset>:

    1. The browser walks up the DOM to find the nearest <fieldset>.
    2. It reads the <legend> and associates it with the control.
    3. The screen reader announces: "[Legend text], group, [field label], edit."

    The Error Announcement Mechanism

    Two ways errors are announced:

    Via role="alert": When the error span's text content is set or changed, the accessibility API fires an alert event. The screen reader interrupts and announces the text.

    Via aria-describedby: When focus lands on the input, the screen reader concatenates the accessible description from all referenced elements and announces it as part of the field's description.

    Both together provide the most robust experience: the error is announced immediately on update and re-announced when the user returns to the field.

    The autocomplete Token Parsing

    The browser parses autocomplete tokens and exposes them to the browser's autofill system. autocomplete="email" tells the browser to fill the field with the user's saved email address. autocomplete="new-password" tells the password manager to offer to generate a new password.

    The tokens are also exposed to the accessibility tree, where they map to aria-* properties such as aria-autocomplete.

    Focus Order vs. DOM Order

    The browser builds the tab order from DOM order, excluding:

    • Elements with tabindex="-1"
    • Disabled elements
    • Hidden elements (display: none, visibility: hidden)
    • Elements inside inert containers

    CSS order, flex-direction, and absolute positioning do not affect tab order — they only affect visual layout. This is why DOM order must match visual order.

    1.  Design the form:
    │   ├── Identify all fields

    Example 3: Custom Error Handling

    const form = document.querySelector('form');

form.addEventListener('submit', (e) => {
    e.preventDefault();

    const fields = form.querySelectorAll('input, select, textarea');
    let firstInvalid = null;

    fields.forEach((field) => {
        const errorId = field.getAttribute('aria-describedby')?.split(' ')
            .find((id) => id.endsWith('-error'));
        const errorEl = errorId ? document.getElementById(errorId) : null;

        // Clear previous state
        field.removeAttribute('aria-invalid');
        if (errorEl) errorEl.textContent = '';

        // Validate
        if (!field.checkValidity()) {
            field.setAttribute('aria-invalid', 'true');
            if (errorEl) errorEl.textContent = getErrorMessage(field);
            if (!firstInvalid) firstInvalid = field;
        }
    });

    if (firstInvalid) {
        firstInvalid.focus();
    } else {
        form.submit();
    }
});

function getErrorMessage(field) {
    if (field.validity.valueMissing) {
        return `${field.labels[0].textContent} is required.`;
    }
    if (field.validity.typeMismatch) {
        return `Please enter a valid ${field.type}.`;
    }
    if (field.validity.tooShort) {
        return `Please enter at least ${field.minLength} characters.`;
    }
    return 'Please check this field.';
}

    Code Breakdown:

    • preventDefault — prevents native submission until validation passes.
    • checkValidity — uses the browser's built-in validation.
    • aria-invalid="true" — marks the field as invalid for the screen reader.
    • role="alert" (on error elements in the HTML) — announces the error text.
    • Focus moves to the first invalid field after all errors are populated.

    Example 7: Password with Show/Hide Toggle

    <div class="field">
    <label for="password">Password</label>
    <input id="password" type="password" autocomplete="new-password" required>
    <button type="button"
            aria-pressed="false"
            aria-controls="password"
            onclick="togglePassword(this)">
        Show password
    </button>
</div>

<script>
    function togglePassword(btn) {
        const input = document.getElementById('password');
        const showing = btn.getAttribute('aria-pressed') === 'true';
        btn.setAttribute('aria-pressed', String(!showing));
        btn.textContent = showing ? 'Show password' : 'Hide password';
        input.type = showing ? 'password' : 'text';
    }
</script>

    Code Breakdown:

    • aria-pressed — announces the toggle state.
    • aria-controls — associates the button with the input.
    • Native <button> — keyboard-operable.
    • The button label changes to reflect the current state.

    11. Best Practices

    1. Associate a label with every form control. Why: without a label, the screen reader announces a generic role with no purpose.
    2. Never use placeholder as a label. Why: it disappears on typing and has poor contrast.
    3. Use fieldset and legend for grouped controls. Why: screen readers announce group context.
    4. Indicate required fields both visually and programmatically. Why: color or asterisk alone is insufficient.
    5. Provide hints via aria-describedby. Why: hints are announced before the user types.
    6. Use autocomplete for every field with a known purpose. Why: enables autofill for all users, including those with disabilities.
    7. Use inputmode and enterkeyhint on mobile. Why: shows the correct keyboard and enter-key label.
    8. Validate on submit, then focus the first invalid field. Why: ensures the error is announced.
    9. Mark invalid fields with aria-invalid="true". Why: tells the screen reader the entry is invalid.
    10. Announce error messages with role="alert". Why: interrupts and announces errors immediately.
    11. Never rely on color alone to indicate errors or required fields. Why: color-blind users cannot perceive color-only indicators.
    12. Use novalidate and implement custom accessible error messages. Why: browser-native messages vary by browser and may not be accessible.
    13. Avoid positive tabindex values. Why: disrupts natural tab order.
    14. Keep DOM order aligned with visual order. Why: tab order follows DOM order.
    15. Use native form elements. Why: native <input>, <select>, <textarea>, <button> are keyboard-operable and announced correctly.
    16. Enable password managers and autofill. Why: they are accessibility tools for cognitive and motor disabilities.
    17. Support paste in password fields. Why: blocking paste blocks password managers.
    18. Do not require cognitive function tests for authentication (WCAG 3.3.8). Why: puzzles and memorization exclude users with cognitive disabilities.
    19. Avoid redundant entry (WCAG 3.3.7). Why: re-asking for the same information increases cognitive load.
    20. Provide error prevention for legal/financial submissions (WCAG 3.3.4). Why: irreversible actions require confirmation.
    21. Test with keyboard only. Why: keyboard accessibility is the foundation.
    22. Test with a screen reader. Why: forms are the most common source of screen reader barriers.
    23. Test on mobile. Why: mobile has different keyboard, autofill, and gesture behavior.
    24. Ensure touch targets are at least 24×24 CSS pixels (WCAG 2.5.8). Why: small touch targets are inaccessible.
    25. Audit forms quarterly or after any change. Why: form accessibility decays as fields change.

    12. Common Mistakes

    ❌ Mistake: Placeholder as Label

    <input type="email" placeholder="Email">

    Why it's wrong: Placeholder is not a label. Screen reader announces "edit" with no context.

    ✅ Correct:

    <label for="email">Email</label>
<input id="email" type="email" placeholder="you@example.com">

    ❌ Mistake: No required Attribute

    <label for="email">Email *</label>
<input id="email" type="email">

    Why it's wrong: The asterisk is visual-only; screen readers do not announce it.

    ✅ Correct:

    <label for="email">
    Email
    <span aria-hidden="true">*</span>
    <span class="visually-hidden">(required)</span>
</label>
<input id="email" type="email" required>

    ❌ Mistake: Color-Only Error Indication

    <input style="border-color: red">

    Why it's wrong: Color-blind users cannot perceive the error.

    ✅ Correct:

    <input aria-invalid="true" aria-describedby="email-error">
<span id="email-error" role="alert">
    Please enter a valid email address.
</span>

    ❌ Mistake: Unassociated Error Message

    <input type="email">
<p class="error">Invalid email</p>

    Why it's wrong: The error is not programmatically associated with the input; the screen reader does not announce it.

    ✅ Correct:

    <input type="email" aria-describedby="email-error" aria-invalid="true">
<span id="email-error" role="alert">Invalid email</span>

    ❌ Mistake: Positive tabindex

    <input tabindex="1">
<input tabindex="2">
<button tabindex="3">

    Why it's wrong: Positive tabindex values override DOM order and disrupt natural tab flow.

    ✅ Correct: Use DOM order; remove tabindex.

    ❌ Mistake: Missing fieldset/legend on Radio Groups

    <input type="radio" name="contact" value="email"> Email
<input type="radio" name="contact" value="phone"> Phone

    Why it's wrong: Screen reader does not announce the group context. The user hears "Email, radio button" with no question.

    ✅ Correct:

    <fieldset>
    <legend>Contact preference</legend>
    <input type="radio" id="c-email" name="contact" value="email">
    <label for="c-email">Email</label>
    <input type="radio" id="c-phone" name="contact" value="phone">
    <label for="c-phone">Phone</label>
</fieldset>

    ❌ Mistake: Blocking Paste in Password Fields

    <input type="password" onpaste="return false">

    Why it's wrong: Blocks password managers — a critical accessibility tool.

    ✅ Correct: Allow paste.

    ❌ Mistake: CAPTCHA with No Accessible Alternative

    <div class="captcha">
    <img src="puzzle.png">
    <input placeholder="Enter the code">
</div>

    Why it's wrong: Violates WCAG 3.3.8 (Accessible Authentication). Users with cognitive or visual disabilities cannot complete it.

    ✅ Correct: Use WebAuthn, magic links, or an accessible CAPTCHA with audio and screen reader support.

    ❌ Mistake: No Focus Management on Error

    // Validation fails but focus stays on the submit button

    Why it's wrong: The user does not know which field failed. Screen readers do not announce the error.

    ✅ Correct:

    firstInvalid.focus();

    ❌ Mistake: Re-Asking for the Same Information

    <!-- Step 1: Email -->
<!-- Step 3: Confirm your email again -->

    Why it's wrong: Violates WCAG 3.3.7 (Redundant Entry).

    ✅ Correct: Pre-fill the email from step 1; allow editing.

    13. Performance Considerations

    • Form accessibility has no runtime cost — labels and ARIA attributes are metadata.
    • Custom validation adds JavaScript but is necessary for accessible error messages.
    • autocomplete improves conversion and reduces typing.
    • inputmode improves mobile keyboard usability.
    • Native <dialog> has no JavaScript focus-trap overhead.

    Performance Tips

    1. Use native validation (checkValidity) rather than writing your own from scratch.
    2. Avoid excessive JavaScript on every input event — use blur and submit.
    3. Use native <dialog> for confirmations — no JavaScript focus trap needed.
    4. Keep forms small — fewer fields, less cognitive load, better conversion.

    14. Security Considerations

    Password Managers Are Accessibility Tools

    Blocking password managers (autocomplete="off", onpaste="return false") excludes users with cognitive and motor disabilities. Modern guidance from NIST and the UK NCSC recommends allowing password managers.

    Autofill and PII

    autocomplete values expose the expected data type to the browser. This is safe if the values are correct. Misconfigured values (e.g., autocomplete="cc-number" on a non-payment field) can cause incorrect autofill.

    CAPTCHA and Accessibility

    Inaccessible CAPTCHAs are both an accessibility barrier and a security theater. Prefer WebAuthn, magic links, and rate limiting over CAPTCHAs.

    Error Message Information Leakage

    Avoid revealing internal validation rules that could aid attackers (e.g., "password must contain..."). Provide minimum guidance rather than a full rule list.

    CSRF

    Forms that change state (POST) must be protected with CSRF tokens. Accessibility and CSRF are orthogonal — but both are required.

    15. Debugging Tips

    • Keyboard only: Tab through every field. Verify labels are announced and focus is visible.
    • Screen reader: Test with NVDA, JAWS, VoiceOver, or TalkBack.
    • Chrome DevTools → Elements → Accessibility pane: Inspect the accessible name and description for any input.
    • element.labels: Returns an array of associated labels for an input.
    • form.checkValidity(): Returns true if all fields are valid.
    • field.validity: Inspect validation state.
    • document.activeElement: Check which field currently has focus.
    • axe DevTools: Flags missing labels and ARIA misuse.
    • Lighthouse: Audits for missing form labels.
    • WAVE: Visualizes label associations.
    • Mobile testing: Test with VoiceOver (iOS) and TalkBack (Android).
    • Zoom to 200%: Verify form remains usable.
    • High contrast mode: Verify form controls remain visible.

    16. When to Use

    • Every form on every website — accessibility is a baseline requirement.
    • Every input, select, textarea, button — labels and states are required.
    • Every error message — must be announced.
    • Every group of controls — fieldset/legend.
    • Every authentication flow — accessible authentication.
    • Every multi-step form — avoid redundant entry.
    • Every form on a mobile device — inputmode and enterkeyhint.

    17. When Not to Use

    • Do not use ARIA to replace native form elements. Native is more reliable.
    • Do not use <div> for buttons or inputs. Use native controls.
    • Do not use placeholder as a label.
    • Do not rely on color alone.
    • Do not block password managers or paste.
    • Do not require CAPTCHA with no accessible alternative.
    • Do not use positive tabindex.
    • Do not use aria-invalid without an associated error message.

    19. Did You Know?

    • Forms are the #1 source of accessibility barriers on the web — missing labels, unannounced errors, and inaccessible widgets.
    • WCAG 2.2 added four new form-related criteria: Redundant Entry, Accessible Authentication (Minimum and Enhanced), and Consistent Help.
    • autocomplete is an accessibility feature — it enables password managers and autofill for users with cognitive and motor disabilities.
    • Blocking paste in password fields blocks password managers — a WCAG violation and a security anti-pattern.
    • Placeholder text is not a label — it disappears on typing and is often not announced.
    • role="alert" is implicitly aria-live="assertive" — it interrupts the screen reader.
    • aria-invalid="true" is the correct way to mark invalid fields for screen readers.
    • Focus must move to the first invalid field after validation fails — otherwise the error is not announced.
    • autocomplete="one-time-code" enables OTP autofill on iOS and Android.
    • inputmode="numeric" shows a numeric keyboard on mobile — critical for OTP and PIN inputs.
    • CAPTCHAs are an accessibility barrier — WCAG 3.3.8 requires accessible authentication.
    • The <dialog> element provides native focus management — no JavaScript focus trap needed.
    • Touch targets must be at least 24×24 CSS pixels (WCAG 2.5.8) — smaller targets are inaccessible on mobile.
    • The "show password" toggle should use aria-pressed — so screen readers announce the toggle state.
    • Redundant entry (WCAG 3.3.7) is a Level A requirement — do not ask for the same information twice in the same process.

    • Accessible forms are a programmatic contract between your markup and assistive technology.
    • Every input needs a label — <label for> or wrapping <label>.
    • Group related controls with <fieldset> and <legend>.
    • Indicate required fields both visually and programmatically — required attribute + non-color indicator.
    • Provide hints with aria-describedby — announced before the user types.
    • Use autocomplete for every field with a known purpose — enables autofill and password managers.
    • Use inputmode and enterkeyhint on mobile — correct keyboard and Enter key.
    • Mark invalid fields with aria-invalid="true" and announce errors with role="alert".
    • Focus the first invalid field on validation failure.
    • Never rely on color alone.
    • Avoid positive tabindex; keep DOM order aligned with visual order.
    • Use native form elements — <input>, <select>, <textarea>, <button>, <dialog>.
    • Support password managers and paste — they are accessibility tools.
    • Meet WCAG 2.2 form criteria: 3.3.7 Redundant Entry, 3.3.8 Accessible Authentication, 3.2.6 Consistent Help, 3.3.4 Error Prevention.
